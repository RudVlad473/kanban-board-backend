<objective>
Prove, with an executable test, that a signup actually writes a bcrypt password hash into the `users`
table, and that the credentials used at signup authenticate against that persisted row on a
subsequent signin.

Purpose: the operator asked whether `passwordHash` is still being saved, having noticed the column is
nullable at the DB level. Investigation confirmed the live signup path is correct today — but that
correctness is currently proven only as a side effect of an unrelated behaviour (see
`<coverage_analysis>`), and nothing in the suite states the persistence property directly. This makes
it stated, checked, and diagnosable.

Output: one new E2E test class asserting the raw database row, plus a deferred follow-up todo for the
two latent null-hash paths found while planning. No production code changes.
</objective>

<data_flow>
## Core mechanism, in three sentences

`POST /api/signup` binds the JSON body to a `SignupRequestDTO` and hands it to `UserService.save`,
which calls the `UserMapper.fromSignupRequestDTO(SignupRequestDTO)` overload whose
`@Mapping(target = "passwordHash", expression = "java(passwordEncoder.encode(dto.getPassword()))")`
is the single place in the codebase where a plaintext password becomes a bcrypt hash, before
`userRepository.save` flushes the `UserEntity` to the Hibernate-managed `users` table. The controller
then immediately re-authenticates the new user via `authenticationManager.authenticate`, so
`UserAuthenticationProvider` reloads the just-written entity and runs
`passwordEncoder.matches(plaintext, entity.getPasswordHash())` before the 201 is returned. The new
test reads that row back with raw SQL rather than through JPA, so nothing in the entity mapping — the
layer that would be at fault if a hash went missing — sits between the assertion and what is actually
stored.
</data_flow>

<coverage_analysis>
## What is actually uncovered today (be precise about this — the naive framing is wrong)

The naive framing is "nothing tests that the hash is persisted." That is not accurate, and shipping a
test justified by an inaccurate claim would be worse than shipping nothing. The precise situation:

`AuthenticationControllerTest.Signup...testWithValidCredential_shouldPopulateCookie_whenUserExists`
asserts a 201 from `POST /signup`. Because `AuthenticationController.signup` auto-authenticates the
new user before returning — `userService.save(...)` commits, then `authenticate(createdUser.getId(),
signupDTO.getPassword(), ...)` reloads the row via `loadUserByUsername` and runs
`passwordEncoder.matches(...)` — that 201 **already implies** the hash was written and matches. If it
had not been, the catch-all would have converted the failure into a 401 and the existing test would be
red.

So the guarantee exists. What is missing is that it is **implicit, load-bearing, and fragile in four
specific ways** — each of which the new test fixes:

1. **It rides entirely on signup auto-login.** Auto-login on signup is an ordinary product decision,
   not an invariant. The day someone changes signup to return 201 without authenticating — a small,
   reasonable diff — the entire persistence guarantee evaporates and **not one test goes red**. The
   new test asserts the row directly, so it survives that refactor.
2. **No test signs in as a user created through the HTTP signup endpoint.**
   `AuthenticationControllerTest.Signin` authenticates `getOwningUser()`, which `AbstractAppTest`
   creates by calling `userService.save(...)` directly — a different entry path that never touches the
   controller. The signup -> signin sequence as a user actually performs it is genuinely uncovered.
3. **The failure mode is misdiagnosable.** If the hash went missing, today's symptom is "signup
   returns 401", which reads as a credentials or validation problem and sends the reader to the wrong
   three classes. A failure that says `PASSWORD_HASH` was null points at persistence immediately.
4. **The storage form is never stated.** Nothing asserts that what is stored is a hash rather than the
   plaintext. That property is currently only inferrable by reasoning across `UserMapper`,
   `BeanConfiguration` and `UserAuthenticationProvider`; the new test states it in one place.

This is the honest justification for the work, and the test's Javadoc must record it — including the
fact that the existing 201 assertion already covers the happy path indirectly. A future reader who
notices the overlap and deletes this class as redundant would be re-opening exactly the gap it closes.
</coverage_analysis>

<tradeoffs>
## Non-obvious trade-offs worth stating

**Security — plaintext in test output.** The test holds a plaintext password in a local and asserts
the persisted hash differs from it, so an AssertJ failure message can print both into CI logs. Both
are random throwaway values generated per run, scoped to an in-memory H2 destroyed at JVM exit, and
belong to no real account — the exposure is nil, but a reviewer will notice the shape, so record it.

**Security — never assert a golden hash.** BCrypt embeds a random salt, so the same password produces
a different hash on every run. Any assertion against a literal hash value is flaky by construction.
Assert the algorithm marker prefix and inequality against the plaintext instead.

**Performance — fixture cost is unavoidable and that is fine.** `AbstractAppTest.setup()` builds two
users, three boards, eight columns, eight tasks and seven subtasks before *every* test method, and
neither new test needs any of it (both create their own user). CODE_STYLE rule 4 makes the shared
fixture mandatory and it is not overridable without deviating from every other class in the suite.
Two test methods means two fixture builds plus roughly four bcrypt operations at default strength 10
(~50-100ms each) — a fraction of a second on top of an existing `@SpringBootTest` context that is
cached across classes. Do not attempt to skip `super.setup()` to shave it.

**State — this class may use absolute counts, unlike its sibling.**
`SessionPersistenceE2ETest` is forced into before/after *delta* assertions because `SPRING_SESSION`
rows carry no foreign key to users and survive `@AfterEach userService.deleteAll()`. `users` rows do
not survive it. Combined with a unique email per test, "exactly one row matches this email" is
deterministic here. Copying the delta pattern would add ceremony that obscures the assertion.

**Flake — email collision is a real, silent hazard.** `dataFactory.getEmailAddress()` draws from a
finite name list and `AbstractAppTest.setup()` already consumes two per test method across the whole
suite. `users.email` is `unique = true`, and `AuthenticationController.signup` converts any exception
— including a constraint violation — into a 401. A collision would therefore fail this test as a
bogus credentials error. Generating the local part from a UUID removes the entire failure class for
one line, and is worth the small deviation from the `dataFactory` convention because this test, unlike
its neighbours, *keys its assertion on the email*.
</tradeoffs>
