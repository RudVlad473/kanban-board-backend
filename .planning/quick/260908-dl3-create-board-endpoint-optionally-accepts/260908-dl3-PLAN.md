<objective>
Let `POST /api/boards` optionally accept a caller-supplied board id in the request body, validated
against this codebase's real id format, uniqueness-checked before insert, and rejected with the
existing conflict envelope when taken. An absent id keeps today's server-generated behaviour
verbatim.

Purpose: allow a client to create a board under an id it already holds (offline-first / optimistic
client-side creation) without opening the primary key to arbitrary untrusted strings.
Output: one composed validation annotation, an id-assignment path through `BoardService.save`, and
positive plus hostile-input test coverage on both the default and explicit-id paths.

<verified_findings>
Everything below was read from the working tree at planning time. The executor should not re-derive
these; treat a contradiction with any of them as a signal that the tree moved.

**1. Board ids are base36, NOT ULID.** `RandFlakeGenerator.generateRandflake()` packs a
Snowflake-shaped positive long (1 unused sign bit + 41 timestamp bits + 22 sequence bits) and
returns `Long.toString(payload, 36)`. Consequences that decide the regex:
- Charset is `[0-9a-z]` — `Long.toString` emits lowercase digits only. An uppercase id is something
  this application has never issued.
- The value is always positive (bit 63 is never written), so a leading `-` is unreachable.
- Maximum length is `Long.toString(Long.MAX_VALUE, 36).length()`. Task 1 pins this with an assertion
  rather than trusting arithmetic done in this document.
- The `id` column is `varchar(255)` (`V1__init.sql`), so the database imposes no useful bound.

The project's `.claude/CLAUDE.md` currently claims "ULID-based entity IDs (RandFlake
implementation)". That is wrong about the exact format this whole task depends on; task 3 corrects
it.

**2. Hibernate discards an assigned id unless the generator opts in.** Verified against
`hibernate-core-6.6.53.Final.jar` on this machine: `org.hibernate.generator.Generator` declares
`allowAssignedIdentifiers`, and `org.hibernate.event.internal.AbstractSaveEventListener` (the
persist path) references it. `RandFlakeGenerator implements IdentifierGenerator`, which extends
`Generator` and inherits the default `false` — so a pre-set id is currently overwritten by a freshly
generated one. Overriding it to `true` is the single change that makes the explicit-id path work at
all, and it is the one architectural unknown in this task, which is why task 1 proves it end to end
before anything else is built.

**3. `save()` still persists rather than merges.** `BoardEntity` carries a non-primitive
`@Version Long version`, so Spring Data's `JpaMetamodelEntityInformation.isNew()` keys on
`version == null`, not on `id == null`. A new board with an assigned id and a null version still
takes the `persist()` branch. No repository change is needed.

**4. The conflict pattern already exists, end to end.** `AppDuplicateResourceException` ->
`GlobalExceptionHandler.handleAppDuplicateResource` -> **409** with `code: DUPLICATE_RESOURCE`. Its
one-arg constructor renders `"<entity> with that name already exists"`, which reads wrong for an id
collision; `AppDuplicateResourceException.withMessage(String)` exists precisely for that case and is
what this plan uses. The broader `handleDataIntegrityViolation` arm already backstops a lost
check-then-act race with **409** and `code: DATA_INTEGRITY_VIOLATION`. No handler or `ErrorCode`
change is required.

**5. The validation idiom to copy is `@ColumnColor`.** That annotation is a composed constraint:
`@Constraint(validatedBy = {})` plus a meta `@Pattern` sourced from `ValidationConstants`, plus
`@ReportAsSingleViolation` and `@Schema(example = ...)`. No validator class. Its Javadoc records the
rule this plan must also follow: do not stack `@OptionalNotBlank` on a pattern that already rejects
blank, because that yields two violations for one bad input and breaks the
one-violation-per-invalid-input convention `docs/CODE_STYLE.md` rule 4 depends on. A closed-charset
pattern cannot match a blank string, so the pattern alone is the whole guard. Jakarta's `@Pattern`
skips `null` by default, which is exactly the "absent means server-generates" semantics wanted here.

`ComposedConstraintPropertyCustomizer` discovers composed constraints generically (it walks
meta-annotations looking for `@Constraint`), so the new annotation's `pattern` publishes to the
OpenAPI document with no registration. Do not add `@BmpOnly`: that marker only affects how a
`@Size(min = n)` bound is published, this annotation declares no `@Size`, and every `@BmpOnly` use
is enumerated in a hardcoded list inside `ComposedConstraintPropertyCustomizerTest`.

**6. MapStruct will silently auto-map a new `id` field.** `BoardMapper.fromSaveBoardRequestDTO` maps
`SaveBoardRequestDTO -> BoardEntity` with `unmappedTargetPolicy = IGNORE`. That policy only ignores
targets with no matching source; a source field literally named `id` would be mapped onto the
entity's primary key implicitly, before any uniqueness check runs. This plan makes that explicit.

**7. Test placement and shape.** `docs/CODE_STYLE.md` rule 13 (enforced by
`architecture/TestPlacementArchTest`) requires a named subpackage. Precedents to model:
- `src/test/java/com/vrudenko/kanban_board/dto/ColumnColorTest.java` — plain JUnit for an annotation,
  no Spring context and no container.
- `src/test/java/com/vrudenko/kanban_board/e2e/board/BoardCreationE2ETest.java` — REST Assured,
  `@Tag("realSocket")`, `extends AbstractAppE2ETest`, already the home of the board-create tracer.
- `InjectionAttemptTest.StoredXss.shouldReturnBadRequestAndPersistNothing_whenColumnColorIsXssPayload`
  — a `@ParameterizedTest` over `XSS_SCRIPT_PAYLOAD` / `XSS_ATTRIBUTE_BREAKOUT_PAYLOAD` proving
  rejection on status **plus absence from persistence**, never on absence from the response body.
  Its Javadoc explains why: Jackson silently drops an unknown JSON key, so a body-only assertion
  would pass even against a codebase where the field does not exist at all. That class is the direct
  model for this task's hostile-input cases.

## Non-obvious trade-offs

**Check-then-act is not atomic, and that is accepted.** An existence lookup followed by an insert has
a window: two concurrent creates naming the same id both pass the check, and one insert loses on the
primary key. That loser surfaces as `DataIntegrityViolationException` -> 409
`DATA_INTEGRITY_VIOLATION`, versus the checked path's 409 `DUPLICATE_RESOURCE`. Same status,
different `code`. This is the identical shape the existing `uk_boards_user_id_name` guard already
has — `GlobalExceptionHandler`'s own comment says the broader arm exists for exactly this race and
must not be deleted as dead code. Do not attempt to collapse the two codes or serialize the check:
the database constraint is the real guarantee and the service check exists only to produce the
friendlier envelope.

**The id namespace is global, so a 409 is a cross-user existence oracle.** `existsByUserIdAndName` is
scoped per user; an id check cannot be, because the id is a global primary key. A caller therefore
learns that a given id is taken *somewhere*, possibly under another account. Unavoidable for a
global PK, and the disclosure is one bit about an opaque token the caller already guessed — no board
name, owner, or content leaks. Accepted and recorded, not silently ignored.

**Ordering: this must stay boards-only, and that is a one-way door.** `BoardEntity.column`,
`ColumnEntity.task` and `TaskEntity.subtasks` all carry `@OrderBy("id")`, using id-ascending as a
creation-order proxy — the invariant quick task 260813-os9's epoch move was specifically performed to
preserve across a deploy boundary. Base36 *string* ordering is not the numeric ordering that proxy
relies on (a shorter string sorts before a longer one lexicographically regardless of magnitude), so
a caller-supplied id inside any of those collections would corrupt creation-order iteration. Boards
are safe today only because `UserEntity.boards` carries no `@OrderBy` and `findAllByUserId` imposes
no order. Extending this feature to columns, tasks or subtasks without first replacing
`@OrderBy("id")` with an explicit ordering column would break it — task 2 records this as a decision
comment, because it is precisely the case where a future reader "completes the oversight" by adding
the obviously-missing symmetry.

**Cost.** One additional indexed primary-key lookup per create that supplies an id; zero additional
work on the default path. No memory or algorithmic complexity change.

## Data-flow mechanism (three sentences)

A client's optional `id` is validated at the DTO boundary by a composed `@Pattern` admitting only
the lowercase base36 charset `RandFlakeGenerator` can actually emit, so a malformed value is
rejected with 400 before it reaches any service or query. If it passes, `BoardService.save` consults
the repository for an existing row and throws the existing duplicate exception (409) when the id is
taken, otherwise assigns it onto the entity explicitly. Hibernate then honours that pre-set id
instead of overwriting it because `RandFlakeGenerator.allowAssignedIdentifiers()` returns true; when
no id was supplied the field is null and the generator produces one exactly as it does today.
</approach_analysis>
