<objective>
Turn two rules this repo currently enforces only by convention and code review into build-failing
ArchUnit tests:

1. Controllers must not reach past the service layer into repositories.
2. The domain services must load entities through their own ownership-verified `findById(userId, id)`,
   never through a direct `repository.findById(id)` (docs/CODE_STYLE.md rule 2).

Purpose: CODE_STYLE.md rule 2 is the entire access-control model of the application and nothing in
the type system enforces it — a direct repository load compiles cleanly, passes a naive test, and
silently removes the ownership check it was supposed to go through. This moves enforcement from a
reviewer's attention to the build.

Output: an ArchUnit test dependency, a `LayeringArchTest` class that runs under plain `./gradlew test`,
and removal of the one genuine pre-existing violation found while planning.
</objective>

<flagged_finding>
## Pre-existing violation found during planning — to be fixed, not exempted

`SubtaskService.findById(String id)` (`src/main/java/com/vrudenko/kanban_board/service/SubtaskService.java`,
lines 75-83) calls `subtaskRepository.findById(id)` directly. This is a real violation of
CODE_STYLE.md rule 2: it loads a `SubtaskEntity` with no ownership verification at all.

Evidence gathered during planning:

- It has **zero production callers.** The only caller anywhere is one test assertion,
  `TaskServiceTest.java:373` (`subtaskService.findById(subtask.getId()).getTask().getId()`).
- `SubtaskService` already has the correct ownership-verified overload,
  `SubtaskEntity findById(String userId, String taskId)` (line 44), which delegates to
  `ownershipVerifierService.verifyOwnershipOfSubtask` and returns `pair.getSecond()`.
- `TaskServiceTest:373` already has `userId` in scope (assigned at line 361), so it can call the
  ownership-verified overload with no restructuring.

Per the task constraints this is flagged rather than exempted: the rule is **not** being loosened to
accommodate it. Task 2 deletes the unverified overload and repoints the one test caller.

The other three domain services are already clean — a grep of every `findById(` site in `src/main`
shows `BoardService`, `ColumnService`, and `TaskService` only ever call their own
`findById(userId, id)`. Controllers are already clean too: no class in `..controller..` or
`..security..` references `com.vrudenko.kanban_board.repository`. The `SecurityContextRepository`
hits in `AuthenticationController` and `SecurityConfiguration` are Spring Security types in
`org.springframework.security.web.context`, which the rules' package predicate excludes.
</flagged_finding>

<approach_analysis>
## Alternate approaches considered (CLAUDE.md GSD execution directive)

**How the enforcement works, in three sentences:** ArchUnit reads the *compiled bytecode* of
`com.vrudenko.kanban_board` off the test classpath and builds an in-memory object graph of classes,
their fields, and every method call site with its resolved target owner and name. Each `@ArchTest`
rule is a predicate over that graph — "no class matching X should contain a call whose target is
named `findById` and whose owner resides in the repository package" — evaluated once per build. The
ArchUnit JUnit5 engine is a JUnit Platform `TestEngine`, so the already-enabled `useJUnitPlatform()`
discovers and runs it as part of plain `./gradlew test` with no new Gradle task.

| Approach | Pros / Cons | Why picked |
|----------|-------------|------------|
| **ArchUnit rules as JUnit5 tests** (chosen) | **+** Rules run against resolved bytecode, so they catch a violation regardless of import style, `var` inference, or fully-qualified usage. **+** Runs inside the existing test task; no CI change, no new tool in the developer loop. **+** Failure output names the exact class, method, and line. **+** Rule 2 is a *call-target* rule and is expressible here — this is the rule that actually matters. **-** Adds a test dependency and a few seconds of classpath scanning per build. | The only option that can express rule 2 at all, and it satisfies CODE_STYLE.md rule 8 (setup fully automated, no manual step) by piggybacking on `./gradlew test`. |
| **Checkstyle / PMD custom rule** | **+** No new test-runtime dependency. **-** Operates on a single file's AST with no cross-file type resolution, so it cannot know that the receiver of `.findById(id)` is a repository — it would have to pattern-match the variable *name* (`*Repository`), which any rename defeats. **-** Introduces a second quality-gate tool alongside Spotless, splitting where "style" lives. | Rejected: rule 2 would degrade into a name-based regex, which is exactly the "compiles cleanly, reviewer has to notice" failure mode this task exists to close. |
| **Compile-time check via ErrorProne / custom annotation processor** | **+** Strongest enforcement — fails at `compileJava`, before tests. **+** Full type resolution available. **-** A custom bug checker is a much larger unit of work (separate module, its own publication and tests) for two rules. **-** ErrorProne adoption is already tracked as its own separate pending todo, so bundling couples two independent changes. | Rejected for scope: the marginal gain over ArchUnit (failing at compile rather than at test) does not justify a custom checker module, and it would entangle this task with the separate ErrorProne todo. |

## Non-obvious trade-offs

- **Build-time cost (performance).** ArchUnit imports and models every class under
  `com.vrudenko.kanban_board` once per test JVM. At this codebase's size that is a one-off cost in
  the low seconds, and `ImportOption.DoNotIncludeTests` keeps the test source set out of the graph.
  ArchUnit caches the imported classes across `@ArchTest` members sharing the same `@AnalyzeClasses`
  configuration, so adding a third and fourth rule later costs approximately nothing extra — the
  import, not the rule evaluation, is the expensive part.
- **Memory.** The imported class graph is held in memory for the duration of the test class, bounded
  by codebase size rather than by test count. Not a concern at this scale, but it is the reason all
  rules belong in **one** `@AnalyzeClasses` class: separate configurations mean separate,
  separately-cached graphs.
- **Security-relevant caveat — the rule is a floor, not a ceiling.** Rule 2 catches direct
  `repository.findById` calls. It does *not* catch the second half of CODE_STYLE.md rule 2 (deriving
  a downstream repository call's id from the verified entity rather than from the raw path variable),
  nor other unverified loaders such as a hand-written `repository.findByX` query. A green build must
  not be read as "ownership is fully enforced" — it closes the single most common hole and review
  still carries the rest. This belongs in the rule's `.because(...)` text so a future reader does not
  over-trust it.
- **False-negative risk from package scoping.** Both rules are deliberately scoped to
  `com.vrudenko.kanban_board.repository..` rather than the loose `..repository..` glob. The loose glob
  would also match `org.springframework.data.repository` and produce false positives on ordinary
  Spring types; the tight scope avoids that, but means a repository introduced outside that package
  would be invisible to the rules. Acceptable given every repository in the project lives there.
</approach_analysis>

  <name>Task 3: Add LayeringArchTest with the two documented rules</name>
  <files>src/test/java/com/vrudenko/kanban_board/architecture/LayeringArchTest.java</files>
  <action>
Create `LayeringArchTest` in a new package `com.vrudenko.kanban_board.architecture` under
`src/test/java`. Annotate the class with `@AnalyzeClasses`, setting `packages` to
`"com.vrudenko.kanban_board"` and `importOptions` to `ImportOption.DoNotIncludeTests.class` so the
test source set stays out of the imported graph. Both rules live in this one class so they share a
single cached class import.

Declare each rule as a `static final ArchRule` field annotated `@ArchTest`. ArchUnit picks up fields,
so no `@Test` methods are involved and no Gradle wiring is needed.

Rule 1 — controllers must not reach into repositories. Select classes annotated with Spring's
`RestController`, ORed with classes residing in `..controller..`, and assert they should not
`accessClassesThat().resideInAPackage("com.vrudenko.kanban_board.repository..")`. The annotation-based
half of the selector is what brings `AuthenticationController` into scope even though it lives in the
`security` package rather than `controller`. Use the fully-qualified project package, never the loose
`..repository..` glob — the loose glob also matches `org.springframework.data.repository` and would
false-positive on ordinary Spring types.

Rule 2 — domain services must load through the ownership-verified loader. Select classes that reside
in `com.vrudenko.kanban_board.service..` AND have a simple name ending with `Service`, then exclude
the two sanctioned roots by simple name: `OwnershipVerifierService` (root of the ownership chain) and
`UserService` (identity root, no owner above it). Assert those classes should not
`callMethodWhere(...)` for a target named `findById` whose owner resides in
`com.vrudenko.kanban_board.repository..`.

Compose that condition from ArchUnit's predicate API rather than a string match. The static imports
you need are `ArchRuleDefinition.noClasses`, `ArchConditions.callMethodWhere`,
`JavaCall.Predicates.target`, `HasName.Predicates.name`, `HasOwner.Predicates.With.owner`, and
`JavaClass.Predicates.resideInAPackage`. The condition is `target(name(...))` ANDed with
`target(owner(resideInAPackage(...)))` — note that `owner` is the one from `HasOwner.Predicates.With`,
not from `HasOwner.Functions.Get`, since it takes a predicate rather than producing a value.

Selecting by name-ending-with-`Service` minus the two exceptions, rather than naming the four domain
services explicitly, is deliberate: it produces exactly the required four plus the already-compliant
`ActivityLogService` today, and it automatically covers any service added later. Naming four classes
explicitly would silently leave a fifth service unguarded.

Give both rules a `.because(...)` explanation. Rule 2's must cite docs/CODE_STYLE.md rule 2, name the
two sanctioned exceptions, and state the caveat that passing this rule does not mean ownership is
fully enforced — it does not catch re-derivation of downstream ids from raw path variables, nor other
unverified loaders such as a hand-written `findByX` query. Keep that caveat out of any string a
verification grep might scan for; it belongs in the rule's `because` text only.

Prove the rules have teeth before declaring done. Temporarily add a direct
`boardRepository.findById(boardId)` statement inside an existing `BoardService` method and run the
arch test — rule 2 must fail and name `BoardService`. Then temporarily add a `BoardRepository` field
to `BoardController` and re-run — rule 1 must fail and name `BoardController`. Revert both mutations
with `git checkout -- src/main/java/com/vrudenko/kanban_board/service/BoardService.java
src/main/java/com/vrudenko/kanban_board/controller/BoardController.java` before the final run.
Neither mutation is ever committed; a rule that cannot fail is worse than no rule because it reads as
coverage.
