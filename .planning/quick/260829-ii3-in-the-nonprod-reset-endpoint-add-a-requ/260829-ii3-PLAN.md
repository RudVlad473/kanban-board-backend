<objective>
Add a REQUIRED, cascade-deleting targeted-user-delete mode to the existing nonprod reset endpoint
(`ResetController` / `ResetService`), selected by a `fullReset` query parameter on the same route
the unconditional full reset already uses, per the locked decisions in
`260829-ii3-CONTEXT.md`.

Purpose: give nonprod test/CI cleanup a way to remove a handful of specific users and everything
they own — without wiping every other user's data the way the existing full reset does, and
without inventing a new deletion mechanism (reuses `UserService.deleteById`'s existing ownership
cascade).

Output: `POST /api/admin/reset?fullReset=true` behaves exactly as it does today (unchanged).
`POST /api/admin/reset` with a `{"userIds": [...]}` body and no (or a non-`true`) `fullReset`
cascades-deletes those users' boards/columns/tasks/subtasks and their own `activity_log` rows,
leaving every other user's data and both Kafka activity topics untouched. Both modes are gated by
the identical `@Profile("nonprod")` + constant-time `X-Reset-Token` check.
</objective>

<design_alternatives>
## Alternate approaches considered (controller method structure — CONTEXT.md leaves this to
discretion; the endpoint-selection-by-query-param design itself and the Kafka/security decisions
below are locked and not re-litigated here)

**Approach A — one `@PostMapping` method, internal `if/else` branch.** A single handler taking
`@RequestParam(defaultValue = "false") boolean fullReset` and
`@RequestBody(required = false) ResetUsersRequestDTO dto`, branching on `fullReset` inside the
method body to call either `resetService.resetAll()` or `resetService.deleteUsers(...)`.

**Approach B — two `@PostMapping` methods on the same path, dispatched by Spring's `params`
condition (`fullReset=true` vs `fullReset!=true`), sharing one private token-check helper.**

| Approach | Pros / Cons | Why picked |
|---|---|---|
| A: single method, internal branch | Pros: one route to read top to bottom. Cons: mixes two incompatible contracts (no body vs. required body) in one signature; `@RequestBody(required=false)` means `@Valid` cannot be declared directly on the parameter for the branch that needs it, so empty/malformed `userIds` would need a second, manual validation call instead of the framework's own 400 path; relies on Spring's `@RequestParam boolean` conversion for a bare `?fullReset` with no `=value`, which is not guaranteed to mean `true`; a future edit to one mode's logic risks touching the other's code path since both live in one method body. | Not picked. |
| B: two methods, `params`-based dispatch | Pros: each method gets a real, type-checked signature — `@Valid @RequestBody` works normally on the targeted-delete method with zero extra plumbing; routing is a pure string-equality test on the raw query value (`fullReset=true` vs. not), so there is no boolean-conversion ambiguity at all; the existing `reset()` method is untouched except for one `params` attribute, so its own already-passing test suite stays a meaningful regression check; the identical-security-posture requirement (D: "Security posture — unchanged, applies identically to both modes") is enforced by construction, not just convention, because both methods call the exact same one-line `verifyResetToken(...)` helper first. Cons: `params = "fullReset!=true"` is a slightly non-obvious Spring idiom (it matches both "parameter absent" and "parameter present with a different value") and needs one code comment to stay legible; two methods to keep in sync if the shared helper's signature ever changes. | **Picked** — matches the locked "one endpoint, mode by query param" decision while keeping both request contracts fully type-safe, and makes "same security check on both paths" a structural fact instead of something a reviewer has to re-verify by diffing two copies of the same `if`. |

## Non-obvious trade-offs

- **Performance (N+1 avoidance — this project's own Epic 2 mandate).** The existence check uses
  `userRepository.findAllById(distinctIds)` — one batched `IN (...)` query regardless of list
  size — never a per-id `existsById` loop. `ActivityLogRepository.deleteAllByUserIdIn` MUST be
  declared `@Modifying @Query(...)`, not a bare derived `deleteAllByUserIdIn(...)`: Spring Data
  JPA's plain derived `deleteBy...` methods execute a SELECT and then one `entityManager.remove()`
  per matched row (confirmed against Spring Data JPA's own reference docs on derived vs. explicit
  delete queries), which would silently reintroduce exactly the row-count-scaling query pattern
  this codebase's whole Epic 2 scope exists to eliminate — for a table (`activity_log`) that can
  hold an unbounded number of rows per user.
- **State invalidation.** The per-user cascade loop (`userService.deleteById`) leaves managed
  entities in the persistence context. `entityManager.flush()` immediately before the bulk
  `activity_log` delete, and `entityManager.clear()` immediately after, are both required — same
  reasoning `TaskService.deleteAllByColumn`'s own Javadoc documents for its bulk statements:
  nothing pending from the cascade loop is silently bypassed by the bulk statement's own implicit
  transaction semantics, and nothing Hibernate still thinks is managed is left stale once those
  rows are gone.
- **Security.** Running the existence check for ALL supplied ids before deleting ANY of them, in
  the same transaction, is itself a security-relevant ordering, not just a data-integrity one:
  without it, a caller who has already cleared the shared-secret gate could use a batch containing
  one real id plus one guessed id to get a partial-success signal (some ids delete, one 404s),
  functioning as a rudimentary "does this exact user id exist" oracle. Checking first makes the
  observable outcome binary — all deleted, or none deleted plus 404 — with no partial-state tell.
- **Accepted, bounded race (documented, not engineered away).** `userService.deleteById`'s cascade
  publishes real domain events (e.g. `BoardDeletedEvent`) that `KafkaEventPublisher` sends
  `@Async` on `AFTER_COMMIT`. If `ActivityLogConsumer` processes one of those events for a
  just-deleted user AFTER this method's own synchronous `activity_log` cleanup has already run and
  after this transaction has committed, a single stray `activity_log` row referencing that
  (now-nonexistent) user can reappear. This is NOT solved by pausing every Kafka listener the way
  `ResetService.resetAll()` does for the full reset: that would stall the entire activity feed for
  every unrelated, still-live user for the duration of a call that is supposed to be narrowly
  scoped to a handful of target users — a disproportionate blast radius, and directly at odds with
  CONTEXT.md's explicit decision to keep Kafka out of this feature's scope. Document this as an
  accepted, self-limited risk in `ResetService.deleteUsers`'s Javadoc (the affected id can never be
  a valid delete target again once its user row is gone) — the same pattern this codebase already
  uses for its concurrent-session-ceiling TOCTOU overshoot
  (`SecurityConfiguration.sessionAuthenticationStrategy`'s Javadoc).
</design_alternatives>
