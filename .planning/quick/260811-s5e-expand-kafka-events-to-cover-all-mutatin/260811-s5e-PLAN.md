## Facts established during planning (re-verify, do not assume)

1. **Subject naming is `RecordNameStrategy`** on both producer and consumer (`application.properties:79`, `:107`), and `AvroSchemaRegistrar` derives each subject from `schema.getFullName()`. **Each new event type is therefore a brand-new subject at version 1, not a new version of an existing subject.** Compatibility checks only ever run within a subject, so an additive-subjects-only change is not a schema evolution at all, and the d-02 BACKWARD-non-transitivity concern does not apply to it. This is the single most important finding for the todo's question 4 — it must be re-verified empirically in Task 1, not taken from this plan.
2. **`ActivityLogEntity.action` is `@Enumerated(EnumType.STRING)`** over an `action varchar(255)` column. New `ActivityAction` values need **no Flyway migration**.
3. **`detail` is a `LinkedHashMap<String,String>` serialised to JSON**, capped at `MAX_ACTIVITY_DETAIL_LENGTH = 2000`, and read back as `Map<String,String>` by `HistoricalActivityEventReconstructor`. Any non-string detail value must be stringified on write and parsed on read.
4. **Four exhaustive switches form a compile-time safety net.** Adding a record to `ActivityEvent`'s `permits` clause breaks `ActivityEventAvroMapper.toAvro` and `ActivityLogConsumer.deriveActionAndDetailIds`; adding an `ActivityAction` value breaks `HistoricalActivityEventReconstructor.reconstruct`. `ActivityEventAvroMapper.toDomain` has a `default` arm and does **not** break — it is the one that fails silently at runtime, so it needs manual attention.
5. **`SchemaCompatibilityE2ETest.productionSubjects()` currently lists 5 subjects, not 6** — `AvroColumnDeletedEvent` is missing. `build.gradle`'s `registerSchemas` task description also says "all 5 Avro schemas" while `AvroSchemaRegistrar` registers 6 and its own Javadoc says 6. Two stale counts; fix both while touching these lists.
6. **Three existing tests encode the gap as a specification** and will go RED: `ActivityEventPublicationTest.UpdateByIdTest.shouldPublishNothing_whenTaskUpdated`, `AddBoardByUserIdTest.shouldPublishNothing_whenBoardUpdated`, `AddColumnByBoardIdTest.shouldPublishNothing_whenColumnUpdated`. Rewrite them into positive assertions — do not delete them.
7. **Cascade paths publish nothing today.** `ColumnService.deleteAllByBoardId` (board delete → columns) and `TaskService.deleteAllByColumn` (column/board delete → tasks + subtasks) emit no per-child events. The existing precedent is: only the directly-requested delete emits.
8. **`AbstractAppTest.cleanup()` calls `userService.deleteAll()`**, which routes through `BoardService.deleteById` once per board — 4 boards per test method. Adding `BoardDeletedEvent` therefore adds ~4 publishes per test method across the whole suite, on top of ~7 new subtask-created publishes in `setup()`. Roughly +50% publish volume per test method. See the performance trade-off below.
9. **`RecordingActivityEventListener` is a singleton `CopyOnWriteArrayList`** shared across every test class in a JVM fork, cleared only inside `ActivityEventPublicationTest`'s arrange blocks. It already accumulates every event for the whole run; this change grows that by ~50%.
10. **`kafkaPublishExecutor` is bounded**: core 2, max 4, queue 200, default (abort) rejection policy.

## Non-obvious trade-offs

**Performance — bounded async executor under ~50% more publish volume (the real risk).**
`kafkaPublishExecutor` is core 2 / max 4 / queue 200 with the default abort rejection policy. Today each test method publishes ~21 events during `@BeforeEach` fixture setup. After this change: +7 (subtask creations in `setup()`) and +4 (board deletions in `cleanup()`), so ~32 per test method. In the test profile every publish *fails* — `max.block.ms=50`, registry at `localhost:8081` with nothing listening for non-Kafka-tagged classes — so each queued task burns its full timeout budget on 2-4 pool threads. If enqueue outruns drain across a fork, the queue reaches 200, the pool maxes at 4, and the next `@Async` dispatch throws `TaskRejectedException` on the committing thread inside the AFTER_COMMIT phase. That is a test failure with a completely misleading stack trace. **This must be measured, not reasoned about** — Task 5 carries a hard before/after wall-clock and green/red gate, with a named fallback (raise `queueCapacity` in the test profile, or make the publish dispatch non-fatal) if it fires.

**Memory — O(n²) accumulation in the test recorder.**
`RecordingActivityEventListener.recorded` is a `CopyOnWriteArrayList` on a singleton bean shared across every test class in a JVM fork. Every add copies the entire backing array. At ~400 tests × 21 events that is already ~35M element copies per fork today; at ~32 events it becomes ~82M. Mitigation folded into Task 5: clear the recorder in `AbstractAppTest.cleanup()`. Safe because every test that asserts on it already clears in its arrange block, and the listener is synchronous (not `@Async`), so ordering within a test method stays deterministic.

**Storage — unbounded activity_log growth, materially accelerated.**
`V3__add_activity_log.sql`'s own comment states there is no retention policy on this feed. Subtask completion toggling is the highest-frequency action in a kanban board; a user checking off seven subtasks now writes seven rows. The `idx_activity_log_board_created_id` index keeps reads an index scan, so this is a growth problem, not a latency problem — but it is a real change in growth rate and belongs in FINDINGS.md as a follow-up todo candidate, not silently absorbed.

**Security — the no-user-authored-content rule is load-bearing, not stylistic.**
Every existing event Javadoc and `ActivityLogEntity`'s Javadoc state D-01: events carry identifiers, actor, action and timestamp only — never a board name, column name, task title, task description or subtask title. This is not a style preference. `ActivityLogConsumer` runs with no `SecurityContext` and never re-verifies ownership, and `detail` is served back out through `GET /boards/{boardId}/activity`. Putting a task title into an `*UpdatedEvent` would push user-authored text through an unauthenticated consumer into a read API. **This rules out "full new state" as an answer to the todo's granularity question before the operator ever sees the fork** — only server-derived metadata (identifiers, positions, booleans, field *names*) is admissible.

**Security — trusted boundary at the publish site.**
Because the consumer never re-verifies, whatever `boardId` an event carries is authoritative downstream. Every new publish site must derive its ids from the ownership-verified entity (`docs/CODE_STYLE.md` rule 2), never from the raw path-variable parameter. For delete paths the ids must additionally be captured into locals *before* the delete runs — the existing `TaskService.deleteById` and `ColumnService.deleteById` Javadocs already document exactly this and are the reference.

## Data-flow mechanism in three sentences

A service method finishes its ownership-verified write and calls `ApplicationEventPublisher.publishEvent(...)` with a plain record; Spring holds that record until the enclosing transaction commits. On commit, `KafkaEventPublisher` — an `AFTER_COMMIT` `@Async` listener — maps the record to its Avro `SpecificRecord` via `ActivityEventAvroMapper` and sends it to `kanban.activity`, where the Confluent serializer looks the schema up by record full name (never registering it). `ActivityLogConsumer` deserializes it back to a `SpecificRecord`, maps it to the domain record, derives an `ActivityAction` plus an identifier map, and writes one deduplicated `activity_log` row.
