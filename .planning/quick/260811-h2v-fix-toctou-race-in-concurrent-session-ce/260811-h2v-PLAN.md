<design_rationale>

## The question this plan actually answers

The source todo offers two dispositions and asks for a judgment: **(a)** serialize the
count-then-register sequence per principal, or **(b)** accept the race as a documented, bounded
trade-off. The load-bearing fact for that judgment is *where the `SPRING_SESSION` row is written*.
`ConcurrentSessionControlAuthenticationStrategy` counts rows that are **committed and visible to
another database connection**; if that row only becomes visible after the controller method (and
therefore after any transaction a controller-scoped advisory lock could live in) has finished, then
a `pg_advisory_xact_lock` around `onAuthentication` releases before the row it was supposed to make
visible exists — and closes nothing while adding a blocking database round trip to every signin.

That is a claim about runtime behaviour, so this plan measures it (Task 2) instead of asserting it.
The disposition below is chosen on the strength of that measurement, and Task 2 defines the halt
condition if the measurement comes back the other way.

## Alternatives considered

**Approach A (picked) — accept a bounded, self-healing overshoot; specify and prove the bound with
a real-concurrency regression test; document it beside the enforcing bean.** Mirrors the treatment
`T-07.1-05-04`/D-14 gave `UserEntity`'s deliberately-unversioned last-write-wins theme updates: a
named, reasoned, test-backed trade-off rather than an unexamined gap.

**Approach B — `pg_advisory_xact_lock(hashtext(principal))` in a `@Transactional` wrapper around
the count-then-register sequence**, i.e. the option the source todo names first.

**Approach C — enforce the ceiling in the database**: a trigger on `spring_session` INSERT that
takes `pg_advisory_xact_lock(hashtext(NEW.principal_name))`, counts, and raises when over the
ceiling. This is the only option that genuinely serializes against the real write, because the lock
is held by the very transaction doing the INSERT.

**Approach D — an in-JVM per-principal striped lock** (`ConcurrentHashMap<String, ReentrantLock>` or
Guava `Striped`, which is already on the classpath) around `onAuthentication`.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A — accept + specify the bound** | **+** Zero added latency on the hot authentication path, zero new failure modes on a security-critical route. **+** The overshoot is transient, self-correcting, and bounded by the number of *simultaneously in-flight* signins for one principal — never unbounded, never persistent, and every extra session still expires on the same 180m clock. **+** Produces the regression test the todo demands and a written rationale a future scan re-raising F6 can be closed against. **−** The product guarantee becomes "at most 2 sessions, plus at most one transient extra per simultaneously-arriving signin" instead of a hard 2. **−** Requires honest documentation in three places or it degrades into folklore. | **Picked.** Severity is low and confidence medium (2/3 panel votes); the worst case is a brief extra session for an account whose credentials the attacker already holds, which grants no capability the two legitimate sessions do not already grant. Every alternative pays a permanent cost on every signin to close a transient window an attacker cannot exploit for anything. |
| **B — transaction-scoped advisory lock in the controller** | **+** Exactly the shape the todo proposes, and cheap to write. **−** Measured premise (Task 2): the `SPRING_SESSION` row is not visible to a second connection when the controller returns, so the lock is released *before* the row it must serialize against exists — two racers can serially pass a lock that protects nothing. **−** A session-scoped `pg_advisory_lock` cannot patch that either: it binds to a pooled JDBC connection that HikariCP returns to the pool the moment the controller's transaction ends, so the release would target the wrong connection. **−** Adds a blocking database round trip to every signin. | **Rejected — subject to Task 2's measurement.** Rejected because it does not work here, not because it is too hard; if Task 2 falsifies the premise, execution halts and this rejection is revisited rather than silently carried forward. |
| **C — `spring_session` INSERT trigger with an advisory lock** | **+** The only genuinely correct serialization: the lock is held by the transaction performing the INSERT, so the count cannot be stale. **−** The failure fires at session-commit time, after the 200 and the `Set-Cookie` have been produced — the user gets a success response for a session that then fails to persist, or a 500 from inside a servlet filter. **−** Puts application policy inside a schema this application does not own: Spring Session creates `spring_session` itself via `initialize-schema=always`, so the trigger needs its own Flyway migration ordered against a table Flyway did not create. **−** Ceiling enforcement would live in SQL, far from `MAX_CONCURRENT_SESSIONS`, free to drift from it. | **Rejected.** Correct and disproportionate — it trades a transient overshoot for a worse user-visible failure mode and a new schema-ownership seam, on a low-severity finding. |
| **D — in-JVM striped lock** | **+** No database round trip; trivially correct within one JVM. **−** Guards the wrong interval for the same reason as B: the row is written after the controller returns, so the lock would have to be held across a servlet filter boundary it has no access to. **−** Even if it did work, it is per-instance, and this session store exists specifically so session state is shared across instances — a control that silently degrades the moment a second instance starts is worse than a documented bound. | **Rejected.** Same premise failure as B, plus it re-introduces exactly the per-instance bookkeeping `SpringSessionBackedSessionRegistry` was chosen to avoid. |

## Decisions this plan locks

- **D-01:** disposition is **accept a bounded, self-healing overshoot** (Approach A). The bound is
  stated as: *live sessions for one principal never exceed `MAX_CONCURRENT_SESSIONS` plus one per
  additional signin that is genuinely in flight at the same instant, and the excess is transient —
  the next non-concurrent signin is refused.* That statement, not "max 2 sessions", is what the new
  test asserts and what the documentation says.
- **D-02:** the proof is a **real-socket, real-thread** test (`AbstractAppE2ETest`,
  `@Tag("realSocket")`, `ExecutorService` + `CountDownLatch`), matching
  `BoardCreationE2ETest.ConcurrentCreate` — per `docs/CODE_STYLE.md` rule 4, genuine multi-threaded
  concurrency is the one thing that earns the real-socket tier. A MockMvc-tier approximation is
  rejected: it would prove a race in the in-process dispatch path, not in the deployed one.
- **D-03:** the shipped assertion is the **invariant** `live rows == 1 + number of racers that got
  200`, plus `successCount` in `[1, 2]`, plus the self-heal check — never a bare "3 sessions
  exist". Asserting that the overshoot *occurs* would be a test that is flaky by construction; the
  overshoot's actual frequency is measured once, via a temporary `@RepeatedTest`, and recorded as a
  number in the summary rather than encoded as an assertion.
- **D-04:** the choice between (a) and (b) is settled by measuring when the session row becomes
  visible to a second connection, using temporary instrumentation that is reverted to a zero net
  diff. Reading Spring Session's source is not accepted as evidence for this decision.
- **D-05:** `MAX_CONCURRENT_SESSIONS` stays at 2 and no production behaviour changes. This plan
  ships a test, comments, and docs — the only `src/main` edit that survives it is Javadoc.

## Non-obvious trade-offs

1. **The bound is a function of concurrency, not a constant.** N genuinely simultaneous signins
   against a ceiling of 2 with headroom H can produce up to `2 - H + N` live sessions. For a
   single-instance, personal-scale deployment with no credential-stuffing pressure, N is realistically
   2; for an attacker who already holds valid credentials and sprays 50 parallel signins, it is 50.
   That is the honest shape of what is being accepted, and the documentation must say so rather than
   implying a hard 3.
2. **The overshoot grants no new capability.** Every extra session belongs to a principal who
   already authenticated successfully. The ceiling is a session-hygiene control (limit blast radius
   of a leaked cookie, bound stored session rows), not an authentication control — so a transient
   breach of it does not cross a trust boundary that `authenticate` had not already let the caller
   cross.
3. **The rejection stays a 401, and that is load-bearing.** Any "fix" that made the ceiling
   rejection distinguishable from a wrong password would hand an attacker a validity oracle. Both
   the accepted-bound documentation and the new test must reinforce D-08 here, because the natural
   instinct when documenting a session-limit behaviour is to give it its own status code.
4. **A characterization run that never observes the overshoot is still a result.** If 10 repetitions
   produce `successCount == 1` every time, the honest conclusion is "the window is narrow enough
   that it did not open in 10 attempts on this machine" — which strengthens acceptance — not "the
   race does not exist". The summary must report the number, not editorialize it.
5. **Test-tier cost.** `@Tag("realSocket")` keeps the new class out of the pre-commit `fastTest`
   gate. That is correct (a two-thread HTTP race in the commit hook would be a flake generator) but
   it means the regression only guards `./gradlew test` and CI, and the plan should say so rather
   than leave a reader assuming pre-commit coverage.
6. **The instrumentation in Task 2 is a probe, not a feature.** It touches the single most
   security-critical method in the codebase. It must be added, run, and reverted inside one task,
   with the zero-net-diff check as a hard gate — an instrumented `authenticate` reaching master
   would be a worse outcome than the finding this plan is closing.

</design_rationale>

**The question:** at the moment `AuthenticationController.authenticate` finishes — the last instant
