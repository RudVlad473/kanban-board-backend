## Approach and trade-offs (project directive: 2 alternatives, matrix, non-obvious trade-offs)

**Data flow (3 sentences).** run-fuzz.py builds a sanitized loopback-only environment, boots the
isolated `kanban-fuzz` compose project, registers the Avro schemas and starts bootRun on a free
127.0.0.1 port, then signs up a random fuzz user and saves the live `/api/docs` document into the
report directory. Schemathesis runs against that saved document with the loopback base URL, and the
hooks module supplies the session cookie, re-signing in on a timer and on any 401 while carrying the
current cookie so the server rotates the session instead of opening another. A `finally` block
stops the app by its port and runs `compose down -v` on the isolated project, then the script
summarizes the JSON report by failure class and exits 0 (run completed, findings or not), 1 (harness
failure) or 3 (refused target).

**D-A Kafka side**

| Approach | Pros/Cons | Why Picked |
|---|---|---|
| **Throwaway compose Redpanda plus `./gradlew registerSchemas` before bootRun** | + Exercises the production publish path (after-commit publish, Avro lookup, activity-log consumer) with the sanctioned schema writer the compose file already documents; removes the ~60 SerializationExceptions the spike logged. − One more Gradle invocation (it compiles main, which bootRun then reuses) and a Redpanda boot of up to ~55 s. | **Picked.** No production configuration changes, and the noise disappears for a reason rather than being hidden. |
| Disable event publishing | + Lighter stack. − No toggle exists, so this needs a new property or profile in main code (weakens the production config surface), or a dead `KAFKA_BOOTSTRAP_SERVERS`, which makes every write block for max.block.ms (2000 ms) and still logs errors. | Rejected: changes production code or slows every write request. |
| Workflow `services:` containers instead of compose | + Native to Actions. − Duplicates docker-compose.yml's broker flags in a second place that drifts, and gives local and CI two boot paths. | Rejected: one boot path for both. |

**D-B Script language**

| Approach | Pros/Cons | Why Picked |
|---|---|---|
| **stdlib Python 3 (orchestrator and selftest), plus a Python hooks module** | + The re-sign-in must run inside Schemathesis's own Python process (the auth-provider hook is the only in-process refresh point), so Python is required for that part anyway; one sign-in implementation shared by orchestrator and hooks; socket bind(0) for the free port, urllib for sign-in, try/finally plus signal handlers for teardown, importable by a selftest exactly like `scripts/verify-*-selftest.py`; python3 is preinstalled on ubuntu-latest. − Subprocess orchestration is wordier than shell. | **Picked** by what the logic needs. |
| fish (the user's default for new shell scripts) | + Terse process control. − No `set -e` (a failing step does not abort), teardown via `--on-event fish_exit` / `--on-signal`, HTTP and Set-Cookie parsing through curl and string slicing, not installed on ubuntu-latest (an apt step), and still a second language for the hook; the repo has no fish scripts or fish selftest convention. | Rejected: two languages and an untestable control flow for a safety-critical teardown. |
| bash (the repo's `.sh` tools) | + `trap EXIT`. − Same Python hook split, awkward JSON report parsing, and the user prefers fish over bash for new scripts. | Rejected. |

**D-C CI tooling**

| Approach | Pros/Cons | Why Picked |

**D-D Safety self-test**

| Approach | Pros/Cons | Why Picked |
|---|---|---|
| **`run-fuzz-selftest.py` run as the workflow's first step and before every local commit of the scripts; guard tested at function and process level in both directions; teardown tested through injected steps plus one live kill-by-port test; each proven to fail against a deliberately broken copy** | + Proves the guard and teardown can fire right where they matter; stays out of PR gating. − Only runs weekly in CI (plus locally). | **Picked.** |
| Add it as an invariant-checks.yml job | + Per-PR. − Makes fuzz tooling a PR gate, which the task rules out. | Rejected (out of scope). |
| Trust the live run alone | − A guard that never fires looks identical to one that works. | Rejected. |

**D-E Re-sign-in mechanism**

| Approach | Pros/Cons | Why Picked |
|---|---|---|
| **Hooks module: `schemathesis.auth(refresh_interval=R).skip_for(path=["/signin", "/signup"])`, whose `get` signs in carrying the current cookie** | + Timed refresh plus the built-in 401 retry; carrying the cookie makes the server rotate the one session instead of opening another, so the 2-session ceiling never trips; the cookie never rides on a fuzzed `/signup`, which would otherwise re-authenticate the shared session as a junk user. − About 60 lines of custom code. | **Picked.** |
| Built-in `[auth.wfc]` login endpoint | + Zero code. − Cannot carry the cookie (verified in its source), so the third timed sign-in opens a third session and is rejected 401; attaches the cookie to `/signup` too. | Rejected: breaks on runs longer than two refresh intervals. |
| Split the run into chunks shorter than 600 s and sign in between them | − Breaks seed and stateful-phase continuity; several reports to merge. | Rejected. |

**D-F Stack isolation**

| Approach | Pros/Cons | Why Picked |
|---|---|---|
| **Compose project name `kanban-fuzz`, `down -v --remove-orphans` on teardown, preflight that host ports 5433, 9092 and 8081 are free** | + Teardown can never stop the developer's own dev stack; fuzz junk never lands in the dev database volume; each run starts with empty Postgres and registry. − Cannot run while the dev stack holds those ports (fails fast, naming the port). | **Picked.** |
| Default project name | − `down` would tear down the developer's running dev stack and fuzz data would persist in its volume. | Rejected. |
| Generated override file with random host ports | + Coexists with the dev stack. − A second compose definition to keep in step. | Rejected: not worth it for a weekly job. |

**Non-obvious trade-offs**

- Session rotation and concurrency: every re-sign-in rotates the session id, which invalidates the
  previous cookie, so `--workers 1` is required; concurrent workers would see 401s on in-flight
  requests carrying the old value.
- The 600 s `Max-Age` is a client-side lifetime; the server keeps an idle session for 180 minutes.
  The timed refresh keeps the run faithful to a browser, and the 401 retry is what recovers a session
  the server actually dropped.
- With the Gradle daemon, the app JVM is the daemon's child, outside the script's process group, so
  stopping it by its listening port is authoritative; the kill is restricted to a PID whose
  `/proc/<pid>/cmdline` contains `java`, so a reused port can never take down an unrelated process.
- A fixed seed fixes generation, not results: server-generated ids and session timing move counts
  between runs (the spike saw this), so the baseline is one sample, not a saturation figure.
- `--exclude-newer 2026-10-06T00:00:00Z` freezes Schemathesis' transitive dependencies (reproducible
  runs, no surprise newer transitive release) at the cost of a manual date bump when upgrading.
- Cost: the spike measured 639 cases in 51 s at 25 examples with 13 fuzzable operations; with 24 it is
  expected around one to two minutes plus boot. Weekly on a hosted runner, memory is not a concern.
