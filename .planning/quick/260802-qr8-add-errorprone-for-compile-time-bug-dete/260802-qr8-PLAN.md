## The source todo flags a gray area; this plan resolves it by MEASURING FIRST, not by guessing

The todo says: *"Before enabling as a hard build gate, run it once against the existing codebase to
check for a wave of false positives / pre-existing findings that would need triage rather than
surprising every future build."*

This is a real risk, not a hypothetical, and it is not resolved by picking the safe option up front.
Landing ErrorProne in permanent warning-only mode without measuring would ship a tool that
**cannot fail a build** — which reads as coverage while providing none. Landing it as a hard gate
without measuring could red CI and the Docker image build for the whole team on the first push.

So the plan is structured as **measure → decide → apply**:

- **Task 1** lands ErrorProne in an explicitly temporary measurement configuration
  (`allErrorsAsWarnings = true`), proves it is actually running via a positive control, and reports
  the finding count broken down by check name and by source set.
- **Task 2** is a blocking decision checkpoint where the operator sees those real numbers and picks
  the gate strength against a written threshold ladder.
- **Task 3** applies the decision, proves the resulting gate has teeth, and documents it.

### Known risk this measurement is specifically looking for

This repo uses Lombok on effectively every entity and DTO, and Lombok's AST manipulation is a live,
currently-open source of ErrorProne friction. Verified against the google/error-prone issue tracker
during planning:

| Issue | State | Why it matters here |
|-------|-------|---------------------|
| [#5855](https://github.com/google/error-prone/issues/5855) | open, filed against 2.50.0 | `UnrecognisedJavadocTag` false positives with Lombok. This repo has heavy JavaDoc using `{@link}` / `{@code}` (CLAUDE.md documents that convention), so this is the most likely single source of a "wave". |
| [#5964](https://github.com/google/error-prone/issues/5964) | open (updated 2026-07-29) | Lombok causes `SourcePositionException` in `UnusedVariable`. |
| [#4802](https://github.com/google/error-prone/issues/4802) | open | Lombok causes `IllegalArgumentException` in `UnusedVariable`. |
| [#4918](https://github.com/google/error-prone/issues/4918) | open | Lombok causes a crash in `StringConcatToTextBlock`. |

Note the failure mode in three of those four is a **crash**, not a finding. An ErrorProne check that
throws surfaces as `An unhandled exception was thrown by the Error Prone static analysis plugin` and
fails the compile outright, regardless of `allErrorsAsWarnings`. Task 1 must treat that as an
expected third outcome with a defined response, not as "the plan is broken."

MapStruct is the second generated-code source: it emits `*Impl.java` into
`build/generated/sources/annotationProcessor/java/main`, and those files are compiled by the same
`compileJava` task, so ErrorProne analyzes them too unless excluded.

<approach_analysis>
## Alternate approaches considered (CLAUDE.md GSD execution directive)

**How it works, in three sentences.** ErrorProne is a `javac` plugin, so the Gradle plugin's real job
is to put `error_prone_core` on the compiler's processor path, add `-Xplugin:ErrorProne` to the
compiler args, and — on JDK 16+ — fork the compiler with the `--add-exports jdk.compiler/...` JVM
args that let that plugin reach javac's internal AST classes. javac parses and attributes each source
file exactly as it normally would, then hands the attributed AST to ErrorProne, which walks it once
with a set of matchers (one per "check") and emits each match through javac's own diagnostic channel.
Because findings ride javac's diagnostics, an ERROR-severity finding fails `compileJava` itself before
a single test runs — which is precisely what makes it a build gate, and equally what makes a false
positive a hard blocker rather than mere noise.

| Approach | Pros / Cons | Why picked |
|----------|-------------|------------|
| **ErrorProne as a javac plugin via `net.ltgt.errorprone`** (chosen) | **+** Runs inside the existing compile, so it covers every build path — `./gradlew test`, CI, and the Dockerfile's `bootJar` — with zero new tasks and zero CI edits. **+** Full type attribution available, so checks reason about resolved types, not text. **+** Earliest possible feedback: fails before tests, before packaging. **+** Severity is per-check and tunable, so the gate strength is a dial rather than a switch. **-** Forces a forked javac on JDK 21, adding a JVM spawn per compile task. **-** Runs against Lombok- and MapStruct-mutated ASTs, which is the live false-positive/crash surface documented above. | It is the only option that satisfies the todo's actual ask — *compile-time* bug detection — and it is the only one whose findings are unavoidable by construction rather than dependent on remembering to run a separate task. |
| **SpotBugs (+ `com.github.spotbugs` Gradle plugin)** | **+** Analyzes compiled bytecode, so Lombok/MapStruct generated code is just ordinary bytecode — none of the AST-mutation crash class above applies. **+** Mature, and `find-sec-bugs` adds a genuine security ruleset ErrorProne has no equivalent for. **-** Runs as a *separate* `spotbugsMain` task that is not in the `test` or `bootJar` dependency graph, so CI and the Docker build would need edits to actually gate on it. **-** Bytecode-level analysis reports findings against synthetic Lombok-generated methods with no meaningful source position, which is its own triage tax. **-** Notably slower than an in-compile AST walk on a repeat build. | Rejected as the primary: it detects *later* than compile time and would not gate any existing build path without touching CI, which is a larger change than this quick task. Genuinely worth reconsidering as a complement later, specifically for `find-sec-bugs` — noted, not scoped here. |
| **javac's own `-Xlint:all -Werror`** | **+** Zero dependencies, zero supply-chain surface, zero build-time cost, one line in build.gradle. **+** Also compile-time, also covers every build path. **-** The `-Xlint` check set is roughly a dozen categories (deprecation, unchecked, fallthrough, serial) and catches almost none of the bug classes the todo names — no null-deref analysis, no ignored-return-value, no misused-API checks. **-** `-Werror` on this codebase would immediately fail on `unchecked`/`deprecation` warnings from Spring and Vavr generics that are not actionable. | Rejected: it is the cheapest option and the closest to a no-op. The todo explicitly asks for the bug classes `-Xlint` does not cover, and `-Werror` would produce exactly the untriageable wave the todo warns against, but from library noise rather than from real findings. |

## Non-obvious trade-offs

- **Performance — a permanent, per-build tax.** On JDK 16+ the plugin *must* fork the compiler to
  pass `--add-exports`, which means an extra JVM spawn per `JavaCompile` task and the loss of
  Gradle's in-process warm compiler. At 94 main + 27 test sources this is on the order of seconds,
  but it is paid on **every** `./gradlew test`, every CI run, and every Docker image build — not just
  on full builds. Incremental compilation still works, but ErrorProne re-analyzes every file javac
  recompiles, so the marginal cost tracks recompile size rather than change size.
- **Memory.** The forked javac gets its own heap, separate from the Gradle daemon's, and ErrorProne
  holds the full attributed AST plus its matcher set during the walk. Not a concern at this size, but
  it is the reason a `bootJar` inside a memory-capped Docker build agent is the first place an OOM
  would show up if this codebase grew substantially.
- **Supply-chain surface (security).** `error_prone_core` is code that executes *inside the compiler*,
  on every build, on every developer machine and CI runner, with `--add-exports` access into
  `jdk.compiler` internals. That is a materially deeper level of access than Spotless (a formatter)
  or ArchUnit (a test-scoped bytecode reader) has. It is Google-maintained and near-ubiquitous in the
  Java ecosystem, so the risk is acceptable — but it is a real widening of what runs at build time
  and it argues for an explicitly pinned version.
- **State-invalidation risk — this is the sharp edge of a hard gate.** With ERROR-severity findings
  failing the build, the enabled check set is versioned by the `error_prone_core` coordinate. A new
  ErrorProne release can add ERROR-severity checks, so a floating version (`2.+`, `latest.release`)
  means an **upstream release with zero local changes can red CI and block the Docker image build.**
  The plugin's own README warns about exactly this. Both versions are therefore pinned exactly, and a
  version bump is treated as its own reviewable change rather than something that drifts.
- **False-green risk in the `excludedPaths` regex.** `excludedPaths` is a regex matched against a file
  path. Writing it with `/` separators only is the obvious thing to do and produces a config that
  matches nothing on this Windows dev machine while working correctly on the Ubuntu CI runner — i.e.
  the exclusion appears to work in CI and silently does not locally, or vice versa depending on how
  the path is normalized. Use a separator class that accepts both.
- **Trusting a low count requires a positive control.** If the plugin is applied but the `errorprone`
  configuration dependency is missing or checks are off, the compile succeeds cleanly and the
  measurement reads "0 findings" — indistinguishable from a genuinely clean codebase. A count is only
  evidence *after* ErrorProne has been observed reporting a deliberately-introduced bug. This is the
  same teeth-proof discipline established by quick task 260802-q6n and it is mandatory here.
</approach_analysis>

Relevant compatibility fact, so it is not rediscovered: plugin 4.4.0 added unconditional
`-XDaddTypeAnnotationsToSymbol=true`, which ErrorProne 2.46.0+ requires on JDK 21. The plugin also
detects the JDK 16+ toolchain and automatically switches to a forked compiler with the necessary
`--add-exports jdk.compiler/...` JVM args. Neither needs to be configured by hand; if a compile fails
with a module-access error mentioning `com.sun.tools.javac`, that auto-fork is what did not engage.

Add a `tasks.withType(JavaCompile).configureEach { options.errorprone { ... } }` block configuring:

- `allErrorsAsWarnings = true` — TEMPORARY, for measurement only. This demotes ERROR findings to
  warnings so the compile completes and emits the FULL finding list instead of the build dying part
  way through. Mark it with a `// TEMPORARY - measurement mode, see Task 2` comment so it cannot be
  mistaken for a settled decision.
- `disableWarningsInGeneratedCode = true` — permanent regardless of the Task 2 outcome.
- `excludedPaths` set to the regex string `.*[/\\]build[/\\]generated[/\\].*` so MapStruct's
  generated `*Impl.java` under `build/generated/sources/annotationProcessor/java/main` is not
  analyzed. Note the character class accepts both separators deliberately — a `/`-only regex is a
  false green on this Windows machine. In a Groovy single-quoted literal each backslash must be
  doubled, so the literal written into build.gradle is `'.*[/\\\\]build[/\\\\]generated[/\\\\].*'`
  and the resulting Java String is `.*[/\\]build[/\\]generated[/\\].*`.

Do NOT set `allDisabledChecksAsWarnings` — that switches on the experimental check set and would
manufacture exactly the wave this measurement exists to detect. Do NOT add `-Werror`.
