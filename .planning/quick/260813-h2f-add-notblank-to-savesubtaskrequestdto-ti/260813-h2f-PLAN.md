<objective>
Add `@NotBlank` to `SaveSubtaskRequestDTO.title` alongside its existing `@SubtaskTitle`, so a JSON
body of `{}` or `{"title":null}` posted to `POST .../tasks/{taskId}/subtasks` is rejected by Bean
Validation with a 400 instead of falling through to the database's `subtasks.title NOT NULL`
constraint and surfacing as a 409.

Purpose: `@SubtaskTitle` resolves to a `@Size` constraint, and Bean Validation's `@Size` passes on
`null` by design. `SaveSubtaskRequestDTO` is the one `Save*RequestDTO` in this codebase that pairs
its size rule with nothing — `SaveBoardRequestDTO`, `SaveTaskRequestDTO` and `SaveColumnRequestDTO`
all pair theirs with `@NotBlank`. Quick task `260811-me4` did not introduce this gap, but by making
the JSON body the endpoint's real binding path it made this the gap a normal client integration will
actually hit.

Output: One production annotation added, four new HTTP-tier test cases proving the failure moved
from the database constraint to Bean Validation, and one todo closed.
</objective>

### Sub-decision (D-02): which `@NotBlank` message

`@NotBlank(message = "Subtask title cannot be empty")` — matching the phrasing of `SaveTaskRequestDTO`
("Task title cannot be empty") and `SaveColumnRequestDTO` ("Column name cannot be empty"), the 2-of-3
majority; `SaveBoardRequestDTO` uses "must not be blank". This string is deliberately identical to
`SubtaskTitle`'s own `message()` default, which has a real mechanical benefit — see the envelope
trade-off below.

## Non-Obvious Trade-offs

**Multiple violations on one field collapse silently.** `GlobalExceptionHandler` (lines 199-207)
builds its `errors` map with `HashMap.put(fieldName, errorMessage)`. Two violations on the same field
therefore overwrite each other, last-writer-wins, in constraint-iteration order that Bean Validation
does not guarantee. After this change, a title of `""` trips both `@NotBlank` and `@Size(min=3)`, so
its rendered `errors.title` message is nondeterministic. Consequences for this plan:

- The `{}`, `{"title":null}` and three-space cases each trip exactly one constraint (`@Size` passes on
  `null`; a three-character whitespace string satisfies `min=3`), so those tests may pin an exact
  message.
- The `""` case may assert status and the presence of `errors.title` only, never a specific message.
- Choosing the same string as `SubtaskTitle`'s default (D-02) makes even the `""` collapse produce a
  stable message in practice. That is a mitigation, not a guarantee, so the test still does not rely
  on it.

**Cost is zero at runtime.** `@NotBlank` is one additional O(1) constraint evaluated at the `@Valid`
controller boundary on a single short string. It runs strictly earlier than the work it replaces: the
current path costs a mapper call, a repository `save`, a JDBC round-trip and an exception-translation
pass before failing.

**Small security improvement, not just an ergonomics one.** The current 409 body's `detail` is the
`DataIntegrityViolationException` message, which names the `subtasks.title` NOT NULL constraint and
leaks internal schema naming to an unauthenticated-shape client error. The 400 replaces it with the
fixed `"Validation failed"` detail plus a field-scoped `errors` map. Tests assert the new envelope's
`code` and `errors.title` rather than just the status, so this property is pinned rather than
incidental.

**No state-invalidation or concurrency dimension.** The change is a pure request-shape guard on a
create path. It does not touch `@Version` optimistic-locking, the Kafka publish path (`SubtaskCreated`
is published after a successful save, so a request rejected at validation publishes nothing — already
the existing behavior for every other rejected mutation), or any cached/derived state.
