<objective>
Replace `RandFlakeGenerator`'s 23 random low bits with a monotonic, thread-shared sequence so
same-millisecond id collisions become structurally impossible instead of a measured ~6.5%-per-1000-calls
event, and reserve the sign bit so the packed value can never go negative.

Purpose: quick task `260813-ncx` measured the collision rate and fixed the *test*; this is the
root-cause fix to the *generator*. The collision has a live production consequence
(`ActivityLogRecorder.persist` silently swallows a colliding event as a redelivery).

Output: a lock-free Snowflake-family generator, a new `RandFlakeGeneratorTest` proving cross-thread
and cross-instance uniqueness, `EventIdGeneratorTest`'s probabilistic threshold tightened to an exact
1000, and the source todo closed.

**Two findings from this plan's own measurement that the source todo did not anticipate — read these
before writing code, they change what "correct" means here:**

1. **A per-instance counter would not work.** `EventIdGenerator` holds
   `private final RandFlakeGenerator randFlakeGenerator = new RandFlakeGenerator()`, and Hibernate's
   `@IdGeneratorType(RandFlakeGenerator.class)` builds its own instance per entity id mapping. An
   instance field would give each its own sequence, so two instances ticking in the same millisecond
   would emit *identical* ids — converting a 6.5% probabilistic collision into a deterministic one.
   The state must be `static`.

2. **The source todo's "no migration concern" claim is only half true.** Persisted ids stay *valid*
   (measured: base36 width is 12 chars under both the old and new layouts, and the column is
   `varchar(255)` — no width risk at all). But *ordering* is not automatically preserved: narrowing
   the low field from 23 to 22 bits halves every future id's magnitude, so with the epoch left alone
   every newly generated id would sort **below** every id already in the live database until
   **2030-03-26** (measured this session). That inverts `@OrderBy("id")` on `BoardEntity.column`,
   `ColumnEntity.task` and `TaskEntity.subtasks` for any collection mixing pre- and post-deploy rows
   — a column or subtask added after the deploy would jump to the front of an existing board's list.
   `BaseEntity` carries no `createdAt`, so id ordering is the *only* ordering those collections have.
   This plan moves `CUSTOM_EPOCH` back to 2018-01-01 in the same change to keep ids globally
   monotonic across the boundary; see the trade-off matrix below.
</objective>

<design_rationale>

## Data-flow mechanism (three sentences)

Every id is one 63-bit value `(millisecondsSinceEpoch << 22) | sequence`, held in its entirety in a
single shared `static AtomicLong` as "the last id payload issued". Each call reads the clock, forms
the candidate `now << 22`, and atomically stores `max(candidate, previous + 1)` — so a fresh
millisecond resets the sequence to zero for free, and a repeat millisecond increments it. Because the
whole `(timestamp, sequence)` pair lives in one CAS'd word, the pair can never be observed or updated
torn, and `previous + 1` carries naturally out of the sequence field into the timestamp field, which
is what makes sequence exhaustion and a backward clock step both non-events instead of special cases.

## Trade-off matrix A — concurrency mechanism

| Approach | Pros / Cons | Why picked |
|---|---|---|
| **Single packed `static AtomicLong`, `updateAndGet(prev -> Math.max(now << SEQ_BITS, prev + 1))`** | **+** `(timestamp, sequence)` is one word, so it is atomic by construction with no lock. **+** Lock-free: contending threads retry a CAS, never park. **+** Sequence exhaustion and NTP step-back need no branch — `prev + 1` covers both. **+** Strictly monotonic across threads *and* instances. **−** Under extreme burst, ids drift ahead of wall-clock. **−** One globally contended cache line. | **PICKED.** Only option that delivers cross-thread uniqueness without reintroducing the serialization point quick task `260802-tbj` deliberately removed. The drift bound is not a real cost: drifting 1 ms ahead requires issuing 4,194,304 ids inside 1 ms. |
| `synchronized` block over two fields (`lastTimestamp`, `sequence`), spin-wait on exhaustion — classic Twitter Snowflake | **+** Easiest to read. **+** Exact tick fidelity, ids never run ahead of the clock. **−** Serializes *every entity insert in the application* behind one monitor — exactly the pointless-lock removal `260802-tbj` performed, reinstated with teeth this time. **−** Spin-wait parks a servlet request thread on a busy-wait. | Rejected. Correct but pays a global lock for a property the CAS gets for free, and its exhaustion strategy blocks a request thread rather than borrowing from the next tick. |
| `ThreadLocal` per-thread counter | **+** Zero contention, no shared state at all, preserves the class's current "no shared mutable state" premise verbatim. **−** **Does not fix the bug.** Two servlet threads entering the same millisecond both start at sequence 0 and emit byte-identical ids. | Rejected — fails the primary requirement. It would close only the *specific test's* single-threaded gap while making real concurrent inserts collide deterministically: strictly worse than today's randomness. |

## Trade-off matrix B — bit layout and epoch

Total budget is 64 bits, of which bit 63 (sign) must stay unwritten, leaving 63.

| Approach | Pros / Cons | Why picked |
|---|---|---|
| 40-bit timestamp + 23-bit sequence, epoch unchanged | **+** Id magnitude identical to today, ordering continuity free. **+** Largest sequence (8.4M/ms). **−** Timestamp field still exhausts **2057-11-03** — reserving the sign bit here only converts a silent sign-flip into a documented cap. | Rejected — does not close the stated 2058 overflow, which is half the task. |
| 41-bit timestamp + 22-bit sequence, epoch unchanged (2023-01-01) | **+** Smallest possible diff, one constant. **+** Horizon 2092-09. **−** Halves every future id's magnitude: new ids sort below all pre-deploy ids until **2030-03-26** (measured), inverting `@OrderBy("id")` on three entity collections that have no other ordering column. | Rejected — trades a 2058 bug for a user-visible ordering regression on live data now. |
| **41-bit timestamp + 22-bit sequence, `CUSTOM_EPOCH` moved to 2018-01-01** | **+** Horizon **2087-09-07**. **+** Every id generated under the new layout exceeds `1058897343283200000`, the highest value the legacy layout could produce even if the old code kept running until 2027-01-01 — so global monotonicity holds across the deploy. **+** Base36 width still 12. **−** The epoch constant no longer decodes *historical* ids to their true creation time. **−** Two constants change instead of one. | **PICKED.** The decode caveat costs nothing — no production code decodes an id; the only decoder was `260813-ncx`'s throwaway probe, and any layout change breaks historical decode anyway. |

## Non-obvious performance, concurrency and security trade-offs

- **Contention.** One `AtomicLong` is shared by every insert path in the app. Each `updateAndGet`
  iteration is a clock read plus a CAS — tens of nanoseconds against a database insert measured in
  microseconds-to-milliseconds. Under contention the loop retries with a *fresher* clock, which is
  correct, not merely tolerable. This is a real cache-line hot spot only at rates this single-instance
  app cannot produce.
- **Sequence exhaustion is not spin-waited.** At >4,194,304 ids in one millisecond, `prev + 1` carries
  into the timestamp field and ids simply borrow from the next millisecond, self-correcting as the
  clock catches up. Sonyflake spin-waits (parks a thread) and reference Snowflake throws (fails an
  insert); borrowing does neither. The accepted cost is that under a sustained impossible-for-this-app
  rate, an id's decoded timestamp can read slightly ahead of true wall-clock.
- **Backward clock steps are absorbed.** An NTP step-back makes `candidate < prev`, so `prev + 1`
  wins and ids never regress. The old design would have happily emitted a lower id; reference
  Snowflake throws.
- **Uniqueness is per-JVM, and that is the whole guarantee.** Two JVMs sharing a database would
  collide on the shared sequence space with no machine-id field to separate them. This is accepted
  deliberately (single-instance, `docker-compose.prod.yml`) and must be stated in the class comment as
  the condition under which the guarantee holds — not left implicit. Note the *old* design was equally
  unsafe across instances, just probabilistically rather than deterministically.
- **Security: ids stop being unpredictable.** Removing 23 random bits makes ids enumerable — given one
  id, a caller can guess neighbours. This is safe *here* because every read and write path runs
  `OwnershipVerifierService` first, so an id is never a capability; but ids now also leak creation
  *order and volume* (how many boards exist between two timestamps), where previously they leaked only
  creation time. See `<threat_model>`. If an unauthenticated share-link feature is ever built on a raw
  entity id, this trade-off must be revisited.
- **Base36 width still changes eventually** — at 2053-10-19 the string goes from 12 to 13 chars under
  the new layout, at which point plain lexicographic (string) comparison of ids stops matching numeric
  comparison. That caveat already exists in `EventIdGeneratorTest`'s third test; it survives this
  change with a new date, it is not introduced by it.
