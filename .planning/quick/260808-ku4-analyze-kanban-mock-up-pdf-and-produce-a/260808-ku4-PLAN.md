<objective>
Produce a single, actionable feature gap document comparing the Kanban design mock-ups
against the backend's actually-implemented REST surface.

Purpose: The backend has been built out over several milestones without a written
comparison against the product design it is meant to serve. Before any frontend
hand-off (or any decision about what to build next), we need one document that states
plainly what the design asks for, what the API provides, and where the two disagree.

Output: `docs/MOCKUP_FEATURE_GAP.md`, plus the extraction script and extracted page
text that make every mock-up claim in it independently re-checkable.

Scope guard: This is a read-only analysis producing documentation. No Java source, no
tests, no build configuration is touched. `./gradlew spotlessCheck` / `./gradlew test`
are deliberately NOT part of this plan's verification, because no compiled code changes.
</objective>

<approach_analysis>
Required by CLAUDE.md before any PLAN.md is created.

The hard constraint driving this decision: the mock-up PDF is **115 MB across 73 pages**
(verified at planning time, not assumed). How it gets read determines whether this task
fits in one executor context at all.

**Approach A — Render and read all 73 pages as images.**
Use the Read tool's `pages` parameter across 4 batched calls (20-page cap per call).

**Approach B — Text extraction only.**
Extract the text layer from all 73 pages and reason purely over labels and copy.

**Approach C (PICKED) — Text index over all pages, bounded visual reads over a
deduplicated subset.**
Extract text from all 73 pages first (complete coverage, cheap), use that index to
identify which pages are visually distinct, then visually read only those.

| Approach | Pros / Cons | Why Picked / Rejected |
|----------|-------------|-----------------------|
| A. Read all 73 pages as images | **Pros:** highest fidelity; catches every purely visual affordance (drag handles, checkbox states, theme toggle, breakpoints). **Cons:** ~110k tokens of image payload for 73 renders; leaves little context left to actually write the document; ~40 of the 73 pages are exact light/dark or repeated-state duplicates, so most of that cost buys nothing. | **Rejected** — pays full price for large redundancy and puts the synthesis step at risk of running out of room. |
| B. Text extraction only | **Pros:** ~20k tokens for all 73 pages (measured, see below); complete page coverage; fast. **Cons:** blind to anything with no text — drag-and-drop affordance, checkbox checked/unchecked state, sidebar show/hide chrome, light-vs-dark theming, responsive column layout. Those are exactly the features most likely to be backend gaps. | **Rejected alone** — would silently under-report the most interesting gaps. |
| C. Text index for all + bounded visual reads (PICKED) | **Pros:** 100% page coverage from the text layer at ~20k tokens; visual confirmation where it actually adds information; the text index is committed as reproducible evidence. **Cons:** requires a working extractor and a judgement call about which pages to view; a purely visual detail on an unviewed page could still be missed. | **Picked** — the only approach that gets full coverage and visual detail while leaving enough context to write the document. The residual miss risk is mitigated by a required-coverage list (below) rather than left to chance, and is disclosed in the document's limitations appendix. |

**Non-obvious trade-offs, measured at planning time rather than guessed:**

- *Extraction viability was a real risk, not a formality.* The PDF's text operands are
  **subsetted glyph indices, not ASCII** — a naive `zlib` + `Tj`-operand scrape returns
  octal garbage (this was tried and failed during planning). Correct output requires
  applying the 78 embedded `/ToUnicode` CMaps, which is why `pypdf` is used rather than
  a hand-rolled stdlib parser. `pypdf` output was spot-checked against pages 1-5 and
  returns clean, meaningful design copy.
- *Memory / time.* Full-document extraction was run at planning time: 73 pages,
  78,808 characters (~20k tokens), completing well inside a bounded timeout. `pypdf`
  loads the 115 MB file into memory; this succeeded on this machine. The extraction
  command therefore carries an explicit timeout so a pathological parse cannot hang the
  executor indefinitely.
- *Supply chain.* `pypdf` 6.15.0 is **already installed** (user-site, from the planning
  feasibility probe). This plan contains **no package-manager install task** — Task 1
  asserts the import as a precondition instead. It is a local Python tool, absent from
  `build.gradle`, so the shipped Java artifact's dependency set is unchanged. See
  `<threat_model>` T-ku4-SC.
- *Freshness / provenance.* The PDF lives outside the repository (`B:\downloads\...`),
  so nothing committed here could otherwise be re-verified by a reviewer or a future
  agent. That is the specific reason the extracted page text is committed as evidence
  rather than left in a scratch directory — consistent with this repo's "every capability
  claim backed by a named artifact" convention.
</approach_analysis>

<planning_findings>
Findings established during planning. Treat these as verified starting points to
confirm and build on, not as conclusions to restate unchecked.

**Mock-up PDF structure** (derived from a full 73-page text extraction):

| Pages | Content |
|-------|---------|
| 1 | Design system — colour palette (hex/RGB/HSL) and typography |
| 2-11 | Desktop, light theme — 10-screen sequence (empty board, populated board, sidebar shown/hidden, modals) |
| 12-21 | Desktop, dark theme — text-identical mirror of pages 2-11 |
| 22-33 | Tablet — light (22-27) and dark (28-33) |
| 34-53 | Further desktop states; pages 40 and 47-53 are 2-up composite pages showing modal/interaction states |
| 54-63 | Mobile, light theme |
| 64-73 | Mobile, dark theme — text-identical mirror of pages 54-63 |

Light/dark page pairs are byte-identical in extracted text (e.g. page 2 and page 12 are
both exactly 199 characters), which is why theming needs visual confirmation and cannot
be established from text alone.

Design copy already observed in the extracted text, useful as orientation:
board switcher with a board count, a create-new-board affordance, a create-new-column
affordance, an add-new-task affordance, an empty-board message, per-task subtask
progress counts, and a sidebar hide control.

**Backend REST surface** (read at planning time; nineteen routes across seven controllers).
Note the two structural observations that matter most for the diff:
- `BoardController` exposes list / update / delete and add-column — but **no board
  creation route**. STATE.md corroborates: boards are only created through
  `UserService.addBoardByUserId`, which no controller exposes.
- No DTO anywhere carries an ordering or position field. `MoveTaskRequestDTO` is
  `targetColumnId` + `version` only — a cross-column move, with no notion of placement
  within the target column.
- `/logout` has no controller method; it is wired declaratively in
  `SecurityConfiguration` via `http.logout(...)`. Confirm the exact path there before
  writing it into the inventory.
</planning_findings>
