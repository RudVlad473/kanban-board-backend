<objective>
Close the `.with(user())` vs. `MAX_CONCURRENT_SESSIONS = 2` test-infra interaction by writing it down
in the two places a test author will actually be standing when it bites them: `docs/CODE_STYLE.md`
rule 4 (the full worked account) and `AbstractAppMockMvcTest`'s class Javadoc (a short pointer, next
to the `signinCookie()` helper that is the way out).

The interaction is real, measured, and currently undocumented outside one test class's Javadoc and a
todo: `SecurityMockMvcRequestPostProcessors.user(userId)` — the shortcut all four
`controller/*ControllerTest` classes use — establishes a brand-new HTTP session on every request it
authenticates, so the third call for one principal inside one test method is refused with a bare 401
that reads exactly like a wrong password. A future test author hitting that has no signal pointing at
the session ceiling.

Purpose: stop the next agent from re-deriving a non-obvious framework interaction by trial and error
against an error message that actively misdirects.

  request. This is option 1 from the source todo, which is also the todo's own recommendation.
  Options 2 (a custom session-propagating `RequestPostProcessor`) and 3 (do nothing) are not

**Non-obvious trade-offs:**

- *The error message is the whole reason this needs documenting.* A ceiling rejection returns the
  same 401 body as a wrong password — that is a deliberate security property (`SecurityConfiguration`
  D-08: not handing an attacker a credential-validity oracle), not an oversight. The consequence is
  that the failure gives a test author **no** signal pointing at sessions, which is why it cost a
  scratch-test investigation the first time. Documenting the observable symptom (`200, 200, 401,
  401`) is therefore more load-bearing than documenting the mechanism.
- *Naming the wrong filter would be worse than naming none.* The temptation is to transcribe the
  source todo's `SessionManagementFilter` attribution into the style guide. But
  `SecurityConfiguration`'s own comment says no filter reads those declarations on this application's
  authentication path — and both statements are currently sitting in the repo unreconciled. A style
  guide that states a mechanism confidently and wrongly is worse than one that states the ceiling and
  stops, because it will be cited. D-03 + D-09 is the honest split: document what holds, track what
  is unresolved.
- *`spotlessCheck` is a live gate here, unlike the last three docs-only quick tasks.*
  `AbstractAppMockMvcTest.java` is under `src/**/*.java`, so Google Java Format AOSP applies to the
  Javadoc block — a line past the column limit fails the build. Run `./gradlew spotlessApply` before
  `spotlessCheck` rather than hand-wrapping. Full `./gradlew test` is deliberately *not* a gate: a
  Javadoc-only change cannot alter behaviour, and `compileTestJava` is the cheap check that actually
  catches the realistic failure (a malformed `{@link}` or an unbalanced brace).
- *The reference-class correction is not cosmetic.* Citing `AuthorizationGatingTest` as a
  cookie-replay example — as the source todo does — would send a reader to a class containing six
  `.with(user(...))` calls and zero `signinCookie()` calls, i.e. to the exact pattern the note warns
  about, presented as the fix. Verifying the citation before writing it is the difference between a
  guide and a rumour.
- *Performance / memory:* not applicable. One markdown paragraph, one Javadoc block, zero runtime
  artefacts, zero bytecode change (Javadoc is not retained in class files).
- *Supply chain:* no package-manager installs, no dependency changes, no `build.gradle` touch.
