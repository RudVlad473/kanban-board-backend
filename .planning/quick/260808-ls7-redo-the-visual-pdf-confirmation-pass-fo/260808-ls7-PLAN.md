### Decision 1 — how much to re-confirm

**Approach A — Redo the full sweep as a fresh general analysis.** Render 20 pages chosen
for broad coverage and re-derive every mock-up inventory row from the images, treating the
existing document as a draft to be superseded.

**Approach B (PICKED) — Targeted confirmation pass.** Render a 20-page selection chosen
specifically to settle the four named open questions, while still satisfying the prior
plan's required-coverage list, and amend only the rows and paragraphs those pages bear on.

**Approach C — Minimal pass.** Render only the ~6 pages strictly needed to answer the four
questions (design system, one populated board per pass, one mobile board, the mobile board
switcher).

| Approach | Pros / Cons | Why Picked / Rejected |
|----------|-------------|-----------------------|
| A. Full re-derivation | **Pros:** would catch errors in rows nobody currently suspects; produces one internally consistent pass. **Cons:** 20 rendered pages (~30k tokens of image payload) *plus* re-reading and re-writing all 109 inventory rows in the same context — the writing half is the expensive half and it duplicates work already verified against the source code; high risk of churning correct, already-page-cited rows and losing the prior pass's cross-checks against the controllers. | **Rejected** — pays to rewrite content that is already backed by evidence, and the re-write is where regressions would enter. |
| B. Targeted confirmation (PICKED) | **Pros:** same 20-page render budget, but the selection is chosen to discriminate between competing hypotheses rather than to sample broadly; the edit surface is small enough to state exactly which rows may change, so the gates can be precise; leaves verified content untouched. **Cons:** a visual error in an unexamined row survives this pass. | **Picked** — the task is to close named gaps, not to re-audit. The residual risk is bounded and already disclosed by the document's own provenance model (every row cites its source, so an unexamined row is visibly unexamined). |
| C. Minimal 6-page pass | **Pros:** cheapest; ~9k tokens of images; leaves the most room for careful writing. **Cons:** discards the prior plan's required-coverage list (each visually distinct modal, a tablet layout) for no saving that matters — the render budget was never the binding constraint; and it samples too thinly to distinguish "these two passes differ by theme" from "these two passes differ by sample data" (see the finding below, which is exactly that ambiguity). | **Rejected** — under-samples the one question that turned out to be genuinely ambiguous. |

### Decision 2 — how to get pages past the Read tool's 100 MB cap

The source PDF is 115 MB, over the Read tool's fixed cap for page rendering, so pages must
be copied into smaller derived PDFs first. Three shapes were available:

| Approach | Pros / Cons | Why Picked / Rejected |
|----------|-------------|-----------------------|
| One derived PDF per page (20 files) | **Pros:** derived page number always equals 1, so no renumbering hazard at all. **Cons:** 20 separate Read calls, blowing the 2-call budget by an order of magnitude; 20 full parses of a 115 MB file. | **Rejected** — violates the stated call budget and re-parses the source 20 times. |
| One derived PDF holding all 20 pages | **Pros:** a single parse and a single file. **Cons:** the Read tool caps a request at 20 pages, so this works only at exactly the budget ceiling with no headroom; and it forces all 20 renders into whichever task issues the call, concentrating the entire image payload in one context alongside the doc edit. | **Rejected** — no headroom, and it defeats the two-task context split. |
| Two derived PDFs (12 + 8 pages), one Read call each (PICKED) | **Pros:** exactly 2 Read calls; splits the image payload across the two tasks so neither carries all 20 renders plus the full document edit; each derived file groups pages that answer a coherent set of questions. **Cons:** page renumbering must be tracked across two mappings instead of one. | **Picked** — the renumbering hazard is real but cheap to mitigate (see below); the context split is not otherwise obtainable. |

### Non-obvious trade-offs

- **Page renumbering is the real correctness hazard, not rendering.** A derived PDF
  renumbers its pages `1..N`. If a citation is written from the derived page number, the
  document acquires *confidently stated wrong page numbers* — strictly worse than the
  honest "unconfirmed" labels it has today, because a wrong citation looks verified. Three
  mitigations: the splitter prints the `derived -> original` mapping; the selection is kept
  in ascending original order so the mapping is monotonic; and — the strongest check —
  every rendered page is cross-checked against its already-committed text block in
  `mockup-pages.txt` before any citation is written from it. That last check is independent
  of the splitter being correct. Recorded as `T-ls7-02`.
- **Image payload dominates the token cost.** At roughly 1.5k tokens per rendered page, 20
  pages is ~30k tokens, arriving before any writing happens. This is the whole reason the
  work is split into two tasks rather than one: Task 1 carries 12 renders, Task 2 carries 8.
- **Memory.** `pypdf` loads the full 115 MB document to split it, and `pdftoppm` rasterizes
  a 1440x1024pt page to roughly 3000x2133 px. Both were feasible on this machine at
  planning time (the prior task's splitter step succeeded; only the renderer was missing).
  The split runs under an explicit bounded timeout so a pathological parse cannot hang.
- **Repository hygiene.** The derived PDFs total roughly 30 MB. They are written **outside
  the repository**, to the session scratchpad, and never committed — the reproducible
  artifact is the splitter script plus the page list, exactly as the prior task committed
  the extraction script rather than the 115 MB source. A gate asserts no PDF exists in the
  working tree, so this cannot be forgotten. Recorded as `T-ls7-03`.
- **Supply chain.** Both tools were verified present at planning time: `pypdf` 6.15.0
  (user-site) and `pdftoppm` 26.02.0 (on PATH, installed by the user out-of-band via scoop,
  after and separately from the prior task). **This plan contains no install task** — Task 1
  asserts both as preconditions and halts if either is absent, upholding the `T-ku4-SC`
  precedent that unattended installs are not a thing an executor decides on. Neither tool
  is in `build.gradle`, so the shipped Java artifact's dependency set is unchanged.
  Recorded as `T-ls7-SC`.
