<approach_analysis>
The single real design decision is **what a sourced script does when resolution fails everywhere**. The inline version ends in `exit 1`. In a sourced script, `exit 1` terminates the *caller's* shell — for an interactive operator that means their terminal dies; for the GSD bash block it happens to be the desired outcome.

### Trade-off Matrix

| Approach | Pros / Cons | Why Picked |
|---|---|---|
| **A. Verbatim `exit 1` (literal fidelity)** | **+** Byte-identical to the inline block; zero interpretation risk. **-** Sourcing it into an interactive shell and missing every path kills that shell outright. **-** Makes the script hostile to the exact ergonomic use case it exists to serve. | **Rejected.** Optimizes for textual sameness over the behavior that made the extraction worth doing. |
| **B. Always `return 1`** | **+** Never kills a caller. **-** Breaks if anyone ever runs the file directly (`./.dev/gsd-run.sh`) — `return` outside a function/sourced context is an error in POSIX sh. **-** Silently drops the "exit 1" half of the stated contract. | **Rejected.** Trades one failure mode for another and quietly narrows the contract. |
| **C. Detect sourced vs. executed; `return 1` when sourced, `exit 1` when executed** *(chosen)* | **+** Identical stderr message and identical non-zero status in both modes. **+** Caller's shell survives sourcing. **+** Direct execution still behaves exactly like the inline block. **-** Three extra lines and one non-obvious shell idiom, which must be commented. | **Picked.** Preserves the observable contract (same message, non-zero status, same search order) in both invocation modes while removing the one behavior that would make sourcing unsafe. |

### Non-obvious trade-offs

- **Blast radius of sourcing vs. executing:** sourcing is not "running a script" — it injects `gsd_run`, `GSD_TOOLS`, `_GSD_SHIM_NAME`, and `_GSD_RUNTIME_ROOT` into the caller's shell namespace and they persist for the rest of that shell. This is intended (that's the whole point), but it means variable names must stay underscore-prefixed/namespaced so they cannot collide with a caller's variables. Do not rename them to something generic.
- **`CLAUDE_ENV_FILE` side effect:** the inline resolver's trailing line appends an `export PATH=...` line to `$CLAUDE_ENV_FILE` when that variable is set. It is append-only and guarded by a non-empty check, so it is a no-op in an ordinary shell — but it is a real filesystem write in a Claude Code session. Transcribe it as-is (dropping it would be a behavior change), and keep its `|| true` suppression so a read-only env file cannot fail the source.
- **Fidelity risk is transcription, not logic:** 19 of the 20 resolution branches cannot be exercised on this machine. The correctness risk is a typo in an env-var name or a wrong default path, which no test here will catch. Transcribe the ordered list below character-for-character rather than reconstructing it from memory.
- **Performance/state:** negligible. One `git rev-parse` and up to 20 `-f` stat calls per source, all O(1).
</approach_analysis>
