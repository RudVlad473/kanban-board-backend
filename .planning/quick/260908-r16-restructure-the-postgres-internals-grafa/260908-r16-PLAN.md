<design_rationale>

## Data-flow mechanism (three sentences)

Grafana's file provider reads every `*.json` under `/etc/grafana/provisioning/dashboards/json`
at startup and re-reads on a 30s interval, inserting each file into its own database keyed by
the dashboard's `uid`. Within a dashboard, an **expanded** row panel owns every panel that
follows it in the top-level `panels` array until the next row panel appears — so row membership
is positional, and `gridPos` only decides where a panel sits *within* its row's band. The change
is therefore purely a re-ordering of that one array plus a rewrite of each entry's `gridPos`;
no query, datasource, threshold or unit is read or rewritten by any step here.

## Alternate approaches considered

**A — Python codemod over the parsed JSON (PICKED).** Load, reassign `gridPos` and array order
by panel id, write back with `json.dumps(indent=2)`. Panels are carried by object identity, so
non-layout fields cannot be altered even by accident.

**B — Hand-edit the raw JSON with the Edit tool.** 23 panels x 4 gridPos fields, plus deleting
one row and inserting five, plus physically relocating panel objects to get the array order
right: roughly 30 error-prone edits across an 88KB file, with no mechanical guarantee that a
`targets` block was not clipped during a move.

**C — Import into a live Grafana, rearrange in the UI, export the JSON.** Grafana's exporter
migrates `schemaVersion` 25 forward, rewrites `singlestat` panels to `stat`, injects
`__inputs`/`__requires`, and renames or drops legacy fields — mass unintended churn that
directly violates the "preserve everything but gridPos" constraint.

## Trade-off matrix

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| **A. Python codemod (parsed JSON)** | **+** Non-layout fields carried by object identity — cannot drift. **+** Round-trip is byte-identical (measured), so the diff shows only intended lines. **+** The transformation is itself reviewable as a table. **-** Requires the round-trip property to hold, which is a precondition that could silently break later. | **PICKED.** The one risk is checkable in one line, so the codemod asserts it before mutating anything and aborts otherwise. |
| **B. Hand-edit raw JSON** | **+** No script artifact. **-** ~30 manual edits with no invariance guarantee. **-** Moving 23 panel objects to fix array order is exactly where a `targets` block gets clipped. **-** Large context cost re-reading an 88KB file. | Rejected: the failure mode (a silently corrupted query) is the specific thing this task must not do. |
| **C. UI round-trip export** | **+** Visual, no arithmetic. **-** Exporter rewrites schemaVersion, migrates singlestat→stat, injects `__inputs`. **-** Diff becomes unreviewable. | Rejected: violates the preservation constraint by construction. |

## Non-obvious trade-offs

- **Row membership is positional, not geometric.** Setting `gridPos.y` correctly but leaving the
  array order alone would produce five empty rows with all 23 panels dangling under the last one.
  The array order is the load-bearing half of this change.
- **Reusing `id: 18` for the first new row** (rather than deleting it and allocating five fresh
  ids) keeps the panel-id set monotone — nothing disappears — which is what lets the verifier
  assert the strictly stronger invariant "no panel id was removed" instead of a bookkeeping
  exception for one deleted row.
- **Height changes are deliberate, not incidental.** Stat panels in the Connections and
  Storage & I/O rows go `h: 3 -> 6` to align with the gauges beside them, and `Locks by state`
  goes `h: 10 -> 9` to align with `Deadlocks by database`. Widths go `w: 4 -> 6` or `8` now that
  three-to-four panels share a line instead of six. Both are inside the user's explicit "gridPos
  width/height where it makes sense" allowance.
- **The collapsed row id 20's 12 nested panels keep their own gridPos untouched.** Grafana
  re-lays a collapsed row's children out relative to the row on expand; rewriting them would be
  churn with no visual effect and would enlarge the diff into the part of the file the user asked
  to leave alone.
- **No credential literal enters any file.** The disposable Grafana runs with anonymous Admin
  auth and a runtime-generated `openssl rand -hex 16` admin password held only in a shell
  variable — a password literal pasted into `.planning/` prose would be refused by
  `.githooks/pre-commit`'s gitleaks scan before formatting ever ran.
- **Memory cost of verification:** the disposable Grafana peaks around 200-400MiB for ~30s on
  the local dev machine only. It publishes no ports, joins no project network, and is removed by
  a shell `trap` on any exit path — it cannot collide with a running local stack.
