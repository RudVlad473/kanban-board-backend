## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Narrowed the live-render container-log error assertion**
- **Found during:** Task 1 (building verify-dashboards.sh, confirmed again during Task 2's full run)
- **Issue:** The plan's specified check (`docker logs <cid> | grep -i 'level=error' | grep -iE 'provision|dashboard'`) always fails on a freshly started `grafana/grafana:13.2.1` container in this environment, regardless of whether the dashboard restructuring is correct. Grafana logs `level=error` from its `provisioning.plugins` and `provisioning.alerting` sub-readers on every cold start whenever `/etc/grafana/provisioning/plugins` and `/etc/grafana/provisioning/alerting` don't exist — which they don't here, since this repo only provisions `dashboards/` and `datasources/` under `docker/grafana/provisioning/` (confirmed by inspecting a disposable container's logs directly, and confirmed the same directory listing is what `docker-compose.prod.yml` mounts into production, so this same noise is present there too, unrelated to this task's changes).
- **Fix:** Scoped the grep specifically to `logger=provisioning.dashboard` (Grafana's actual logger name for its dashboard file provider, confirmed by inspecting a disposable container's `starting to provision dashboards` / `finished to provision dashboards` log lines) before checking for `level=error`, rather than a bare `provision|dashboard` substring match anywhere in the log.
- **Files modified:** `.planning/quick/260908-r16-restructure-the-postgres-internals-grafa/verify-dashboards.sh`
- **Verification:** Re-ran `verify-dashboards.sh 69d8e7e` after the fix; Step 4 passes with "OK: no dashboard-provisioning errors in container log" while the (unrelated, expected) plugins/alerting noise remains present in the raw container log.
- **Committed in:** `f6647c4` (Task 1 commit — the fix was made before the script was ever committed, since it was discovered while building the harness)

The script's existing bounded-retry loops (health check ~60s, dashboard fetch ~30s) absorbed this variance in every actual verify-dashboards.sh run; no timeout adjustment was needed in practice, but a slower machine could plausibly need one.
