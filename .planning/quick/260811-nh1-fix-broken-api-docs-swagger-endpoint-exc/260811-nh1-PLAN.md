## Core fix: how to remove the shadowing artifact

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Per-dependency `exclude` on the Confluent coordinate** (chosen) | + Smallest blast radius — only this one dependency's transitives change. + Sits next to the existing `kafka-clients` exclude, so the file already reads as "this dep needs pruning". + This is the exact form the todo author already ran and confirmed working. − Does not stop a *different* future dependency reintroducing the same artifact. | **Picked.** It is the verified fix, and the failure mode it does not cover (a second, different introducer) does not exist today and would announce itself the same loud way. |
| **B. Global `configurations.all { exclude group: 'io.swagger.core.v3', module: 'swagger-annotations' }`** | + Immune to reintroduction via any path. − Silently strips the artifact from every configuration, including any future dependency that legitimately needs the non-jakarta variant, and the failure would surface as an unrelated `NoClassDefFoundError` far from this line. | Rejected: buys insurance against a hypothetical at the price of a much worse diagnostic story if it ever misfires. |
| **C. Gradle capability conflict rule** (declare `swagger-annotations` and `swagger-annotations-jakarta` as providing the same capability, resolve to jakarta) | + The most accurate model of reality — these genuinely are two artifacts of one capability, which is precisely why Gradle failed to dedupe them. + Self-documenting and reintroduction-proof. − Needs a `ComponentMetadataRule`/capability block, machinery that appears nowhere else in this build. − Not the verified fix. | Rejected for a quick task. Worth revisiting only if a second same-package collision ever appears — at that point the modelling cost is justified by two instances rather than one. |

## Secondary: `.dockerignore` shape

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **Denylist** (chosen) | + Cannot break the build by omission — a new file that the build needs is included by default. + Matches what the todo asked for. − A newly added junk directory is shipped in the context until someone adds a line. | **Picked.** The failure mode of the alternative (a silent build break) is strictly worse than the failure mode of this one (a slightly larger context). |
| **Allowlist** (`*` then `!gradlew`, `!src`, ...) | + Provably minimal context. − A future build input added at the repo root is silently excluded, and the resulting Gradle failure inside a Docker build stage is painful to diagnose. | Rejected. |

## Non-obvious trade-offs

- **Availability risk (the real one):** `kafka-schema-registry-client` is compiled against classes in
  `io.swagger.v3.oas.annotations`. Removing the pre-jakarta jar is only safe because
  `swagger-annotations-jakarta` supplies the *same package and class names* — those references still
  resolve, just from the other jar. If any Confluent class referenced a member that exists only in
  the 2.1.x variant, the failure would move from SpringDoc into the Kafka publish path. This is why
  Task 1's gate is the FULL `./gradlew test` (Kafka/Avro E2E classes included), not `fastTest`.
- **Security, direction 1 (improvement):** `.env` holds `DB_USER`/`DB_PASS` and is currently swept
  into the build stage by `COPY . .`. The runtime stage copies only the jar, so it does not reach the
  final image — but it does sit in an intermediate/cached layer. Excluding it is a real, if modest,
  credential-hygiene win.
- **Security, direction 2 (exposure):** this fix *re-exposes* an endpoint that has been de facto
  disabled by its own 500. `/api/docs` is `permitAll` by design and publishes the full route surface
  unauthenticated. That is the intended design and the point of the frontend hand-off, but it is a
  genuine change in live attack surface, not a neutral bug fix. Registered as T-NH1-02 below.
- **Performance:** the new test class adds `@AutoConfigureMockMvc` to a `@SpringBootTest`, which is
  the same context-cache key shape the four existing `controller/*ControllerTest` classes already
  use — expect context reuse, not a new context startup. Do not assert zero cost; if the suite grows
  by more than this project's documented ~18s run-to-run variance, say so rather than rounding it to
  noise.
</tradeoffs>
