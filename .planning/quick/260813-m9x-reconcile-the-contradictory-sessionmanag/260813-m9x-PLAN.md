<objective>
Settle, by measurement, which component invokes `sessionAuthenticationStrategy` on which
authentication path in this application — then correct exactly the claims that measurement
falsifies.

Three places in this repo currently assert two incompatible things about the same mechanism.
`InjectionAttemptTest`'s class Javadoc and the now-closed 2026-08-10 todo attribute the
`MAX_CONCURRENT_SESSIONS = 2` ceiling to `SessionManagementFilter` treating each MockMvc
`.with(user())` call as a fresh login. `SecurityConfiguration` asserts twice — once in the inline
comment on its `sessionManagement` DSL block, once in its `sessionAuthenticationStrategy` bean
Javadoc — that no filter reads those declarations on this application's authentication path and that
`AuthenticationController.authenticate` is the sole invoker. Quick task 260813-k47 deliberately
refused to adjudicate this and filed the todo this plan closes.

Both claims may be true under different conditions, or one may be flatly wrong. The plan does not
prejudge: Task 1 measures, Task 2 edits. Nothing is written down until it has been observed.

Purpose: a security-relevant mechanism should be described in this codebase the way it actually
behaves, path by path — and the next agent to reason about the session ceiling (for a scaling
decision, a test-tier decision, or a security review) should not have to re-derive it against three
mutually contradictory comments.
Output: raw probe evidence preserved in the plan directory, at most two Javadoc/comment blocks
corrected and path-scoped, the throwaway probe deleted and verified gone, and the source todo closed
with a Resolution that reports measurements rather than theory. No behavioural change anywhere.
</objective>

## Approach & Trade-offs

**Decisions locked for this task** (derived from the task constraints plus facts confirmed by
reading `SecurityConfiguration`, `AuthenticationController`, `InjectionAttemptTest`,
`AbstractAppMockMvcTest`, `AuthenticationTest` and `docs/CODE_STYLE.md` rule 4 during planning):

- **D-01** — **Measure first, edit second.** Task 1 runs the probe and records its output; Task 2 is
  the only task that touches prose, and its edits are selected by the verdict Task 1 recorded. No
  file is corrected on the strength of framework reasoning, however confident — reasoning is what
  produced all three of the existing contradictory comments.
- **D-02** — **Probe technique: read-only introspection of the live filter chain, plus behavioural
  replication.** Autowire the `springSecurityFilterChain` bean, walk `FilterChainProxy`'s chains, and
  read the relevant private fields with `ReflectionTestUtils`. No filter is removed, replaced,
  neutralised or re-ordered (see the matrix row B and the key_links note on chain-scoped mutation
  leaking across the cached context).
- **D-03** — **The probe must answer four questions explicitly, each with the observation that
  supports it:**
  - **Q1 — composition.** Which filters does this application's chain actually contain, in order? Is
    `SessionManagementFilter` among them? Is `ConcurrentSessionFilter`?
  - **Q2 — identity (the load-bearing question).** If `SessionManagementFilter` is present, is the
    `SessionAuthenticationStrategy` it holds the *same instance* as the application's
    `sessionAuthenticationStrategy` `@Bean`, or a separate one the DSL composed? If separate: what
    are its delegates, what `SessionRegistry` implementation backs its concurrency control, and what
    maximum does it carry?
  - **Q3 — behaviour on the injected-principal path.** Do four identical `.with(user(<one
    principal>))` requests in one test method really return `200, 200, 401, 401`, and does the
    `SPRING_SESSION` row count for that principal climb one per request?
  - **Q4 — the shape of the refusal.** Is the third response the RFC 7807 envelope this application
    produces, or a servlet-container `sendError` (non-null `MockHttpServletResponse.getErrorMessage()`,
    no ProblemDetail body)? These have different producers, so the shape is a fingerprint of who
    rejected the request.
- **D-04** — **Evidence outlives the probe.** The probe writes raw observations to
  `PROBE-RAW.txt` in this plan's directory (both printed and file-written, so the finding does not
  depend on Gradle log capture), and the executor writes `PROBE-FINDINGS.md` interpreting it. Both
  are committed. `PROBE-FINDINGS.md` carries exactly one line matching `VERDICT: <token>` with token
  one of `SMF_ABSENT`, `SMF_PRESENT_INVOKES`, `SMF_PRESENT_INERT` — Task 2 branches on it
  mechanically. Neither file may contain credential material or a raw session-cookie value; log
  principal ids, class names, counts and statuses only.
- **D-05** — **The probe is throwaway and never enters git history.** It is created untracked, run,
  and deleted in Task 2 before the final commit. Task 1 commits only the two evidence files. Deletion
  is gated, not asserted.
- **D-06** — **Correction scope is exactly the falsified claims, in at most two files.** In

  else in either file is touched: no DSL call, no bean, no test body.
- **D-07** — **Whatever the verdict, every surviving claim is path-scoped** (the source todo's option
  2, applied unconditionally rather than only in the both-true case). Each sentence about who invokes
  the strategy states the path it holds on: the real signin/signup path through
  `AuthenticationController.authenticate`, or a MockMvc request carrying a `.with(user())`-injected
  principal. An unqualified mechanism claim is what created this contradiction; replacing it with a
  differently-unqualified claim would only reset the clock.
- **D-08** — **`docs/CODE_STYLE.md` rule 4 and `AbstractAppMockMvcTest`'s Javadoc are out of scope**

- **D-10** — **Full suite green on the shipped tree.** `./gradlew spotlessApply` after the Java

**Non-obvious trade-offs:**

- *The load-bearing question is Q2, not Q1.* "Is `SessionManagementFilter` on the chain" reads like
  the whole dispute, but the interesting outcome is the one where it is present **and** holds a
  strategy the application never wrote — a DSL-composed `CompositeSessionAuthenticationStrategy`
  whose concurrency control is backed by an in-memory `SessionRegistryImpl` rather than the
  `SpringSessionBackedSessionRegistry` the application's bean uses. That would mean two ceiling
  enforcers coexist with different memories of what "live sessions for this principal" means. A probe
  that stops at Q1 would answer the argument and miss the finding.
- *Correcting the record here has a downstream security consequence.* `docs/ARCHITECTURE.md` argues
  the ceiling survives horizontal scaling because its registry reads live from the shared JDBC store.
  That argument holds for whichever enforcer the real signin path invokes. If a second enforcer with
  per-instance memory also guards some requests, that is a bounded but real qualification to a
  documented scaling claim — worth surfacing in the Resolution even though this task does not change
  `ARCHITECTURE.md`.
- *The probe must not leak credentials into a committed artefact.* It authenticates, so it holds a
  session cookie and a fixture credential in memory. `PROBE-RAW.txt` is committed, so it records
  class names, principal ids, row counts and statuses — never cookie values, never credential
  material (D-04, gated).
- *Reflection failure must be loud, not silent.* If a private field name has moved in Spring Security
  6.5, `ReflectionTestUtils.getField` throws or returns null and a naive probe NPEs into an
  uninformative stack trace. The probe dumps the declaring class's declared field names when a lookup
  misses, so a version drift produces a usable observation instead of a dead end.
- *Performance / memory:* zero runtime impact — comments and Javadoc only, not retained in bytecode.
  Test-suite cost is one extra class for the duration of Task 1, deleted before the final green run.
  The real cost is the full Testcontainers-backed `./gradlew test`, bounded explicitly per D-10.
- *Supply chain:* no dependency added. `ReflectionTestUtils` (spring-test), `FilterChainProxy`
  (spring-security-web) and `SecurityMockMvcRequestPostProcessors` (spring-security-test) are all
  already on the test classpath. No package-manager install, so no legitimacy gate applies.
