## Verified facts (established during planning — do not re-derive)

These were checked against the actual file and against GitHub's documented expression semantics. The executor should rely on them rather than re-investigating.

**F-1 — Current job graph.** `setup` -> `run-tests` (`if: success()`) -> `build-and-push-docker-image` (`if: success()`) -> `deploy-to-ec2` (`needs: build-and-push-docker-image`, `if: success()`) -> `cleanup-old-images` (`needs: [deploy-to-ec2, build-and-push-docker-image, setup]`, `if: success()`) and `cleanup-unused-image` (same `needs`, `if: failure()`).

**F-2 — The job already has an `if:` key** (`if: success()`, line 77). The change is a *replacement* of that value with `false`, not the addition of a second `if:` key. Two `if:` keys in one YAML mapping is a duplicate-key error.

**F-3 — Both cleanup jobs skip, for two independent documented reasons.** There is no way to execute a GitHub Actions workflow from this sandbox, so this is a careful reading of GitHub's documented semantics, not an empirical result. It holds under both applicable rules:

- *Skip propagation.* GitHub's `jobs.<job_id>.needs` documentation states that in a chain of dependent jobs, a failure or skip applies to all jobs downstream of it, **unless** a job's conditional expression causes it to continue. The expressions that cause continuation are `always()` and `!cancelled()`-style guards. Neither cleanup job uses one, so both are skipped once `deploy-to-ec2` is skipped.
- *Status-function evaluation.* Independently: a skipped job's result is `skipped` — neither `success` nor `failure`. `success()` returns true only when all `needs` jobs succeeded, so `cleanup-old-images` evaluates false. `failure()` returns true only when an ancestor job **failed**, so `cleanup-unused-image` also evaluates false. Skipped is not failure.

Both readings converge on the same outcome, which is why this change is safe to make without a live run: there is no interpretation of the documented semantics under which either cleanup job fires.

**F-4 — Non-obvious operational consequence (accepted, not fixed here).** `cleanup-old-images` is what deletes every Docker Hub tag except the current one, and `cleanup-unused-image` is what removes a just-pushed image when a deploy fails. With `deploy-to-ec2` skipped, both stop running, so **every push to `master` will push a new `:<sha7>` tag to Docker Hub that nothing ever deletes.** Tags will accumulate for the whole migration window. This is accepted for now (the alternative — rewiring the cleanup jobs' `needs` to drop `deploy-to-ec2` — widens the blast radius well past "disable one job" and would have to be undone again in Phase 5) but it must be written into the todo so it is a known cost rather than a surprise.

**F-5 — Pre-existing defect, out of scope.** The file is 151 lines and its final line ends with a trailing `\` line-continuation and no newline: `cleanup-unused-image`'s last `curl -s -X DELETE -H "Authorization: Bearer $TOKEN" \` has no URL argument. That job would fail with "no URL specified" if it ever ran. Do **not** fix it in this task — it is outside the stated scope, and it is one more piece of evidence that Phase 5 rewrites this file rather than reviving it. Record it in the todo.

**F-6 — Line endings.** The file uses CRLF. Preserve them; a full LF rewrite would show as a ~151-line diff and is a fail condition (gated in Task 1's verify).

## Alternate approaches considered

Required by `.claude/CLAUDE.md` GSD Execution Directives.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. `if: false` on the job, comment above it** *(picked)* | **+** Smallest possible diff; job body, secrets, and step logic all stay intact and reviewable. **+** Keeps `deploy-to-ec2` a real node in the graph, so the `needs:` references in both cleanup jobs stay valid. **+** Reversal requires a code change through normal review. **−** Job still appears in the run list (as skipped), which is mild noise. **−** Silences the cleanup jobs as a side effect (F-4). | **Picked.** It is the only option that changes deployment behavior without changing the *shape* of the dependency graph, which is what keeps the downstream reasoning in F-3 simple enough to verify by reading. |
| **B. Comment out the whole `deploy-to-ec2` block** | **+** Unambiguously dead. **−** **Breaks the workflow outright:** both cleanup jobs declare `needs: [deploy-to-ec2, ...]`, and GitHub rejects a workflow whose `needs` names a job that does not exist ("depends on unknown job"). Fixing that means also editing both cleanup jobs — a much larger diff to write now and to revert in Phase 5. **−** ~35 commented-out lines are a magnet for drift. | **Rejected.** The failure mode is non-obvious and total: instead of one failing job you get a workflow that will not start at all, so tests stop running too. |
| **C. Gate on a repo variable: `if: vars.DEPLOY_ENABLED == 'true'`** | **+** Toggle without a code change; arguably the "proper" long-term pattern. **−** Moves a deployment-affecting control out of version control into repo settings, where the change is invisible in `git log` and unreviewed. **−** Anyone with variable-write access can re-arm a deploy that SSHes at a dead host. **−** Phase 5 rewrites this job anyway (INFRA-05: new target, new credentials), so the toggle infrastructure is built to be thrown away. | **Rejected.** Worse security posture and worse auditability for a control we intend to delete within one phase. |
| **D. Delete the job entirely (rely on git history)** | **+** Cleanest file. **−** Same unknown-job breakage as B. **−** Loses the in-place record of what the deploy step used to do, which is genuinely useful reference material when writing the Oracle Cloud replacement. | **Rejected.** Discards the most useful artifact — the working shape of a deploy step — right before the phase that needs it. |

### Non-obvious trade-offs

- **Security (positive, small).** An unexecuted job never materializes its secrets: `EC2_SSH_KEY` is not written to `~/.ssh/id_rsa` on a runner, and `DB_PASS` is not interpolated into a remote `docker run`. Skipping the job strictly reduces secret exposure versus today, where every push writes the key to a runner and then fails. Separately: INFRA-05 requires newly-generated SSH credentials, so the AWS-era secrets in repo settings should eventually be *revoked*, not just left unused — noted in the todo, not done here.
- **Security (negative, small).** The step bodies remain in the file, so a future reader could re-enable a deploy pointed at a host that no longer belongs to us. The comment must therefore say "rewrite", not "re-enable", loudly enough that flipping the flag back feels wrong. This is why the comment text is a hard part of the acceptance criteria, not decoration.
- **Cost / CI minutes (positive).** Each push currently burns runner time on `ssh-keyscan` and an SSH attempt against a dead host before failing. A skipped job consumes no runner minutes.
- **State (see F-4, negative).** Docker Hub tag accumulation is the one genuine regression, and it is unbounded in time rather than in rate — it grows one tag per merge until Phase 5 lands. Free-tier repo limits make this worth tracking; it is the main reason the todo carries `severity: major` rather than `minor`.
- **No tracer task.** Tracer-first decomposition does not apply: this is a single-key configuration change with no layers to slice vertically, and the "end-to-end path" (an actual GitHub Actions run) is not executable from this environment by construction.
