## Core mechanism, in three sentences

`SecurityConfiguration` gains a `SessionAuthenticationStrategy` bean that wraps two delegates — a
`ConcurrentSessionControlAuthenticationStrategy` reading live session counts out of the JDBC session
store through a `SpringSessionBackedSessionRegistry`, and a `ChangeSessionIdAuthenticationStrategy`
that rotates the servlet session id — and `AuthenticationController.authenticate` calls
`onAuthentication(authentication, request, response)` on it the instant credentials verify, before
the `SecurityContext` is saved. On the third signin for one principal the registry's principal-name
lookup returns two live `SPRING_SESSION` rows, `2 < 2` is false, and the strategy throws
`SessionAuthenticationException`, which the existing Vavr `Try` collapses into `false` and the
existing blanket catch turns into a 401. On a signin that presents an already-authenticated cookie,
`request.getSession(false)` is non-null so the fixation delegate calls `changeSessionId()` on Spring
Session's request wrapper, which deletes the old row and re-saves the session under a fresh id, and
the response carries a different cookie value than the one presented.
</data_flow>

## Sub-decision: which `SessionRegistry` backs the ceiling

Verified before planning: `grep -rn "SessionRegistry|SessionAuthenticationStrategy" src/` returns
ZERO matches. No registry bean exists anywhere in this codebase under any name, so nothing is being
duplicated by adding one.

| Approach | Pros / Cons | Why Picked |
|---|---|---|
| **R1. `SpringSessionBackedSessionRegistry` constructed privately inside the strategy bean method** (CHOSEN) | **Pros:** the session count is read live from `SPRING_SESSION` by principal-name index, so it is correct across restarts and across instances — matching the JDBC session store `260802-shl` just landed; holds no state, so no entry can go stale; `registerNewSession` is a documented no-op, which is precisely why D-01's two-delegate composite is complete as specified. **Cons:** one extra indexed `SELECT` per successful authentication; `getAllPrincipals()` is unsupported (irrelevant here). | Correctness. The alternative's stale-entry failure mode is a hard lockout of a legitimate user, which is strictly worse than the defect being fixed. |
| **R2. In-memory `SessionRegistryImpl` as a bean + a third `RegisterSessionAuthenticationStrategy` delegate** | **Pros:** no DB read on the signin path; it is the textbook Spring Security wiring. **Cons:** requires a THIRD delegate that D-01 does not name — omit it and nothing is ever registered and the fix is silently inert, reproducing the exact bug being fixed; entries are only removed on Spring Security's `SessionDestroyedEvent`, which `JdbcIndexedSessionRepository` does not publish, so with `maxSessionsPreventsLogin(true)` a user would be permanently locked out after their second-ever login until the JVM restarts; per-instance and reset by every redeploy, contradicting the JDBC store. | Rejected. |
| **R3. R1, but exposed as a `SessionRegistry` `@Bean`** | **Pros:** `SessionManagementConfigurer` would pick the bean up, so the DSL's `maximumSessions` and the strategy would share one registry — one source of truth; the expire-oldest path would work if `maxSessionsPreventsLogin` were ever flipped to `false`. **Cons:** the DSL's `maximumSessions(...)` ALREADY installs `ConcurrentSessionFilter` in the chain, where it currently no-ops because its private registry is always empty. Publishing the bean makes that filter call `getSessionInformation(sessionId)` on EVERY authenticated request, which is a `JdbcIndexedSessionRepository.findById` (session row + attribute rows, with deserialization) on the hot path — for a code path that is dead by design, since `maxSessionsPreventsLogin(true)` prevents login instead of expiring sessions and therefore never marks a `SessionInformation` expired. | Rejected: real per-request cost, zero functional gain under the configured semantics. Promote to a bean only if the ceiling is ever switched to expire-oldest. |

## Non-obvious trade-offs

- **Time complexity, signin path:** +1 indexed `SELECT` on `SPRING_SESSION.PRINCIPAL_NAME` plus its
  attribute rows, per successful authentication. Signin already performs a user lookup and a bcrypt
  verify (deliberately ~100ms of CPU), so this is well under the existing noise floor. It is on
  signin/signup only, NOT on every request — see R3 for why that distinction is load-bearing.
- **Time complexity, session-fixation path:** `changeSessionId()` against a Spring-Session-backed
  session is a DELETE + INSERT of the session row, not an in-place update. It only fires when a
  signin presents an already-live session, which is rare in normal use.
- **Memory:** the chosen registry is stateless. The rejected `SessionRegistryImpl` keeps two
  `ConcurrentHashMap`s that, in this application, nothing would ever prune.
- **State invalidation:** this is the whole substance of the R1/R2 decision. A ceiling backed by
  bookkeeping that can go stale, combined with `maxSessionsPreventsLogin(true)`, converts a stale
  entry into a permanent denial of service against a legitimate user.
- **Security — failure indistinguishability:** a ceiling rejection surfaces as `401 Invalid username
  or password`, identical to a wrong password. This is deliberately left alone: collapsing the two
  avoids handing an attacker an oracle for "these credentials are valid, this account just has
  sessions open." The cost is that a genuine user who hits the ceiling cannot tell why. Recorded in
  the test Javadoc and in `.claude/CLAUDE.md` rather than silently accepted.
- **Test-suite blast radius:** enforcing a per-principal ceiling of 2 inside a suite that never
  clears `SPRING_SESSION` rows is the obvious way this change breaks unrelated tests. It does not,
  for two independent reasons, both verified during planning: the registry keys on the ULID user id
  and `AbstractAppTest` mints a fresh user per test method; and no existing test method calls
  `signin()` more than once (`UserPersistenceE2ETest`'s signup-then-signin is the maximum at two,
  which is at the ceiling, not over it). Task 2's full-suite run is what holds that conclusion
  honest.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> `/api/signin`, `/api/signup` | Unauthenticated, attacker-controlled input; the only two routes that mint a session cookie. |
| pre-auth session -> post-auth session (inside `AuthenticationController.authenticate`) | The privilege transition itself. An id that survives this boundary unchanged is a session-fixation exposure. This change is what makes the boundary an actual transition rather than a continuation. |
| application -> PostgreSQL `SPRING_SESSION` | Now the authoritative source for "how many sessions does this principal hold", not just for session contents. A wrong answer here is a wrong security decision. |
| shared `authenticate()` helper -> both signin and signup | One code path, two public entry points. Any control added here silently applies to both — which is why it is called out explicitly rather than reasoned about as a signin-only change. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-m2z-01 | Spoofing | `AuthenticationController.authenticate` — session id not rotated across the privilege transition | medium | mitigate | `ChangeSessionIdAuthenticationStrategy` now runs on every successful authentication, before the `SecurityContext` is saved, on both signin and signup. Proven by Task 2's `SessionFixation` test, which presents a live cookie so the strategy's non-null-session precondition is actually met. | T-m2z-02 | Elevation of Privilege | Unbounded concurrent sessions per principal | low | mitigate | `ConcurrentSessionControlAuthenticationStrategy` with `setMaximumSessions(2)` and `setExceptionIfMaximumExceeded(true)`, counting live rows via `SpringSessionBackedSessionRegistry`. Proven by Task 1. Closes `T-shl-04`. | T-m2z-03 | Denial of Service | The ceiling becomes a self-lockout vector if the registry over-counts | medium | mitigate | This is the failure mode that drove the registry sub-decision. `maxSessionsPreventsLogin(true)` means an over-count denies a legitimate user login entirely. `SpringSessionBackedSessionRegistry` holds no bookkeeping — it reads live, non-expired `SPRING_SESSION` rows — so there is nothing to go stale.
