<design_rationale>

## The non-obvious part: the host port is only half the conflict

Remapping `docker-compose.yml` alone does **not** unblock the rehearsal. `rehearseHistoricalSchemas`
is a Gradle `Test` task that deliberately never sets `spring.profiles.active=test`, so it resolves
`application.properties`, whose datasource URL is:

```
spring.datasource.url=jdbc:postgresql://${DB_HOST}:5432/${DB_NAME}
```

The **port is a hardcoded literal**, not a placeholder. Run that on the host with `DB_HOST=localhost`
after remapping the container to 5433 and it still connects to the native PostgreSQL 17 service —
the identical failure 04-04 hit, with an extra step of misdirection. The host port and the JDBC port
must both move, or neither does.

The in-container path is genuinely unaffected either way: the compose `app` service sets
`DB_HOST: postgres` and reaches the container's own 5432 over the compose network, which no host
port mapping touches.

## Approaches considered

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| **A (picked): publish host 5433, and parameterize the JDBC port as `${DB_PORT:5432}`** | **Pro:** the default preserves in-container, CI, and deploy behavior byte-for-byte (nothing sets DB_PORT — verifiable by grep against the compose `app` block and `.github/workflows/deploy.yml`). Makes the host-vs-container distinction explicit and discoverable, and lets the rehearsal be pointed at *either* Postgres instance without editing tracked files. **Con:** adds one new environment variable to the project's config surface. | The one-variable cost buys the ability to aim the rehearsal at whichever instance actually holds historical rows — which, given 04-04 ended with `docker compose down -v`, is the difference between a real verification and a guaranteed-empty one. |
| **B: publish host 5433, change no source; override at run time with `SPRING_DATASOURCE_URL`** | **Pro:** zero tracked-file changes to Java/properties; Spring's relaxed binding accepts the full URL as an env var. **Con:** undiscoverable — nothing in the repo would tell the next person the port moved; every host run needs a hand-assembled full JDBC URL including database name and driver prefix, so a typo silently produces a *different* wrong target rather than an error. | Rejected: it turns a documented config knob into oral tradition, and CODE_STYLE.md rule 8 explicitly prefers encoding a fix in the codebase over a runbook. |
| **C: stop publishing the Postgres port at all; reach it only via `docker compose exec`** | **Pro:** the conflict becomes structurally impossible, and it shrinks the host attack surface to nothing. **Con:** breaks every host-side client — DBeaver, psql, and, fatally, the Gradle rehearsal itself, which runs in a host JVM and cannot use `docker compose exec`. | Rejected: it would close the port conflict by permanently closing the very access path this task needs. |
| **D: stop or reassign the native PostgreSQL 17 Windows service** | **Pro:** no repo change at all; 5432 behaves as every tutorial assumes. **Con:** needs administrator rights (already tried and refused with `Access is denied` in 04-04), is hostile to whatever else on the machine depends on that service, and fixes only this one machine — a teammate with the same conflict gets nothing. | Rejected: unavailable, machine-local, and non-transferable. |

## Non-obvious trade-offs

- **Security (exposure, unchanged in kind):** Compose's short `"5433:5432"` form binds `0.0.0.0`, so
  the database is reachable from anything that can reach this host — exactly as true at 5432 before
  this change. Binding `127.0.0.1:5433:5432` would genuinely shrink that surface, but it also breaks
  WSL/other-VM access patterns and is a behavior change beyond this task's scope. Recorded as
  considered-and-not-taken (see `<threat_model>` T-nd3-01), not overlooked.
- **Security (blast radius of a wrong target):** the rehearsal's final step republishes a sample
  through the real topic and lets the real consumer write. That write is a structural no-op *only*
  because every republished `eventId` already has a row in the database being read
  (`ActivityLogRecorder.record` short-circuits on `existsByEventId`). Point the run at the wrong
  database and that guarantee evaporates — which is why Task 2 proves *which server answered* before
  Task 2 runs anything that writes.
- **Performance / memory:** none. A published-port number is a NAT rule in Docker's proxy; an
  additional property placeholder is resolved once at context startup. The rehearsal's own cost is
  already bounded at 100 sampled rows per action (T-04-16).
- **Test-suite risk: provably zero.** `application-test.properties` overrides
  `spring.datasource.url` to `jdbc:h2:mem:testdb`, so no test running under the `test` profile can
  observe the port placeholder at all. `rehearseHistoricalSchemas` is the only task that reads the
  default profile's datasource.
</design_rationale>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host network → published container port | Compose's short port form binds all host interfaces; anything that can reach this host can reach the database. |
| Host JVM (Gradle) → a real, non-disposable Postgres | The rehearsal is the only path in this repo that connects a test process to a production-shaped database holding irreplaceable historical rows. |
| Shell/process environment → committed artifacts | Database credentials pass through env vars and command lines during the probe steps. |
