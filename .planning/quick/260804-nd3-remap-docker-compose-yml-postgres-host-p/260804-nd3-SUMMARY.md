# Quick Task 260804-nd3: Remap docker-compose.yml Postgres host port Summary

**Moved the docker-compose Postgres off the contested host port 5432 onto 5433, parameterized the
JDBC port so host-run JVMs (the `rehearseHistoricalSchemas` Gradle task) can reach it, proved from
the host that 5433 answers as the Postgres 16 container and 5432 still answers as the unrelated
native PostgreSQL 17 service, ran the rehearsal (which first failed honestly on its own empty-corpus
gate), then -- per the coordinator's checkpoint resolution (option b) -- exercised the running app's
real REST API to generate a genuine 6-row, all-5-action corpus through the actual Avro/Kafka
pipeline, and reran the rehearsal to a clean pass.**

## Task 1: Move Postgres to host port 5433 and make the JDBC port configurable

Committed as `ffa5587`.

- `docker-compose.yml`: `postgres` service now publishes `"5433:5432"` (container-internal port
  untouched), with a comment explaining the native-PostgreSQL-17-on-5432 conflict this avoids and
  citing `.planning/phases/04-schema-registry/04-04-SUMMARY.md`. The `app` service gained no
  `DB_PORT` entry.
- `src/main/resources/application.properties`: `spring.datasource.url`'s hardcoded `:5432` became

  doesn't pass it to the app container and Gradle doesn't read `.env`, so a key would be inert).
- `docs/LOCAL_DEV.md`: added a Quickstart bullet for the Postgres host port and a new section
  explaining why it moved, the symptom of the conflict, and the exact host-run command shape for
  the rehearsal.

## Task 2: Prove host 5433 reaches the container, locate the real corpus, and run the rehearsal

No files modified -- this task produced recorded observations only.

1. **`docker compose up -d postgres` / readiness:** Docker Desktop was already running with the
   compose stack up (postgres, redpanda, app) from environment setup earlier in this session.
   `docker compose exec -T postgres pg_isready -U kanban` → `accepting connections`.

2. **Runtime port mapping:** `docker compose port postgres 5432` → `0.0.0.0:5433`, confirming
   Task 1's mapping at runtime, not just on disk.

3. **Server-identity proof (host → 5433):** connected from the HOST via `psql -h 127.0.0.1 -p 5433`
   and ran `SHOW server_version;`. Result, verbatim:
   ```
   16.14 (Debian 16.14-1.pgdg13+1)
   ```
   This is the `postgres:16` container, not the native PostgreSQL 17 service -- proven from the
   host path, not via `docker compose exec` (which would only prove the container's local socket
   works, exactly the check that gave 04-04 false confidence).

4. **Container corpus probe (read-only, on 5433), first attempt:**
   - `select count(*) from activity_log;` → `0`
   - `select action, count(*) from activity_log group by action order by 1;` → no rows returned
   The table existed (Hibernate `ddl-auto=update` on the running `app` service created it) but held
   zero rows -- consistent with 04-04 having ended with `docker compose down -v`, which destroyed
   the named volume, and this session's containers being freshly created.

5. **Native-service probe (read-only, best-effort, on 5432):** attempted the same connection via
   `psql -h 127.0.0.1 -p 5432`. Result, verbatim:
   ```
   psql: error: connection to server at "127.0.0.1", port 5432 failed: FATAL:  password authentication failed for user "kanban"
   ```
   This is the exact failure mode 04-04 diagnosed: a genuinely different Postgres server (the
   native PostgreSQL 17 Windows service, unrelated to this project) answered, with different
   credentials. Per the plan, no `pg_hba.conf` edit, role creation, or service stop/start was
   attempted -- this machine grants no such rights, and it was out of scope regardless.

6. **First rehearsal run:** since neither instance held rows, ran it once against the container
   instance per the plan's explicit fallback ("If neither instance holds rows, still run it once
   against the container so the failure is observed rather than assumed"). **Result: FAILED**, with
   the designed, honest "SCHEMA-06 UNVERIFIED" empty-corpus assertion (full text preserved below,
   under Checkpoint Resolution). No rows were fabricated and `HistoricalSchemaRehearsalE2ETest` was
   not edited.

## Task 3: Checkpoint resolution -- generate a real corpus via option (b), rerun the rehearsal

The plan's final `checkpoint:human-verify gate="blocking"` task was reached with the rehearsal
failing on its own empty-corpus gate (see Task 2). The coordinator resolved it: **option (b)** --
exercise the already-running compose app instance via real HTTP requests to generate a genuine
corpus through the actual Avro-cutover pipeline, then rerun the rehearsal.

### Schema registration

The compose Redpanda's schema registry had zero subjects registered (`curl
http://localhost:8081/subjects` → `[]`) -- expected, since nothing had published through it yet in
this session. Ran `./gradlew registerSchemas -PschemaRegistryUrl=http://localhost:8081` →
`Registered 5 Avro schemas against http://localhost:8081`. Without this, the producer's
`auto.register.schemas=false` means every publish attempt below would have failed at the schema
lookup step.

### A genuine architectural gap found: no REST endpoint creates a board

Before generating any events, grepped every `@GetMapping`/`@PostMapping`/`@PutMapping`/
`@PatchMapping`/`@DeleteMapping` across every controller in
`src/main/java/com/vrudenko/kanban_board/controller/`. Confirmed: **no HTTP route creates a
board.** `BoardController` has only `GET` (list), `DELETE`, `PUT` (update), and `POST .../columns`
(nested, requires an existing board). `UserService#addBoardByUserId` -- the only method that
creates a board -- has zero controller callers anywhere in `src/main`; its only caller is a test
fixture (`AbstractAppTest.createColumnForUser`, already noted in STATE.md). This matches the
project's own documented deferred scope (`FULL-01..03`, "no REST endpoint exists to create a board
directly").

This is a real gap, not a workaround-able HTTP mistake, so triggering `BOARD_CREATED` via "real
HTTP requests through its REST API" as literally instructed is not possible in the current
codebase. Adding a new production write endpoint to close this gap would be a genuine architectural
change (new attack surface, needs its own tests/threat-model entry) well outside a docker-compose
port-remap quick task's scope, so it was not done here.

**Resolution taken:** a throwaway, single-purpose test class
(`ZZTempSeedBoardForRehearsalTest`, never part of any committed scope, deleted immediately after
one run) called `UserService#addBoardByUserId` directly, configured against the exact same real
Postgres and real Redpanda the compose `app` container uses (via `DB_HOST=127.0.0.1 DB_PORT=5433`,
run through the `rehearseHistoricalSchemas` task machinery with `--tests` scoped to just this
class, so it never sets `spring.profiles.active=test`). This mirrors 04-04's own
`ZZTempSeedHistoricalDataTest` precedent for the identical class of problem (see
`.planning/phases/04-schema-registry/04-04-SUMMARY.md`). Critically, this still goes through
`BoardService#save`'s real, production `@Transactional` path and its real after-commit
`KafkaEventPublisher` publish -- the exact same code any real caller would exercise -- landing on
the real `kanban.activity` topic, consumed by the compose `app` container's own already-running
consumer (`groupId=activity-log`), which persisted the row into `activity_log` exactly as it would
for any genuine request. Every subsequent step used real HTTP against the already-running app.

The seed test was deleted immediately after its one run and was never staged or committed --
confirmed via `git status --short` showing no trace of it.

### Explicit caveat (per the coordinator's instruction)

**This corpus proves the reconstructor and the Avro round-trip work correctly end-to-end against
the real, currently-shipped pipeline. It does NOT prove compatibility with genuinely pre-cutover
(pre-Avro) historical row shapes**, because no such rows exist anywhere in this environment any
more -- 04-04 ended with `docker compose down -v`, destroying whatever pre-existing local corpus
this machine may once have had, and every row generated in this session was produced entirely
after the Avro cutover, through the new pipeline. Whoever revisits SCHEMA-06 rigor later (e.g. at
Phase 5's cutover, or if this concern resurfaces before a production migration) should treat this
result as "the round-trip mechanism is proven correct," not "historical-shape compatibility is
proven" -- the latter specifically needs rows that predate this cutover, which no longer exist to
test against on this machine. A developer machine that still holds genuine pre-cutover
`activity_log` rows (option (a) from the original checkpoint) remains the only way to close that
narrower, stronger claim.
