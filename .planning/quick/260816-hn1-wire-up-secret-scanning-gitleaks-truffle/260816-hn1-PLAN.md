<objective>
Wire real secret scanning into this repo at both gates it can meaningfully sit on: the
pre-commit hook (blocks a credential before it is ever written to an object) and CI (catches
what the hook was bypassed on, and re-checks the full history).

Purpose: the motivating question — "did anything leak into `.planning/STATE.md` or
`docs/INFRA_RUNBOOK.md` during the live Netcup deploy?" — was answered by hand-grepping,
which does not scale and does not run again tomorrow. Neither GSD nor Claude Code ships a
scanner; `gsd-core/bin/lib/secrets.cjs` only masks API keys for settings display. This closes
that with a mechanism rather than a habit.

Output: a pinned, version-controlled scanner configuration; a measured baseline of what this
repo's 647 commits actually contain; a pre-commit gate; and a CI workflow.
</objective>

Required by `.claude/CLAUDE.md`'s GSD Execution Directives. Three decisions had to be made, and
each is recorded separately because they resolved on different evidence.

## Decision 1 — which scanner

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| **gitleaks** (picked) | **+** Single static Go binary, official Docker image, no runtime. **+** Native `--pre-commit --staged` mode built for exactly this hook. **+** Config is one committed TOML with `[extend] useDefault = true`, so custom rules layer on the maintained defaults instead of replacing them. **+** `--baseline-path` and per-rule allowlists give two independent tuning levers. **−** Regex/entropy only: no live credential validation, so a rotated-and-dead key still reports. | Picked. The two things this repo needs are a fast staged-diff mode and a committed, reviewable config — gitleaks is strongest on both, and its allowlist granularity is what makes the narrative-text false-positive problem tractable. |
| **TruffleHog** | **+** Verification: it can call the provider to prove a found key is *live*, which collapses false positives in a way regex cannot. **+** Broad detector set. **−** Verification is a network call per candidate — unacceptable in a hook, and it phones out from a developer machine holding real credentials. **−** Config/allowlisting is less ergonomic to hold in one committed file. | Rejected as the primary. Its verification advantage is real but lands in the wrong place: at *commit* time you want to block on suspicion, not confirm exploitation. Worth revisiting as a CI-only second pass if the gitleaks baseline turns out to be noisy — file a todo, do not build it here. |
| **detect-secrets** (Yelp) | **+** Mature `.secrets.baseline` + audit workflow, purpose-built for exactly this "old repo, lots of prose" problem. **−** Python runtime. This is a Java/Gradle repo with zero Python in the toolchain; a hook that needs `pip install` on every clone is a new host-level prerequisite, which `docs/CODE_STYLE.md` rule 8 exists to forbid. | Rejected on the runtime prerequisite alone. |

## Decision 2 — how the hook acquires the binary

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| **Official Docker image** (picked) | **+** Adds no new prerequisite — *measured, not assumed*: `build.gradle`'s `fastTest` (the task this hook already runs) sets `maxParallelForks = 2` against `AbstractPostgresContainerTest`, so the existing hook already starts two PostgreSQL Testcontainers and, per its own comment, sometimes a Redpanda container. Docker is already a hard requirement of committing to this repo. **+** Version pin is exact and identical to CI's. **−** ~1-2s container start per commit. **−** Windows/Git-Bash friction: MSYS path rewriting and git's dubious-ownership check inside the container. | Picked. The prerequisite objection — the only serious one — is empirically void here. The friction is a one-time cost paid at authoring time and then frozen in a committed hook. |
| **Gradle task downloads a pinned native binary** | **+** No Docker, fastest possible invocation, satisfies rule 8 by automating the fetch. **−** ~60 lines of per-OS asset-selection Gradle for a benefit that is zero on a machine that already runs Docker for its tests. **−** Adds a network fetch to the configuration phase of *every* `./gradlew` invocation unless carefully guarded. | Rejected. Solves a prerequisite problem this repo does not have. |
| **Require a manual `choco`/`brew` install; hook warns and skips if absent** | **+** Trivial to write, zero latency when absent. **−** Violates rule 8. **−** Worse: it produces exactly the failure mode `.github/workflows/security-scan.yml`'s preflight step was written to prevent — "the difference between 'loudly not configured' and 'silently reporting nothing'." A security gate that silently no-ops on every machine that forgot to install it is worse than no gate, because it is believed. | Rejected. |

## Decision 3 — scan scope, and where the gate has teeth

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| **Staged diff locally, full history in CI** (picked) | **+** Matches the split `security-scan.yml` already documents in prose: the hook catches "what the committer authored"; the slow, whole-corpus check belongs in CI. **+** Staged-diff scan is bounded by the size of the commit, not the repo, so hook cost does not grow with 7.3 MB of `.planning/`. **−** A secret that entered history before this lands is invisible to the hook forever — which is precisely why the CI half scans history. | Picked. |
| **Full-history scan in the hook too** | **+** Every commit re-proves the whole corpus is clean. **−** Re-scans 647 commits to validate a three-line change; cost grows monotonically forever. **−** Redundant: history is immutable, so a clean history stays clean unless CI's own history job is broken. | Rejected. |
| **Report-only first, gate later** (the `260813-q1i` precedent) | **+** Consistent with this repo's measure-then-ratchet culture. **−** Its motivating condition does not hold here. dependency-check is report-only because *its verdict is not a pure function of the commit* — a new advisory reds an unchanged tree. A gitleaks scan at a **pinned version** against a **committed config** IS a pure function of the commit, so the drift risk that justified report-only is absent. **−** And the measurement that report-only exists to gather is gathered inside this plan, in Task 1, before the gate is switched on. | **Partially adopted, deliberately.** The *sequence* is kept — measure, triage, then gate — but compressed into one plan instead of deferred to a later ratchet, because the measurement takes minutes, not weeks. The version pin is what earns the hard gate; see the trade-off note below. |

## Non-obvious trade-offs

**The scanner's own output is a secret.** A gitleaks report contains the matched secret values in
plaintext. Uploading one as a CI artifact publishes every finding to anyone who can read Actions
artifacts; committing a baseline file does the same, permanently, to anyone who can read the repo.
Every report path in this plan must be redacted, and no report may be committed unredacted. This
also interacts with `--baseline-path`: whether redaction changes the fingerprint gitleaks matches
baselines on is **not assumed** here — Task 1 verifies it empirically before any baseline ships.

**Allowlisting `.planning/` would defeat the entire task.** The narrative-heavy `STATE.md` is the
most tempting thing to exempt — it is 93 KB of prose in which "password", "secret" and "key" appear
constantly — and it is also the exact file the motivating question was asked about, written by an
agent during a live production deploy. A blanket path allowlist there converts this work into
security theatre. Allowlists must be narrow and evidence-cited, per the precedent `build.gradle`'s
`dependencyCheck` block already set ("pre-writing suppressions before a real run creates permanent
blind spots"). Task 2 proves non-exemption behaviourally with a planted canary, not by reading the
config.

**Pinning is what makes a hard gate safe, and unpinning silently un-safes it.** `latest` means a
new gitleaks release can add a rule that reds an unchanged commit — the same "it broke and I changed
nothing" failure mode `security-scan.yml` documents. Here that would block commits, not just a
scheduled job. The version pin is therefore load-bearing, in both the hook and CI, and they must be
the same value.

**Hook latency is negligible, but placement is not.** The existing hook runs `spotlessCheck` plus a
container-backed `fastTest` measured at ~242s. A ~1-2s scan is under 1% of that. But it must run
**first**: a staged credential should be refused in two seconds, not after four minutes of tests.
Placement is a usability decision with no cost, so take it.

**A supply-chain inversion worth stating plainly.** A secret scanner is handed read access to every
credential in the tree and then, in CI, network egress. A typosquatted or compromised scanner image
is a close-to-ideal exfiltration channel — and it would be invoked automatically on every commit by
every developer. The image must be verified as the upstream-published one and pinned, not merely
name-matched. Tracked as `T-hn1-SC` below.

**Scope honesty.** This detects credential *shapes*. It will not catch a plaintext connection string
with an unusual format, a secret pasted into prose as a sentence, or a leaked value below the entropy
threshold. It raises the floor; it does not make leaks impossible.
</approach_analysis>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer working tree -> git object store | Where a credential becomes permanent and un-deletable; the pre-commit hook is the only control sitting here |
| git object store -> GitHub remote | Where a leak becomes externally reachable; the CI job is the backstop, and it is already too late by design |
| scanner process -> repo contents and network | The scanner reads every credential in the tree, and in CI has egress |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-hn1-01 | Information Disclosure | scanner report / baseline files | high | mitigate | Redaction enforced on every report path; report paths gitignored; no unredacted report committed or uploaded (Tasks 1 and 3) |
| T-hn1-02 | Information Disclosure | working-tree scan reading gitignored `.env` / `.env.prod` | high | mitigate | Task 1 determines empirically whether these are read and records the answer; if they are, that report is treated as a live secret |
| T-hn1-03 | Tampering / bypass | over-broad allowlist | high | mitigate | Blanket directory exemptions prohibited; non-exemption of `.planning/` proven behaviourally by a planted canary (Task 2), not by config inspection |
| T-hn1-04 | Denial of Service (self-inflicted) | unpinned scanner version reds unchanged commits | medium | mitigate | Explicit version pin in hook and CI, asserted byte-identical between the two (Task 3 verify) |
| T-hn1-05 | Repudiation | hook silently no-ops when the scanner cannot run | high | mitigate | Three-outcome exit-code branching; the cannot-run case refuses the commit with distinct wording, falsified by stopping the daemon (Task 2) |
| T-hn1-06 | Elevation / bypass | `git commit --no-verify` bypasses the hook entirely | medium | accept | Unfixable at the hook layer by construction; this is exactly why the CI half is not optional. Stated, not pretended away |
| T-hn1-SC | Tampering | scanner container image (supply chain) | high | mitigate | Verify the image is the upstream-published one, record the registry choice and resolved digest, and prefer a digest-pinned reference (Task 1).
