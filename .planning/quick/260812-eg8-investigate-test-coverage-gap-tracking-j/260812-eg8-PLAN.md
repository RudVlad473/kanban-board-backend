## Non-Obvious Trade-offs

1. **Measurement validity, not performance, is the dominant risk.** Lombok-generated accessors,
   `equals`/`hashCode` and builders; MapStruct's `*Impl` mappers; and the Avro codegen output all
   land in bytecode JaCoCo instruments. Unexcluded, they systematically deflate the baseline — and
   the *entire* D-01 decision would then be made on a wrong number. JaCoCo honors `@lombok.Generated`
   automatically, but only when `lombok.config` sets `lombok.addLombokGeneratedAnnotation = true`,
   and this repo has **no `lombok.config` at all** today. This is the single highest-value detail in
   the plan.
2. **`maxParallelForks = 2` and one `.exec` file.** Two separate test-worker JVMs append execution
   data to a single JaCoCo destination file. This normally works, but a degenerate merge (near-zero
   coverage, or whole classes absent) is a known failure mode and would be easy to mistake for a
   genuine coverage finding. Task 1 must sanity-check plausibility before the numbers are trusted.
3. **Instrumentation tax on the pre-commit gate.** JaCoCo typically adds 5-20% wall clock. The
   pre-commit hook runs `fastTest` (~242s). Wiring coverage into `fastTest` would tax every single
   commit for a signal nobody reads at commit time. Coverage stays off `fastTest`.
4. **Coverage % is a drift alarm, not a safety property.** On this codebase a high line-coverage
   number would be dominated by DTO and entity surface, not by the ownership-chain branches that
   actually carry the access-control model. Whatever rung is chosen must be documented as "detects
   a class going dark", not "proves this is tested."
5. **Relocation is downward-safe with respect to Spring.** `@SpringBootTest` without an explicit
   `classes` attribute walks *up* the package hierarchy looking for `@SpringBootConfiguration`.
   Moving a class from the root into a subpackage keeps `KanbanBoardApplication` reachable, so no
   context configuration changes. Moving *out* of the tree would not be safe — nothing here does.
6. **The fold is where coverage can actually be lost.** Merging `TaskOrderingTest` into an existing
   class by hand can silently drop `@Test` methods. Two independent gates gate this: non-decreasing
   total test count, and no JaCoCo regression against Task 1's baseline.
7. **`LayeringArchTest` cannot host the placement rule.** It declares
   `importOptions = ImportOption.DoNotIncludeTests.class`, so the test source set is deliberately
   outside its imported graph. The placement rule needs its own `@AnalyzeClasses` class.
8. **Supply chain.** The `jacoco` plugin ships inside Gradle core — no new plugin coordinate is
   resolved. Only `org.jacoco` agent/ant artifacts are fetched, from Maven Central, at an explicitly
   pinned `toolVersion` (matching this repo's precedent of pinning ErrorProne and the Avro plugin
   exactly rather than floating them).
</approach_analysis>

<data_flow>
JaCoCo attaches a Java agent to each Gradle test-worker JVM, which instruments classes as they load
and writes a binary `.exec` file of executed probes on JVM shutdown. The `jacocoTestReport` task
then reads that `.exec` alongside the compiled `build/classes` bytecode and the `src/main/java`
sources to emit HTML and XML reports. Exclusions are applied at report time against class-file
patterns, which is why generated code must be named there rather than hidden at instrumentation time.
</data_flow>
