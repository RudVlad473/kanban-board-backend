<objective>
Delete `UserMapper.toSigninRequestDTO(UserEntity)` and `UserMapper.toSignupRequestDTO(UserEntity)` —
two uncalled methods that MapStruct compiles into `dto.setPassword(entity.getPassword())`, copying the
stored bcrypt hash into a request DTO that could be serialized into an HTTP response.

Purpose: closes the security-marked todo filed during quick task `260803-m3i`, which found this while
re-verifying that task's callers and deliberately left it because that task's scope was locked to two
other, differently-named methods. Nothing leaks today — there are zero callers — so this is removing a
loaded gun, not disarming a fired one.

Output: one `src/main` file loses two methods and one import and gains a short invariant note, the
originating todo is closed, and STATE.md records the task.
</objective>

<data_flow>
## Core mechanism, in three sentences

`UserEntity` implements Spring Security's `UserDetails`, which forces it to expose a public
`getPassword()` — implemented here as a one-line delegate returning the stored bcrypt hash from
`getPasswordHash()` — and both `SigninRequestDTO` and `SignupRequestDTO` declare a `password`
property with a matching name. MapStruct binds source and target properties by name, and because this
mapper is configured `unmappedTargetPolicy = ReportingPolicy.IGNORE`, the generated `UserMapperImpl`
emits `dto.setPassword(entity.getPassword())` for both entity-to-request-DTO methods without warning,
error, or any signal at build time. Deleting the two method declarations deletes the generated
mapping with them, so the hash has no compiled route out of the entity into a serializable DTO —
which is a stronger guarantee than the current one, whose entire safety rests on nobody ever calling
a public method.
</data_flow>

<tradeoffs>
## Non-obvious trade-offs worth stating

**Security — this closes a latent vector, it does not fix a live breach; say so plainly.** Zero
callers means zero hashes have ever crossed this boundary. The value is that the class of bug becomes
impossible rather than merely improbable. Any summary, commit message, or STATE.md wording that
implies a leak was occurring is false and must not be written. The honest framing: a public method
existed whose invocation would have serialized a stored credential hash, and it no longer exists.

**Why a leaked bcrypt hash would matter even though bcrypt is a hash.** The reflex objection is
"it's hashed, so who cares." A bcrypt hash is an offline-attackable artifact: it discloses the work
factor, it is a stable per-account identifier that survives display-name and email changes, it lets
an attacker verify a password guess without touching the login endpoint (so rate limiting, lockout,
and the session controls wired in `260803-m2z` all stop applying), and it confirms account existence.
It is a credential verifier, not a public value.

**Performance and memory: none.** Two abstract method declarations are removed, so `UserMapperImpl`
loses two generated methods. No runtime path changes, no query changes, no allocation changes, no
behaviour to benchmark. Compilation gets marginally faster in a way nobody will measure. If a
reviewer expects a perf note here, the note is that there is nothing to say — and claiming otherwise
would be padding.

**The invariant note must not name the deleted methods, and this is not pedantry.** Task 1's
acceptance criteria negative-grep `src/` for both method names. A tombstone comment ("removed
`toSigninRequestDTO` ...") would put those exact literals back into `src/`, turning a real check into
a permanent false positive and training the next reader to ignore it. The note therefore describes
the invariant generically — no `UserEntity`-to-request-DTO mapper — and never names a corpse.

**Comment accuracy is a maintenance liability this project has already paid for twice.** Commit
`500fde5` ("correct every session documentation claim to match wired JDBC store") and quick task
`260803-m2z` both existed because comments outlived the code they described. The Javadoc note added
here is a claim about the file's future, so it must be phrased as a rule to follow ("do not add such
a method without an explicit ignore mapping"), not as a fact about the present that a later edit can
quietly falsify.

**Test coverage: deliberately none added.** The natural instinct is a test asserting the hash never
appears in a signin/signup response. It is not in this plan because such a test would pass identically
before and after this change — there are no callers either way, so it would assert nothing about the
work being done and would provide false confidence that a real regression guard exists.
`SessionPersistenceE2ETest` already asserts no bcrypt hash reaches the session store, and
`UserPersistenceE2ETest` already asserts the hash is persisted and never echoed. The full green suite
is the check that the deletion breaks nothing; the deletion itself is verified by compilation and by
grep, and the SUMMARY must report it that way rather than claiming test-proven.

**Blast radius is genuinely one file, and the plan should not pretend otherwise.** No database, no
DDL, no configuration, no dependency, no `build.gradle` change, no `user_setup`. The second task is
bookkeeping. Over-structuring this would cost more review attention than the change itself.
</tradeoffs>
