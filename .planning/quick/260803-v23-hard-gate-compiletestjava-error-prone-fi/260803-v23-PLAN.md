## The finding that changes the shape of this task

The todo assumes removing the demotion is what turns the gate on. **It is not.** Planning ran the
build a second time through a throwaway Gradle init script that forced the demotion off without
editing the repo. Result:

```
PROBE: allErrorsAsWarnings forced false on compileTestJava
... 27 warnings
BUILD SUCCESSFUL in 20s
```

All 27 findings are **WARNING severity by default**. The demotion flag only downgrades
ERROR-severity checks, so today it downgrades nothing — removing it is a **no-op against the
current 27**. Corroborating evidence on the main side: `compileJava` is already un-demoted and
still passes today while printing an `EscapedEntity` warning at `UserMapper.java:23`, proving
`compileJava`'s "hard gate" is likewise ERROR-only.

Two consequences the executor must hold onto:

1. Removing the demotion is still correct and still buys something real — a *future*
   ERROR-severity finding in test code will now fail the build instead of being silently
   downgraded. It just does not, on its own, make today's 27 findings enforceable.
2. Therefore "hard-gate" as the todo means it (the 27 stay gone) requires promoting the triaged
   checks to ERROR. That is beyond the todo's literal text, so it is Task 1's blocking decision
   rather than something this plan assumes.

## Non-obvious trade-offs

- **Performance (test wall-clock).** Switching 16 `kafkaTemplate.send(...)` calls to an
  ack-checked send serializes a producer round-trip that is currently fire-and-forget. Against a
  local Testcontainers broker each ack is single-digit milliseconds, so the expected total cost
  across the `activitylog` package is well under a second — but this is a projection, and Task 3
  verifies it by comparing suite runtime rather than assuming it.
- **State / correctness.** Blocking on ack does not weaken what the idempotency test proves: the
  duplicate-`eventId` race is arbitrated by the database unique constraint, not by send ordering,
  and the topic is single-partition/single-consumer either way. What it does change is the
  failure mode — a broker rejection currently surfaces as a misleading 30-second Awaitility
  timeout ("row never appeared"); after the change it surfaces immediately as the actual send
  exception. That diagnostic gain is the real reason to fix these rather than suppress them.
- **Security.** None of the 27 sites touch authentication, secrets, or the ownership chain.
  `DefaultCharset` is the only finding with genuine behavioral risk: `new String(value)` decodes
  Kafka JSON bytes with the platform default charset, which is windows-1252 on the dev machine
  and UTF-8 on CI. It sits inside a dead-letter *negative* assertion, so a mis-decode fails to
  match and the assertion passes — a false green. That is a test-integrity defect, not a
  production one, but it is the single finding here that could have been hiding a real failure.
- **Memory.** Negligible. The two `Future<?> unused` locals reference objects `executor.submit`
  already allocates.
- **Style tension (worth naming).** Error Prone accepts a deliberately-dropped `Future` when it
  is assigned to a variable *named* `unused`; the existing main-source precedent
  (`KafkaEventPublisher`) wrote that as `var unused = ...`. `docs/CODE_STYLE.md` rule 9 says
  prefer `var` only when the RHS type is obvious, and `executor.submit(...)` returns a
  non-obvious `Future<?>`. Both rules are satisfiable at once by writing `Future<?> unused = ...`
  — Error Prone matches on the name, not the keyword. Task 3 verifies that empirically instead of
  trusting it.
</approach_analysis>
