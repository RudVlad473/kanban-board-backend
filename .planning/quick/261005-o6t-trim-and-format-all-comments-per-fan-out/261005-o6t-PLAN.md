## Approaches considered (project directive: 2 alternates per decision)

Decision 1: how to do the rewrite

| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Per-comment executor judgment over a tool-generated worklist. Mechanical equivalence and functional-marker checks guard it. Disjoint file sets go to parallel executors | + Only this approach can apply rubric step 1 (delete restatements) and step 4 (recognise a decision record), and its default outcome is deletion. − About 1.35M executor tokens. − Judgment varies between executors (one shared procedure and one final gate offset this). − About 280 files to review (the equivalence proof lets a reviewer read comment hunks only) | **Picked.** The rubric's decisions are semantic, and the guards make judgment safe to apply at scale |
| B. Scripted mechanical pass: regex-delete ids, truncate blocks over N lines, reflow | + Minutes of runtime, deterministic, reviewable as one script. − This is exactly the failure the rubric warns about: it compresses and keeps instead of asking whether the comment should exist. − Deleting an id that was a sentence's only justification leaves orphan claims ("see ()"). − It cannot tell a restatement from a one-way-door record | Rejected: it optimises the metric the rubric calls wrong |
| C. Hybrid: strip ids mechanically first, then a judgment pass | + Removes about 850 hits cheaply. − An id is often a comment's only justification, so the judgment pass revisits every hit anyway. − Two overlapping diffs per comment double the review cost | Rejected: the hits need rewording, not deletion, so it saves little |

## Non-obvious trade-offs

- **Flyway state (one-way).** Flyway stores a CRC32 over every line of each applied migration,
  comments included, and validates it at boot (verified against Flyway's `ChecksumCalculator`
  source via Context7). Any comment edit to `src/main/resources/db/migration/V*.sql` makes prod
  fail to start with a checksum mismatch. These files are FROZEN: never edited, exempt from the
  lint, and `equiv` refuses any byte change under that directory even with `--allow`.
- **Rollout-triggering comments.** The two files in `k8s/data/postgres/init/*.sh` are
  `configMapGenerator` inputs with a hash suffix (rendered today as `postgres-init-62tc4bg5h4`).
  Any byte change renames the ConfigMap and restarts the one Postgres StatefulSet that serves
  BOTH prod and nonprod. Comments inside the YAML block scalars of
  `k8s/monitoring/controllers/alloy.yaml` (5 Alloy `//` lines) and
  `k8s/platform/traefik/helmchartconfig.yaml` (6 `#` lines in `valuesContent`) are object
  content, so editing them redeploys Alloy and Traefik (a blip on the public edge). All of these
  edits go in ONE isolated, final T4 commit. The operator keeps it or reverts it at the merge gate.
  **Default if no answer: revert it**, so cosmetics never cost a restart. The lint permanently
  exempts the init scripts (ROLLOUT_GATED), so reverting never turns the gate red.
- **Deploy.** Any `src/` change on main triggers `deploy.yml`: a new image, and app pods roll in
  both environments with behaviour-identical code. One deploy cycle, accepted. Comment-only k8s
  YAML edits render identically, so Flux applies nothing.
- **Performance.** `check` is a single O(bytes) pass and should take under 1s on about 300 files.
  That is noise next to the pre-commit hook's ~4 min of fastTest. `equiv` runs one `git show` per
  changed file: seconds.
- **Host memory.** Three parallel worktrees each running pre-commit fastTest (Gradle +
  Testcontainers) on this 10GB WSL host risks the JVM kills in `docs/SESSION_LESSONS.md` lesson 9.
  Mitigation: batch commits (one per package or family). If the kill signature appears, run Wave
  2 sequentially. The file partition is unchanged either way.
- **Gate coupling.** R1 allows a planning id only inside a path that exists in the repo.
  Archiving a cited `.planning/` directory therefore turns the gate red until the citation is
  updated. That is the point (dangling evidence gets detected), but it couples gsd-cleanup commits
  to code comments. Only `.gitleaks.toml`'s evidence citations are expected to use it.
- **Pre-commit interpreter.** The hook tries `python3`, then `python` (only if it reports 3.x).
  If neither exists, it prints a loud WARNING and skips, and CI is the backstop. This is
  deliberately not fail-closed like the gitleaks step: a missed comment violation can be fixed
  later, a leaked secret cannot. Windows behaviour cannot be verified on this host. A Docker
  fallback was rejected because the lint enumerates files with `git ls-files`, which breaks inside
  a container for worktrees. The hook's own gitleaks mount notes document the same problem.
- **Security.** If a comment edit touches a line that holds a baseline-suppressed historical
  finding, the finding re-appears in a new commit. The pre-commit gitleaks scan refuses it.
- **Escape hatches.** The decision-record marker and the exemption lists can be abused. Every
  use is visible in diff review, and T5 must report any exemption added beyond this plan's list.

## Comment-pass procedure (T1-T4 apply this to every comment in their files)

1. Worklist: `python3 scripts/verify-comments.py report --all <paths>` lists every block with
   its flags. Read the code under each block before deciding anything.
2. Skip everything on the never-edit list below.
3. Before cutting a comment, check whether anything points at it:
   `git grep -n -i -E '<ClassOrFileName>.{0,60}(javadoc|header|docstring|comment)' -- . ':!.planning' ':!docs/raw' ':!docs/wiki'`.
   If another file points at a comment, keep the content that pointer relies on and trim only
   ids and narration around it. Known pointers include `SecurityConfiguration.sessionAuthenticationStrategy`,
   `RandFlakeGenerator`, `HistoricalSchemaRehearsalE2ETest`, and the `infra/vm/k3s-host-firewall.sh`
   header. Never edit the pointing markdown or `.claude/`. List every comment kept for this reason
   in the SUMMARY.
4. Apply the rubric's order. The first "yes" decides:
   1. Restates the code → delete it.
   2. Task or "revisit later" → `TODO: <URL | #N | existing repo path> - <what>` if a tracked item
      exists. Otherwise delete it and list its text in the SUMMARY so the orchestrator can capture it.
   3. A rename would carry it → renames are code changes and out of scope here. Leave the comment
      and list the rename in the SUMMARY as a suggestion.
   4. A settled decision a reader would otherwise undo (one-way door, observed tool behaviour,
      something deliberately not checked) → keep it as a decision record: a one-line summary, a
      blank comment line, then a `Decisions:`, `Known holes:` or `Why this is the way it is:`
      marker line followed by the records. Keep each record's observation, version/date and
      falsifier as written. Never invent a date the original lacks.
   5. Names a sibling symbol only to say "same as that" → cut the name.
   6. Otherwise → one line, at a different abstraction level than the code, in the imperative.
5. Planning ids (decision ids, threat ids, quick-task ids, "Phase N", "plan NN-NN", requirement
   ids such as SCHEMA-03, "Epic N", plan artifact names): delete them. If an id was the only
   justification, state the reason inline or delete the comment. A `.planning/` citation survives
   only as a full repo path, and only where the evidence exists nowhere else (expected: only
   `.gitleaks.toml`). Ambiguous suspects (`13-06`, `Task 3`): fix the ones that are plan
   references.
6. A multi-line comment gets a summary of at most 2 lines (wrapping included), a blank comment
   line, then detail. After any Java edit, run `./gradlew spotlessApply`, which reflows Javadoc.
   Error Prone `NotJavadoc` is an ERROR on test sources, so use `/**` only on declarations.
7. Add no new comments, except a shorter replacement for one being cut. Never change code,
   string literals, annotation values, or log/exception messages.
8. For each batch: spotlessApply (Java/Gradle) → `equiv --base comment-pass-start <batch>` →
   `check <batch>` → commit.
9. "I could not verify X" is an acceptable outcome. Report it rather than working around it.

**Never edit:**
- shebangs;
- Flux `# {"$imagepolicy": ...}` markers (`k8s/overlays/*/kustomization.yaml`);
- `shellcheck disable=`, `noqa`, `nosemgrep`, `gitleaks:allow` and `spotless:off/on` directives;
- Dockerfile parser directives;
- the `MEASURED`/`PROVISIONAL` keyword on a memory-cap comment (text around it may be reworded,
  but the keyword must stay within the 25 lines above its `memory:` line, which is invariant I4);
- `// arrange` / `// act` / `// assert` markers (CODE_STYLE rule 5; trailing text after a marker
  may be trimmed);
- string literals and YAML block-scalar content (except in T4's rollout commit);
- FROZEN, VENDORED and GENERATED files.
