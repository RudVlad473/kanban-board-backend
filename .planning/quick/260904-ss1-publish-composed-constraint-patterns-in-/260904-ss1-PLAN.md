<objective>
Make the OpenAPI document publish the constraints this API already enforces, for the fields whose
constraints arrive through a composed custom annotation rather than a direct Jakarta one.

Purpose: every one of this codebase's 9 custom constraint annotations is invisible to the generated
spec. A client generated from the document cannot know that `color` must be `#RRGGBB`, that a board
name rejects punctuation, or that a password has a shape — each rule is discoverable only as a
runtime 400. Verified live on 2026-09-04: the production document contains **zero** `pattern` keys
and **zero** `example` keys.
Output: one springdoc `PropertyCustomizer` bean covering all 9 annotations and any future one, one
document-level regression test proving the values are actually published, one equivalence test
proving the published values agree with the enforcer, and four annotations gaining a
documentation-only `@Schema`.
</objective>

<root_cause>
Not inferred — read from the resolved dependency sources
(`swagger-core-jakarta-2.2.30-sources.jar`, pulled in by
`org.springdoc:springdoc-openapi-starter-webmvc-ui:2.8.8` under Spring Boot 3.5.16).

`ModelResolver.applyBeanValidatorAnnotations` (`ModelResolver.java:1696-1699`) builds:

```
Map<String, Annotation> annos = new HashMap<>();
for (Annotation anno : annotations) { annos.put(anno.annotationType().getName(), anno); }
```

from `annotatedType.getCtxAnnotations()` — the field's **directly declared** annotations — and then
tests `annos.containsKey("jakarta.validation.constraints.Pattern")` and friends. There is no walk
into an annotation's own meta-annotations anywhere on that path. `@ColumnColor` is in the map under
its own name and is never opened, so its composing `@Pattern` never reaches the schema.

Two consequences of that same `HashMap`, both load-bearing for this plan:

1. It is keyed by annotation type name, so **even in the direct case only one `@Pattern` can
   survive**. Any design that hopes swagger will merge two patterns for us is wrong.
2. `@NotBlank` → `minLength(1)` lives in the group-aware sibling at `ModelResolver.java:1771-1782`,
   which is why `SaveBoardRequestDTO.name` and `SaveSubtaskRequestDTO.title` show `minLength: 1`
   today while carrying no direct `@Size`. That published `1` is what X-2 has to raise.

`org/springdoc/core/utils/SchemaUtils.java:222-236` does its own, separate version of this for
query/path **parameters** only; request-body component schemas do not pass through it. So there is
no second code path to piggyback on.
</root_cause>

<approach_analysis>

The headline mechanism — one systemic bean rather than per-field `@Schema` — is locked by the user
(D-1) and is not re-litigated here. The two open questions are *which* springdoc extension point,
and *how deep* to walk. Both are answered from the dependency sources rather than from memory.

## Alternates considered

**Approach A — a `PropertyCustomizer` bean.** (PICKED) springdoc's per-property extension point.
`PropertyCustomizingConverter` (verified in the 2.8.8 sources jar) runs
`chain.next().resolve(type, context, chain)` first, then, if `type.isSchemaProperty()`, hands the
already-resolved `Schema` **and** the `AnnotatedType` to every `PropertyCustomizer` bean it found.
So the customizer receives the field's own annotation array and the schema swagger just built from
the direct annotations, together, in one call. Wiring is `@Component` and nothing else.

**Approach B — a custom `ModelConverter` bean.** Same inputs, more power (it can restructure whole
schemas, not just properties). But it has to implement chain delegation by hand and reason about
its own ordering against springdoc's ten registered converters — and `PropertyCustomizingConverter`
already exists to spare exactly that. Strictly more code for byte-identical output.

**Approach C — a `GlobalOpenApiCustomizer` post-processing the finished document.** This is the
shape the codebase already uses (`ProblemDetailOpenApiCustomizer`), so it deserves a real answer
rather than a dismissal — precedent is a genuine argument here.

## Trade-off matrix

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A — `PropertyCustomizer`** | **+** Receives `AnnotatedType.getCtxAnnotations()`, i.e. the annotations themselves, which are the whole input to this task. **+** Receives the schema *after* swagger applied the direct annotations, so a most-restrictive merge is natural instead of a guess. **+** Wiring is one `@Component`; springdoc collects the beans itself. **+** Removing the `@Component` empties springdoc's list and makes the converter a no-op — a clean, non-invasive RED lever. **−** Invoked for every property in the document, including response DTOs that carry no constraints; requires an early return. **−** Slightly less familiar in this repo than approach C. | **PICKED.** It is the only option that has the annotation in hand at the moment it must be read. |
| **B — custom `ModelConverter`** | **+** Identical access to `AnnotatedType`. **+** Could also fix the parent schema's `required` list, which A can also reach via `AnnotatedType.getParent()`. **−** Must hand-roll `chain.next()` delegation and null-handling. **−** Introduces an ordering question against springdoc's own converters that A does not have. **−** No output A cannot produce. | **REJECTED.** It reimplements `PropertyCustomizingConverter`, which ships in the dependency already on the classpath. |
| **C — `GlobalOpenApiCustomizer` over the finished document** | **+** Matches the in-repo precedent exactly; a reader finds it next to `ProblemDetailOpenApiCustomizer`. **+** Sees the whole document, so it could enforce cross-schema invariants. **−** By that point the document holds schema *names* and property *names* — the Java field and its annotations are gone. Recovering them means mapping `"SaveColumnRequestDTO"` back to a class by simple name, which breaks silently on `@Schema(name=...)`, on generics, and on two DTOs sharing a simple name across packages. **−** Cannot tell whether a value it is about to overwrite came from a direct annotation or from nothing, so "never loosen" (X-2) becomes unimplementable. | **REJECTED despite the precedent.** `ProblemDetailOpenApiCustomizer` is a document-level customizer because its input (`@ControllerAdvice` arms) genuinely is not a property annotation. Here the input IS the property annotation, and C is precisely the option that throws it away. |

Second axis — **how deep to walk**:

| Option | Pros / Cons | Why picked / rejected |
|---|---|---|
| **One level deep** | **+** Covers all 9 annotations as they exist today; every one composes plain Jakarta constraints directly. **+** Trivially terminating, no visited-set. **−** `@AppEmail` already composes `@Email`, which is itself a `@Constraint`-annotated composable — so the codebase is one refactor away from needing depth 2, with no compiler signal when it crosses. | **REJECTED** as one saved `Set` allocation in exchange for a silent future failure. |
| **Recursive with a visited-set, gated on `@Constraint`** (PICKED) | **+** Handles composition-of-composition. **+** The `@Constraint` gate is also what keeps the walk out of `java.lang.annotation.*` — `@Documented` is annotated `@Documented`, so an ungated walk is an infinite loop. **+** Costs a `HashSet<Class<?>>` per property at document-build time. **−** Two more lines and one more branch to cover. | **PICKED.** The recursion guard is not optional defensiveness; without it the walk does not terminate. |

<non_obvious_tradeoffs>

**1. The merge direction is the whole correctness story, and this repo already has a live victim.**
`SaveSubtaskRequestDTO.title` publishes `minLength: 1` today (from its direct `@NotBlank`) while
the server enforces `>= 3` (from `@SubtaskTitle`'s `@Size(min = 3)`). A naive
`schema.setMinLength(size.min())` happens to fix that one — but the same naive assignment on a
field where the direct constraint is the tighter one would publish a bound *looser* than the
enforcer, which is worse than publishing nothing: the client submits, the server 400s, and the
document said it was fine. So the rule is `minLength = max(all)`, `maxLength = min(all)`,
unconditionally, seeded from whatever swagger already put on the schema. Verified before/after
values for all 13 affected properties are tabulated in Task 1.

**2. OpenAPI has one `pattern` key; two fields contribute two regexes each.**
`UpdateBoardRequestDTO.name` carries `@BoardName` (`^[a-zA-Z0-9 ]*$`) **and** `@OptionalNotBlank`
(`.*\S.*`); `SignupRequestDTO.displayName` carries `@DisplayName` (`^[a-zA-Z ]*$`) and the same
`@OptionalNotBlank`. Publishing either one alone is incomplete *in the permissive direction* —
`^[a-zA-Z0-9 ]*$` accepts `"   "`, which the server rejects. The conjunction is built from
zero-width lookaheads (exact form in Task 1); it is correct under JSON Schema's search semantics
because each lookahead is `^`-anchored and `^` without the `m` flag matches only at index 0.

**3. Java `@Pattern` and JSON Schema `pattern` are different dialects, and this codebase happens to
sit in the intersection — checked, not assumed.** `@Pattern` evaluates with `Matcher.matches()`
(whole-string); JSON Schema `pattern` is an ECMA-262 *search*. The five distinct regexes in play
are `^[a-zA-Z0-9 ]*$`, `^[a-zA-Z ]*$`, `^#[0-9a-fA-F]{6}$`, the password regex (`^(?=…)…$`), and
`.*\S.*`. The first four are `^…$`-anchored, so search and whole-string agree. The fifth means
"contains a non-whitespace character" under both readings. None uses a Java-only construct
(possessive quantifier, `\p{…}`, backreference, `\A`/`\z`). The one genuine gap is
`@OptionalNotBlank`'s `Pattern.Flag.DOTALL`, which has no OpenAPI equivalent — and at both sites
where it is conjoined, the sibling pattern forbids newlines anyway, while at the two sites where it
stands alone the search-mode reading is equivalent. So no field is misdocumented today. That is a
claim about behavior, so Task 2 **tests** it against the real `Validator` rather than resting on
this paragraph.

**4. Performance and memory: zero per-request cost.** The customizer runs once per schema property
at document-**build** time, not per request, and springdoc caches the built `OpenAPI` instance. The
live document has 13 request-DTO properties carrying custom annotations out of roughly a hundred
total; the recursion is depth ≤ 2 in practice and allocates one `HashSet` and one small `List` per
property visited. Against a ~20 s Spring context startup this is unmeasurable. Nothing is added to
any request path, no reflection happens at request time, and no constraint evaluation changes.

**5. Security: the password regex becomes public, deliberately.** Approved by the user with the
tradeoff stated. What it discloses is the *composition* rule set — one lowercase, one uppercase,
one digit, one special — plus `minLength: 8` / `maxLength: 64`. It discloses nothing about hashing,
storage, or session handling, and every one of those facts is already recoverable by sending one
bad password and reading the 400 body, which quotes the same rules verbatim in
`Password.message()`. The genuine gain is client-side: a signup form can validate before submitting
instead of round-tripping. Do not add a suppression flag and do not exclude `@Password` (D-3).

**6. gitleaks is a real hazard for the `@Password` example, and the plan routes around it rather
than exempting it.** `.githooks/pre-commit` runs a pinned gitleaks scan of the staged diff before
formatting or tests, and a password-shaped string literal in a Java file is exactly what its
generic rules look for. So `@Password` gets a `description` (the four character-class rules in
prose, which is more useful to a human than a specimen password anyway) and **no** `example`. If a
future contributor wants one, the correct move is still not a `.gitleaks.toml` exemption.

**7. `openapi: 3.1.0` means the string-type check has two spellings.** Read live 2026-09-04: this
document is 3.1.0 even though the serialized JSON shows the singular `"type": "string"` (the
serializer collapses a one-element `types`). In the in-memory model `getType()` can be null with
`getTypes()` holding `["string"]`. A check written against `getType()` alone would match nothing
and produce a document byte-identical to today's — the exact silent no-op this plan is required to
rule out. `SchemaUtils.java:222-225` is the in-dependency precedent for covering both.

</non_obvious_tradeoffs>

     `StringBuilder` or a `Collectors.joining` — no regex library call.
