## Approaches considered

**Approach A (CHOSEN) — add class-level `@Validated` to the four controllers.**
Converges all seven controllers onto `MethodArgumentNotValidException` for `@Valid @RequestBody`
failures, which the existing `handleMethodArgumentNotValidException` arm already turns into
`VALIDATION_FAILED` + `errors` map. Four one-line source edits.

**Approach B — teach the `HandlerMethodValidationException` arm to build the same `errors` map**
by extracting field names from `ex.getParameterValidationResults()`, leaving all controllers
untouched. Larger diff confined to one class; no risk of changing path-variable behavior.

**Approach C — delete `@PathVariable @NotBlank` from all controllers.** The split's actual root cause
is that Spring 6.1+ activates built-in method validation for a handler method *because* it carries a
constrained `@PathVariable`; with no constrained parameters, `@Valid @RequestBody` always falls
through to `RequestResponseBodyMethodProcessor` and throws `MethodArgumentNotValidException`
uniformly, with no `@Validated` needed anywhere.

## Trade-off matrix

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. `@Validated` on 4 controllers** | **+** Smallest diff (4 annotations). **+** Makes all 7 controllers structurally identical, so the invariant is greppable and ArchUnit-enforceable. **+** Aligns the outliers with the majority rather than inventing a new shape. **−** Silently reroutes path-variable validation from Spring MVC's built-in path to the AOP `MethodValidationInterceptor`, which throws a different exception type the handler may not cover — a real 400→500 risk. **−** Touches 4 files instead of 1. | **PICKED.** The 400→500 risk is real but *measurable and bounded*, and Task 1 measures it before any source edit rather than assuming either way. Critically, the same risk already exists unmeasured on Board/User/Activity/Authentication today — so Approach A does not create the exposure, it forces the pre-existing one into the light and fixes it for all eight controllers at once. |
| **B. Build the `errors` map in the `HandlerMethodValidationException` arm** | **+** Zero controller files touched, zero risk to path-variable behavior. **+** Would also cover any future non-`@Validated` controller automatically. **−** Leaves seven controllers structurally inconsistent, so nothing prevents the *next* divergence; the invariant stays invisible. **−** Produces two independent code paths that must be kept emitting an identical envelope forever — a duplication that drifts. **−** `getParameterValidationResults()` field-name extraction is fiddly for nested `@Valid` body objects and would itself need careful new tests. | **REJECTED** as the primary fix — it hides the asymmetry instead of removing it. Note it is *not* mutually exclusive with A, and stays available as a follow-up if a genuine reason to keep a controller un-`@Validated` ever appears. |
| **C. Drop `@PathVariable @NotBlank` everywhere** | **+** Removes the root cause outright; one uniform validation path, no AOP proxying question at all. **−** Deletes an input guard (weak, but real) with no replacement. **−** Changes malformed-id behavior across every route, blast radius far larger than the bug. **−** Contradicts the todo's own framing, which explicitly wants the CONSTRAINT_VIOLATION branch retained. | **REJECTED.** Correct diagnosis, disproportionate cure. Recorded here because it explains *why* the split exists at all, which neither A nor B makes obvious. |

## Non-obvious trade-offs

**1. Two validation engines, not one (the load-bearing risk).** Spring's
`HandlerMethod.MethodValidationInitializer` gates built-in MVC method validation behind
`if (!AnnotationUtils.hasAnnotation(beanType, Validated.class))` — i.e. adding `@Validated` does not
*add* validation to a controller, it *switches which engine validates it*. Constrained path
variables then go through Spring's AOP `MethodValidationInterceptor`, which raises
`jakarta.validation.ConstraintViolationException` (or, with `adaptConstraintViolations`, a
`MethodValidationException` subclass of it) — a type `GlobalExceptionHandler` has no arm for today.
Unhandled, it falls to the `Exception.class` catch-all and surfaces as **500 INTERNAL_ERROR**.
Prediction: the four controllers regress 400→500 for blank path variables, and Board / User /
Activity / Authentication already have that latent 500 today. **Task 1 measures this before Task 2
edits anything.** Do not skip the measurement and do not pre-emptively write the handler arm.

**2. Proxying and per-request cost: already paid.** All four controllers already carry class-level
`@PreAuthorize("isAuthenticated()")`, so Spring Security's method-security infrastructure has already
made each of them an AOP proxy. `@Validated` appends one advisor to an existing proxy — it does not
create a new CGLIB subclass. Three of the four (`TaskController`, `SubtaskController`,
`TaskMoveController`) are package-private classes; CGLIB proxies those in the same package, a
mechanism the existing `@PreAuthorize` proxying already proves works here. Expected runtime cost:
one extra interceptor invocation per request, negligible.

**3. Security posture: strictly additive disclosure, no new class of leak.** The change makes 400
responses carry a per-field map naming which field failed and its constraint message. Those field
names and messages are already public via `/api/docs` (SpringDoc) and already emitted by the three
`@Validated` controllers, so no new *category* of information is disclosed. Nothing about
authentication or the ownership chain moves: `@PreAuthorize` and `OwnershipVerifierService` run
unchanged, and field validation only ever runs on an already-authenticated request.

**4. This is a breaking API-contract change, deliberately.** `ErrorCode`'s Javadoc states these
values are a published contract. Any client keying off `CONSTRAINT_VIOLATION` for a *body-field*
failure on the four controllers will break. Accepted because (a) the frontend is not yet integrated —
Phase 07.1 was frontend-readiness work — (b) the change moves toward the documented D-01/D-02 target
shape rather than away from it, and (c) `CONSTRAINT_VIOLATION` is neither removed from the enum nor
made unreachable; it remains the path-variable-violation code.

**5. Test cost.** ~4 new MockMvc cases in an untagged (`fastTest`-tier) class reusing the existing
shared Testcontainers PostgreSQL context — no new container, no new Spring context, marginal
wall-clock added to the pre-commit gate.
</design_rationale>
