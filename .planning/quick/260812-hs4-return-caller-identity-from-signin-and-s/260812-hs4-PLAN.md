<objective>
Change `POST /signin` and `POST /signup` to return the caller's identity as a JSON body so a
frontend BFF can learn who just authenticated, instead of receiving nothing but an opaque
`JSESSIONID` cookie. Fix `POST /signup`'s `Location` header, which today points back at `/signup`.

Purpose: a frontend team building a BFF has no documented way to learn which user just
authenticated. This shapes their session payload, their MSW mocks, and every downstream route
handler. Option 3 of the three discussed (change the auth endpoints themselves) was chosen over
re-deriving identity in the BFF or adding a separate `GET /users/me` call.

Output: both auth endpoints return `UserResponseDTO`; signup's `Location` resolves to a real
resource URI shape; auth tests assert the new bodies plus a credential-non-leakage property; the
signin sequence diagram and the README API table stop describing an empty response.
</objective>

## Fork 1 — how does `signin` obtain a `UserResponseDTO`?

`signup` needs no decision here: `UserService.save(SignupRequestDTO)` **already returns
`UserResponseDTO`** (`UserService.java:63-71`), and `AuthenticationController.signup` already holds
it in `createdUser`. Only `signin` holds a raw `UserEntity` (from `userService.findByEmail`).

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Thin `UserService.toResponseDTO(UserEntity)` delegate; controller maps the entity it already loaded** | **+** Zero additional queries. **+** Entity→DTO mapping stays in the service layer, matching CLAUDE.md's "Service methods return DTOs". **+** No new cross-package dependency. **−** A service method taking an entity and returning a DTO is a signature shape this repo has no precedent for. | **PICKED.** The one cost is a mildly unusual signature; the two rejected options each cost something that actually matters (a build-gate-invisible layering precedent, or a redundant query on the timing-sensitive endpoint). |
| **B. Inject `UserMapper` into `AuthenticationController`** | **+** Fewest new methods. **−** Makes `AuthenticationController` the first controller in the repo to depend on `mapper/` (verified: `grep -i mapper` across `controller/` and `security/` matches only `ObjectMapper`). **−** `LayeringArchTest`'s rule 1 blocks only `com.vrudenko.kanban_board.repository..`, so this new precedent would land with the build fully green and nothing to catch it. | **REJECTED.** Setting a layering precedent that the project's own architecture gate cannot see is the worst of the three. |
| **C. New `UserService.findResponseDTOById(userId)`, called after authentication succeeds** | **+** Most conventional signature. **−** Pays a redundant `SELECT ... FROM users WHERE id = ?` on every successful signin, for a row signin already loaded. **−** Lands that extra read on the exact endpoint whose F1 fix (`AuthenticationController.java:79-88`) already documents a residual sub-millisecond DB-read asymmetry as its known remaining timing channel. | **REJECTED.** Widens an explicitly-documented residual security trade-off to buy a nicer method signature. |

## D-05 — `theme` in the payload

No special handling needed, confirmed by reading the code rather than assumed: `UserMapper`
(`UserMapper.java:34`) maps `theme` by name with no explicit `@Mapping`, and `UserEntity.theme` is
`@Column(nullable = false)` with a `@Builder.Default` of `LIGHT` (`UserEntity.java:53-60`). The
same `UserResponseDTO` with the same populated `theme` already ships from
`GET /users/me/theme`. Tasks assert the value rather than trusting this paragraph.

## Non-obvious trade-offs

1. **Performance — zero added queries, negligible added latency.** Approach A adds no database
   round-trip on either endpoint. MapStruct mapping is compile-time generated with no reflection;
   mapping four scalar fields plus Jackson-serializing them is microseconds against signin's
   dominant cost of one BCrypt `matches` (tens of milliseconds, cost factor set in
   `BeanConfiguration`).

2. **Security — timing channel is untouched.** The identity mapping runs only after authentication
   has already succeeded. Both failure arms (unknown email, wrong password) return before reaching
   it. `SigninTimingEqualizationTest`'s "exactly one `matches` invocation per request" assertions
   and `AuthenticationTest.AntiEnumeration`'s byte-identical-failure-body assertion must be re-run
   to confirm this rather than reasoned about — both are in the task gates.

3. **Security — bcrypt hash exposure is a live, twice-realized risk in this repo, not a
   hypothetical.** `UserEntity` implements `UserDetails`, so its `getPassword()` returns the stored
   bcrypt hash, and `UserMapper` carries `unmappedTargetPolicy = ReportingPolicy.IGNORE`, which
   silently name-matches. That exact combination produced two prior security-marked todos
   (260803-m3i, 260803-ns9) and `UserMapper`'s own class Javadoc warns about it. `UserResponseDTO`
   declares no password-shaped field, so there is nothing for MapStruct to map into — but the tasks
   below assert the **exact set of field names in the serialized JSON**, which fails on any future
   field addition, rather than relying on that reasoning holding forever.

4. **Security — response cacheability.** The signin/signup responses now carry PII where they
   previously carried nothing. Spring Security's `HeaderWriterFilter` sets no-store cache headers by
   default on every response in the chain; the task asserts this rather than assuming it, with a
   documented escape hatch if the assertion proves false (file a todo, do not widen this task into
   header configuration).

5. **State invalidation — this is an OpenAPI response-schema change with no CI detector.** Changing
   `ResponseEntity<Void>` → `ResponseEntity<UserResponseDTO>` is additive and non-breaking for
   existing clients (a client ignoring the body keeps working), but springdoc will regenerate a
   different response schema and nothing in CI diffs it. The open todo
   `2026-08-11-add-openapi-breaking-change-detection-to-ci.md` covers exactly this gap. Flag in the
   summary; do not fix here.

6. **A deliberate, documented divergence from a repo-wide idiom.** All five `ResponseEntity.created`
   sites (`BoardController:54,80`, `ColumnController:51`, `TaskController:65`,
   `AuthenticationController:134`) currently use `URI.create(request.getRequestURI())`. This task
   changes exactly one of them. The other four are out of scope (their `Location` at least resolves
   to the parent collection they were POSTed to; signup's resolves to nothing). The divergence needs
   a Javadoc note at the call site or a future reviewer normalizes it straight back.

7. **The chosen `Location` target does not currently resolve — and that is still an improvement.**
   `GET /api/users/me` has no handler (`UserController` exposes only `/me/theme`). Neither does
   `GET /api/signup`, which is POST-only — so today's header is equally non-dereferenceable and
   additionally meaningless. Task 3 files a todo for the missing `GET /users/me`. The endpoint is
   deliberately **not** added here: it was option 2 of the three the todo considered, and option 3
   was chosen instead; adding it now would blur that decision.

8. **JaCoCo ratchet headroom is thin — 0.93pp on LINE.** The gate is
   INSTRUCTION ≥ 0.90 / LINE ≥ 0.90 / BRANCH ≥ 0.75 against a measured baseline of
   91.23% / 90.93% / 78.62%. Every production line added here must ship covered. All of it is on
   the happy path the new tests drive, so this is a check, not a risk.

9. **`./gradlew test --tests <X>` is unusable for per-task verification in this repo.**
   `tasks.named('test')` is `finalizedBy jacocoTestCoverageVerification` (`build.gradle:228`), so a
   *filtered* `test` run computes the ratchet over a partial exec file and fails on coverage for
   reasons unrelated to the change. Per-task gates therefore use `fastTest --tests <X>`, which opts
   out of the JaCoCo agent entirely (`build.gradle:274-278`) and includes `AuthenticationTest`
   (it carries neither `@Tag("kafka")` nor `@Tag("realSocket")`). Full `./gradlew test` runs once,
   at the final gate.
</design_rationale>
