<objective>
Give `TaskController.addSubtaskByTaskId`'s DTO parameter the `@RequestBody` annotation every
sibling creation endpoint in this codebase already carries, and back it with the controller-tier
HTTP test that would have caught the defect in the first place.

Purpose: `POST .../tasks/{taskId}/subtasks` is the only creation endpoint in the API that does not
read its payload from the JSON request body. A frontend that posts JSON the way it posts to every
other creation route has its `title` silently dropped — the request does not create the subtask the
client asked for. Closes the todo filed at
`.planning/todos/pending/2026-08-09-fix-subtask-creation-dto-missing-requestbody-binds-as-mode.md`.

Output: a one-annotation production change, two new controller-tier tests written RED-first, a
closed source todo, and one newly-filed todo for a validation gap this work surfaces but
deliberately does not fix.
</objective>

<approach_analysis>

## Approaches considered

**Approach A — Add `@RequestBody`; rewrite the controller test to post JSON, plus a guard proving
the query-parameter form no longer binds.** (CHOSEN)

**Approach B — Change nothing in code; standardise the endpoint's documented contract on
model-attribute binding instead.** Treat the query-parameter/form binding as the intended shape,
and correct the OpenAPI description and frontend contract to match.

**Approach C — Add `@RequestBody` *and* harden `SaveSubtaskRequestDTO.title` with `@NotBlank` in
the same change**, so a missing title becomes a clean 400 rather than dying at the database's
NOT NULL constraint.

## Trade-off matrix

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A — `@RequestBody` + JSON test + param-no-longer-binds guard** | **Pros:** restores consistency with all six sibling creation endpoints (`BoardController.save`, `BoardController.addColumnByBoardId`, `ColumnController.addTaskByColumnId`, `TaskController.updateById`, `SubtaskController.updateById`, `UserController` theme update); one-line production diff; the paired tests falsify in both directions (JSON now works, params now do not), so the fix cannot silently regress; closes a latent mass-assignment surface (see trade-offs below). **Cons:** breaking for any client currently sending query parameters — a grep of `src/` shows the only such caller is the workaround test itself, so the real blast radius is zero. | **PICKED.** Smallest diff that makes the endpoint behave the way every other one already does, and the only option that leaves behind a test capable of catching a recurrence. |
| **B — Document the current binding as intended** | **Pros:** zero code risk; nothing to regress. **Cons:** entrenches a one-off shape in an otherwise uniform REST surface; `SaveSubtaskRequestDTO` is a `@Setter`-annotated DTO, so model-attribute binding keeps the query string wired to its property setters; every future frontend integration hits the same surprise; `docs/MOCKUP_FEATURE_GAP.md`'s frontend contract assumes JSON bodies throughout. | **REJECTED.** Optimises for not touching code rather than for the API being correct, and pushes recurring cost onto every client. |
| **C — `@RequestBody` + `@NotBlank` on the DTO in one change** | **Pros:** one pass fixes both the binding and the validation gap; missing-title becomes a proper 400. **Cons:** bundles two independent behavioural changes (how input is parsed, and what a missing title returns) into one commit, defeating the reason the source todo was filed separately in the first place — the `@NotBlank` change alters the response status for an existing failure mode and deserves its own test and its own reviewable unit. | **REJECTED as scope**, filed as its own todo in Task 3. Not dropped — the gap is real and gets recorded with the evidence Task 1 produces. |

## Non-obvious trade-offs

**Security (the actual reason this is worth more than a cosmetic consistency fix).** Without
`@RequestBody`, Spring resolves the parameter through `ServletModelAttributeMethodProcessor`, which
populates it by invoking the DTO's setters from request parameters. `SaveSubtaskRequestDTO` is
`@Getter @Setter`, so *every* settable property on it is reachable from the query string. Today
that set is exactly one harmless field (`title`), so nothing is over-bindable right now — but the
exposure is structural, and any field added to that DTO later inherits it silently. Moving to
`@RequestBody` removes the class of problem, not just the current symptom.

**Behavioural compatibility.** This is a genuine breaking change for a client that posts
`?title=...` with no body: such a request goes from creating a subtask to a 400. Verified blast
radius before committing to it: `grep -rn "SUBTASKS" src/` shows six test call sites and two
production ones, and the only caller relying on parameter binding is the workaround inside
`TaskControllerTest` (which carries a comment naming this very todo). `AuthorizationGatingTest`
already sends a real JSON body to this route and asserts 403 — it passes today only because that
body is ignored and `@SubtaskTitle` is a `@Size` alias that tolerates `null`; it must still pass
once the body is genuinely parsed, which is exactly why it is named as a key link.

**Performance / memory.** Neither. `MappingJackson2HttpMessageConverter` and
`ServletModelAttributeMethodProcessor` are both linear in payload size on a single-field DTO; there
is no measurable difference and no new allocation of consequence.

**Validation gap surfaced, not created.** `@SubtaskTitle` composes only `@Size`, which passes on
`null` — unlike `SaveBoardRequestDTO` (`@NotBlank @BoardName`), `SaveTaskRequestDTO`
(`@NotBlank @Size`) and `SaveColumnRequestDTO` (`@NotBlank @Size`), each of which pairs its size
rule with a null/blank rule. So a JSON body of `{}` reaches `subtasks.title NOT NULL` in the
database rather than being rejected by Bean Validation. That is true before this change and after
it; the change only makes it reachable by the normal JSON path. Filed in Task 3, not fixed here.
</approach_analysis>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → `POST .../tasks/{taskId}/subtasks` | Untrusted request payload crosses into a JPA-persisted entity. Both the request body and the query string are attacker-controlled for any authenticated session. |
| request payload → `SaveSubtaskRequestDTO` property setters | The binding mechanism decides which attacker-controlled key/value pairs can reach which DTO properties. This is the boundary the change moves. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-me4-01 | Tampering | `TaskController.addSubtaskByTaskId` DTO binding | low | mitigate | Model-attribute binding wires the query string to every setter on a `@Setter` DTO — a mass-assignment surface that is empty today (one field) but grows silently with any field added to `SaveSubtaskRequestDTO`. Task 2 switches the parameter to explicit body binding, and Task 1's second test locks the query-parameter path out with a 400 so the surface cannot quietly return. |
| T-me4-02 | Elevation of Privilege | ownership check on the subtask creation route | low | mitigate | Body parsing now happens before the controller method runs, so an unparseable body could in principle short-circuit the ownership check and change a 403 into a 400 for a cross-user request. `AuthorizationGatingTest`'s route table already sends a well-formed JSON body for this route and asserts 403 + `ACCESS_DENIED`; Task 2's verify runs that class explicitly, so the ownership outcome is re-proven rather than assumed. |
| T-me4-03 | Denial of Service | `subtasks.title NOT NULL` reached via unvalidated null | low | accept | A `{}` body bypasses `@SubtaskTitle` (a `@Size` alias, which passes on null) and fails at the database constraint instead of at validation. Pre-existing, requires an authenticated session, produces a handled error response rather than an outage, and is a behavioural change of its own — accepted here and filed as a todo in Task 3 rather than bundled into a binding fix. |
| T-me4-SC | Tampering | npm/pip/cargo installs | n/a | accept | No package-manager install of any kind occurs in this plan. No new dependency is added; the change uses annotations already on the compile classpath. |
