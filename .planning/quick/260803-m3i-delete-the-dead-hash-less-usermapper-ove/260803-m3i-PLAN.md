<objective>
Remove two dead `UserMapper` overloads that could silently produce a user entity with no password
hash, and make `UserEntity.passwordHash` non-nullable so the database rejects such a row rather than
storing it — with the production DDL bridge, and its own failure mode, handled explicitly.

Purpose: quick task `260803-l6f` proved the live signup path writes a real bcrypt hash today, then
filed a security-marked todo for the two latent ways that could stop being true without any test
going red. This closes both. The mapper overloads are a spoofing/credential-loss hazard invisible to
the type system; the nullable column is what turns that hazard from a rejected write into a silently
created, permanently unusable account.

Output: two `src/main` changes, one corrected test comment, one new manual production DDL script plus
its STATUS.md note, the originating todo closed, and one newly discovered finding filed rather than
silently absorbed.
</objective>

<data_flow>
## Core mechanism, in three sentences

`UserService.save` passes a `SignupRequestDTO` to `userMapper.fromSignupRequestDTO`, and Java
overload resolution selects the one declaration carrying
`@Mapping(target = "passwordHash", expression = "java(passwordEncoder.encode(dto.getPassword())))"`
— the only place in the codebase where a plaintext password becomes a bcrypt hash — before
`userRepository.save` flushes the entity to `users`. A sibling overload differing only in parameter
type (`SigninRequestDTO`) carries no such mapping, and because the mapper is configured
`unmappedTargetPolicy = ReportingPolicy.IGNORE`, selecting it would compile cleanly and write a null
hash with no error anywhere. Deleting that sibling makes the hazard unrepresentable, and marking the
column non-nullable makes any *other* route to a null hash fail loudly at the write instead of
producing an account that `passwordEncoder.matches(plaintext, null)` can never authenticate.
</data_flow>

<approaches_considered>
## Alternate approaches and trade-off matrix

The interesting decision here is not whether to delete the overloads — it is how the production DDL
handles the case where a null `password_hash` row already exists.

| Approach | Pros / Cons | Why Picked |
|----------|-------------|------------|
| **A. Guarded DDL — a `DO` block that counts null rows, raises a legible `EXCEPTION` if any exist, and otherwise performs the `SET NOT NULL` in the same block; the standalone pre-flight `SELECT` is also documented as runbook step 1** (CHOSEN) | **Pros:** fails before touching the constraint, with a message naming the actual problem and the row count, regardless of whether the operator remembered `-v ON_ERROR_STOP=1`; still fully idempotent, since `SET NOT NULL` is a no-op once applied; the pre-flight `SELECT` in the header lets the operator check days ahead of the deploy window rather than inside it. **Cons:** more SQL machinery than either precedent script — a PL/pgSQL block where the precedents are one-liners, so a reader must be told why the extra structure is earned. | It is the only option that makes the failure mode named in RO-3 impossible to hit blind. The precedents are one-liners because `ADD COLUMN ... DEFAULT 0` *cannot* fail on existing data; `SET NOT NULL` can. Matching their shape here would be imitating the form while dropping the reason for it. |
| **B. Bare `ALTER TABLE users ALTER COLUMN password_hash SET NOT NULL;`, with the pre-flight `SELECT COUNT(*)` documented in the header only** | **Pros:** visually identical to `02-optimistic-locking-ddl.sql` and `03-activity-log-ddl.sql`, so it needs no explanation and a reviewer recognises it instantly; genuinely idempotent on its own. **Cons:** the entire protection is "the human read the header and ran the check first." If they did not, the first signal is a raw Postgres constraint violation inside the deploy window — precisely the outcome RO-3 asks the plan to design against. | Rejected. The header-only guard optimises for looking like the precedents rather than for the risk that makes this migration different from them. |
| **C. Backfill first — `UPDATE users SET password_hash = '<unusable sentinel>' WHERE password_hash IS NULL;` then `SET NOT NULL` unconditionally** | **Pros:** never fails, never needs a decision from the operator, completes in one pass with no branching. **Cons:** silently manufactures exactly the defect this task exists to eliminate — an account that exists, passes the constraint, and can never authenticate — while destroying the evidence that anything was wrong. A null hash in production means something upstream is broken; a migration that quietly paves over it removes the only signal. | Rejected outright. It converts a loud, diagnosable failure into a silent data problem, and it makes a data-disposition decision (what happens to those users) that belongs to a human, not to a migration script. |
</approaches_considered>

<tradeoffs>
## Non-obvious trade-offs worth stating

**Availability / correctness — this closes an account-recovery gap, not a breach.** A null hash never
granted access: `passwordEncoder.matches(plaintext, null)` returns false forever. The real damage was
availability plus diagnosability — signup returns 201, the account exists, every subsequent signin
returns 401, and nothing at creation time points at the cause. The value of the constraint is that
the failure moves to the write, where it is attributable.

**Schema — the annotation change is a test-only change until a human acts.** `ddl-auto` is unset in
`application.properties` and `create-drop` in `application-test.properties`. So `nullable = false`
reshapes the H2 schema on the next test run and does *precisely nothing* to production. The two
halves of this change ship at different times through different mechanisms, and the codebase half is
the harmless one. Any summary that reports "passwordHash is now non-nullable" without that
qualification is wrong (RO-4).

**Migration ordering — this one is safe in either order, unlike the precedent.**
`02-optimistic-locking-ddl.sql` had to run *before* merge or every Task/Column request hit a missing
column. Here the constraint is additive and the application already only ever writes non-null hashes,
so neither ordering breaks production. It should still run before merge, for the same reason as the
precedents — leaving schema drift outstanding is how it gets forgotten — but the pressure is
"do not lose this," not "production breaks at merge." Say so rather than copying the precedent's
urgency language, which would be false here.

**Naming — the `04-` prefix collides with Epic 4 and that is a deliberate, documented choice.**
`docs/plans/backend-modernization/` already numbers `.md` plan docs by epic (`04-redis.md`) and `.sql`
bridges by their originating unit of work (`02-` Epic 2, `03-` Phase 3 of v1.1). This script comes
from a quick task, which has no number in either sequence. Continuing the DDL sequence (02, 03, 04)
is the most legible option available; the alternative of inventing a quick-task-keyed filename would
break the one ordering a reader can actually follow. The script's first header line names quick task
`260803-m3i` explicitly so nobody reads `04-` as Redis.

**Testing — a schema-constraint assertion is deliberately NOT added here.** The natural new guard
would be a test asserting H2 now rejects a null `PASSWORD_HASH`. It is not in this plan because
RO-5 requires `UserPersistenceE2ETest`'s assertions to remain unchanged so it keeps functioning as
the untouched regression guard across this change, and because a constraint assertion belongs with
that class rather than in a new one. The full suite passing green *is* the check that the tightened
schema breaks nothing. Recommend the assertion as a follow-up, do not smuggle it in here.

**Comment hygiene — one existing comment becomes a lie and must be fixed.** `UserPersistenceE2ETest`
lines 143-146 explain that a NOT NULL assertion "would fail today" because the column is deliberately
nullable. After Task 2 that sentence is false and actively misleads the next reader into thinking the
constraint does not exist. Correcting it is not a violation of RO-5's "unmodified" — RO-5 is about
the assertions, which must not move. This project has already set that standard (commit `500fde5`,
"correct every session documentation claim to match wired JDBC store").
</tradeoffs>
