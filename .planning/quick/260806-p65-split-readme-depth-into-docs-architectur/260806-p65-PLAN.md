<objective>
Restructure the documentation written in quick task 260806-nyj into a conventional front door plus a
linked deep-dive, without losing a single technical claim.

Purpose: the rewritten README is accurate but 2,265 words — roughly a ten-minute read — and puts
"Running it locally" tenth of eleven sections. Measured against the audience it was written for, that
is the wrong shape: recruiters spend 10–30 seconds deciding whether to keep reading and 2–5 minutes
at most on a portfolio, and the standard-readme spec orders sections description → install → usage,
recommending a table of contents past 100 lines. The depth is the differentiator and must not be
deleted — but at ten minutes of prose it is not being read at all, so it needs to be *signalled* in
the README and *housed* one click away.

This directly reverses the Approach A / Approach B decision recorded in
`.planning/quick/260806-nyj-rewrite-readme-md-to-reflect-current-arc/260806-nyj-PLAN.md`. That plan
rejected the split on the reasoning that "a reader evaluating depth in 90 seconds does not open the
second file." The reasoning was inverted: at ten minutes, they do not read the first file either.

Output: a trimmed README.md and a new docs/ARCHITECTURE.md. No source changes.
</objective>

<approach_analysis>

## Alternate Approaches Considered

**Approach A (picked): Split — README trimmed to a ~120-line front door; the five deep-dive sections
move to a new `docs/ARCHITECTURE.md`; an "Engineering highlights" list of five linked one-liners
keeps the depth visible from the landing page.**

**Approach B: Trim in place — keep one file, compress each deep-dive section to two or three
sentences, add a table of contents, move the run instructions up.**

**Approach C: Reorder only — keep all content, hoist "Running it locally", add a table of contents.**

## Trade-off Matrix

| Approach | Pros / Cons | Why Picked / Rejected |
|----------|-------------|----------------------|
| **A — split into README + docs/ARCHITECTURE.md** | **Pros:** satisfies the conventional section order *and* preserves every mechanism paragraph; matches the repo's existing `docs/` habit (`CODE_STYLE.md`, `LOCAL_DEV.md`, `SESSION_LESSONS.md`, `DIAGRAM_CONVENTIONS.md`); the highlights list gives a 20-second reader the depth signal and a 10-minute reader the depth itself. **Cons:** one more file to keep true; anchor links can rot silently if a heading is renamed. | **PICKED.** The only option that serves both audiences instead of trading one for the other. Anchor rot is mitigated by an automated link check in this plan's verify block. |
| **B — trim in place** | **Pros:** one file; no anchor-link surface. **Cons:** the "why" clauses *are* the differentiator — compressing "explicit version check in addition to `@Version`, because a load-then-save flow otherwise cannot detect a stale read" down to "uses optimistic locking" deletes exactly the signal the document exists to send. There is nowhere for the detail to go. | **REJECTED.** Buys the right length by spending the thing being sold. |
| **C — reorder + table of contents** | **Pros:** smallest change; fixes navigation genuinely. **Cons:** still a ten-minute read; a table of contents helps a reader who has already committed to the document, which is not the reader at risk. | **REJECTED.** Fixes the symptom (can't navigate) and not the cause (too long to start). |

## Non-obvious trade-offs

- **Anchor links are the fragile part of this design.** GitHub derives heading anchors by lowercasing,
  stripping punctuation and replacing spaces with hyphens — so `## Concurrency: optimistic locking`
  becomes `#concurrency-optimistic-locking`. A future heading rename breaks the README's links
  silently, with no build step to catch it. This plan's verify block extracts every intra-repo anchor
  from README.md and asserts each resolves to a real heading, so at least the initial state is proven
  rather than assumed.
- **The split must not duplicate claims.** If a fact lives in both files they will drift, and the
  drift will be invisible. The README keeps *assertions* ("409 on a stale write"); ARCHITECTURE.md
  keeps the *mechanism* ("because a load-then-save flow cannot otherwise detect a stale read"). Any
  sentence carrying a mechanism belongs in exactly one file.
- **The Process View diagram moves with its section**, not to the README. It is the single most
  compelling artifact in the document and there is a real temptation to keep it on the landing page —
  but it only makes sense alongside the four failure-path bullets that explain it, and a diagram
  without its explanation is decoration. `docs/DIAGRAM_CONVENTIONS.md`'s one-view discipline travels
  with it.
- **The forbidden-claims list from 260806-nyj now applies to two files.** No `/full` endpoint, no
  current deploy target, no Redis/Kubernetes/Actuator, no directive to open `/api/docs`. Moving text
  between files is exactly the operation during which such a claim can be reintroduced by
  paraphrase, so the verify block runs the same greps across both.
- **Build/performance surface: none.** Spotless targets `src/**/*.java`; both files are markdown. The
  only cost is `.githooks/pre-commit` (`spotlessApply` + `fastTest`) on each commit, which Gradle
  will resolve as UP-TO-DATE for a zero-Java change — so the hook is fast here but still needs a
  generous timeout, per `docs/SESSION_LESSONS.md` lesson 2.
- **Security.** Both files are public-facing. Same constraint as 260806-nyj: environment variable
  *names* only, repo-relative paths only, no hostnames, connection strings, credentials, or
  machine-local absolute paths.

## Data-flow mechanism (3 sentences)

Both tasks write markdown; nothing reads either file at build or run time, so there is no code path.
The only executable consequence is the commit, which fires `.githooks/pre-commit`. Verification is
therefore textual: a line-count bound on README.md, a heading-set comparison proving each moved
section landed, an anchor-resolution check across the two files, and the 260806-nyj forbidden-claim
greps re-run over both.
