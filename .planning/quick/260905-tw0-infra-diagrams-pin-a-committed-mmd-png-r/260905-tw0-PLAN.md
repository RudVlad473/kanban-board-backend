<objective>
Make the repository's Mermaid diagrams reproducible, then use that capability to record two things
the current diagram set cannot express: the actual inbound packet path through this VM's network
layers, and which of this deployment's trust boundaries are not in this repository at all.

Purpose: no `.mmd` -> `.png` render command exists anywhere in this repo, and `mmdc` is not
installed. Every committed PNG is therefore an artifact of an unknown renderer on an unknown
machine — unreproducible, and unable to drift-check. That blocks everything downstream: a layout
convention nobody can render is not a convention, and a new diagram authored under it would inherit
the same unverifiability. Pinning the renderer first is what turns the rest into checkable work.

Output: a digest-pinned render script plus a scale manifest; a measured, reported drift audit of the
existing nine PNG pairs; four layout rules in `docs/DIAGRAM_CONVENTIONS.md`; a new Scenario (+1)
packet-path view with the `DOCKER-USER` chain drawn empty and dated; numbered trust boundaries on
the Physical/Deployment view; and a Maintenance Note that lists all of it.

Scope: documentation plus one shell script. No Java, no compose, no workflow changes.
</objective>

### The core decision: where the pinned renderer lives and what pins it

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. `scripts/render-diagrams.sh` driving a digest-pinned `ghcr.io/mermaid-js/mermaid-cli/mermaid-cli:11.17.0@sha256:a6fb05…` container** | **+** Bundles Chromium AND fonts, so text metrics — and therefore layout — are identical on any machine and any CI runner. **+** Exactly matches this repo's established pinning discipline: `.githooks/pre-commit` already pins `ghcr.io/gitleaks/gitleaks:v8.30.1@sha256:…` for the same "the pin is load-bearing" reason, and `deploy.yml` pins `flyway/flyway:11.7.2`. **+** Docker is already a hard dependency of this repo's workflow (pre-commit hook, Testcontainers). **-** 2.36GB on disk once pulled. **-** Needs a running daemon. | **PICKED.** Reproducibility is not a nice-to-have here, it is the entire deliverable: a drift check whose baseline shifts with the host's font set cannot distinguish drift from a different laptop. | **B. `pnpm dlx @mermaid-js/mermaid-cli@11.17.0` in the same script** | **+** Matches the user's standing tooling preference directly, no daemon, ~10x smaller footprint. **+** Version-pinned, so the mermaid layout engine itself is fixed. **-** Puppeteer renders text using the HOST's installed fonts, which the package cannot pin. The user preference is honoured where it actually applies — the fallback is written as `pnpm dlx`, never `npx`. |
| **C. | **B. ### Non-obvious trade-offs, stated explicitly

1. **Adding one file under `scripts/` changes this commit's CI cost from zero to a full deploy.**
   `deploy.yml` and `invariant-checks.yml` both carry `paths-ignore: [docs/**, "**/*.md",
   .planning/**]`. A pure docs change skips both. `scripts/render-diagrams.sh` matches none of those
   patterns, so on merge to `main` this triggers `invariant-checks.yml` (wanted — its two gates must
   pass, baseline confirmed green 2026-09-05) and a full production+nonprod redeploy via
   `deploy.yml` (~14 jobs, unwanted but harmless and idempotent). Accepted rather than dodged: the
   alternative is hiding the renderer under `docs/` to preserve the skip, which would put executable
   tooling somewhere no one looks for it in order to game a path filter.
2. **Pixel-equality with the committed PNGs is unattainable and must not be promised.** Measured at
   the pinned renderer, `-s 2`: width reproduces EXACTLY for both infra diagrams (1568px), height is
   +6.21% on the flowchart and −8.37% on the sequence diagram. Opposite signs rule out a scale
   artifact — the committed set came from a different mermaid version. So this change resets the
   baseline for the two diagrams it touches, under a pin, and says so.
3. **The committed set is not internally consistent, which the manifest exposes rather than hides.**
   Committed widths are 784 (`auth-*`, scale 1), 1568 (`infra-*`, scale 2) and 3136 (`architecture-*`
   sequence diagrams, scale 4), with `architecture-mutation-flowchart` at 2044 matching no integer
   scale of the 784 base at all. A single uniform scale would silently downgrade the architecture
   diagrams from 3136px to 1568px — a visible resolution regression in seven files this task has no
   business touching.
4. **State invalidation:** the `empty as of 2026-09-05` annotation is deliberately falsifiable and
   deliberately time-bounded. `.planning/todos/pending/2026-09-05-docker-user-chain-empty-on-the-vm.md`
   exists precisely to make it false. The diagram must therefore carry the date inside the node and
   the prose must name the todo that will invalidate it, or the annotation becomes the same kind of
   silently-stale claim that let this document describe Neon for four months after the cutover.
5. **Security/exposure:** nothing here changes a firewall rule, a port, or a running host. The
   packet-path diagram DOCUMENTS an existing exposure that is already tracked; it does not widen or
   narrow it. The one real hazard is the reverse — a diagram that draws container traffic traversing
   `INPUT` would manufacture false assurance, which is why the DNAT-through-FORWARD path is a
   must-have and not a stylistic detail.
6. **Time/space complexity:** irrelevant at this scale (9 diagrams). The dominant cost is the
   one-time image pull (2.36GB on disk); subsequent renders are ~15-40s each, wall-clock bound by Chromium
   startup, and the `--check` mode is O(n) over the diagram set with a constant-time header read per
   file.
</tradeoffs>
