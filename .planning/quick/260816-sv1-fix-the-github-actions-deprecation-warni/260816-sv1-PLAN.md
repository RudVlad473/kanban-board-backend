## Non-obvious trade-offs (per CLAUDE.md's PLAN.md directive)

- **`adopt` -> `temurin` is expected to be a functional no-op.** `setup-java` already maps the legacy `adopt` alias onto Temurin and warns; the JDK actually installed is Temurin 21 both before and after. So the correct expectation is **identical test results**, not "tests now run on a different JDK". If the suite's pass count changes, something else is wrong -- treat that as a finding, not as success.
- **Supply chain (mutable tags).** Every bump here re-affirms trust in a *moving* tag (`@v5` retargets on each minor release). This repo already pins its scanner by tag **plus** digest (`.githooks/pre-commit`, `secret-scan.yml`), so the codebase is internally inconsistent about action pinning. This task does not make that worse, but it is the moment the inconsistency becomes visible -- surface it as a todo, do not fix it here (digest-pinning every action is a separate, wider decision).
- **Verification requires a production deploy.** `deploy.yml` fires on `push: branches: [master]` only, and `run-tests` gates `deploy-to-netcup`. There is no branch, no `workflow_dispatch`, and no PR trigger, so the *only* way to see the run-tests log for this change is to push to master, which re-deploys the app to the live Netcup VM. The app code is untouched, so the deployed artifact is functionally identical -- this is a re-deploy, not a change of production behavior. This is a stated, deliberate deviation from the global branch-per-work-item preference, forced by the workflow's own trigger config; STATE.md records plan 05-05 doing exactly this three times.
- **Expect `cleanup-old-images` noise.** STATE.md records an open, deliberately-unfixed bug: Docker Hub's v2 API rejects that job's Basic auth on DELETE. It may log failures on this run. That is pre-existing and unrelated -- do not attribute it to this change and do not fix it here.
- **Local commit cost.** `.githooks/pre-commit` runs gitleaks + `spotlessCheck` + `fastTest` unconditionally, roughly 4 minutes, even for a YAML-only edit. Budget for it; do not use `--no-verify`.
