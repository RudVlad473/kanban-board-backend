**`providers.exec` shape in 8.x:** `providers.exec { ... }` returns an `ExecOutput`. `execOutput.standardOutput.asText.get()` forces execution and yields stdout as a `String`; `execOutput.result.get()` forces execution and yields an `ExecResult` (`.exitValue`). The closure delegate is an `ExecSpec`, so `commandLine`, `workingDir`, and `ignoreExitValue` are all available. Without `ignoreExitValue = true`, a non-zero exit throws — and `git config --get <unset-key>` exits **1** by design, which is precisely the fresh-clone case, so the flag is mandatory, not defensive padding.

**Why `providers.exec` and not `ProcessBuilder`/`project.exec`:** Gradle 7.5+ instruments `ProcessBuilder.start()`, `Runtime.exec`, and `project.exec` at configuration time and reports an "external process started" configuration-cache problem. `providers.exec` is the sanctioned configuration-cache-compatible path. This project has no `gradle.properties` and therefore no configuration cache enabled today (verified), so this is future-proofing rather than a present-day fix — but it costs nothing extra.

**`.githooks/pre-commit` (verified, 14 lines):** `#!/bin/sh`, captures `git diff --staged --name-only` into `stagedFiles`, echoes a message, runs `./gradlew spotlessApply`, then re-`git add`s each still-existing staged file. `git ls-files -s .githooks/pre-commit` currently reports mode **100644** — not executable. <design_rationale>
Per `.claude/CLAUDE.md`: alternatives considered and the trade-offs behind the chosen approach.

## Alternatives considered

**Approach A (chosen) — configuration-phase block in `build.gradle` using `providers.exec`.** Top-level build-script code, guarded on `rootProject.file('.git').exists()`, that probes the effective `core.hooksPath` and writes `--local` only when it differs from `.githooks`.

**Approach B — a dedicated `installGitHooks` Gradle task wired into the build lifecycle** (e.g. `tasks.named('compileJava') { dependsOn 'installGitHooks' }`).

**Approach C — a third-party git-hooks Gradle plugin** (e.g. `com.star-zero.gradle.githook`), which declares hooks in the DSL and generates them into `.git/hooks`.

## Trade-off matrix

| Approach | Pros / Cons | Why picked |
|----------|-------------|------------|
| **A. Config-phase block + `providers.exec`** | **+** Fires on *any* `./gradlew` invocation, including `help`, `tasks`, and `spotlessApply` — so the hook is armed no matter what the contributor's first command is. **+** ~20 lines, zero new dependencies, honours the "no new frameworks for this scope" constraint. **+** Reuses the already-committed `.githooks/` dir as the single source of truth. **-** Spawns one short-lived `git` process per configuration phase. **-** Build-script code with a side effect on developer-local state, which is unusual and needs a clear comment to not read as a smell. | **Picked.** It is the only option that satisfies the actual requirement — "armed on the first `./gradlew` command, whatever that command is" — and the cost is a single ~10 ms process spawn against a configuration phase already measured in hundreds of milliseconds. |
| **B. Dedicated task + `dependsOn`** | **+** No configuration-time process spawn; runs inside the task graph where side effects are conventional; up-to-date checks available. **-** Only fires when that task's graph actually runs: `./gradlew help`, `./gradlew tasks`, and `./gradlew spotlessApply` would all leave the hook uninstalled, so a contributor whose first command is not a compile still commits unformatted code. **-** Wiring it onto *every* task to close that hole is invasive and pollutes every task graph in the build. | **Rejected.** It trades the one property the todo explicitly asks for ("the first time **any** `./gradlew` command is invoked") for a purity gain that this build cannot spend. |
| **C. Third-party hooks plugin** | **+** Declarative DSL, maintained upstream, generates hook bodies for you. **-** Adds a build-classpath dependency and a plugin-resolution round trip for ~20 lines of logic. **-** Violates the project's stated "no new frameworks introduced for this scope" constraint. **-** Generates hooks into `.git/hooks`, duplicating and competing with the `.githooks/` directory that already exists, is already committed, and is already code-reviewed. | **Rejected.** Strictly more moving parts and a new supply-chain dependency to replace a mechanism that already works and only needs pointing at. |

(The status-quo fourth option — document the `git config` command in the README — is ruled out by `docs/CODE_STYLE.md` rule 8, which is what generated this todo in the first place.)

## Non-obvious trade-offs

**Performance.** One extra `git config --get` process spawn (~5-15 ms) per Gradle configuration phase, on *every* invocation including trivial ones like `./gradlew tasks`. Gradle's own configuration phase for this build is orders of magnitude larger, so this is unmeasurable in practice. Memory impact is a transient child process; nothing is retained. The write path spawns a second process, but only on the one build per clone where the value is actually wrong.

**Configuration cache (state invalidation risk).** `providers.exec` results are backed by a `ValueSource` whose result is cached with the configuration-cache entry. If configuration caching is ever enabled on this project, the probe stops re-running on every build and only re-executes when the entry is invalidated (which includes any `build.gradle` change). That is acceptable precisely because the operation is idempotent and only genuinely needed once per clone — but it is a real behavioral difference worth knowing before someone enables the cache and wonders why the block appears not to run.

**`.git` is not always a directory.** In git worktrees and submodules, `.git` is a *file* containing a `gitdir:` pointer. The guard therefore uses `.exists()`, not `.isDirectory()` — the latter would silently skip the bootstrap for every worktree-based contributor.

**Security — blast radius of a build script that mutates git state.** The write is `git config --local`, so it can only ever touch this clone's `.git/config`; `--global` and `--system` are never candidates. The exec spec's `workingDir` is additionally pinned to the root project directory rather than inheriting the daemon's CWD, so a build run with `-p <somewhere-else>`, or from inside an unrelated repository, cannot mutate that other repository's config. The `.git`-existence guard and the pinned `workingDir` are a deliberate pair, not redundancy.

**Security — arming a hooks directory is itself a supply-chain decision.** Once `core.hooksPath` points at `.githooks/`, every `git commit` in that clone executes a repository-controlled shell script. A malicious or careless edit to `.githooks/pre-commit` would then execute on a reviewer's machine the next time they commit. This is the standard, accepted trade-off of any committed-hooks setup, and it is bounded here: the mechanism only *points at* a directory — it never downloads, generates, or rewrites hook content, so the only way to change what runs is a reviewable diff to a 14-line file in `src`-adjacent version control.

**Silently overriding a deliberate developer choice.** Writing whenever the value differs (rather than only when unset) means a contributor who intentionally pointed `core.hooksPath` at their own directory gets stomped on every build. This is accepted as the todo's stated direction ("if unset or wrong"), because the failure mode of the alternative — a contributor silently opted out of formatting enforcement — is worse for a shared repo than the failure mode of this one, which is loud and immediately visible.

**Failure-mode discipline.** `ignoreExitValue = true` plus a `try/catch` means neither an unset key (exit 1), a missing `git` binary, nor a corrupt repo can fail a build. The command chosen is a non-interactive `git config`, which — unlike network-touching git subcommands — cannot block on a credential or SSH prompt and hang the configuration phase.
</design_rationale>

Insert exactly this section (Groovy DSL, 4-space indentation to match the file):

    // --- Git hooks bootstrap ---------------------------------------------------
    // Points this clone at the version-controlled .githooks/ directory so the
    // pre-commit spotlessApply hook is armed on a fresh checkout with no manual
    // `git config` step (docs/CODE_STYLE.md rule 8: dev setup must be automated).
    //
    // Runs at configuration time so it fires on ANY ./gradlew command, not only on
    // builds that compile. Idempotent: it re-probes each configuration phase and
    // writes only when the effective value is missing or wrong, so the steady state
    // is one cheap process spawn and no output.
    //
    // Never fails the build: skipped entirely when there is no .git (exported source
    // tree), and any git failure (missing binary, unset key exiting 1) is swallowed.
    // providers.exec is used rather than ProcessBuilder/project.exec because it is
    // the configuration-cache-compatible way to run an external process here.
    def desiredHooksPath = '.githooks'
    def repoRoot = rootProject.projectDir

    if (rootProject.file('.git').exists()) {
        try {
            // Read the EFFECTIVE value (system/global/local merged) - that is what git
            // will actually resolve hooks from.
            def currentHooksPath = providers.exec {
                commandLine 'git', 'config', '--get', 'core.hooksPath'
                workingDir = repoRoot
                ignoreExitValue = true
            }.standardOutput.asText.get().trim()

            if (currentHooksPath != desiredHooksPath) {
                // Write LOCAL only - never touch the developer's global/system config.
                providers.exec {
                    commandLine 'git', 'config', '--local', 'core.hooksPath', desiredHooksPath
                    workingDir = repoRoot
                    ignoreExitValue = true
                }.result.get()
                logger.lifecycle("Configured git core.hooksPath -> ${desiredHooksPath} (pre-commit hook armed)")
            }
        } catch (Exception ignored) {
            // git unavailable or not a usable work tree: leave hooks unconfigured and
            // carry on. A build must never fail because of hook wiring.
        }
    }

Implementation constraints that are load-bearing and must not be "simplified" away:
- `rootProject.file('.git').exists()` — `.exists()`, not `.isDirectory()`, because `.git` is a regular file in git worktrees and submodules.
- `workingDir = repoRoot` on **both** exec specs — without it the spec inherits the Gradle daemon's working directory, which can be an entirely different repository.
- `ignoreExitValue = true` on the probe — `git config --get` of an unset key exits 1, which is the fresh-clone case; without the flag `.get()` throws there.
- `--local` on the write, and only on the write.
- The lifecycle log line fires **only** inside the `if`, so a correctly-configured clone stays silent on every subsequent build.
- The write is forced by resolving `.result.get()`; leaving the `ExecOutput` unresolved means the process never runs.

Do not add a Gradle task, do not add a plugin, do not touch `settings.gradle`, do not add a `.dockerignore`, and do not add any README or docs instruction — the point of this change is that no instruction is needed.
