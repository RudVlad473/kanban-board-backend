## Problem

Filed from quick task 260903-dvp (edge rate limiting), where it was a knowingly deferred decision
rather than an oversight — see the "What is deliberately NOT here" block in `Caddyfile`.

Every error this API emits is `application/problem+json` with a stable `code`, produced either by
`GlobalExceptionHandler` or by `ProblemDetailAuthenticationEntryPoint`. The 429 is the one
exception: it is generated by Caddy's `rate_limit` handler and never reaches the JVM, so it returns
Caddy's plain default error body. A client written against the documented envelope — reading
`code` to branch on the failure — gets a response shape it cannot parse, for the one status most
likely to need programmatic handling (back off and retry).

## Solution

Add a `handle_errors 429` block to the `{$APP_DOMAIN}` site block emitting a body matching the
project's envelope, with a `code` consistent with the existing set.

**The acceptance criterion is the reason this was deferred, not the body itself:** it must be
proven that the module's `Retry-After` header survives being rewritten by an error handler. That
header is the actionable part of a 429, and shipping an unproven header interaction alongside the
limiter itself would have made any failure ambiguous between the two. Verify by driving a real
429 through the custom image and asserting `Retry-After` is still present and numeric — the local
harness in `scripts/loadtest/` already produces 429s and observed `Retry-After: 297` before the
error handler existed, so that value is the baseline to compare against.

Also decide whether the nonprod site block needs the same treatment. It has no limiter, so it
cannot emit a 429 today; adding one there would be dead configuration.
