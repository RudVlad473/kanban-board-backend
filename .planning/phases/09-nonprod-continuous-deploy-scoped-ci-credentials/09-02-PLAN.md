<objective>
Close CI-02 by removing the last unscoped deploy credentials, and expand the proven tracer path with
the two behaviours that make a nonprod deploy trustworthy: a bounded health gate that fails the
workflow when nonprod does not come up, and a per-repository image-retention pair that cannot reach
the other environment's tags.

Purpose: plan 09-01 built the fence and walked one deploy through it, but production's nine secrets
were still readable from any job by name. Deleting them is what turns "the nonprod job declares
`staging`" into "a job that forgets to declare an environment gets nothing and fails loudly". The
health gate and retention jobs then make the nonprod path behave like production's, rather than like
a deploy that succeeds whatever happens.

Output: `deploy.yml` carrying `health-check-nonprod`, `cleanup-old-images-nonprod` and
`cleanup-unused-image-nonprod`; a repository secret store holding one entry; a runbook record.
</objective>

<design_alternatives>
Two alternate technical approaches were considered before this plan was written, as required by
`.claude/CLAUDE.md`'s GSD Execution Directives.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Health poll as a final `run:` step inside `deploy-to-nonprod`** | **Pros:** the closest literal reading of ROADMAP criterion 2 ("the nonprod *deploy* is reported successful only after…") — the deploy job itself turns red. One less job, one less runner start. **Cons:** the poll would sit inside `deploy-to-nonprod`'s `concurrency: deploy-to-nonprod-vm` group, so up to five minutes of pure waiting would hold the VM's nonprod deploy lock and queue a following push behind it for no reason. It also buries a 15-line bash loop inside a job whose other steps are all `uses:` actions. | **Rejected** on the lock-holding cost. The criterion is satisfied either way: with a separate job, a failed poll fails the workflow run, and `cleanup-old-images-nonprod` is re-pointed at `health-check-nonprod` so "the deploy is complete" materially depends on health. |
| **B. Separate `health-check-nonprod` job, `needs: [deploy-to-nonprod]`, with the retention sweep re-pointed behind it** | **Pros:** releases the deploy concurrency lock immediately; matches RESEARCH.md's and PATTERNS.md's job-graph sketch; makes the health result a first-class node other jobs can depend on — which is what lets the retention sweep be gated on health rather than merely on "the SSH script exited 0". **Cons:** `deploy-to-nonprod` itself shows green even when nonprod is dead; only the run is red. | **Picked.** The run-level failure is the visible signal that matters, and gating retention on the health node is a strictly stronger guarantee than production currently has. |
| **C. A marketplace "wait for URL" action instead of a bash loop** | **Pros:** fewer lines; someone else maintains the retry semantics. **Cons:** one more unpinned third-party `uses:` to vet and trust for a ~15-line loop, in a repo where digest-pinning every existing `uses:` is already a scheduled Phase-10 task (HARDEN-03) — adding an unpinned action mid-phase makes that task larger and this phase's supply-chain surface wider for no functional gain. | **Rejected**, per RESEARCH.md's "Don't Hand-Roll" table, which explicitly names this as the case where hand-rolling is correct. |
| **D. One parameterized cleanup job with `strategy.matrix: [prod, nonprod]`** | **Pros:** DRYer; one script to fix if a third Docker Hub bug appears. **Cons:** GitHub Environments scope secrets per *job*, not per matrix cell, so both environments' credentials would resolve inside one job context — the exact boundary CI-02 exists to draw. It also puts production's repository name and nonprod's in the same job's variable space, which is how the cross-repository deletion in ROADMAP criterion 4 becomes reachable. | **Rejected.** Duplication is the cheaper risk here. |

**Non-obvious trade-offs this plan deliberately accepts:**

- **Availability (irreversible-ish, seconds of exposure):** deleting the nine repository secrets is
  the point of no return for the retrofit. If any environment secret was mis-set in plan 09-01, the
  next production deploy fails after the deletion rather than falling back. Mitigated by ordering
  only: the deletion happens *after* 09-01's environment-scoped run concluded `success`, which is
  direct evidence every production job already resolves its credentials from `production`. Recovery
  is re-setting the environment secret, not re-creating repository secrets.
- **Retention (deliberate asymmetry with production):** `cleanup-old-images-nonprod` is gated on
  `health-check-nonprod` rather than on the deploy job, so a deploy that starts containers but never
  becomes healthy leaves its tag in place. That tag is swept by the next healthy run. This is a
  deliberate one-run retention overshoot bought in exchange for keeping a debuggable image around
  after a failed bring-up — production, having no health job, does not have this property.
- **Correctness (unverified DELETE, pre-existing):** production's `cleanup-unused-image` issues a
  Registry-API-v2 manifest `DELETE` with **no status check at all**, so whether that call has ever
  actually deleted anything is unproven in this repository's history. The nonprod copy adds a
  status check that emits `::warning::` on a non-2xx rather than failing — the job already runs on
  the failure path, and turning it red would mask the original deploy failure. This surfaces the
  latent question without changing pass/fail semantics; hardening it (and production's copy) belongs
  with Phase 10's CI work, not here.
- **Timing (poll bound):** 300s is chosen against `docker-compose.nonprod.yml`'s real healthcheck
  numbers plus image-pull and Flyway margin, explicitly overriding RESEARCH.md's illustrative 60s,
  whose own Assumption A3 warns it was never sized against real CI-runner conditions. The loop
  prints every attempt's status code so the first few real runs produce the timing profile needed to
  tighten it later.
</design_alternatives>

`environment: staging`. No `concurrency` block — this job takes no VM lock and must not hold the
`deploy-to-nonprod-vm` group while it waits (that is the whole reason it is a separate job rather

block carrying `NONPROD_HEALTH_URL: https://kanban-board-rud-vlad-473-nonprod.duckdns.org/api/actuator/health`,

The loop follows RESEARCH.md's Code Examples shape and this repo's own status-check idiom: iterate
`seq 1 "$ATTEMPTS"`, capture `curl -s -o /dev/null -w "%{http_code}"` into a variable with a
`|| echo "000"` fallback so an outright connection failure yields a comparable sentinel rather than
an empty string, compare the captured value against `200` as a string, and on a match echo the
attempt count and exit 0. On a miss echo the attempt number, the total, and the observed status,
then sleep. After the loop, emit an `::error::` annotation naming the attempt count and the total
elapsed bound in seconds and `exit 1`.

Size the bound deliberately and comment the arithmetic inline: `app-nonprod` cannot be marked healthy
by Compose before `start_period 30s`, and can take up to `30s + interval 10s x retries 5` = 80s, and

migration pass, and DNS/TLS latency from a GitHub-hosted runner. 30 x 10s = 300s comfortably covers
that with margin, and deliberately overrides RESEARCH.md's illustrative 12 x 5s = 60s, whose own
Assumption A3 flags it as unsized against real CI conditions. State in the comment that the per-attempt
status lines exist so the first few real runs yield a timing profile to tighten this against later.
