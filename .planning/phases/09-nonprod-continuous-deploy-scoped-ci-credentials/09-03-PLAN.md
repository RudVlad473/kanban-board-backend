<objective>
Automate the last hand-run step in this project's deploy: registering the application's 14 Avro
schemas against both the production and the nonprod registries on every push, reusing the existing
`AvroSchemaRegistrar`/`PropertiesLauncher` one-off-container mechanism, ordered so that nonprod's
registration completes before its app process exists.

Purpose: `spring.kafka.producer.properties.auto.register.schemas=false` makes an unregistered
subject a hard runtime publish failure rather than a lazy self-heal. Today the only thing standing
between a schema-changing commit and that runtime failure is an operator remembering a runbook step.
This plan removes the operator from that loop and makes an incompatible schema fail the deploy
instead.

Output: a registration step inside `deploy-to-nonprod` and a `register-schemas-production` job, both
running the identical documented invocation against their own broker, plus the runbook record that
supersedes the two manual procedures.
</objective>

<design_alternatives>
Two alternate technical approaches were considered before this plan was written, as required by
`.claude/CLAUDE.md`'s GSD Execution Directives. This section also constitutes the explicit
resolution of RESEARCH.md **Open Question 2**, which asked the planner to decide the production
ordering rather than copy it unexamined.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Two symmetric `register-schemas-*` jobs, each `needs:` its environment's deploy job, both running after the app is already up** (RESEARCH.md's job-graph sketch) | **Pros:** perfectly symmetric graph; each half is an independently visible node; neither touches a proven deploy script. **Cons:** fails CI-05's own pre-traffic clause for *both* environments — "within each single environment registration completes before that environment's app serves traffic". For nonprod, which is being automated from scratch with no existing traffic to protect, accepting that window is a choice with no upside: Phase 8's own manual bring-up already proved the correct order (broker up -> register -> app up) and it costs one extra line in a script that is already SSHed in. | **Rejected for nonprod, adopted for production.** |
| **B. Nonprod registers inside `deploy-to-nonprod` between `up -d redpanda-nonprod` and `up -d app-nonprod`; production registers in its own `register-schemas-production` job after `deploy-to-netcup`** | **Pros:** nonprod gets the literal guarantee — the app process does not exist until registration has succeeded, and a registration failure aborts before the app is ever started. Zero extra SSH round-trips and zero extra runner starts for nonprod, and no second job holding or contending for the `deploy-to-nonprod-vm` concurrency group. Production gets automation without a behaviour change to a live, proven deploy path. **Cons:** asymmetric; a reader scanning job ids finds `register-schemas-production` but no `register-schemas-nonprod`, so the asymmetry must be documented or it reads as an omission. | **Picked.** The asymmetry is justified per-environment and is recorded in both the workflow comments and the runbook. CONTEXT.md explicitly places CI-05's job/step ordering under Claude's discretion. |
| **C. Fully symmetric and fully gating: restructure production's deploy too, so `deploy-to-netcup` becomes `up -d redpanda` -> register -> `up -d app`** | **Pros:** the strongest reading of CI-05, applied uniformly; no asymmetry to explain. **Cons:** a real behaviour change to production's live deploy script — today it runs a bare `up -d` after `pull app`, and splitting it introduces a new ordering the pipeline has never executed. It also creates a new production failure mode: a schema-registry outage would block a production deploy that would otherwise have succeeded, on a path where registration has *never* been a precondition. RESEARCH.md's recommendation is explicitly the non-regressing reading. | **Rejected for this phase** — offered as `option-b` at Task 1's checkpoint so the user can choose it knowingly. It is a reasonable future hardening, not a silent default. |
| **D. Register from the CI runner directly over HTTPS instead of a one-off container on the VM** | **Pros:** no SSH step; the runner could call the registry REST API directly. **Cons:** structurally impossible here — neither broker publishes a host port for its schema registry (`docker-compose.nonprod.yml` has no `ports:` key at all, matching production), so the registry is reachable only from inside each stack's own Compose network. It would also mean a second schema-writing path, violating SCHEMA-01. | **Rejected.** Not available and not wanted. |

**Non-obvious trade-offs this plan deliberately accepts:**

- **Availability (nonprod, new failure mode):** placing registration ahead of `up -d app-nonprod`
  means a registry hiccup now blocks nonprod's app from starting at all, where previously it would
  have started and merely failed on first publish. That is the intended trade: nonprod exists to
  surface exactly this class of failure in CI rather than in a Playwright run later.
- **Availability (production, deliberately unchanged):** production keeps its existing brief window
  between `up -d` and registration. This is not an oversight — it is the status quo automated, and
  it is strictly better than the status quo, where the window lasted until an operator remembered
  the runbook. Recorded in writing so a later reader does not mistake it for a gap.
- **Correctness (exit-code propagation, the whole mechanism):** the "fails visibly" guarantee rests
  on a four-link chain — `AvroSchemaRegistrar.registerThenSetCompatibility` throws
  `IllegalStateException`, the JVM exits non-zero, `docker compose run --rm` propagates the
  container's exit code, and `appleboy/ssh-action` fails the step on a non-zero script exit. Task 2
  verifies this chain by deliberately breaking it once, not by reading it.
- **Performance (CI wall-clock, ~10-20s per environment):** each registration is a one-off JVM start
  of the already-pulled application image. Nonprod pays it inside a job that is already SSHed in;
  production pays one extra runner start. Neither is on the critical path of the other environment.
- **Correctness (`docker compose run` starts dependencies):** `run` honours `depends_on` and will
  start `redpanda-nonprod` if it is not already up. Since the preceding line brings the broker up and
  its healthcheck gates readiness, this is a no-op in practice — but it also means the registrar
  cannot silently run against a dead broker.
</design_alternatives>

  <action>
Automate both registrations using the two invocations the runbook already proves work, changing
nothing about how schemas are produced.

**A. Nonprod — insert the registration into `deploy-to-nonprod`'s existing SSH script (D-03).**
Per D-03 the nonprod registration reaches the broker over the *same* nonprod-scoped deploy identity
the deploy job already uses — it is part of the nonprod deploy path, not a separate credential
surface — which is a second, independent reason to place it inside that job's existing SSH step
rather than in a job of its own that would have to re-present the same key.
Between the `up -d redpanda-nonprod` line and the `up -d app-nonprod` line, add the documented one-off
container invocation: `docker compose --env-file ./.env.nonprod -f docker-compose.nonprod.yml
--profile nonprod run --rm --entrypoint java app-nonprod`, passing
`-Dloader.main=com.vrudenko.kanban_board.config.AvroSchemaRegistrar`, `-cp app.jar`,
`org.springframework.boot.loader.launch.PropertiesLauncher` and the registry URL
`http://redpanda-nonprod:8081` as the single argument. Both the `--env-file` and `--profile nonprod`
flags are mandatory on this invocation exactly as on the surrounding ones — Compose auto-loads only a
file literally named `.env`, and without the profile flag no service is selected at all. `IMAGE_TAG`
is already exported earlier in the same script, so the one-off container resolves the same image the
deploy just pulled; do not re-derive it and do not substitute a floating tag, which does not exist
for this project.

Add an `echo` line before it announcing the registration, and a comment block above the SSH step
recording *why* it sits here rather than in a job of its own: this position is the only one that
makes CI-05's "registration completes before that environment's app serves traffic" literally true
for nonprod, because `app-nonprod` does not exist as a process until the following line runs, and a
failed registration aborts the script before it. Note in the same comment that
`docker compose run` honours `depends_on`, so the registrar cannot run against a broker that is not
healthy.

Do **not** add `|| true`, `set +e`, or `continue-on-error` anywhere near it. The `appleboy/ssh-action`
script runs under a shell that fails the step on a non-zero command exit, which is the mechanism that
turns an incompatible schema into a red run.

**B. Production — add `register-schemas-production` (assuming option-a or option-c from Task 1).**
`runs-on: ubuntu-latest`, `needs: [ deploy-to-netcup ]`, `if: success()`, `environment: production`.
Its `needs:` names only the production deploy node — adding any nonprod node here would couple the two
vertical paths and break CI-01's parallel-independence requirement, and the reverse is equally true.
No `concurrency` block: it runs after the deploy job has released the VM lock, and it neither copies
files nor mutates the Compose project.

One `appleboy/ssh-action@v1.2.5` step named `Register Avro schemas (production registry)`, with the
same four connection inputs production's deploy step uses (`host`, `username`, `key`, `fingerprint`,
all resolving from the `production` environment), and a script that `cd`s to
`/opt/deploy/kanban-board-backend`, exports `IMAGE_TAG` from
`needs.build-and-push-docker-image.outputs.image_tag` — add `build-and-push-docker-image` to this
job's `needs:` so that output is in scope — and runs the documented production invocation:
`docker compose --env-file ./.env.prod -f docker-compose.prod.yml run --rm --entrypoint java app`
with the same `-Dloader.main`/`-cp app.jar`/`PropertiesLauncher` arguments and the registry URL
`http://redpanda:8081`. Production's Compose file has no profiles, so no `--profile` flag here.

Add a comment on the job recording the deliberate asymmetry decided at Task 1: this runs *after*
production's deploy rather than gating it, because production has served traffic before registration
since v1.2 Phase 5 (registration was a hand-run step), and making the registry a deploy precondition
would introduce a failure mode production has never had. If Task 1 selected option-c, also file the
Phase 10 revisit todo and reference its id in the comment.

**C. Prove the failure path is real, then restore.** After the first green run, deliberately break
registration once — the cheapest safe way is to temporarily point the nonprod invocation at a
registry URL that cannot answer — and confirm three things in one run: the SSH step exits non-zero,
`deploy-to-nonprod` goes red, and `app-nonprod` was *not* restarted (its container id and image are
unchanged on the VM, proving the abort really did precede the app start). Revert immediately and
re-run green. Verifying this by reading the exit-code chain is not sufficient; four links have to
hold and only a run proves all four.

**D. Prove idempotency and cross-registry independence by measurement.** Capture each broker's

after a run, then re-run the same commit and capture again: subject counts and version lists must be
identical across the re-run (idempotency), and a nonprod run must leave production's version lists
untouched (independence — `RecordNameStrategy` keys compatibility by Avro record full name per
broker).
