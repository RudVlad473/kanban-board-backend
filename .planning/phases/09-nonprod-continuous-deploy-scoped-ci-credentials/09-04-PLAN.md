<objective>
Close API-01: make the generated OpenAPI document declare the `ProblemDetail` error envelope on
every operation, centrally, and put an automated guard behind it so the gap cannot silently reopen.

Purpose: springdoc's reflection-based generation only documents a controller method's declared
return type. It has no visibility into a `@ControllerAdvice` class elsewhere in the application, so
every `400/401/403/404/409/500` this API actually returns at runtime is invisible in the spec today.
A downstream frontend planning agent hit this live during this phase's own planning and had to
hand-author the error type instead of generating it (D-07). This repo's own tests never noticed,
because they assert runtime response bodies and never the separately-generated document.

Output: one springdoc customizer bean, one guard test that iterates every operation in the live
document and cross-checks the declared schema against what both envelope producers actually emit,
and the architecture note recording the mechanism and its rationale.
</objective>

<design_alternatives>
Three alternate technical approaches were considered before this plan was written, as required by
`.claude/CLAUDE.md`'s GSD Execution Directives.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Per-endpoint springdoc response annotations on every controller method** | **Pros:** most precise — each operation can declare exactly the codes it can really produce; no framework-internals knowledge needed; entirely local, reviewable change. **Cons:** ~24 operations × 6 codes of annotation noise on methods that currently carry none; and, decisively, it must be *remembered* on every controller method written from now on. The defect API-01 describes arrived silently; a mechanism whose correctness depends on future recall would let it arrive silently again. | **Rejected — and rejected by name in D-08**, which specifies the global-customizer mechanism precisely because the annotation route "would require every future controller method to remember to add them." |
| **B. One global springdoc customizer bean; the six codes attached uniformly to every operation; a hand-built `ProblemDetail` component schema whose `code` enum is derived from `ErrorCode.values()`** | **Pros:** exactly the mechanism D-08 mandates. Zero per-controller surface, so coverage of a future endpoint is automatic rather than remembered. One named component schema means a consumer's codegen emits one error type. Deriving the `code` enum from the Java enum makes spec/enum drift structurally impossible rather than merely tested. **Cons:** uniform attachment over-documents — `GET /api/boards` will advertise a `409` it cannot actually produce (see trade-offs below). Requires care around springdoc's own model classes. | **Picked.** |
| **C. An operation-level customizer that introspects the `HandlerMethod` and attaches only the codes each operation can plausibly produce (e.g. `404`/`409` only where a path variable or a mutating verb is present)** | **Pros:** no over-documentation; the spec would assert only reachable outcomes. **Cons:** the heuristic is a guess about the runtime — `handleGeneralException` catches `Exception`, so `500` is reachable everywhere, and `ConstraintViolationException` on a `@PathVariable` makes `400` reachable almost everywhere too, leaving the conditional logic covering only `404`/`409`. It reintroduces exactly the per-operation reasoning D-08 removes, and every future controller shape becomes a question about whether the heuristic still holds. | **Rejected.** It trades a structural guarantee for a heuristic, to remove a cost (below) that is genuinely small. |
| **D. Derive the component schema by reflecting over `ProblemDetail.class` (springdoc's `extractSchema` helper)** | **Pros:** no hand-maintained schema; would track Spring's own class. **Cons:** it produces the wrong shape. `ProblemDetailJacksonMixin` annotates `getProperties()` with `@JsonAnyGetter`, so the extension map is flattened onto the root at serialization time — this repo's `GlobalExceptionHandlerTest` line 71 asserts `$.properties` does not exist, and line 69 asserts `$.code` does. A reflected schema would publish a nested `properties` object that never appears on the wire, and would omit `code` and `errors` entirely. | **Rejected.** Publishing a confidently wrong contract is worse than today's absent one — it would give the frontend generated types that do not match reality. |

**Also considered and rejected: a Spectral CI lint step against the generated document.** CONTEXT.md
D-08 and REQUIREMENTS.md API-01 both phrase the guard as "a test ... **and/or** a CI lint step", and
the planning brief marks the lint step explicitly optional. It is rejected here for three reasons,
none of them scope reduction: (1) it adds no coverage the guard test does not already have — the
test asserts the same document, per-operation, with the schema/wire fidelity cross-check a generic
linter cannot perform at all; (2) it would require touching `.github/workflows/deploy.yml`, the file
plans 09-01/09-02/09-03 own, breaking this plan's file-disjointness and its ability to run in any
order; (3) it introduces a Node toolchain and a new supply-chain surface into a Gradle-only repo for
that zero marginal coverage (see `<threat_model>` T-09-SC). The guard test runs inside
`deploy.yml`'s existing `run-tests` job, which already gates every build and deploy, so the
enforcement point is identical.

**Non-obvious trade-offs this plan deliberately accepts:**

- **Correctness (over-documentation, accepted):** attaching all six codes uniformly means a handful
  of operations advertise a status they cannot reach — `GET /api/boards` cannot produce `409`, and
  the `permitAll` `signin`/`signup` operations cannot produce the *unauthenticated* `401` (though
  `signin` does produce a `BAD_CREDENTIALS` `401`, so that one is real). The cost is bounded and
  one-directional: because every error response references the same single `ProblemDetail` type, a
  consumer's generated client is byte-identical either way; the only real cost is that a consumer
  writing exhaustive per-status handling gets one or two unreachable branches. Under-documentation
  is what broke the frontend consumer; over-documentation does not. Recorded rather than hidden.
- **Memory / aliasing (the non-obvious one):** the natural implementation builds six response
  objects once and attaches the same six instances to all ~24 operations. That is ~140 fewer small
  allocations, but it makes the in-memory document a graph with shared mutable nodes — a future
  customizer that sets a description on one operation's `404` would silently mutate every
  operation's `404`. This plan therefore requires a **fresh response object per (operation, status)
  pair**: ~144 short-lived objects, built once per document generation, in exchange for a document
  model with no aliasing hazard. Serialized output is identical either way (the schema is a `$ref`
  in both cases, so nothing is duplicated on the wire).
- **Performance / state invalidation:** the customizer runs `O(paths × methods × 6)` map insertions
  — around 144 — once per document build. springdoc caches the built document (`springdoc.cache.disabled`
  is not set, so caching is on), meaning this runs once per JVM rather than per request. That
  caching is also why the guard test must read the document **through the HTTP endpoint** as
  `OpenApiDocsTest` already does, never by autowiring the `OpenAPI` bean: a test that mutated the
  cached instance would corrupt every later assertion in the same Spring context.
- **Security (a pre-existing behaviour this plan makes more visible, not one it introduces):** the
  document is served on a `permitAll` path, and documenting the `500` response advertises that
  `detail` carries `ex.getMessage()` straight from `handleGeneralException` — i.e. raw internal
  exception text reaches clients. Publishing the spec does not create that leak, but it lowers the
  effort needed to notice it. Fixing it would be a runtime API behaviour change, which D-08
  explicitly puts outside this plan. Task 3 files it as a pending todo instead of quietly leaving it
  or quietly fixing it. See `<threat_model>` T-09-21.
</design_alternatives>

Give the class a Javadoc that states what it exists for and why it is central: springdoc's
reflection-based generation documents only a controller method's declared return type and has no
visibility into a `@ControllerAdvice` class, so without this bean every error status this API
actually returns is absent from the document (API-01). Name `GlobalExceptionHandler` and

Declare three constants: `PROBLEM_DETAIL_SCHEMA_NAME` with value `ProblemDetail`;
`PROBLEM_DETAIL_SCHEMA_REF` with value `#/components/schemas/ProblemDetail`; and `ERROR_RESPONSES`,
an insertion-ordered `LinkedHashMap` from status-code string to human description. Write each
description so it names the concrete `ErrorCode` members a consumer will actually see on that
status, taken from the handler arms read above — `400` covers malformed body, failed field
validation with its per-field map, and violated path or param constraints; `401` covers both an
absent session and rejected credentials, naming both producers; `403` covers an authenticated caller
who does not own the resource; `404` covers a resource that does not exist or is not visible to the
caller; `409` covers optimistic-lock version mismatch, duplicate resource and database integrity
violation; `500` covers the unhandled catch-all.

Implement `customise(OpenAPI openApi)` in four steps. First, if `getComponents()` is null, set a new
`Components` — springdoc supplies one in practice, but a null here would be a `NullPointerException`
at startup rather than a missing schema. Second, register `problemDetailSchema()` under
`PROBLEM_DETAIL_SCHEMA_NAME`. Third, if `getPaths()` is null, return. Fourth, for every `PathItem`,
iterate `readOperations()` (this returns exactly the operations present, so no verb list is
hardcoded); for each operation, create an empty `ApiResponses` if it has none, then for each entry
