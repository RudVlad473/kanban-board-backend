<ordering_uniqueness_decision>
RESEARCH.md Open Question 1 asks whether to add a database `UNIQUE(column_id, position)` /
`UNIQUE(board_id, position)` constraint, and recommends adding it on the grounds that this codebase
prefers database-enforced invariants.

**Planner's decision: do not add it. Enforce ordering in the service layer, and make every ordered
read a total order via a two-key sort.** This is a deliberate, recorded deviation from that
recommendation. CONTEXT.md explicitly leaves "exact renumbering mechanics" to the planner.

Reasoning:
1. **PostgreSQL checks a non-deferrable UNIQUE constraint per row, not per statement.** A single
   bulk `UPDATE ... SET position = position + 1 WHERE ...` — the exact mechanism D-02 and
   RESEARCH.md's own Don't-Hand-Roll table prescribe — can transiently collide mid-statement against
   such a constraint. Making it work therefore requires `DEFERRABLE INITIALLY DEFERRED`, a
   constraint form this codebase has never used anywhere.
2. **A deferred violation surfaces at commit**, outside any service method, as an integrity
   exception with no useful context — a strictly worse failure mode than the one it prevents.
3. **The V5 columns landed with `DEFAULT 0`**, so every pre-existing sibling row currently ties at
   position 0. Adding the constraint would additionally require a windowed backfill migration.
4. Together that is four new concepts (deferrable constraints, a backfill migration, a commit-time
   failure path, another exception-mapping arm) to protect a **presentational ordering field**.
   D-02 chose the simple integer scheme precisely because it "matches this codebase's existing
   no-new-concepts style."

**What replaces it is not a shrug.** Ordering correctness is delivered by two concrete, testable
mechanisms:
- Every renumber runs as one bulk statement inside the same `@Transactional` method as the moved
  row's own position write, so a partially-applied shift cannot be observed.
- Every read that returns siblings sorts by `(position ASC, id ASC)`. The ULID `id` tiebreak makes
  the ordering a **genuine total order** even if two rows transiently tie — the same reasoning and
  the same mechanism this codebase already shipped for the activity feed in Phase 3 Plan 03, whose
  recorded decision reads "the ULID id tiebreak makes offset pagination a genuine total order
  instead of merely newest-first."

**Residual risk, accepted and recorded:** two concurrent inserts into the same column can both
compute the same next position, leaving two rows tied. The consequence is a stable but arbitrary
relative order between those two rows, resolved deterministically by the id tiebreak — not data
loss, not a security issue, and not user-visible as a corruption. The realistic exposure is one user
racing themselves across their two permitted concurrent sessions. Recorded as `T-06-19` in the
threat model with disposition `accept`.
</ordering_uniqueness_decision>

<design_rationale>
## Alternate approaches considered (required by CLAUDE.md GSD Execution Directives)

D-02 already rejected fractional/LexoRank keys, so the live decision is the *shift mechanism*.

**Approach A (chosen): one bulk `@Modifying @Query` shift statement per move, scoped by parent id.**

**Approach B: load all siblings, renumber them in Java, save each one.**

**Approach C: renumber the entire sibling set from zero on every mutation (read all, rewrite all).**

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| A — one bulk statement | **+** Statement count is constant regardless of sibling count. **+** The race window is the width of one statement rather than of a read-modify-write loop. **+** Matches this codebase's own stated precedent — `SubtaskRepository.deleteAllByTaskIdIn`'s comment explicitly prefers one bulk statement over N per-row calls for exactly these two reasons. **−** Bulk JPQL bypasses the persistence context, so managed entities holding a stale `position` in the same transaction must be refreshed or the write ordered so it does not matter. | **PICKED.** The bypass is a known, already-handled hazard in this codebase (`TaskService.deleteAllByColumn` documents the flush/clear idiom for it). |
| B — Java loop, save per row | **+** Persistence context stays coherent. **−** N statements per move; a 40-task column costs 40 UPDATEs. **−** Widens the race window to the whole loop. **−** Directly contradicts the in-repo precedent above. | **REJECTED.** |
| C — full renumber from zero | **+** Self-healing: any drift is repaired on the next mutation. **−** Rewrites every sibling on every single move, so the cost of moving one task scales with the column's size. **−** Every rewritten row bumps its `@Version`, so an unrelated concurrent edit to a sibling task now 409s because someone reordered a different task. | **REJECTED.** The `@Version` interaction makes this actively harmful. |

## Non-obvious trade-offs

- **Time complexity:** one indexed bulk UPDATE per move, touching at most the siblings between the
  old and new position. Constant in statement count, linear in rows shifted.
- **State invalidation (the real hazard here):** the bulk shift is JPQL, which Hibernate executes
  directly against the database without updating managed entities. If the moved task is loaded and
  managed when the shift runs, its in-memory `position` can disagree with the row. Order the
  operations so the shift runs first and the moved entity's own `position` is assigned afterwards,
  then `entityManager.flush()` before building the response DTO — the same flush the move path
  already performs for `@Version`. Where a managed sibling could be read back in the same
  transaction, follow `TaskService.deleteAllByColumn`'s documented flush-then-clear idiom.
- **`@Version` interaction:** the bulk shift does not bump shifted siblings' `@Version`, because
  bulk JPQL never loads them as managed entities. This is desirable — a client editing a sibling
  task should not be 409'd because someone reordered a different task. It also means a client's
  cached `position` for a sibling can silently go stale. That is correct for a presentational field
  and is why `position` is exposed on the response DTOs: a client that needs current order refetches.
- **Backward compatibility:** `targetPosition` is nullable with no `@NotNull`. An existing client
  that sends only `targetColumnId` and `version` keeps working and gets append-at-end semantics.
  This is load-bearing — the move endpoint shipped in v1.1 and has existing tests.
- **Security:** `targetPosition` is client-supplied and feeds a `WHERE position >= ?` predicate. It
  is bounds-checked at the DTO (`@Min(0)`) and clamped server-side against the actual sibling count,
  so a large or negative value cannot be used to renumber outside the intended range.
</design_rationale>
