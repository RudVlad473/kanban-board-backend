<flat_dto_exception_justification>
`.planning/PROJECT.md` records: "DTOs are flat (no nested entity graphs) specifically to avoid
`LazyInitializationException` — the deferred `/full` endpoint DTO will need deliberate nested
structure, a departure from this pattern that should be justified explicitly."

**The justification.** The flat-DTO rule is not a stylistic preference; it is a defence against
`LazyInitializationException`, which occurs when a mapper touches an unfetched association *after*
the transaction that could have loaded it has ended. This endpoint does not weaken that defence, it
satisfies it by a different, stronger mechanism:

1. The entity graph is fetched **eagerly and explicitly**, in one chained `LEFT JOIN FETCH` query,
   so by the time any mapper runs there are no unfetched associations left to touch.
2. The mapping runs **inside** the `@Transactional` service method, and the method returns a fully
   materialised DTO tree, not an entity. Nothing lazy escapes into the serialisation layer.
3. The exception is **scoped to one endpoint and one DTO family** (`*FullResponseDTO`). The four
   flat DTOs are untouched, so the general rule still holds for every other route.

The alternative — keeping DTOs flat and having the client fan out — is exactly the cost
`docs/MOCKUP_FEATURE_GAP.md` §1.4 filed as a gap: four sequential HTTP round trips to render one
screen. Trading one documented, tested, single-endpoint exception for that is the right trade, and
this block is the explicit justification `PROJECT.md` asked for.
</flat_dto_exception_justification>

<design_rationale>
## Alternate approaches considered (required by CLAUDE.md GSD Execution Directives)

Two separable questions: how the graph is fetched, and how the DTO tree is assembled.

**Approach A (chosen): one chained `LEFT JOIN FETCH` JPQL query + MapStruct `uses` composition.**

**Approach B: a hand-written aggregation service — fetch board, fetch columns, fetch tasks per
column, fetch subtasks per task, assemble by hand.**

**Approach C: keep the naive `findById` and rely on Hibernate's lazy loading inside the transaction,
letting the mappers trigger the loads.**

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| A — fetch join + `uses` | **+** Exactly one prepared statement, assertable with the existing `countQueries` helper. **+** MapStruct already generates the loop-and-delegate shape for every other `List` field in this codebase, so the DTO half adds no new mechanism. **+** The leaf level reuses the existing `SubtaskMapper` untouched. **−** `uses` composition is new to this repository (no existing mapper uses it), so it is CITED from MapStruct's reference docs rather than copied from an in-repo precedent. | **PICKED.** It is the only option that actually delivers the endpoint's reason for existing. |
| B — hand-written aggregation | **+** No new MapStruct mechanism. **−** Reintroduces the N+1 fan-out this endpoint exists to eliminate, unless paired with the same fetch-join query anyway — in which case the query half is identical and only the assembly is more code. **−** Breaks the documented "MapStruct owns Entity-to-DTO mapping" convention. | **REJECTED.** Strictly more code for the same or worse result. |
| C — lazy loading inside the transaction | **+** Zero query authoring. **−** Costs 1 + 1 + N + M statements: one for the board, one for its columns, one per column for its tasks, one per task for its subtasks. On a realistic board that is dozens of round trips to save four. **−** Silently correct-looking; only a query-count assertion reveals it, which is exactly why task 2 exists. | **REJECTED.** It is the failure mode this endpoint exists to fix, wearing the endpoint's clothes. |

## Non-obvious trade-offs

- **Time complexity:** one statement instead of 1+1+N+M. The single query returns a row-multiplied
  cartesian-ish result (board rows repeated per column per task per subtask), so bytes-over-the-wire
  from the database grow multiplicatively even as round trips collapse to one. For a board of
  realistic size (a handful of columns, tens of tasks) this is an unambiguous win; for a pathological
  board it would not be, and that is the trade being made knowingly. `DISTINCT` is required on the
  query to de-duplicate the multiplied root rows.
- **`MultipleBagFetchException` — why it does not apply here.** Hibernate rejects fetching two or
  more `List` collections hanging off the *same* parent in one query. This query fetches a **linear
  chain** at three different nesting depths (board to its columns, column to its tasks, task to its
  subtasks), never two sibling lists from one parent, so the restriction is not engaged. If a second
  `List` association is ever added directly to `BoardEntity` and fetched here, this analysis stops
  holding — note that in the query's comment.
- **Memory:** the whole board graph is materialised in one heap-resident DTO tree. Bounded by one
  user's one board; no pagination is offered and none is needed at this scale.
- **Security:** a nested response discloses strictly more per request than any flat one, so the
  ownership check is more load-bearing here, not less. The service must load through the
  ownership-verified path before the fetch-join result is mapped.
- **Field-name trap:** `BoardEntity.column` and `ColumnEntity.task` are singular field names on
  `List`-typed fields — a real, existing inconsistency in this codebase, not a typo. MapStruct
  matches by name, so the new mappers need explicit source-to-target `@Mapping` annotations. Do not
  rename the entity fields; a JPA field rename with existing `mappedBy` references is out of scope
  and risks an unrelated regression.
</design_rationale>
