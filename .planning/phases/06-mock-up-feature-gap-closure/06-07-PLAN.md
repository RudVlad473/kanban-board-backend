<reversibility_analysis>
Changing `activity_log.event_id` from `uuid` to a string type is one-way in three compounding
senses, which is why this plan opens with a blocking decision checkpoint rather than proceeding:

1. **Schema:** the column type on a table holding real production rows changes, and the unique
   constraint on it is dropped and recreated. Reverting means another migration plus a reverse cast
   that cannot succeed — a Base36 Snowflake string is not parseable back into a UUID, so any row
   written after the cutover is unrecoverable into the old type.
2. **Registered Avro subjects:** all six subjects change their `eventId` field. Under Phase 4's
   BACKWARD compatibility policy (D-04), the registry governs what future shapes are accepted;
   reverting is itself a compatibility-checked change, not a `git revert`.
3. **Public API contract:** `ActivityLogResponseDTO.eventId`'s JSON type changes on the
   already-shipped, documented `GET /boards/{boardId}/activity` endpoint. There is no frontend
   consumer today, so the blast radius is currently zero — but that is a fact about right now, not a
   property of the change.

CONTEXT.md additionally instructs, verbatim, to "flag to the user if that broader decision
[on project-wide ID generation strategy] hasn't been made before implementing this in isolation."
The checkpoint below is that flag. The rating itself is carried on the task that walks through the
door, immediately after that checkpoint.
</reversibility_analysis>

<design_rationale>
## Alternate approaches considered (required by CLAUDE.md GSD Execution Directives)

**Approach A (chosen): reuse the existing `RandFlakeGenerator`, exposed through a thin injectable
component, and change `eventId`'s type to `String` everywhere.**

**Approach B: add a third-party Snowflake library and generate a `long`, storing `event_id` as
`bigint`.**

**Approach C: keep `UUID` as the type but generate UUIDv7 (time-ordered UUID) instead of v4.**

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| A — reuse `RandFlakeGenerator` | **+** `RandFlakeGenerator` already *is* a Snowflake-style generator: a 41-bit timestamp above 23 random bits, Base36-encoded, with a custom epoch — exactly what the todo asks for, already written, already used for every entity primary key in the project. **+** The todo says this "should probably follow whatever the broader decision on project-wide ID generation strategy lands on"; that decision is already made and shipped, it was simply scoped to primary keys. Reusing it *is* following it. **+** Zero new dependencies. **−** The type change from `UUID` to `String` ripples through the sealed interface, six records, six schemas, an entity, a repository method and a response DTO. | **PICKED.** Any option that does not reuse the existing generator creates a second ID scheme in a project that deliberately has one. |
| B — third-party Snowflake library, `bigint` column | **+** A `bigint` key has better index locality than any string. **−** Adds a dependency for ~15 lines the project already has. **−** Creates a second, differently-shaped ID scheme alongside the ULID/RandFlake primary keys — precisely the fragmentation the todo's own "follow the broader decision" caveat warns against. **−** A numeric key in JSON is a worse API contract than a string (precision loss in JavaScript above 2^53). | **REJECTED.** |
| C — UUIDv7 | **+** No type change anywhere: the column, the Avro logical type, the DTO and the repository method all stay as they are, making this by far the smallest and most reversible diff. **+** Time-ordered, which is the todo's actual ask. **−** Requires a UUIDv7 source; the project's `ulid-creator` dependency is a ULID library, so this needs verification and possibly a dependency. **−** Leaves two ID schemes (ULID primary keys, UUIDv7 event ids) rather than converging on one. | **REJECTED as the plan's default, but it is the strongest alternative and is offered as option-b at the checkpoint below** — a reviewer who weighs reversibility above scheme convergence should be able to choose it, because on that axis it genuinely wins. |

## Non-obvious trade-offs

- **Index locality — the actual point of the change.** A random UUID scatters inserts across the
  `uk_activity_log_event_id` B-tree, dirtying many pages per insert. A time-ordered key appends to
  the right-hand edge, so recently-written pages stay hot. This is a real, if modest, win on an
  insert-only table.
- **Sortability caveat, and why Base36 still works.** `RandFlakeGenerator` renders the value with
  `Long.toString(id, 36)`, which is **not** fixed-width — as the timestamp advances the string
  eventually gains a character. Base36 strings of *different* lengths do not sort correctly
  lexicographically (a shorter string sorts before a longer one that should follow it, but also
  before one that should precede it). At the current epoch the value is a stable width and will
  remain so for years, so ordering holds in practice. Do not build anything that *depends* on
  lexicographic ordering of `event_id`; the activity feed already sorts by `(createdAt desc, id
  desc)` on the row's own ULID and must keep doing so. Task 4 asserts the ordering property and
  documents this caveat next to the assertion.
- **Collision probability is unchanged in kind.** 23 random bits within a millisecond means
  same-millisecond collisions are possible, at the same probability they already are for every
  entity primary key in this project — `RandFlakeGenerator`'s own comment records this. The
  `uk_activity_log_event_id` constraint remains the backstop.
- **Consumer idempotency:** `ActivityLogRecorder` checks `existsByEventId` before every insert. That
  method's parameter type changes with the column. The dedupe semantics do not change at all — only
  the type of the key being compared.
- **Memory / storage:** a Base36 string of ~10-11 characters versus a 16-byte UUID. Marginally
  larger on disk; smaller in the JSON payload.
- **Sequencing:** this plan is in wave 4, after every other plan in the phase, specifically because
  RESEARCH.md's Pitfall 2 identified that interleaving this type change with plan 03's new sixth
  event record risks a half-migrated event package — five records on the old type and one on the new.
  Running fully after plan 03 means all six records exist before any of them change type.
</design_rationale>
