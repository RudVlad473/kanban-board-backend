<design_rationale>
## Alternate approaches considered (required by CLAUDE.md GSD Execution Directives)

Both open questions here — how the cascade is performed, and whether a new event type is warranted
— were pre-decided by D-05 and D-06. The genuine planner decision is the cascade *mechanism*.

**Approach A (chosen): `ColumnService.deleteById` calls the existing package-private
`TaskService.deleteAllByColumn(column)`, then removes the column row, then publishes the event.**

**Approach B: JPA cascade — annotate `ColumnEntity.task` with `cascade = CascadeType.ALL,
orphanRemoval = true` and let Hibernate walk the graph on `columnRepository.delete(column)`.**

**Approach C: a database-level `ON DELETE CASCADE` on the `tasks.column_id` and
`subtasks.task_id` foreign keys, added in a migration.**

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| A — reuse `deleteAllByColumn` | **+** D-05 names this method explicitly. **+** It is already a batched bulk-JPQL delete with a documented flush/clear afterwards, so the query count does not scale with task count. **+** `ColumnService.deleteAllByBoardId` already loops exactly this call per column — `deleteById` is literally the single-column case of code that already ships. **−** Bypasses `@Version` on tasks/subtasks (documented, accepted tradeoff already recorded in that method's Javadoc). | **PICKED.** It is the locked decision, and it is also the only option that does not change the behaviour of the board-delete path that already calls it. |
| B — JPA cascade annotations | **+** Declarative. **−** Changing `ColumnEntity.task`'s cascade settings alters `BoardService.deleteById`'s existing behaviour too, since that path walks the same association — a silent, untested change to a shipped delete path. **−** Reintroduces per-entity fetch-then-remove, i.e. the N+1 the batched delete exists to avoid. | **REJECTED.** Blast radius extends to an already-working path this plan is not supposed to touch. |
| C — database `ON DELETE CASCADE` | **+** Fastest at the database. **−** Hibernate's persistence context has no visibility into rows the database deleted behind its back, so anything still managed in the same transaction goes stale with no flush/clear to fix it — precisely the hazard `deleteAllByColumn`'s Javadoc documents. **−** Requires a migration that drops and recreates two foreign keys, for a behaviour Java already implements correctly. | **REJECTED.** Higher-risk schema surgery for no gain over A. |

## Non-obvious trade-offs

- **Time complexity:** the cascade is O(1) in statement count regardless of task count — one query
  to collect task ids, one bulk subtask delete, one bulk task delete, one column delete. It is O(n)
  in rows touched, which is unavoidable.
- **State invalidation:** `deleteAllByColumn` issues bulk JPQL that bypasses the persistence
  context, then flushes and clears it. Any entity reference held across that call in the same
  transaction is detached afterwards. Capture the ids needed for the event (`columnId`, `boardId`,
  `userId`) into locals BEFORE calling it — this is exactly the pattern `TaskService.deleteById`'s
  Javadoc already documents, and the reason it exists.
- **`@Version` bypass:** the bulk task/subtask deletes proceed even if a concurrent transaction
  bumped a task's version a moment earlier. This is the accepted delete-wins tradeoff already
  recorded in `TaskService.deleteAllByColumn`'s Javadoc — a delete racing a version-mismatched
  update correctly discards the update's effect on a row being removed anyway. Not re-litigated here.
- **Security:** the new route is the first column-level destructive operation. Ownership must be
  verified before anything is deleted, and per D-07 there is deliberately no second confirmation
  gate — the mock-up puts the confirm dialog client-side, and board delete already behaves this way.
- **Schema evolution:** adding a sixth event type is additive at the registry (a brand-new subject),
  so BACKWARD compatibility on the five existing subjects is unaffected. Under `RecordNameStrategy`
  the subject name is derived from the schema's full name, so no subject string is hardcoded anywhere.
</design_rationale>
