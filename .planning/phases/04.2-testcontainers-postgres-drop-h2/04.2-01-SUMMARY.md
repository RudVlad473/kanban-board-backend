# Phase 04.2 Plan 01: Testcontainers Postgres tracer Summary

**Proved Flyway V1-V4 + Hibernate `ddl-auto=validate` + Spring Session JDBC coexist against one real, imperatively-started `postgres:16` Testcontainers container, through a single new test class, with H2 and all ~25 existing test classes left completely untouched.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 2 completed
- **Files modified:** 3 (`build.gradle` + 2 new test classes)

## Accomplishments

- Added `org.testcontainers:postgresql` (unversioned, resolves to 1.21.0 via Spring Boot's BOM, same release train as the existing `:kafka`/`:redpanda`/`:junit-jupiter` lines)
- Created `AbstractPostgresContainerTest`, a third shared test ancestor: `api.version=1.44` pin fires first in its own static initializer, then a `@ServiceConnection static final PostgreSQLContainer<?> postgres` (`postgres:16`, matching `docker-compose.yml` exactly) is started imperatively — no `@Testcontainers`/`@Container` JUnit extension anywhere, consistent with the landmine already documented for the Kafka container
- Created `FlywaySchemaProvenanceTest` (extends the new base, `@TestPropertySource`-overrides `spring.flyway.enabled=true`/`ddl-auto=validate` TEMPORARILY) with four `@Nested` groups — `FlywayHistory`, `SchemaShape`, `FlywayOnlyArtifacts`, `SpringSessionCoexistence` — covering 9 assertions total, all passing on the first run
- Confirmed H2 and the pre-commit gate are both undisturbed: `./gradlew clean test` (208 tests, 0 failures) and `./gradlew fastTest` (153 tests, 0 failures) both green after the tracer landed
- Recorded three wall-clock numbers for 04.2-03's delta measurement (see below)

The pre-tracer H2 baseline (4m 48s / 199 tests) is the same-machine number 04.2-03 must compare its post-cutover full-suite delta against — not the ~232s figure in ROADMAP.md, which was measured in a different session (Phase 4 Plan 02). The +22s post-tracer delta is the isolated cost of one additional Postgres container start plus one extra Spring context (`FlywaySchemaProvenanceTest`'s 9 tests), which is useful signal but is *not* itself the cutover cost 04.2-03 measures.

**`fastTest` now requires Docker** — this is the first commit at which that is true. `fastTest` excludes `*E2ETest` classes, which does not exclude `FlywaySchemaProvenanceTest` (deliberately not `E2ETest`-suffixed: it is fast, and per D-03 every test needs Docker after the full cutover anyway, so there is nothing left for the suffix to protect). This is an intentional consequence of D-03, arriving one plan earlier than the full cutover.

**Pre-existing condition, not a regression from this phase:** `HistoricalActivityEventReconstructorTest` extends `AbstractKafkaContainerTest` but is not `*E2ETest`-suffixed, so `fastTest` was already starting a Redpanda container before this plan — the hook's "container-free" premise was already partly false. Confirmed present in the post-tracer `fastTest` run's test results. Fixing that naming is out of this phase's scope.

## Decisions Made

- Both contingencies the plan flagged (switching to `RANDOM_PORT` if `SpringSessionCoexistence` found zero session tables under `MOCK`; loosening `SchemaShape`'s nine-table assertion if the actual set differed) were written into the design but never triggered — the default `@SpringBootTest` `MOCK` web environment already ran Spring Session's initializer correctly, and the actual table set matched the expected nine exactly on the first run.

## Deviations from Plan

None - plan executed exactly as written. Both `containsExactlyInAnyOrder` assertions and the `FlywayOnlyArtifacts`/`SpringSessionCoexistence` checks passed without needing any of the plan's documented fallback paths.

## Issues Encountered

- The pre-commit hook's `fastTest` run (now Docker-backed and taking ~4 minutes) was killed once by the harness's 3-minute default Bash timeout mid-run, leaving a Windows file lock on `build/test-results/fastTest/binary/output.bin` from the orphaned Gradle daemon. Resolved by `./gradlew --stop` (stopped 2 daemons) followed by removing the locked directory, then re-running the commit with a longer timeout — the commit succeeded cleanly on retry with no code changes needed. Purely a tooling/environment hiccup, not a defect in the tracer.
