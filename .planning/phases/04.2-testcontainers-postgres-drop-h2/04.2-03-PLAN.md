## Approaches considered (project directive: 2 alternates + trade-off matrix)

The open decision here is **Testcontainers reuse**, which D-03 named as "the mitigation to evaluate"
for the pre-commit gate's new Docker requirement.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Measure first, default to NOT enabling reuse (picked)** | **Pros:** honours `docs/CODE_STYLE.md` rule 8 with no argument, adds nothing to maintain, and leaves a recorded number so the question can be reopened on evidence rather than re-litigated on feeling. **Cons:** if repeated local `fastTest` runs really are painful, developers pay that cost until someone reopens it. | Picked, subject to the measurement. D-01 already pins exactly one static container per JVM run, so container startup is paid once per `./gradlew` invocation regardless — reuse cannot speed up a single suite run at all, only a *second* invocation. That structurally caps the upside before any measurement is taken. |
| **B. Enable `.withReuse(true)` plus a project-local automated opt-in** | **Pros:** genuinely faster for a developer running `fastTest` repeatedly in one session. **Cons:** the environment-level opt-in is traditionally a per-machine `~/.testcontainers.properties` file, which is precisely the hand-edited, out-of-version-control setup step rule 8 forbids; the `TESTCONTAINERS_REUSE_ENABLE` environment-variable alternative is a MEDIUM-confidence claim (research Assumptions Log A2, sourced from a doc summary rather than primary text); and upstream documents reuse as experimental, unsuited to CI, and leaving containers running after the suite finishes. | Rejected unless the measurement says otherwise AND a mechanism is found that a fresh clone gets for free. A plan that adds `withReuse(true)` without answering "how does the opt-in get set on a fresh clone" has silently reintroduced a manual setup step. |
| **C. Weaken `fastTest` to spotless + compile so the hook needs no Docker** | **Pros:** instant commits, zero Docker requirement locally. **Cons:** gives up ArchUnit's `LayeringArchTest` and every unit/service test at commit time — exactly the enforcement the 2026-08-03 todo added on purpose. | Rejected, and rejected explicitly by D-03, which accepted the new Docker requirement rather than weaken the gate. Recorded here so it is not re-proposed. |

### Non-obvious trade-offs

- **Performance:** the number that matters is not total `fastTest` wall-clock but the *container-start
  fraction* of it. Testcontainers logs its own start duration per container; that line is the honest
  upper bound on what reuse could ever save, and it is what Task 1 extracts rather than inferring
  from totals.
- **Correctness risk of reuse:** a reused container keeps its data between `./gradlew` invocations.
  Combined with this phase's `@AfterEach` isolation model (D-02) — which only cleans what it knows
  about — a reused container would carry `spring_session` rows, dead-lettered state, and any table a
  future author forgets to add to the hook across runs. That converts a currently-deterministic suite
  into one whose behaviour depends on whether you happened to run it before. This is a real
  correctness argument against reuse, independent of rule 8, and it is stronger here than in a
  codebase using transactional rollback.
- **Security:** a reused container is a long-lived database process holding test credentials that
  outlives the test run by design. Small, but it is the opposite direction from ephemeral.
- **Documentation as a correctness surface:** `docs/CODE_STYLE.md` rule 4 is not decoration — it is
  the instruction a future test author (or agent) follows to decide what to extend and what to assert
  on. Leaving it saying "in-memory H2" would actively mis-instruct, which is why the doc pass is a
  task in this phase rather than deferred cleanup.
