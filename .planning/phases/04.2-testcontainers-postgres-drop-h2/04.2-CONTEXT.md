# Phase 04.2: Testcontainers Postgres, drop H2 - Context

**Gathered:** 2026-08-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Move the entire test suite's database substrate from in-memory H2 to a real PostgreSQL container, with the schema built by the same Flyway V1–V4 migrations that run in production. This is modernization Epic 5 (`docs/plans/backend-modernization/05-testcontainers.md`), pulled forward and inserted ahead of Phase 5 (Infra Migration). It collects the deferral Phase 04.1 made explicitly in its own D-04: "`application-test.properties` stays on `create-drop` … 'Flyway against Testcontainers' is Epic 5's job, not this phase's."

The reason it goes *before* Phase 5 rather than after: the V1–V4 migrations are currently verified only by 04.1-03's one-off manual clean-volume run against local docker-compose. CI has never executed them. Phase 5 points production at a brand-new Neon database and adds a pre-merge DDL verification gate, so shipping that cutover while migration correctness rests on a single manual run would make the cutover itself the first real test.

Covers: adding `org.testcontainers:postgresql`, a container base class both test hierarchies inherit, removing `com.h2database:h2`, and removing the test profile's `spring.flyway.enabled=false` and `spring.jpa.hibernate.ddl-auto=create-drop`. Does not cover: rewriting or renumbering the V1–V4 migrations themselves (04.1 D-01 made them immutable checksummed history), production schema ownership changes, OpenAPI polish (still Epic 3's other half), or anything in Phase 5.

</domain>

<decisions>
## Implementation Decisions

### Container topology
- **D-01:** One static PostgreSQL container in a shared base that **both** test hierarchies inherit — `AbstractAppTest` and `AbstractKafkaContainerTest`. Not behind `AbstractAppTest` alone, which is what `05-testcontainers.md` literally says. Scouting found `AbstractKafkaContainerTest` does not extend `AbstractAppTest`, yet its 9 subclasses persist `ActivityLogEntity`, so a container reachable only from `AbstractAppTest` would leave them without a datasource or force a second one. Lifecycle follows the precedent `AbstractKafkaContainerTest` already set here: an imperative `start()` in a static initializer, **not** the `@Testcontainers`/`@Container` JUnit 5 extension — that extension-driven singleton was already found unreliable across sibling classes in this environment (see `AbstractKafkaContainerTest`'s Javadoc and STATE.md's Phase 3 Plan 02 entry). — **Reversibility:** costly — the base-class shape is inherited by ~34 test classes; changing it later is a suite-wide edit.

### Test isolation
- **D-02:** Isolation stays exactly as it is — `AbstractAppTest`'s `@AfterEach userService.deleteAll()`. **No test-managed `@Transactional` rollback.** Rollback was considered and rejected on three verified grounds, none of which are Postgres-specific (all are true on H2 today):
  1. `RecordingActivityEventListener` (`src/test/java/com/vrudenko/kanban_board/support/RecordingActivityEventListener.java:19`) and the production `KafkaEventPublisher` (`src/main/java/com/vrudenko/kanban_board/config/KafkaEventPublisher.java:48`) are both `@TransactionalEventListener(phase = AFTER_COMMIT)`. A rolled-back test transaction never commits, so held events are discarded rather than delivered, and `ActivityEventPublicationTest` / `TaskMoveE2ETest` would fail by asserting on an empty list — a silent-looking failure that reads as if the publishing code broke.
  2. `AbstractAppTest.countQueries()` measures `Statistics.getPrepareStatementCount()` (used in `TaskServiceTest:39`, `OwnershipVerifierServiceTest:37`). A test-level transaction shares one persistence context across `@BeforeEach` and the act, so fixtures sit in the first-level cache and `findById()` stops hitting the database. CLAUDE.md chose this metric precisely *because* it catches `findById()`.
  3. `AbstractAppE2ETest` extends `AbstractAppTest` and drives a real server on a random port via REST Assured. The test thread's transaction never spans the HTTP request, so rollback provides those tests no isolation at all.
- **D-02a:** Because the schema is no longer dropped and recreated per Spring context, planning must verify that rows **not reachable from a `UserEntity`** are actually cleaned between tests — `activity_log` in particular, plus any dead-letter state. Under H2 this was masked; under a persistent container it is not. This is a gap to close, not an assumption to carry.

### Pre-commit gate
- **D-03:** `fastTest` keeps its `*E2ETest` exclusion and its role in `.githooks/pre-commit`, and now requires Docker. The exclusion still skips the 9 Kafka container classes, so the gate keeps covering ArchUnit's `LayeringArchTest` and every unit/service test — but the remaining ~25 classes now start a Postgres container, so the hook's original "container-free" premise is gone. Accepted deliberately rather than weakening the gate to spotless+compile, which would give up the enforcement the 2026-08-03 todo added on purpose. Testcontainers reuse is the mitigation to evaluate for local commit latency. — **Reversibility:** reversible — hook and Gradle task config, no schema or API impact.

### Spring Session tables
- **D-04:** Phase 04.1's D-02 stands unchanged — Flyway does **not** take ownership of `SPRING_SESSION`/`SPRING_SESSION_ATTRIBUTES`. `spring.session.jdbc.initialize-schema=always` keeps creating them, now against Postgres instead of H2. Folding them into Flyway was considered (this phase is the first time CI would catch session-schema drift) and rejected as scope widening from test substrate into production schema ownership, one phase after the opposite call was made. Planning must verify Spring Session's Postgres DDL coexists with Flyway's `flyway_schema_history` without ordering conflicts at context startup.

### Scope shape
- **D-05:** Full drop, not a hybrid. No H2 fallback profile is retained behind a flag. Two schema paths is exactly the drift `docs/CODE_STYLE.md` rule 8 exists to prevent, and keeping one would forfeit the phase's actual prize — that the migrations are exercised on every run.

### Claude's Discretion
- Exact name and package of the shared container base class, and whether `AbstractAppTest`/`AbstractKafkaContainerTest` inherit it or compose it — planner's call, subject to D-01's single-container, imperative-start constraint.
- Postgres image tag/version — should track what `docker-compose.yml` and the Phase 5 Neon target use, planner to confirm rather than guess.
- Whether Testcontainers reuse (`withReuse(true)` / `testcontainers.reuse.enable`) is enabled, and whether it is opt-in for local only — informed by measured `fastTest` wall-clock, per D-03.
- How `spring.datasource.*` is wired: `@ServiceConnection`, `@DynamicPropertySource`, or removing the properties from `application-test.properties` entirely. Note the hierarchy hazard already recorded in STATE.md (Phase 4 Plan 03): `@DynamicPropertySource` methods resolve subclass-first, superclass-last, so a subclass overriding a superclass's key always wins.
- Whether the H2-era `spring.jpa.properties.hibernate.generate_statistics=true` and the bounded Kafka producer timeouts in `application-test.properties` need revisiting — out of scope to change, in scope to not break.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `AbstractKafkaContainerTest` is a working, battle-tested template for exactly this problem in this repo: static container field, imperative `start()` in a static initializer, `@ServiceConnection` for the parts Boot supports, `@DynamicPropertySource` for the parts it doesn't, plus the Docker API-version pin. D-01's base class should mirror its shape rather than invent one.
- `AbstractAppTest.@AfterEach userService.deleteAll()` already does the cleanup work — isolation today does not actually depend on `create-drop`, which is what makes D-02 a genuine no-op rather than a compromise.
- V1–V4 already exist and were proven to apply cleanly against a wiped local Postgres volume in 04.1-03. This phase does not author schema; it points the suite at schema that is already correct.

### Established Patterns
- Test data comes from real service calls (`createUser()`, `createTask()`), not fixtures loaded into the DB — so nothing depends on H2-specific seeding.
- Query-count assertions use `getPrepareStatementCount()` deliberately, per CLAUDE.md, because `getQueryExecutionCount()` misses `findById()`. Any dialect-driven change in statement counts H2→Postgres will surface here first and must be understood, not silenced.
- CI runs `./gradlew test` then `./gradlew spotlessCheck` on `ubuntu-latest`.

### Integration Points
- `build.gradle` — add `org.testcontainers:postgresql`, remove `com.h2database:h2`.
- New shared container base class under `src/test/java/com/vrudenko/kanban_board/`.
- `src/main/resources/application-test.properties` — remove the H2 datasource, the Flyway disable, and `ddl-auto`.
- `.githooks/pre-commit` / `fastTest` — per D-03.

### Known Risks To Carry Into Planning
- ~25 fixture-heavy classes move off in-memory H2. Full-suite baseline is ~232s (measured in Phase 4 Plan 02); the delta must be measured and recorded, not estimated.
- H2→Postgres dialect differences may shift `getPrepareStatementCount()` results in `TaskServiceTest` and `OwnershipVerifierServiceTest`. Treat a changed count as a finding to explain, not a number to update.
- `application-test.properties` currently points `schema.registry.url` at a dead local address on purpose, so non-container classes fail fast. That deliberate arrangement must survive this phase.

</code_context>

<specifics>
## Specific Ideas

Operator's stated sequencing motivation: run this before Phase 5 so the Neon cutover happens against CI-exercised migrations rather than a single manual verification. That is the reason the phase was inserted at 04.2 rather than taken up after the milestone, and it is what makes "the suite executes V1–V4" the success criterion rather than merely "tests run on Postgres."

Test-managed `@Transactional` rollback was initially selected for isolation, then reversed after the three conflicts in D-02 were verified against the actual code. Recorded here so the option is not re-proposed downstream as an obvious optimization.

</specifics>

<deferred>
## Deferred Ideas

- Folding `SPRING_SESSION`/`SPRING_SESSION_ATTRIBUTES` into Flyway ownership — genuinely more attractive after this phase than before it, since CI would then catch session-schema drift. Own future phase; explicitly not taken here (D-04).
- Selective `@Transactional` rollback for the subset of service tests that assert neither events nor query counts — a real speed win, rejected for now because two coexisting isolation models is a trap for future test authors (D-02). Revisit only if measured suite time forces it.
- OpenAPI polish — still Epic 3's other half, untouched.
- Parallel test execution / Gradle `maxParallelForks` — a plausible answer to suite time, but it interacts with the single shared container and `deleteAll()` cleanup in ways this phase should not open up.
