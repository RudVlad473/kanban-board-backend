## User Constraints (from CONTEXT.md)

### Locked Decisions

**Container topology**
- **D-01:** One static PostgreSQL container in a shared base that **both** test hierarchies inherit — `AbstractAppTest` and `AbstractKafkaContainerTest`. Not behind `AbstractAppTest` alone, which is what `05-testcontainers.md` literally says. Scouting found `AbstractKafkaContainerTest` does not extend `AbstractAppTest`, yet its 9 subclasses persist `ActivityLogEntity`, so a container reachable only from `AbstractAppTest` would leave them without a datasource or force a second one. Lifecycle follows the precedent `AbstractKafkaContainerTest` already set here: an imperative `start()` in a static initializer, **not** the `@Testcontainers`/`@Container` JUnit 5 extension — that extension-driven singleton was already found unreliable across sibling classes in this environment (see `AbstractKafkaContainerTest`'s Javadoc and STATE.md's Phase 3 Plan 02 entry). — **Reversibility:** costly — the base-class shape is inherited by ~34 test classes; changing it later is a suite-wide edit.

**Test isolation**
- **D-02:** Isolation stays exactly as it is — `AbstractAppTest`'s `@AfterEach userService.deleteAll()`. **No test-managed `@Transactional` rollback.** Rollback was considered and rejected on three verified grounds, none of which are Postgres-specific (all are true on H2 today):
  1. `RecordingActivityEventListener` and the production `KafkaEventPublisher` are both `@TransactionalEventListener(phase = AFTER_COMMIT)`. A rolled-back test transaction never commits, so held events are discarded rather than delivered, and `ActivityEventPublicationTest` / `TaskMoveE2ETest` would fail by asserting on an empty list — a silent-looking failure that reads as if the publishing code broke.
  2. `AbstractAppTest.countQueries()` measures `Statistics.getPrepareStatementCount()`. A test-level transaction shares one persistence context across `@BeforeEach` and the act, so fixtures sit in the first-level cache and `findById()` stops hitting the database.
  3. `AbstractAppE2ETest` extends `AbstractAppTest` and drives a real server on a random port via REST Assured. The test thread's transaction never spans the HTTP request, so rollback provides those tests no isolation at all.
- **D-02a:** Because the schema is no longer dropped and recreated per Spring context, planning must verify that rows **not reachable from a `UserEntity`** are actually cleaned between tests — `activity_log` in particular, plus any dead-letter state. Under H2 this was masked; under a persistent container it is not. This is a gap to close, not an assumption to carry.

**Pre-commit gate**
- **D-03:** `fastTest` keeps its `*E2ETest` exclusion and its role in `.githooks/pre-commit`, and now requires Docker. The exclusion still skips the 9 Kafka container classes, so the gate keeps covering ArchUnit's `LayeringArchTest` and every unit/service test — but the remaining ~25 classes now start a Postgres container, so the hook's original "container-free" premise is gone. Accepted deliberately rather than weakening the gate to spotless+compile, which would give up the enforcement the 2026-08-03 todo added on purpose. Testcontainers reuse is the mitigation to evaluate for local commit latency. — **Reversibility:** reversible — hook and Gradle task config, no schema or API impact.

**Spring Session tables**
- **D-04:** Phase 04.1's D-02 stands unchanged — Flyway does **not** take ownership of `SPRING_SESSION`/`SPRING_SESSION_ATTRIBUTES`. `spring.session.jdbc.initialize-schema=always` keeps creating them, now against Postgres instead of H2. Folding them into Flyway was considered and rejected as scope widening from test substrate into production schema ownership, one phase after the opposite call was made. Planning must verify Spring Session's Postgres DDL coexists with Flyway's `flyway_schema_history` without ordering conflicts at context startup.

**Scope shape**
- **D-05:** Full drop, not a hybrid. No H2 fallback profile is retained behind a flag. Two schema paths is exactly the drift `docs/CODE_STYLE.md` rule 8 exists to prevent, and keeping one would forfeit the phase's actual prize — that the migrations are exercised on every run.

### Claude's Discretion
- Exact name and package of the shared container base class, and whether `AbstractAppTest`/`AbstractKafkaContainerTest` inherit it or compose it — planner's call, subject to D-01's single-container, imperative-start constraint.
- Postgres image tag/version — should track what `docker-compose.yml` and the Phase 5 Neon target use, planner to confirm rather than guess.

- Whether the H2-era `spring.jpa.properties.hibernate.generate_statistics=true` and the bounded Kafka producer timeouts in `application-test.properties` need revisiting — out of scope to change, in scope to not break.

### Deferred Ideas (OUT OF SCOPE)
- Folding `SPRING_SESSION`/`SPRING_SESSION_ATTRIBUTES` into Flyway ownership — genuinely more attractive after this phase than before it, since CI would then catch session-schema drift. Own future phase; explicitly not taken here (D-04).
- Selective `@Transactional` rollback for the subset of service tests that assert neither events nor query counts — a real speed win, rejected for now because two coexisting isolation models is a trap for future test authors (D-02). Revisit only if measured suite time forces it.
- OpenAPI polish — still Epic 3's other half, untouched.
- Parallel test execution / Gradle `maxParallelForks` — a plausible answer to suite time, but it interacts with the single shared container and `deleteAll()` cleanup in ways this phase should not open up.

## Summary

This phase swaps the test suite's database substrate from H2 in-memory (`create-drop`) to a real,
shared PostgreSQL Testcontainers instance running the same V1–V4 Flyway migrations production runs.
Every piece of this is either already proven elsewhere in this exact codebase (the Kafka/Redpanda
container pattern in `AbstractKafkaContainerTest`, the Flyway+`validate` pairing already live in
`application.properties` and proven end-to-end via `docker-compose.yml`) or is well-documented,
stable Spring Boot 3.5.0 / Testcontainers 1.21.0 behavior. There is no unknown technology here —
the work is disciplined transplantation of a pattern this repository already trusts, onto a second
resource (Postgres) and a second, sibling test hierarchy (`AbstractAppTest`).

The two genuine risks are not "will this work" but "what changes when it does": (1) query-count
assertions in `TaskServiceTest`/`OwnershipVerifierServiceTest` are dialect-sensitive and may shift
under Postgres — a finding to explain, not silently update; (2) `activity_log` has no FK to `users`
(confirmed by reading `V3__add_activity_log.sql` directly — see below), so `AbstractAppTest`'s
existing `@AfterEach userService.deleteAll()` cascade never reaches it. Under H2's per-context
`create-drop` this was invisible; under a persistent container it will leak state across tests
within the same class the first time two tests in one class both touch activity logging, unless the
cleanup hook is extended.

**Primary recommendation:** Build one new shared container base class (imperative `static { start()
}`, no `@Testcontainers`/`@Container`) that both `AbstractAppTest` and `AbstractKafkaContainerTest`
inherit from, wired via `@ServiceConnection` on a static `PostgreSQLContainer` field exactly as
`AbstractKafkaContainerTest` already does for its `RedpandaContainer`. Set
`spring.jpa.hibernate.ddl-auto=validate` in the test profile (matching prod exactly, not omitted),
delete the H2 datasource/`flyway.enabled=false`/`ddl-auto=create-drop` lines, add
`activityLogRepository.deleteAll()` to `AbstractAppTest.cleanup()`, and move the Docker API 1.44
pin up into the new shared base class so it fires before either container type starts.

### Pattern 1: Static `@ServiceConnection` container, imperative start
**What:** A `static final PostgreSQLContainer<?>` field annotated `@ServiceConnection`, started in a
plain `static { }` initializer block — no `@Testcontainers`/`@Container`.
**When to use:** Any container meant to be shared across every test class in one JVM run, where the
JUnit 5 extension's per-class singleton semantics have already proven unreliable in this environment.
**Example:**
```java
// Source: pattern already live in this repo — AbstractKafkaContainerTest.java:111-129,
// adapted for org.testcontainers.containers.PostgreSQLContainer, which Spring Boot Testcontainers
// supports out of the box (PostgresContainerConnectionDetailsFactory autoconfigures
// spring.datasource.* from it — no manual @DynamicPropertySource needed, unlike the Schema
// Registry case AbstractKafkaContainerTest already documents as the exception, not the rule).
public abstract class AbstractTestcontainersBase {
    static {
        // Moved up from AbstractKafkaContainerTest so it fires before EITHER container type
        // starts, regardless of which concrete test class the JVM initializes first.
        System.setProperty("api.version", "1.44");
    }

    @ServiceConnection
    static final PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>(DockerImageName.parse("postgres:16"));

    static {
        postgres.start();
    }
}
```

### Pattern 2: Test-profile Flyway/Hibernate ordering (already proven in this repo's prod profile)
**What:** With `spring.flyway.enabled=false` removed, Flyway runs its V1-V4 migrations against the
DataSource before Hibernate's `EntityManagerFactory` bean is created — this is Spring Boot's default
behavior (`spring.jpa.defer-datasource-initialization` defaults to `false`, meaning
script/migration-based DataSource initialization runs BEFORE any JPA `EntityManagerFactory` beans
are created) [CITED: docs.spring.io/spring-boot/how-to/data-initialization.html]. `ddl-auto=validate`
then only checks agreement — it never creates or alters.
**When to use:** This is not optional configuration for this phase — it is the same ordering already
governing `application.properties` in production, and already exercised end-to-end against a real
Postgres instance via `docker compose down -v && up --build`
[VERIFIED: .planning/STATE.md:90 — "Full V1-V4 history proven end-to-end via docker compose down -v
&& up --build: flyway_schema_history shows 4 rows (versions 1-4, all success=t)..."]. The test
profile should mirror prod's `ddl-auto=validate`
[CITED: docs/plans/backend-modernization/03-flyway-openapi.md:41-45 — "Set
spring.jpa.hibernate.ddl-auto=validate in prod once Flyway owns the schema — this is the correct
pattern (Hibernate validates, Flyway migrates)"], not omit it (Spring Boot's embedded-database
`create-drop` default does not apply to Postgres, which is never treated as embedded) and not leave
it at `create-drop` (that would defeat the entire point of this phase).
**Example:**
```properties
# src/main/resources/application-test.properties — after this phase
# spring.datasource.* lines REMOVED entirely (wired by @ServiceConnection instead)
# spring.flyway.enabled=false REMOVED (Flyway now runs V1-V4 for real)
spring.jpa.hibernate.ddl-auto=validate
```

### Pattern 3: Spring Session JDBC schema coexisting with Flyway
**What:** `spring.session.jdbc.initialize-schema=always` keeps running Spring Session's own
non-idempotent `schema-postgresql.sql` on every context startup
[VERIFIED: src/main/resources/application.properties:37-49, and its Javadoc-style comment: "What
actually makes `always` safe to re-run is Spring Boot's JdbcSessionDataSourceScriptDatabaseInitializer
setting continueOnError(true)"]. Spring Boot's own dependency-detection machinery orders any
`DataSourceScriptDatabaseInitializer`-family bean (which Spring Session JDBC's initializer is) to run
after Flyway/Liquibase automatically, without any explicit `@DependsOn` needed in this codebase
[CITED: Spring Boot's "Order detector for AbstractDataSourceInitializers" commit and
`DataSourceScriptDatabaseInitializer` API docs — see Sources; the general mechanism is documented
Spring Boot behavior, not something this project wires by hand].
**When to use:** No code change needed for this ordering — it already works, and has already been
exercised together (Flyway + `initialize-schema=always`, same `application.properties`) against a
real, persistent Postgres instance via the full `docker-compose.yml` stack in Phase 04.1's
verification run. This phase is the first time that combination runs inside a *Testcontainers*
Postgres rather than the docker-compose one, but the coexistence mechanism itself is unchanged.
**Recommendation for planning:** Add one assertion (in a smoke/E2E test, or as a `@BeforeAll` context
check) that both `flyway_schema_history` and `SPRING_SESSION`/`SPRING_SESSION_ATTRIBUTES` tables
exist after context startup, closing D-04's "planning must verify" requirement with an automated
check rather than a one-off manual read.

### Anti-Patterns to Avoid
- **`@Testcontainers`/`@Container` for the new Postgres container:** Already falsified in this exact
  repo for a sibling container type — do not reintroduce it for Postgres on the theory that "maybe it
  works for Postgres even though it didn't for Kafka." The failure mode (a second container silently
  started while cached Spring beans keep talking to the first) is a property of the JUnit extension
  lifecycle, not of Kafka specifically.
- **Leaving `ddl-auto` unset in the test profile:** Spring Boot's `create-drop` default only applies
  to embedded databases (H2/HSQL/Derby) it auto-detects; against a real Postgres URL, Hibernate's
  effective default is `none`, meaning schema mismatches would go completely unchecked — silently
  worse than today, not neutral.
- **A subclass-local `@DynamicPropertySource` overriding a superclass-registered property key:**
  Already a proven landmine in this codebase — subclass methods are discovered and invoked *before*
  superclass ones, so the superclass's registration always wins last and silently overwrites the
  subclass's intended override [VERIFIED: .planning/STATE.md:124 — "`@DynamicPropertySource` methods
  across a class hierarchy are discovered/invoked subclass-first, superclass-last (opposite of
  `@BeforeAll`) -- a subclass overriding the same property key as its superclass always loses"]. Not
  directly triggered by this phase (Postgres wiring uses `@ServiceConnection`, which has no such
  hierarchy hazard), but must be remembered if any future override of `spring.datasource.*` is ever
  attempted the same way the Schema Registry override was.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Wiring `spring.datasource.*` from a running container | Manual `@DynamicPropertySource` methods setting `spring.datasource.url/username/password` | `@ServiceConnection` on the `PostgreSQLContainer` field | Spring Boot ships a dedicated `PostgresContainerConnectionDetailsFactory` — the exact same category of built-in support `AbstractKafkaContainerTest` already relies on for `spring.kafka.bootstrap-servers` via `RedpandaContainerConnectionDetailsFactory` (see that class's own Javadoc) |
| Per-test cleanup of tables unreachable from `UserEntity`'s cascade | A new manual `TRUNCATE activity_log` or raw JDBC cleanup step | `activityLogRepository.deleteAll()` (already exists — `ActivityLogRepository extends JpaRepository`, which supplies `deleteAll()` for free) added to `AbstractAppTest.cleanup()` | No new repository method is needed; `JpaRepository` already provides it. Confirmed no FK exists from `activity_log` back to `users`/`boards` [VERIFIED: src/main/resources/db/migration/V3__add_activity_log.sql:5-13 — `board_id varchar(255) NOT NULL` and `user_id varchar(255) NOT NULL` carry no `CONSTRAINT fk_...` clause, unlike every other table in V1__init.sql, which all declare an explicit `FOREIGN KEY`], so `userService.deleteAll()`'s cascade genuinely cannot reach it |
| Detecting Flyway/Hibernate/Spring-Session startup ordering conflicts | A custom `@Order`/`@DependsOn` wiring between the three initializers | Nothing — rely on Spring Boot's existing, already-proven-in-this-repo ordering | Spring Boot already special-cases this ordering internally; hand-rolling it risks fighting the framework's own dependency graph rather than complementing it |

**Key insight:** every mechanism this phase needs (`@ServiceConnection`, Flyway-before-Hibernate
ordering, Spring Session's `continueOnError` initializer) is stock Spring Boot 3.5.0 behavior already
exercised somewhere else in this exact codebase. The actual new work is almost entirely
*subtraction* (H2, `flyway.enabled=false`, `create-drop`) plus one small *addition*
(`activityLogRepository.deleteAll()` in the cleanup hook) — resist the temptation to add
infrastructure this phase does not need.

## Common Pitfalls

### Pitfall 1: `activity_log` rows leaking across tests within the same class
**What goes wrong:** Two `@Test` methods in the same class that both cause an activity-log write
(directly, or indirectly via `RecordingActivityEventListener`/`ActivityLogRecorder`) will see each
other's rows once the schema stops being wiped between contexts, because `activity_log` has no FK
back to `users` and `userService.deleteAll()`'s cascade never reaches it.
**Why it happens:** H2's `create-drop` silently masked this — the whole schema (including
`activity_log`) was destroyed and rebuilt on every fresh `ApplicationContext`, which historically
happened often enough (before context caching stabilized across ~19 classes) that leakage was never
observed. A single, long-lived, shared Postgres container removes that accidental safety net.
**How to avoid:** Add `activityLogRepository.deleteAll()` alongside `userService.deleteAll()` in
`AbstractAppTest.cleanup()` (both the `@Autowired` field and the call). This is a one-line, purely
additive change to an existing, well-understood method.
**Warning signs:** A test asserting an exact count of activity-log rows for a board (e.g.
`ActivityReadE2ETest`) that only fails intermittently, or fails only when run as part of the full
suite but passes in isolation — the classic cross-test-pollution signature.

### Pitfall 2: Query-count assertions silently drifting under a different SQL dialect
**What goes wrong:** `TaskServiceTest.DeleteAllByColumnIdQueryCountTest` and
`OwnershipVerifierServiceTest.QueryCountTest` assert exact `getPrepareStatementCount()` values
[VERIFIED: src/test/java/com/vrudenko/kanban_board/service/TaskServiceTest.java:33-51 — asserts
`populatedColumnQueryCount).isEqualTo(emptyColumnQueryCount + 2)`; src/test/java/com/vrudenko/kanban_board/service/OwnershipVerifierServiceTest.java:30-44
— asserts `queryCount).isEqualTo(1)`]. H2 and Postgres can differ in how Hibernate batches identifier
generation, sequence/version-column handling, or statement caching, which could change these counts.
**Why it happens:** These assertions were written and last calibrated against H2's dialect; nothing
about them is Postgres-aware.
**How to avoid:** Run the full suite once against the new Testcontainers Postgres setup and diff the
actual counts against current values before touching the assertions. If a count changed, the plan
must document *why* (a real dialect difference — cite it) rather than mechanically updating the
expected number to whatever the new run produces. Silently rewriting the assertion to match new
output defeats the entire purpose of these tests (per CLAUDE.md's own stated rationale for using
`getPrepareStatementCount()` over `getQueryExecutionCount()`).
**Warning signs:** A CI failure on these two specific test classes with no other suite changes is the
expected first signal, not a surprise to be redirected around.

### Pitfall 3: Reuse silently violating CODE_STYLE rule 8
**What goes wrong:** Testcontainers reuse (`.withReuse(true)` + the environment-level opt-in) is
tempting for `fastTest`/pre-commit latency (D-03's stated mitigation to evaluate), but its
environment-level opt-in traditionally requires a per-machine `~/.testcontainers.properties` file —
exactly the kind of manual, host-level, out-of-version-control step CODE_STYLE rule 8 forbids.
**Why it happens:** Reuse is deliberately gated behind two separate opt-ins (code-level `withReuse`
+ environment-level) specifically so CI and casual local runs don't accidentally leave containers
running forever [CITED: java.testcontainers.org/features/reuse/ — "not suited for CI usage... still
experimental... containers won't stop after all tests are finished"].
**How to avoid:** The environment-level opt-in also accepts the `TESTCONTAINERS_REUSE_ENABLE=true`
environment variable, not only the properties file [CITED: java.testcontainers.org/features/reuse/].
An environment variable can be exported from a project-local, version-controlled script (e.g. a
Gradle `init.gradle` snippet, or documented in a `.env`-style file already read by tooling) without
requiring a developer to hand-edit a file in their home directory — but this still needs a concrete
mechanism decided at plan time, not assumed to "just work" the same way `.withReuse(true)` alone
would suggest. If no clean automated mechanism is found, the honest call per rule 8 is: do not enable
reuse, and instead measure whether the ~232s baseline delta (this phase's actual measured cost) makes
`fastTest` latency a real problem before spending effort here — D-03 already frames reuse as "the
mitigation to evaluate," not a foregone requirement.
**Warning signs:** A plan that adds `.withReuse(true)` without an explicit, automated answer to "how
does `testcontainers.reuse.enable` get set on a fresh clone" has silently reintroduced a manual setup
step.

### Pitfall 4: Assuming `docker-compose.yml`'s Postgres port remap (5433) matters here
**What goes wrong:** `docker-compose.yml` publishes Postgres on host port 5433, not 5432, specifically
to dodge a native Windows Postgres service already bound to 5432
[VERIFIED: docker-compose.yml:8-15]. A developer or planner might assume the Testcontainers Postgres
needs the same remap.
**Why it happens:** Pattern-matching to the adjacent, well-documented docker-compose workaround.
**How to avoid:** Testcontainers containers get dynamically assigned host ports by default (Docker
picks a free ephemeral port, and `@ServiceConnection` resolves the actual mapped port at runtime) —
there is no fixed-5432-host-port exposure to collide with the native service in the first place. No
action needed; this is a non-issue for the Testcontainers path specifically, unlike the
docker-compose path.

## Open Questions

1. **Exact final query-count numbers for `TaskServiceTest`/`OwnershipVerifierServiceTest` under Postgres**
   - What we know: The current H2-calibrated expected values (`emptyColumnQueryCount + 2`, and `1`
     respectively) are documented and verified in this research.
   - What's unclear: Whether Postgres's dialect produces the same counts. This is genuinely
     undeterminable without running the suite against the container — no amount of documentation
     research substitutes for the actual run.
   - Recommendation: The plan should include a task that runs the full suite once early, captures
     actual counts, and only then decides whether the assertions need updating (with a documented
     reason) or are unaffected.

2. **Whether Testcontainers reuse is worth enabling at all, given the rule 8 tension**
   - What we know: D-03 frames it as "the mitigation to evaluate," not a requirement; the ~232s
     H2 baseline is the number to beat/compare against.
   - What's unclear: How much of the container-per-suite (not per-class — one shared container) cost
     is actually container *startup* versus per-test fixture/query volume. Since D-01 already locks
     in exactly ONE static container for the whole JVM run (not per-class), container startup cost is
     paid once regardless of reuse — reuse would only help across separate `./gradlew` invocations
     (e.g. repeated local `fastTest` runs during active development), not within a single suite run.
   - Recommendation: Measure the actual full-suite delta first (this phase's own success criterion
     requires recording it against the ~232s baseline anyway). Only pursue reuse if repeated local
     `fastTest` invocations during a single dev session are the actual pain point, and only with a
     concrete, rule-8-compliant automation mechanism identified — not by default.
