# Phase 04.2 Plan 02: Cutover to Postgres Summary

**Cut the entire test suite off H2 onto the shared PostgreSQL 16 container proven in Plan 01 -- both test hierarchies plus the two orphan `@SpringBootTest` classes now boot against Flyway-built schema, `com.h2database:h2` is gone from the build entirely, the `activity_log` cross-test isolation gap is closed, and the full suite finished ~19s FASTER on the container than the H2 baseline it replaces.**

## Performance

- **Duration:** ~55 min
- **Tasks:** 3 completed (Task 4 was a checkpoint, approved by the operator with no code changes)
- **Files modified:** 9 modified, 1 created

## Accomplishments

- `application-test.properties`: removed the H2 datasource block, removed
  `spring.flyway.enabled=false`, set `spring.jpa.hibernate.ddl-auto=validate` -- the test
  profile now carries production's exact schema-management posture
- `AbstractAppTest` and `AbstractKafkaContainerTest` both now extend
  `AbstractPostgresContainerTest`; the Docker `api.version=1.44` pin moved up into the shared
  superclass and still fires before either container type starts (JVM superclass-first static
  init order)
- The two orphan `@SpringBootTest` classes with no prior base class --
  `KanbanBoardApplicationTests` and `ActivityEventAvroMapperTest` -- now extend
  `AbstractPostgresContainerTest` too, since the test profile no longer names any datasource
- `FlywaySchemaProvenanceTest`'s temporary `@TestPropertySource` override from Plan 01 is
  deleted; it now asserts against the profile's own configuration with no overrides
- Closed the `activity_log` isolation gap (D-02a): `AbstractAppTest.cleanup()` now also calls
  `activityLogRepository.deleteAll()`, guarded by a new `ActivityLogCleanupIsolationTest` whose
  falsification was verified manually (temporarily commenting out the call failed exactly 1 of
  its 2 structurally-identical test methods; restoring it, both passed)
  isolation is still `@AfterEach` deletion -- no `@Transactional` rollback was introduced
  anywhere (D-02 stands)
- Repaired the two assertions that were silently coupled to H2's identifier-casing behavior:
  `SessionPersistenceE2ETest.SchemaCreation` now queries `information_schema.tables` for
  lower-case `spring_session`/`spring_session_attributes` names (PostgreSQL folds unquoted
  identifiers to lower case, the opposite of H2); `UserPersistenceE2ETest`'s comments were
  corrected to attribute the NOT NULL constraint to `V4__add_password_hash_not_null.sql` and
  the identifier casing to PostgreSQL's folding plus `ColumnMapRowMapper`'s case-insensitive
  row lookup (the SQL itself needed no change)
- `com.h2database:h2` deleted outright from `build.gradle` -- no fallback, no guard, no
  commented-out line (D-05). Confirmed absent from the resolved `testRuntimeClasspath`
- Stale H2 references in the `fastTest`/`rehearseHistoricalSchemas` task comments corrected to
  describe the per-run Testcontainers PostgreSQL database
- Full suite run and timed on the container: **210 tests, 0 failures, 0 errors, 4m51s (291s)**

| Post-tracer H2 (04.2-01, like-for-like basis) | `./gradlew clean test` | BUILD SUCCESSFUL | 5m 10s (310s) | 208, 0 failures |
| **Post-cutover, this plan (real Postgres container)** | `./gradlew clean test` | BUILD SUCCESSFUL | **4m 51s (291s)** | **210, 0 failures** |
| **Delta vs. post-tracer H2 (like-for-like)** | -- | -- | **-19s, -6.1% (FASTER)** | +2 tests |

**The duration result is counterintuitive and is the headline of this plan.** The container run
finished faster than the H2 baseline it is compared against, not slower. The +2 test-count
difference (208 -> 210) is exactly `ActivityLogCleanupIsolationTest`'s two new methods added in
Task 2; no other test count changed between the two runs.

This is presented as an observation with a **hypothesis, not a settled conclusion**: the likely
mechanism is that H2's `create-drop` rebuilt the schema from scratch on every one of the ~30
Spring context creations across the run, while Flyway now migrates the schema ONCE against a
container shared for the entire JVM lifetime -- so a genuine per-context Hibernate DDL rebuild
against in-memory H2 appears to cost more wall-clock than a single Flyway migration plus the
per-test-method row-level `@AfterEach` cleanup this plan relies on instead. **Wave 3's dedicated
measurement task should confirm or correct this reading** -- it is not independently verified
here beyond the raw before/after numbers.

**Superseded stale baseline, for wave 3's doc-correction task:** the "~232s baseline" quoted in
`04.2-CONTEXT.md` and `ROADMAP.md` was measured in a different session (Phase 4 Plan 02) and was
already flagged as stale by 04.2-01-SUMMARY.md. It remains stale here. The authoritative,
same-machine, same-session figures for wave 3 to write into both docs are: **4m48s/199 tests
pre-tracer, 5m10s/208 tests post-tracer, 4m51s/210 tests post-cutover.**
