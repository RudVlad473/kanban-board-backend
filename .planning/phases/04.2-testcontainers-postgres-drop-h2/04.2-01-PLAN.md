<objective>
Prove, end-to-end and on one thin path, that this repository's test suite *can* run against a real
PostgreSQL container whose schema is built by the production Flyway migrations — before anything is
cut over.

Purpose: this phase's hard part is not "add a dependency". It is whether four separate mechanisms
coexist inside one Spring test context against one container: Testcontainers lifecycle, Flyway
V1–V4, Hibernate `ddl-auto=validate` against the migrated schema, and Spring Session JDBC's own
non-idempotent schema initializer. If they do not, every downstream edit is wasted. This plan wires
exactly one test class through all four and verifies it, leaving H2 and all ~25 existing test classes
completely untouched.

Output: a shared container base class both hierarchies will inherit in 04.2-02, a permanent
schema-provenance test that is this phase's actual success criterion in executable form, and a
recorded same-machine H2 baseline.
</objective>

<design_alternatives>
## Approaches considered (project directive: 2 alternates + trade-off matrix)

The decision under review here is **how the container reaches the test contexts, and how thin the
first slice is**. D-01 already locks *one static container, imperative start, shared by both
hierarchies*, so the container topology itself is not re-litigated — what is open is the wiring
mechanism and the tracer's blast radius.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. New third ancestor + `@ServiceConnection`, tracer scoped to ONE new test class (picked)** | **Pros:** the four coexisting mechanisms are proven before ~25 classes and 6 files move; `@ServiceConnection` is Spring Boot 3.1+'s sanctioned wiring for `PostgreSQLContainer` and carries no `@DynamicPropertySource` hierarchy hazard; a failure costs one commit. **Cons:** for the length of this one plan the repo holds two schema paths (H2 profile + the tracer's overridden context), which is exactly the drift D-05 dislikes. | Picked. D-05 forbids *retaining* a hybrid — no fallback profile survives the phase — it does not forbid a single intermediate commit whose entire purpose is to falsify the design cheaply. The two `@TestPropertySource` overrides that create the temporary second path are deleted in 04.2-02 Task 1, and that deletion is an acceptance criterion there, so the hybrid cannot survive by neglect. |
| **B. Cut everything over in one commit (base class + both hierarchies + properties + H2 removal), no tracer** | **Pros:** no intermediate hybrid at all; fewest commits. **Cons:** if Flyway/Hibernate/Spring-Session coexistence fails, or `validate` rejects the migrated schema, the failure arrives with 6 files changed and ~30 test classes red at once — the "which of the four mechanisms broke" question becomes a bisect instead of a read. | Rejected. This is precisely the failure mode tracer-first exists to prevent, and the phase's own carried risk ("~25 fixture-heavy classes move off in-memory H2") names it. |
| **C. `@DynamicPropertySource` wiring `spring.datasource.url/username/password` by hand** | **Pros:** no reliance on Spring Boot's connection-details machinery; visually explicit. **Cons:** more code for a container type Spring Boot ships a dedicated factory for; and it walks straight into the landmine already recorded in STATE.md (Phase 4 Plan 03) — `@DynamicPropertySource` methods resolve subclass-first/superclass-last, so any future subclass override of a datasource key would silently lose to this superclass. | Rejected. `@DynamicPropertySource` stays correct where it is already used (`schema.registry.url`) precisely *because* no `ConnectionDetails` type exists for a schema registry. Postgres has one. |

### Non-obvious trade-offs

- **Performance:** one container per JVM run, not per class — container startup cost is paid once and
  is `O(1)` in the number of test classes. The cost that *does* scale is per-test fixture SQL over a
  TCP socket instead of an in-process H2 call; that is the real source of any suite-time regression
  and is why 04.2-03 measures rather than estimates. Testcontainers reuse cannot help inside a single
  run (the container already starts once); it could only help *across* separate `./gradlew`
  invocations — evaluated in 04.2-03, not assumed here.
- **Context-cache pressure:** adding a `@ServiceConnection`-bearing superclass changes the Spring
  `ApplicationContext` cache key via a new `ContextCustomizer`. Because the customizer is identical
  for every class that inherits it, the existing context-sharing across `AbstractAppTest` subclasses
  is preserved rather than fragmented. Fragmenting it would multiply Flyway runs and context builds —
  worth watching in the duration measurement.
- **State-invalidation:** H2 `create-drop` gave an accidental per-context schema wipe. A long-lived
  container removes that safety net for any table not reachable from `userService.deleteAll()`'s
  cascade. This plan does not yet expose that risk (nothing is cut over), but it is why 04.2-02 Task
  2 exists and why it is a first-class task, not an incidental edit.
- **Security:** net positive and confined to test scope. Removing the test profile's
  schema-management divergence from production (`ddl-auto=create-drop` + Flyway disabled, versus
  production's `validate` + Flyway-owned) closes a configuration-drift gap (ASVS V14) that currently
  hides migration defects until a real Postgres sees them — which, per the phase's own framing, would
  otherwise first happen during Phase 5's Neon cutover.
</design_alternatives>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Test JVM -> Docker daemon | Testcontainers speaks to the local Docker daemon over a named pipe / socket; a malicious or wrong image would execute on the developer's or CI runner's host |
| Test JVM -> containerised PostgreSQL | Ephemeral, host-port-mapped database holding only generated test fixtures; no production data ever reaches it |
| Build -> Maven Central / Confluent repo | A new test-scope dependency is resolved and executed at test time |
