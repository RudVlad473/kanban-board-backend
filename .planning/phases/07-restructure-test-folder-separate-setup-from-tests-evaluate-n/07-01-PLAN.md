<tradeoffs>
## Approach considered A — one flat `support/` package (CONTEXT.md's own illustrative example)

## Approach considered B — three-way split by concern (`containers/`, `fixtures/`, `listeners/`) — CHOSEN

## Approach considered C — leave fixtures in place, only add a marker/Javadoc convention

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — flat `support/` | Pro: smallest diff, one directory to remember. Con: puts "things you extend" (`Abstract*`) next to "things you autowire" (`RecordingActivityEventListener`), and puts pure Testcontainers lifecycle next to app-domain fixture data — exactly the mixed-organizing-principle problem the source todo complains about | Rejected. D-01 explicitly asks for "one location, categorized within it," and CONTEXT.md marks the exact boundary as Claude's discretion |
| B — three-way split | Pro: each folder has one answerable question ("does this start a container / build app state / observe events?"); matches what the five files actually do, verified by reading them. Con: three directories for five files can read as over-structured today | **Picked.** Matches RESEARCH.md's file-by-file analysis; the split lines are the same lines the class hierarchy already draws (`AbstractPostgresContainerTest` knows nothing about `UserService`; `AbstractAppTest` knows nothing about Docker) |
| C — convention only | Pro: zero churn, zero import blast radius. Con: does not answer the todo at all — the files remain interspersed, which is the whole complaint | Rejected. D-04 locks this phase to executing, not recommending |

**Non-obvious trade-offs:**
- **Import blast radius is asymmetric, and the compiler only half-warns.** 22 files hold an explicit
  import of one of the five classes (mechanical path edit). The ~25 files currently sharing the root
  package with `AbstractAppTest`/`AbstractAppE2ETest`/`AbstractPostgresContainerTest` hold **no import
  at all** — same-package implicit visibility — and need a brand-new import line. Both cases fail
  `compileTestJava` loudly, so neither is a silent risk, but the second class of edit is invisible to
  a naive find-and-replace over import lines.
- **Visibility, checked not assumed.** `AbstractPostgresContainerTest.postgres` and
  `AbstractKafkaContainerTest.kafka` are both package-private `static final` fields. Moving either
  class across a package boundary would break any external reader. A fresh grep across the test tree
  found **zero** readers outside each declaring class (only Javadoc mentions), so no visibility
  widening is needed. Do not widen them "just in case" — that would advertise a field the design
  deliberately keeps internal.
- **Spring component scan, not the compiler, is what could break the listener.**
  `RecordingActivityEventListener` is a real `@Component`. `support.listeners` stays inside
  `KanbanBoardApplication`'s scan root, so it is still discovered — but a compile-green build proves
  nothing about that. Task 2 runs `ActivityEventPublicationTest` specifically to prove it at runtime.
- **`@DynamicPropertySource` discovery across a package boundary.** `AbstractKafkaContainerTest`'s
  registrar method is package-private `static`; its 9 subclasses currently share its package and will
  not after the move. Spring discovers these reflectively up the class hierarchy, so this should hold,
  but "should" is not "does" — task 2 runs one real Kafka E2E class rather than trusting compilation.
- **`AbstractAppMockMvcTest` carries no class-level `@SpringBootTest`/`@AutoConfigureMockMvc`.** This
  matches the existing precedent: `AbstractAppE2ETest` carries no `@SpringBootTest` either — every
  concrete subclass declares it. Relying on inheritance of `@AutoConfigureMockMvc` through an abstract
  base is exactly the kind of framework-behaviour assumption this phase is supposed to stop making.
</tradeoffs>
