<objective>
Downgrade the theme-persistence class and the activity-read class from the real-socket RestAssured
tier to the in-process MockMvc tier (D-03, verdict-table rows 15 and 16).

Purpose: neither needs a socket. The activity class seeds its rows directly through the repository and
asserts pagination and sort order — its own Javadoc states it needs no broker. The theme class asserts
status codes, JSON bodies and a logout-then-re-signin round trip, all of which MockMvc reproduces
provided the session cookie is relayed by hand.

The theme class is the subtler of the two: its logout round trip is the entire proof that the
preference lives in the users table rather than in the session, and it also signs a *second*,
independently-created user in to prove per-user isolation. Both of those need real session cookies, so
this class must use the real-signin relay throughout — the same discipline RESEARCH.md's Pitfall 2
imposes on the security classes, applied here for the same reason.

Output: two converted files, same coverage, one tier cheaper.

Zero production-code changes: `src/main/java` is untouched by this plan.
</objective>

<tradeoffs>
## Approach considered A — replace the theme class's logout round trip with two independent authenticated reads

## Approach considered B — keep the logout round trip and relay real session cookies — CHOSEN

## Approach considered C — keep the theme class on the real-socket tier

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — drop the logout | Pro: simplest possible conversion, no cookie handling at all. Con: deletes the specific evidence this class exists to produce. Two fresh authentications happening to see the same value is weaker than proving the value survives an explicit server-side session teardown, and the test would no longer assert that the two sessions differ | Rejected. This is scope reduction disguised as a conversion |
| B — real cookies, logout preserved | Pro: the test proves exactly what it proved before; the second-user isolation case also keeps working, since it needs a distinct session for a distinct principal. Con: the conversion is more careful than the other downgrades in this phase | **Picked** |
| C — leave it on the socket tier | Pro: zero risk to this class. Con: RESEARCH.md read it in full and found no socket-specific assertion; the cookie-relay idiom needed here is already proven by plan 07-01 and used by plan 07-02 | Rejected. The stated reason for KEEP would be "conversion is fiddly", which is not one of the three legitimate reasons to defer work |

**Non-obvious trade-offs:**
- **Logout must actually clear the session server-side under MockMvc, or the test passes vacuously.**
  The round trip is only meaningful if the second signin genuinely mints a new session. The existing
  assertion that the two cookie values differ is what detects that, and it must be carried across —
  if it were dropped, a logout that silently did nothing would still leave the test green.
- **Cookie values are Base64-encoded by the cookie serializer.** Compare cookie values to each other,
  never to a session-id column value. This is documented in the session tests and applies identically
  here.
- **Two signins per principal is the live ceiling.** The theme round trip signs the same user in twice
  within one test method, which is exactly at the limit. Do not add a third signin for that user
  anywhere in that method — a rejected third signin surfaces as a status that reads like a credentials
  bug.
- **The second user is created through the service layer, not the signup route, and with an explicit
  password.** That is deliberate: the fixture helper that creates arbitrary users does not expose a
  usable password. The conversion must keep using the explicit-password overload and the
  email/password form of the cookie helper for that user.
- **The activity class's independence from Kafka is an asserted property, not an accident.** Its rows
  are seeded straight into the activity-log repository precisely so the read API can be tested without
  a broker. Nothing in this conversion may introduce a Kafka container dependency, and the class must
  not gain the Kafka container base as an ancestor.
</tradeoffs>
