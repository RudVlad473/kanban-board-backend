<tradeoffs>
## Approach considered A — convert all three in one task

## Approach considered B — one task per class, smallest first — CHOSEN

## Approach considered C — split the move class across two plans because of its size

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — one task | Pro: one test run at the end. Con: ~1,100 lines of translation before any feedback; a systematic translation error would be discovered three files late | Rejected |
| B — one task per class, ascending size | Pro: the smallest class validates the translation pattern in this package before the 500-line move class is touched; each task has its own runnable gate. Con: three test runs instead of one | **Picked** |
| C — split the move class out | Pro: smaller plans. Con: the move class shares no files with the other two, so splitting buys no parallelism, and it would separate the event-listener assertions from the sibling task conversions that inform them | Rejected |

**Non-obvious trade-offs:**
- **"ConcurrentConflict" is a misnomer, and that is load-bearing.** The move class's nested group of
  that name issues two sequential requests to prove a stale-version conflict, not two threads racing.
  Had it been genuinely concurrent it would have been a KEEP like `BoardCreationE2ETest`. Read the
  body, not the group name, and if any group in these three files turns out to spawn threads or
  submit to an executor, stop and report it rather than converting it.
- **Event-listener assertions are tier-independent, so they must not change.** The recording listener
  is a real `@Transactional` Spring component registered in the application context. It observes
  after-commit events identically whether the request arrived over a socket or through MockMvc.
  Rewriting those assertions during the conversion would be pure churn and would obscure whether the
  conversion preserved behaviour.
- **After-commit event delivery still needs a committed transaction.** These assertions work today
  because the fixture base deliberately uses per-test deletion rather than transactional rollback —
  a rolled-back test transaction never commits and never fires an after-commit listener. Nothing in
  this conversion may introduce a test-managed `@Transactional` annotation on these classes.
- **Version fields are `Long` and compared exactly.** Optimistic-lock assertions compare precise
  version numbers before and after each write. An extra request inserted by the conversion (for
  example an accidental duplicate signin against a versioned resource) would not change a version,
  but any accidental extra write would. Translate one-for-one.
</tradeoffs>
