<tradeoffs>
## Approach considered A — merge first at the real-socket tier, downgrade the merged file afterwards

## Approach considered B — merge and downgrade in one edit — CHOSEN

## Approach considered C — downgrade the two E2E classes, leave three separate files

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — merge, then downgrade | Pro: each step is individually smaller and separately reviewable. Con: produces an intermediate committed state where one file mixes RestAssured and MockMvc dispatch, and every RestAssured chain then gets rewritten a second time | Rejected. This is exactly RESEARCH.md Pitfall 3, and it does the translation work twice |
| B — one edit | Pro: each source chain is translated exactly once; the merged file is single-tier from birth; the pre-existing setup duplication in `AuthenticationControllerTest` disappears as a side effect rather than being carried through an intermediate state. Con: one larger diff to review | **Picked.** The two operations touch the same lines, so splitting them creates work rather than reducing risk |
| C — downgrade only, no merge | Pro: smallest diff. Con: leaves D-02's single unconditionally-justified merge candidate unexecuted, and leaves `AuthenticationControllerTest` still duplicating the fixture base's port/cookie wiring field-for-field | Rejected. D-02 and D-04 together require approved merges to actually land in this phase |

**Non-obvious trade-offs:**
- **Security-coverage risk is the real risk here, not compile risk.** The concurrent-session ceiling
  and session-fixation rotation are enforced by an explicit
  `sessionAuthenticationStrategy.onAuthentication(...)` call inside `AuthenticationController`. A
  downgraded test that authenticates by injecting a principal never reaches that call, compiles fine,
  and passes fine — while proving nothing. The falsification probe in task 3 is the only thing that
  distinguishes "the test still works" from "the test still passes."
- **Session-row bookkeeping is delta-based for a reason.** `SPRING_SESSION` has no foreign key to
  users, so the fixture base's per-test cleanup never clears those rows and they accumulate for the
  whole JVM run. The existing assertions are written as before/after deltas and set differences
  precisely because of this. Rewriting any of them as an absolute count during the merge would make
  them order-dependent and flaky. Carry the delta idiom across verbatim.
- **Two signins per principal is the hard ceiling.** `maximumSessions(2)` is enforced live against
  `SPRING_SESSION.PRINCIPAL_NAME`. Merging tests into one file does not change this (each test method
  still gets fresh fixture users), but any *new* helper that signs in more than twice for the same
  user inside one test method will be rejected with a 401 that reads like a credentials bug.
- **Cookie values are Base64-encoded by the cookie serializer.** They must be compared to each other,
  never to a `SESSION_ID` column value. Both source classes document this; the merged file must keep
  those comparisons as written.
</tradeoffs>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated HTTP client → signin/signup endpoints | The boundary these tests exist to guard. Credentials cross it, and a session is minted on success. |
| session cookie → authenticated request | The relay this plan rebuilds under MockMvc. If the relay is faked (injected principal), the boundary is never actually crossed in the test. |
| test tree → production tree | Normally one-way and read-only. Task 3 deliberately and temporarily violates this, which is why the restore is gated by `git diff`, not by inspection. |
