<design_alternatives>
Phase-level design record (project directive: two alternatives + trade-off matrix, recorded once here; later plans cite it).

| Approach | Pros / Cons | Why picked |
|---|---|---|
| **Interim plumbing — PICKED:** Caddy keeps 80/443 and proxies the nonprod host to a Traefik NodePort (30080) via the docker0 gateway 172.17.0.1; nonprod pods reach Compose Postgres through a selector-less Service + EndpointSlice -> 172.17.0.1:5432; k3s installed with ServiceLB disabled | + Production edge and data untouched until the D-03 window. + NodePort unreachable from the internet (DOCKER-USER allows only 80/443 from eth0). − One new published port on Compose Postgres (bound to 172.17.0.1 only) and a scoped verify-compose-ports exception. − Recreates the Compose postgres container once (~10 s prod DB blip). | Only option that keeps D-02's seam: nothing production-facing moves during the nonprod half. |
| Interim — alternative A: Traefik takes 80/443 at the nonprod cutover and proxies prod to Compose | + No Postgres port. − Moves the production public edge and TLS during the nonprod half. | Rejected: violates D-02/D-03 ordering. |
| Interim — alternative B: move Postgres into k3s with nonprod; Compose prod app reaches it cross-runtime | + No second data move later. − Migrates production data outside the D-03 window. | Rejected: violates D-05 (dump/restore inside the window). |
| **Schema registration — PICKED:** initContainer on the app pod | + Pod template changes every deploy anyway, so no Job immutability problem; a failing init blocks the app container. − Registrar JVM runs on every pod start (idempotent, ~5-10 s). | Stronger ordering than Flux `dependsOn`; D-14 satisfied without a Job. |
| Schema — alternative: a `Job` (D-14's literal wording), made workable with Flux `force: true` + `dependsOn` | + Matches D-14 word for word; runs once per image rather than once per pod start. − The Job needs Redpanda up and the app needs the Job done, so each environment must split into three Flux Kustomizations (broker → schemas with force-recreate → app) to avoid a dependency cycle. That is 6 Kustomizations instead of 2, and 2 setter markers per env. | Not picked. **Deviation from D-14's literal `Job`, flagged for operator confirmation.** D-14's substance (in-cluster, ordered before the app, CI SSH step retired) is met, and the orchestrator's research guidance names the initContainer. Switching later touches 13-01/02/04/05/06 but no data. |
| **Flux bootstrap — PICKED:** `flux install --export` committed as gotk-components.yaml + hand-made SSH deploy key | + No PAT, CI gains no credential (D-15); Flux version pinned and reviewable in git. − Flux upgrades are a regenerate-and-commit, not `bootstrap` re-runs. | D-15 forbids new CI credentials; `flux bootstrap github` needs a PAT. |
| **Rollout — PICKED:** `strategy: Recreate` for app | + Memory envelope stays one app pod per env (~0.6 GiB steady-state headroom). − ~30 s downtime per deploy, same as Compose today. | RollingUpdate maxSurge 1 adds ~0.5 GiB prod requests transiently against that headroom. |
| **Prod data activation — PICKED (13-06):** two commits — W1 scales nonprod app to 0 and brings up in-cluster Postgres; restore + parity; W2 starts apps | − One extra commit in the window. + No app pod can run Flyway against an empty database before the restore. | A single activation commit lets an app start first, migrate the empty DB, and make the restore fail. |
| **kubeconfig — PICKED:** k3s default root-only (0600) | + CI SSH users on the VM (`deploy`, `deploy-nonprod`) get no cluster-admin. | Research's `--write-kubeconfig-mode 644` would expose prod Secrets to the nonprod CI identity, breaking Phase 9 isolation. |
| **CI Flyway verify (D-14) — PICKED (13-06):** runner-side Flyway through an SSH local forward limited by `PermitOpen` to the pinned Postgres ClusterIP 10.43.54.32:5432 | + No Docker Engine or kubeconfig needed on the VM; migrations come from the runner checkout (no SCP staging). − New sshd Match block. | Alternatives: keep Docker Engine alive only for CI; or give CI users namespaced kubeconfigs (new RBAC surface). |
| **Third-party charts — PICKED:** Flux HelmRelease (cert-manager, kube-prometheus-stack, Loki, Alloy, postgres-exporter); Traefik stays k3s-packaged + HelmChartConfig | + dependsOn, health checks, drift detection in one reconciler. | D-09 allows either; k3s HelmChart has no dependency ordering. |

**Non-obvious trade-offs:**
- *Memory:* Kubernetes schedules on `requests`, the kernel kills on `limits`. `limits` carry the already-measured Compose caps; `requests` = measured steady RSS. In the interim, k8s Burstable pods get `oom_score_adj` near 1000 while Compose containers sit at 0, so a global OOM kills nonprod pods before Compose prod.
- *State invalidation:* Flux commits tag bumps straight to `main` — local pushes are rejected until rebased (`git pull --rebase` before every push this phase). `k8s/**` in deploy.yml `paths-ignore` stops Flux's commit from rebuilding the image, which would create a new tag and loop.
- *Security:* manifests reference Secret *names* only; values are created on the VM from filtered env files (D-10) — the prod app Secret must not inherit the superuser, Grafana or nonprod keys that `.env.prod` also holds. When Docker Engine goes (13-10), DOCKER-USER stops guarding forwarded traffic, so 13-08 adds a k3s-era forward-path filter first.
- *Pinning:* the Postgres Service ClusterIP is pinned (10.43.54.32) because the VM host cannot resolve cluster DNS and CI's SSH forward targets it.

**scripts/verify-k8s-manifests.sh:** `set -euo pipefail`, with a WHY/SCOPE/KNOWN HOLES header shaped like verify-compose-ports.py.
- Pin kubectl `v1.36.4` and kubeconform at the latest release when you write the script. Record the exact version and sha256 of each. Download on demand to `${XDG_CACHE_HOME:-$HOME/.cache}/kanban-k8s-tools/<tool>-<version>/` and verify the sha256.
- `--tool <kubectl|kubeconform|helm>` prints the pinned binary's path and exits. Pin helm too, but download it only when asked: it is for local chart inspection by later plans, and the CI path never calls it (D-09).
- Default mode: take every directory under `k8s/` that holds a `kustomization.yaml`, sorted. Pipe `kubectl kustomize <dir>` into `kubeconform -strict -summary -kubernetes-version 1.36.4 -schema-location default -schema-location '<datreeio/CRDs-catalog raw URL pinned to a commit SHA>/{{.Group}}/{{.ResourceKind}}_{{.ResourceAPIVersion}}.json'`. Exit non-zero if any root fails, or if zero roots are found.
- Kubernetes version: first confirm the default location serves `v1.36.4-standalone-strict`. If it does not, use the newest `v1.36.x` it does serve and record the substitution in the header; API schemas do not change within a minor. If no `v1.36.x` exists, stop and report it (D-12 requires the k3s version).
- CRD kinds the phase will use: HelmChartConfig (helm.cattle.io/v1), IngressRoute and Middleware (traefik.io/v1alpha1), Certificate and ClusterIssuer (cert-manager.io/v1), ServiceMonitor and PodMonitor (monitoring.coreos.com/v1), HelmRelease (helm.toolkit.fluxcd.io/v2), HelmRepository and GitRepository (source.toolkit.fluxcd.io/v1), Kustomization (kustomize.toolkit.fluxcd.io/v1), ImageRepository, ImagePolicy and ImageUpdateAutomation (image.toolkit.fluxcd.io/v1).
