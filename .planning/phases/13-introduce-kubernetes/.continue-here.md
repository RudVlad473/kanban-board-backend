## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| caddy-reload-stale-inode | `appleboy/scp-action` replaces `Caddyfile` via rename/untar (new inode), but Docker's bind mount was captured at container start and keeps pointing at the OLD inode. `caddy reload` inside the container reloads stale content — genuinely different file, confirmed via differing md5sum/inode/mtime between host and `docker exec cat`. Caused a real ~2min public 502 on nonprod after 13-05's Caddyfile push, even though `deploy-to-netcup` reported green. Went undetected historically because the deploy that introduced this reload mechanism (quick task 260903-dvp) also recreated the container for an unrelated reason (new image tag), masking the bug. | blocking | Replace the `caddy reload` step in `.github/workflows/deploy.yml`'s `deploy-to-netcup` job with `docker compose ... up -d --force-recreate caddy` (or another mechanism proven to survive scp-action's rename-based replacement), and verify with a real Caddyfile-only push (confirm host/container md5sum match afterward) before trusting this path again — especially before 13-06's one-way production cutover. |
| trust-green-ci-blindly | A CI run reported `deploy-to-netcup: success` while production was actually serving a 502 on the changed path. The gap between "the deploy script executed without error" and "the intended live state actually changed" was invisible from the Actions UI alone. | advisory | For any production-facing push in this phase, independently check the actual live resource after CI goes green (curl the public endpoint, diff a checksum, inspect the running container) — don't stop at the green checkmark. |
