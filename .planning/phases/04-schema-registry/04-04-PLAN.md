<objective>
Rehearse the new Avro schemas against real historical activity-log data before this phase is treated as cutover-safe.

The risk SCHEMA-06 names is specific: Avro's model is stricter than the JSON one it replaces, and every field in all 5 schemas is required with no default. If any real, already-shipped event ever carried a shape the new schemas cannot express, the failure would appear in production as dead-lettered valid traffic. The only way to know is to run real rows through the real schemas.

**Core data-flow mechanism (3 sentences):** The durable historical record of this pipeline is the `activity_log` Postgres table, not the Kafka topic — the local topic has no retention guarantee and its volume is disposable, while every consumed event left a row behind. Each row carries `boardId`, `userId`, an `action` enum, a `detail` JSON object whose key set is fixed per action, `eventId` and `createdAt`, which together are exactly the fields of the originating `ActivityEvent`, so the consumer's forward mapping is invertible. The rehearsal reconstructs each historical event from its row, pushes it through `toAvro`, a real `KafkaAvroSerializer` against the registry, back through the deserializer and `toDomain`, and asserts field equality — writing nothing anywhere.

Purpose: this is the last thing that should be true before Phase 5 repoints the registry at a production target, and it is the one check that uses data nobody designed for the new schemas. It is also the only direct exercise of what D-02's BACKWARD compatibility actually promises — that data written under the old contract stays readable by the new schemas — and it exercises all 5 of D-03's independently-evolving schemas against real traffic rather than against fixtures derived from the same record definitions the schemas came from.
Output: an inverse-mapping helper proven against the real pipeline, and a rehearsal run whose corpus size and coverage are recorded rather than assumed.
</objective>

<design_alternatives>
Required by `.claude/CLAUDE.md`'s GSD Execution Directives.

**The decision: where does "real historical data" come from?**

| Approach | Pros / Cons | Why Picked |
|---|---|---|
| **A. Reconstruct events from `activity_log` Postgres rows (PICKED)** | **+** This is the project's actual durable historical record — every consumed event left a row, and the rows survive `docker compose down -v`. **+** The forward mapping is invertible because `detail`'s key set is fixed per `ActivityAction`, so reconstruction is total rather than best-effort. **+** Read-only: no writes to the source database, and the consumer's `eventId` idempotency makes even an end-to-end republish a no-op. **−** Reconstruction is inferred from the consumer's mapping and could drift from it, so the inverse must itself be tested rather than trusted. | The only source of genuinely historical data that still exists. The drift risk is retired by Task 1, which proves the inverse against the real shipped pipeline instead of against a reading of its source. |
| **B. Replay the `kanban.activity` Kafka topic from offset zero** | **+** The most literal reading of "historical messages", and preserves the original wire bytes. **−** The local broker volume is disposable and is about to be replaced outright by the compose migration; there is no documented retention or backup of raw topic bytes. **−** The production broker this data would have come from no longer exists. | Rejected as unavailable, not merely inconvenient. A rehearsal against a topic that may hold nothing older than the current test run is a rehearsal against nothing. |
| **C. Generate a synthetic corpus covering every field permutation** | **+** Deterministic, runs anywhere, covers cases real data may not contain. **−** Defeats the requirement outright: synthetic events are constructed from the same record definitions the schemas were derived from, so they cannot disagree with the schemas. That circularity is precisely why SCHEMA-06 says "not just synthetic fixtures". | Rejected as the requirement's named anti-pattern. Note that Plan 01's mapper round-trip test already provides the synthetic coverage, so nothing is lost by refusing it here. |

**Decision 2: what happens when the corpus is empty?** The production database was deleted before this milestone began, so the only surviving corpus is whatever a developer's local Postgres volume holds — which may be nothing. The rehearsal therefore must fail loudly and report the corpus size and the set of actions it covered, rather than passing on zero rows. A green rehearsal that examined nothing is worse than a red one, because it converts an unanswered question into a false answer. This is also why the rehearsal is a separate build step rather than part of the default `test` task: the H2 test database is created fresh per run and is empty by construction, so wiring this into `test` would guarantee either a permanent failure or a permanently vacuous pass.

**Non-obvious trade-offs:**

- **Correctness / strictness:** the actual gate is Avro's `build()` call, which rejects a required field left unset. That is where a historical row with an unexpected shape will fail, and it fails before any network call. Do not defensively default missing values in the reconstructor to keep the rehearsal green — a row that cannot produce a complete event is the finding, and swallowing it destroys the entire value of the exercise.
- **Precision:** if `timestamp` is carried as `timestamp-millis`, sub-millisecond precision in `createdAt` does not survive the round trip. This project has already been bitten by the equivalent on the JSON path and resolved it with a tolerance-based assertion rather than by rounding inputs. Assert with an explicit tolerance and a comment naming the wire format's precision, so the tolerance reads as a documented property rather than a loosened assertion.
- **Safety:** the rehearsal reads a real database. It must open no write transaction, and any end-to-end republish must rely on `ActivityLogRecorder`'s `eventId` idempotency rather than on a cleanup step. State this explicitly in the test's Javadoc — a future contributor adding an assertion that writes a row would silently turn a safe read-only rehearsal into a mutation against real data.
- **Performance:** the corpus is bounded by whatever the local table holds. Cap the sample if it is large; a few hundred rows spanning all 5 actions proves what an exhaustive pass would, at a fraction of the runtime.
</design_alternatives>
