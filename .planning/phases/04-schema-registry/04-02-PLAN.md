<objective>
Cut the live activity-log pipeline over to Avro against a real, Confluent-API-compatible schema registry, and prove one event type's full round trip end to end.

This is the phase's tracer: the thin axis is *verification depth*, not event-type count. All 5 schemas must be wired simultaneously because a single topic carries a single value serializer — there is no green intermediate state in which two of five event types speak Avro. What this plan deliberately does not do is prove the failure paths (Plan 03) or rehearse real historical data (Plan 04); it proves the happy path works, all the way through, with the registry actually enforcing something.

**Core data-flow mechanism (3 sentences):** `KafkaEventPublisher` maps the domain event to its Avro record and hands it to `KafkaTemplate`, whose `KafkaAvroSerializer` looks the schema up in the registry by the record's full name and writes a magic byte plus the returned 4-byte schema id ahead of the binary payload. On the way back, `ErrorHandlingDeserializer` wraps `KafkaAvroDeserializer`, which reads the schema id, fetches the schema, and reconstructs the generated `SpecificRecord`; `ActivityLogConsumer` converts it back to a domain event with the mapper and passes it to its existing, unmodified exhaustive switch. Because `auto.register.schemas` is off, the serializer only ever *looks up* schemas — writing them is a separate step, so a producer with a drifted schema fails loudly instead of quietly registering a new version.

Purpose: SCHEMA-01, SCHEMA-03 and SCHEMA-04 all become true at once here, and the two research assumptions that could still invalidate the design (Redpanda's `RecordNameStrategy` namespace handling, and whether registry latency re-introduces the publish-path stall that cost this project a 20-minute suite hang in v1.1) get answered against a real registry rather than argued about.
Output: a live Avro pipeline, a reusable registration step, an enforced BACKWARD compatibility mode with a proven rejection, and a local compose stack that has a registry in it.
</objective>

**Decision 2: `RecordNameStrategy` versus the default `TopicNameStrategy`.** The default makes the subject equal to the topic name, which would force all 5 event types to share one subject and one schema — a direct contradiction of D-03. `RecordNameStrategy` makes the subject the record's full name, so 5 types coexist as 5 independently-versioned subjects on the one `kanban.activity` topic. `TopicRecordNameStrategy` is strictly more flexible and costs the same to configure, but scopes subjects per-topic, which only pays off if a second topic ever reuses one of these record types. It does not today, and adopting it now would bake the topic name into 5 subject names for no current benefit.

**Non-obvious trade-offs:**

- **Performance — the one that has bitten this project before.** The Avro serializer performs a *synchronous HTTP call* to the registry inside `KafkaProducer.doSend`, on the calling thread. Results are cached per schema after the first lookup, so steady state is one call per schema per producer. The danger is the cold path: 17 fixture-heavy test classes each publish roughly 18 events against a test profile that points at a registry which is not running. v1.1 already paid for this exact shape of mistake with a 20-minute full-suite hang from an unbounded `max.block.ms`. Two things keep it bounded here: publishing already runs off-thread on `kafkaPublishExecutor`, and a refused TCP connection to a non-listening local port fails immediately. The remaining exposure is the Confluent REST client's *retry* behaviour (it retries a failed registry call several times with a wait between attempts by default), which is why this plan measures full-suite wall-clock as an acceptance criterion rather than assuming it is fine.
- **Memory:** `CachedSchemaRegistryClient` holds an unbounded-by-default schema cache per serializer instance. With 5 schemas and 2 producer factories this is a handful of objects; it is worth knowing the cache exists, not worth capping.
- **Security (net improvement):** the JSON path's `spring.json.trusted.packages` allowlist was a deserialization-gadget control — it existed because `JsonDeserializer` could otherwise be steered to instantiate arbitrary types from a message header. Avro's `SpecificRecord` deserialization has no equivalent surface: it instantiates exactly the generated class the resolved schema names, never a type the message author chose. Those two now-meaningless properties must be *deleted*, not left inert, so nobody later reads them as a live control.
- **Security (deferred, not solved):** the registry is plain HTTP with no authentication in this phase. That is correct for a Testcontainers instance and a local compose stack, and wrong for anything internet-reachable. Phase 5's INFRA-08 owns keeping it off the public network. Do not attempt a TLS/auth story here.
- **Reversibility:** the compose broker swap discards the existing `kafka-data` named volume's usefulness, since Redpanda's data directory format differs. This is local-dev-only, ephemeral state — costly to un-do only in the sense that a developer loses whatever is in their local topic, which the project already treats as disposable.
</design_alternatives>
