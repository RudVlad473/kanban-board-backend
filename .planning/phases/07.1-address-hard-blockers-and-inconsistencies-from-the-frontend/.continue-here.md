## Critical Anti-Patterns (do NOT repeat these)

- **Master moves independently during a wave.** Twice this session, `master` gained a commit
  from outside this session/worktree tree while a wave was executing (once a `docs: capture
  todo` commit from what looked like a parallel session, once this session's own todo-capture
  commit). Both times, using current `HEAD` as the worktree merge manifest's `expected_base`
  caused `cleanup-wave` to fail with `base_mismatch`. Fix: always compute
  `git merge-base HEAD <worktree-branch>` fresh right before building the merge manifest —
  never assume `expected_base == current HEAD`.
- **`gsd_run query commit` has an internal timeout shorter than this repo's pre-commit hook**
  (which runs the full `fastTest` Testcontainers suite, sometimes 3+ minutes). It killed the
  underlying `git commit` process mid-hook twice, each time leaving a stale `.git/index.lock`
  behind (harmless — `rm -f .git/index.lock .git/next-index-*.lock` after confirming no live
  git process holds it, e.g. via the lock file's mtime predating any currently-running java
  process). Workaround: for any commit expected to trigger the full test suite, run `git
  commit` directly via Bash with a long explicit timeout (400s+) instead of going through the
  `gsd_run query commit` wrapper.
- **`./gradlew --stop` on the main tree can race with a concurrently-running worktree's Gradle
  build.** Gradle daemons appear to be shared across worktrees of the same repo (matched by
  JVM/Gradle version, not project path). Running `--stop` while another wave's executor is
  mid-`./gradlew test` in its own worktree crashed that executor's build ("Gradle build daemon
  has been stopped: stop command received") — it recovered on its own retry, but this is a
  live hazard. Avoid running `git commit` (which triggers the hook) or `./gradlew --stop` on
  the main orchestrator tree while any wave executor is active; if a commit on the main tree
  is unavoidable mid-wave (e.g. capturing a todo), expect possible daemon contention and be
  ready for the executor to self-recover via its own documented `./gradlew --stop` + retry
  fallback (which it has shown it does).
- **A killed background agent may leave an orphan Gradle daemon (`java` process) alive** in its
  worktree — harmless to leave running (it idles out on its own), but don't mistake it for
  "the agent is still working."
