# Phase 07.1 Plan 04: Signin/Signup Validation & Duplicate-Email 409 Summary

**Turned on `@Valid` for the two `permitAll()` auth routes (previously dead-code field constraints), added a real 409 for duplicate signup emails without regressing the anti-enumeration 401 collapse, and delivered the `getForeignUser()` cross-owner fixture plan 07.1-08 depends on.**

- **Tasks:** 3 (all `type="auto"`, task 3 also `tdd="true"`)
- **Files modified:** 9 (0 created, 9 modified)

## Accomplishments

- `AbstractAppTest.generateValidPassword()` — composes `dataFactory`'s random word with a fixed `Aa1!` suffix so every generated password satisfies `@Password`'s lowercase/uppercase/digit/special-char regex regardless of what `dataFactory` produces. `owningUserPassword`/`noBoardsUserPassword`/`foreignUserPassword` and `createUser()`'s no-arg overload all route through it.
- `getForeignUser()`/`getForeignUserBoard()`/`getForeignUserColumn()` (D-20) — a user who owns a genuine board+column, created last in `setup()` specifically so it never shifts the insertion order several pre-existing tests assert against positionally (see key-decisions).
- `@Valid` added to both `AuthenticationController.signin`/`signup`'s `@RequestBody` parameters — `MethodArgumentNotValidException` fires during argument resolution, before either method body runs, so the existing blanket `catch (Exception e)` cannot intercept it. D-08's plain 400 field errors and D-09's validation-before-duplicate-check ordering both fall out with zero explicit ordering code, exactly as RESEARCH.md Pattern 3 predicted — and Task 3 now proves it empirically instead of resting on that prediction.
- `UserRepository.existsByEmail` + a check-then-throw guard in `UserService.save(SignupRequestDTO)` (D-07) — reuses the `AppDuplicateResourceException`/`DUPLICATE_RESOURCE` 409 path `GlobalExceptionHandler` already has from plan 07.1-01. `AppDuplicateResourceException.withMessage(String)` static factory added so the email-duplicate message reads correctly ("Email 'x' is already taken") instead of the entity-name template's "x with that name already exists".
- Fixed the swallowing defect in `AuthenticationController.signup`: `userService.save(signupDTO)` hoisted above the try block so a duplicate-email `AppDuplicateResourceException` reaches `GlobalExceptionHandler` as a 409 instead of being collapsed into the generic 401. The try block now scopes exactly what it always meant to catch — a failed authentication of the account just created — with `createdUser` still in scope for the compensating rollback.
- 8 new `AuthenticationE2ETest` behaviors across `Signin.FieldValidation`, `Signin.AntiEnumeration`, `Signup.FieldValidation`, and `Signup.DuplicateEmail`, each backed by a passing test proving D-06 through D-09 empirically — including the two (D-08, D-09) CONTEXT.md itself describes as "falling out naturally" and which would otherwise have shipped with zero regression guard.
- Full `./gradlew test` (whole suite, all tiers, 285/285) green after each of the three tasks individually; `./gradlew spotlessCheck` green throughout.

## Decisions Made

- **`AppDuplicateResourceException.withMessage(String)` is a static factory, not a literal second constructor.** The plan's action text said "add a second constructor taking an explicit message" — but Java cannot overload two constructors on the same single-`String` erasure. Implemented as a private `(String message, boolean rawMessage)` constructor behind a public static factory instead; the boolean discriminator is referenced in an `assert` purely to keep Error Prone's `UnusedVariable` warning silent (harmless either way — not a promoted-to-`ERROR` check in this repo's Error Prone config).
- **D-20's foreign-user fixture is created LAST in `AbstractAppTest.setup()`.** Creating it right after `owningUser`/`noBoardsUser` (before `owningUser`'s own boards) shifted `boardService.findAll()`'s insertion order and broke `BoardServiceTest.testUpdateById_shouldUpdateBoard_whenBoardExists()`, which takes `boardService.findAll().getFirst()` and assumes it's an `owningUser` board. Moving the foreign-user block to the end of `setup()` fixed it without touching the pre-existing test.
- **`uk_users_email UNIQUE (email)` already exists** (`V1__init.sql:11`), so the plan's anticipated "no unique constraint at the DB level, file a race-window todo" branch does not apply here. The check-then-act `existsByEmail` guard's only residual race is a `DataIntegrityViolationException` fallback, itself already mapped to 409 by `GlobalExceptionHandler`'s existing broader arm — the same pattern `BoardService.updateById` already relies on for board-name uniqueness. No new todo filed.
- **D-09's test uses an invalid password, not a malformed email, alongside a genuine duplicate.** A malformed email can never simultaneously equal an already-registered email, since every registered email already passed `@AppEmail` to be created in the first place — so "malformed and duplicate" is only constructible by violating a different field while the email itself is a real duplicate target. Documented inline in the test's Javadoc so a future reader doesn't "fix" it to use a malformed email instead.
