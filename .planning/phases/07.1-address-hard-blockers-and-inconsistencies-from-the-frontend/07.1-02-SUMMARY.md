# Phase 07.1 Plan 02: CORS Configuration Summary

Added a `CorsConfigurationSource` bean with an explicit, property-driven origin allow-list and credentialed cross-origin support, closing the audit's single hardest blocker — without it no browser-based frontend could call this API at all.

## What Was Built

- `com.vrudenko.kanban_board.config.CorsConfig`, a `@Configuration` class exposing one `@Bean corsConfigurationSource(List<String> allowedOrigins)` method. Builds a `CorsConfiguration` with `GET`/`POST`/`PUT`/`PATCH`/`DELETE` allowed methods (PATCH required for the reorder/move endpoints), `*` allowed headers, `allowCredentials(true)`, and registers it on a `UrlBasedCorsConfigurationSource` under `/**`.
- `app.cors.allowed-origins=http://localhost:5173,http://localhost:3000` added to `application.properties`, with a comment naming the Vite/create-react-app default dev ports and recording why an explicit list is mandatory once credentials are allowed. The bean's `@Value` injection also carries an inline default of the same two origins, so a deployment that omits the property still boots.
- `CorsConfigTest`, asserting the resolved bean configuration for the `/api/boards` path: non-null configuration, exactly the two configured origins (no wildcard), all five D-11 methods present, and `allowCredentials` true. Extends `AbstractPostgresContainerTest` directly rather than the heavier `AbstractAppTest` fixture base, since the test needs no user/board/column data.

`SecurityConfiguration.java` was not touched — its existing `http.cors(Customizer.withDefaults())` call already auto-detects the new `UrlBasedCorsConfigurationSource` bean per Spring Security's documented behavior; adding a second `.cors(...)` call or an explicit `.configurationSource(...)` form would have been redundant and risked a filter-ordering surprise (Pitfall 4).
