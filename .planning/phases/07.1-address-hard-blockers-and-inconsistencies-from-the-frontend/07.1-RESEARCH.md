## User Constraints (from CONTEXT.md)

### Locked Decisions

**Error Response Envelope**
- **D-01:** Converge every `GlobalExceptionHandler` branch onto Spring's built-in RFC 7807 `ProblemDetail` type (`ResponseEntity<ProblemDetail>`), replacing today's mix of bare-string bodies and the one `Map<String,String>` branch. — **Reversibility:** costly — every handler's return type changes, and any frontend code already written against the old bare-string shape would break.
- **D-02:** Field-level validation errors (from `MethodArgumentNotValidException`) nest under an `errors` extension property inside the `ProblemDetail`, rather than being their own top-level shape.
- **D-03:** Each `ProblemDetail` carries a stable `code` extension property (e.g. `BOARD_NOT_FOUND`, `OPTIMISTIC_LOCK_CONFLICT`), one per exception type, so the frontend can branch on more than just HTTP status.
- **D-04:** Wire a custom `AuthenticationEntryPoint` so a genuinely unauthenticated request (rejected by the Spring Security filter chain before reaching any controller or `GlobalExceptionHandler`) returns the same `ProblemDetail` shape as every other error path — today it likely falls through to Spring Security's own default response instead.

**401 vs 403 Split**
- **D-05:** `AppAccessDeniedException` and `AccessDeniedException` (both ownership-related, currently mapped to 401 at `GlobalExceptionHandler.java:60-68`) move to **403 Forbidden**. `BadCredentialsException` stays 401 (bad signin credentials). The new `AuthenticationEntryPoint` (D-04) is the sole source of true 401s for unauthenticated access — `@PreAuthorize("isAuthenticated()")` failures at the filter-chain level ARE that case, already covered by D-04; no separate `AccessDeniedHandler` needed.

**Signup / Signin Validation & Exposure**
- **D-06:** Add `@Valid` to both `SigninRequestDTO` and `SignupRequestDTO` parameters in `AuthenticationController` so field-level Jakarta Validation constraints (`@AppEmail`/`@Password`/`@DisplayName`) actually fire — currently silently skipped.
- **D-07:** Signup reveals duplicate-email conflicts explicitly: 409 via the existing `AppDuplicateResourceException` pattern (already used for board-name uniqueness), with a clear "email already taken" message. Deliberately accepts the enumeration tradeoff — judged acceptable for this project's personal/portfolio scope versus building an email-verification flow.
- **D-08:** Signin's malformed-input validation failures (e.g. malformed email format) return normal 400 field errors, same as every other `@Valid`-annotated endpoint. Only genuine bad-credentials failures (valid-shaped input, wrong password/unknown email) stay collapsed into the existing generic-401 anti-enumeration behavior.
- **D-09:** On signup, Jakarta field validation runs before the duplicate-email check — this falls out naturally from `@Valid`'s automatic pre-method execution; no explicit ordering code needed.

**CORS Configuration**
- **D-10:** New `CorsConfigurationSource` bean; allowed origins externalized via a new `app.cors.allowed-origins` property in `application.properties` (comma-separated), defaulting to `http://localhost:5173,http://localhost:3000` when unset.
- **D-11:** Allow `GET/POST/PUT/PATCH/DELETE` (every method this API's controllers expose, including `PATCH` for reorder/move), all headers, `allowCredentials(true)` (required for cookie-based session auth — forces an explicit origin allow-list, no wildcard).
- **D-12:** No special handling needed in the test profile — CORS is browser-enforced and MockMvc never triggers preflight/origin checks. A dedicated test may assert the bean's configuration or an `OPTIONS` response's headers directly if coverage of the config itself is wanted.

**Optimistic Locking — Board/User**
- **D-13:** Add `@Version` to `BoardEntity`, matching Column/Task/Subtask. Requires a new Flyway migration **V7** (current highest is `V6__change_activity_log_event_id_to_varchar.sql`) adding `boards.version`, and `UpdateBoardRequestDTO` gains a required `version` field following the existing `Update*RequestDTO` pattern. — **Reversibility:** one-way — once boards ship with a required `version` field, removing it later breaks any frontend already built against it.
- **D-14:** `UserEntity` does **NOT** get `@Version`. Per the audit, `UpdateThemeRequestDTO`'s last-write-wins is a deliberate, already-documented design choice for a low-stakes UI setting, not a gap — this phase closes only the genuinely inconsistent, undocumented Board asymmetry the audit flagged.
- **D-15:** `BoardFullResponseDTO` gains the board's `version` field (today it only exposes column/task/subtask versions) — needed so a frontend that loads a board via `GET /boards/{boardId}/full` has the version it needs to make a version-safe board rename afterward.

**Security/Injection Test Coverage**

## Summary

This phase is a hardening pass on an already-complete REST API, not new-feature work — every decision in CONTEXT.md targets a specific, already-located line range in existing source. Research confirms all 26 decisions are technically sound and locates the exact non-obvious mechanics the plan must get right. The two highest-value findings, both verified by reading the live filter chain and exception handler:

1. **The 401/403 split is simpler than it looks.** `SecurityConfiguration.java`'s `auth.anyRequest().authenticated()` filter-chain rule (not `@PreAuthorize`) is what currently rejects unauthenticated requests, and Spring Security's default `AuthenticationEntryPoint` for a config with no `httpBasic()`/`formLogin()` is `Http403ForbiddenEntryPoint` — meaning **today's unauthenticated-request response is already a bare 403, not a 401**, contradicting the audit's implicit "overloaded 401" framing for that specific path. The `AppAccessDeniedException`/`AccessDeniedException` cases currently mapped to 401 in `GlobalExceptionHandler.java:60-68` are a *separate* code path entirely (thrown deep in the service layer for an already-authenticated, ownership-denied user, caught by `@ControllerAdvice`, never touching the security filter chain at all) — so D-05's remap to 403 is a pure `GlobalExceptionHandler` edit with zero interaction with the new `AuthenticationEntryPoint`, confirming D-05's own "no separate `AccessDeniedHandler` needed" claim.
2. **`ProblemDetail.setProperty()` flattens to top-level JSON, not a nested `"properties"` object**, because Jackson is on the classpath and Spring registers `ProblemDetailJacksonMixin` automatically. D-02's `errors` and D-03's `code` extension properties will appear as `$.errors` and `$.code` in the response body — every MockMvc/REST Assured assertion in this phase's new tests must target that flattened shape, not `$.properties.code`.

Beyond those two, research located: the exact V2 migration precedent to copy verbatim for D-13's V7 migration; confirmation that `@Valid`'s pre-method-body validation timing means D-06 requires zero changes to `AuthenticationController`'s existing try/catch structure; the verified, file-and-line-cited list of which `*E2ETest` classes are genuinely Kafka/socket-bound (9) vs. safely renameable (11) for D-21; and a concrete, pre-existing status-code inconsistency (column/subtask creation returns 200, board/task/signup creation returns 201) that the phase description's "inconsistent create-status-codes" item refers to but CONTEXT.md's decisions do not explicitly resolve — flagged as an open question below since no D-number covers it.

**Primary recommendation:** Sequence the phase as CONTEXT.md's D-24/D-26 already mandate (code fixes and tests first, `/claude-security` scan second, diagrams last), and within "code fixes," do the `ProblemDetail` convergence (D-01..D-05) before CORS/locking/validation work, since every other new test class in this phase will assert against the new error envelope shape — building it last would mean rewriting test assertions twice.

### Pattern 1: ProblemDetail with a stable `code` extension, converged across every handler (D-01..D-03)

**What:** Replace every `@ExceptionHandler` return type in `GlobalExceptionHandler` with `ResponseEntity<ProblemDetail>`, built via `ProblemDetail.forStatusAndDetail(status, ex.getMessage())`, then `.setProperty("code", "...")`.
**When to use:** Every existing handler branch (`EntityNotFoundException`, `AppEntityNotFoundException`, `IllegalArgumentException`, `HttpMessageNotReadableException`, the `Exception.class` catch-all, `AccessDeniedException`/`AppAccessDeniedException`, `HandlerMethodValidationException`, `OptimisticLockingFailureException`, `AppDuplicateResourceException`, `DataIntegrityViolationException`, `BadCredentialsException`, `MethodArgumentNotValidException`).
**Example:**
```java
// Source: Spring Framework 6.x org.springframework.http.ProblemDetail (spring-web, already on classpath)
// Pattern synthesized from GeeksforGeeks' verified Spring Boot 3 ProblemDetail walkthrough
// and Spring's own ProblemDetail/ProblemDetailJacksonMixin Javadoc (see Sources).
@ExceptionHandler(AppEntityNotFoundException.class)
public ResponseEntity<ProblemDetail> handleAppEntityNotFound(AppEntityNotFoundException ex) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    problem.setProperty("code", "ENTITY_NOT_FOUND");
    return ResponseEntity.status(problem.getStatus()).body(problem);
}

// D-02: MethodArgumentNotValidException nests field errors under "errors"
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ProblemDetail> handleMethodArgumentNotValidException(
        MethodArgumentNotValidException ex) {
    Map<String, String> errors = new HashMap<>();
    ex.getBindingResult().getAllErrors().forEach(error -> {
        String fieldName = ((FieldError) error).getField();
        errors.put(fieldName, error.getDefaultMessage());
    });

    ProblemDetail problem =
            ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Validation failed");
    problem.setProperty("code", "VALIDATION_FAILED");
    problem.setProperty("errors", errors);   // flattens to top-level "errors" key, NOT "properties.errors"
    return ResponseEntity.status(problem.getStatus()).body(problem);
}
```
**Non-obvious mechanic [VERIFIED via WebSearch of Spring Framework/Spring Boot official API docs and issue tracker]:** because Jackson is present on the classpath, Spring auto-registers `ProblemDetailJacksonMixin`, which unwraps `ProblemDetail.getProperties()` and renders every `setProperty()`'d key as a **top-level** JSON field alongside `type`/`title`/`status`/`detail`/`instance` — never nested under a literal `"properties"` key. A response body for the example above looks like:
```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "Board was not found",
  "instance": "/api/boards/xyz",
  "code": "ENTITY_NOT_FOUND"
}
```
Test assertions must target `jsonPath("$.code")` / `jsonPath("$.errors.name")`, never `jsonPath("$.properties.code")`.

### Pattern 2: Custom AuthenticationEntryPoint, explicitly wired (D-04)

**What:** A bean implementing `AuthenticationEntryPoint`, producing the same `ProblemDetail` JSON shape as `GlobalExceptionHandler`, wired via `http.exceptionHandling(...)` — **not** auto-detected the way `CorsConfigurationSource` is.
**When to use:** Whenever a request reaches `AuthorizationFilter` (the `auth.anyRequest().authenticated()` rule at `SecurityConfiguration.java:69` [VERIFIED: src/main/java/com/vrudenko/kanban_board/security/SecurityConfiguration.java:69 — `auth.anyRequest().authenticated();`]) with no valid session — i.e. today's default `Http403ForbiddenEntryPoint`.
**Example:**
```java
// Source: pattern synthesized from Spring Security 6 docs (exceptionHandling DSL) + this
// codebase's own GlobalExceptionHandler shape, so both paths produce byte-identical envelopes.
@Component
public class ProblemDetailAuthenticationEntryPoint implements AuthenticationEntryPoint {
    private final ObjectMapper objectMapper;

    @Override
    public void commence(HttpServletRequest request, HttpServletResponse response,
            AuthenticationException authException) throws IOException {
        ProblemDetail problem =
                ProblemDetail.forStatusAndDetail(HttpStatus.UNAUTHORIZED, "Authentication is required");
        problem.setProperty("code", "UNAUTHENTICATED");

        response.setStatus(HttpStatus.UNAUTHORIZED.value());
        response.setContentType("application/problem+json");
        objectMapper.writeValue(response.getWriter(), problem);
    }
}
```
```java
// SecurityConfiguration.java — wiring (CorsConfigurationSource needs NO equivalent wiring;
// Spring Security auto-detects a UrlBasedCorsConfigurationSource bean and http.cors(Customizer.withDefaults())
// at SecurityConfiguration.java:53 already picks it up with zero further change)
http.exceptionHandling(handling -> handling.authenticationEntryPoint(problemDetailAuthenticationEntryPoint));
```
**Filter-chain-ordering finding [VERIFIED via WebSearch of Spring Security default-entry-point behavior]:** with no `httpBasic()`/`formLogin()` configured (true of this app — neither appears in `SecurityConfiguration.java`), Spring Security's current default `AuthenticationEntryPoint` is `Http403ForbiddenEntryPoint`, which unconditionally returns **403**, not 401. This means the phase description's "overloaded 401" complaint does not describe today's unauthenticated-request path (that path is silently 403 today) — it describes the *collision* between that implicit 403 and `GlobalExceptionHandler`'s explicit-401 mapping of `AppAccessDeniedException`/`AccessDeniedException` (ownership failures). D-04+D-05 together resolve this: after the change, 401 means "not authenticated at all" (entry point) and 403 means "authenticated but not permitted" (exception handler) — two genuinely distinct, non-overlapping cases.

### Pattern 3: `@Valid` on `AuthenticationController` is a pure addition, not a restructuring (D-06, D-08, D-09)

**What:** `@Valid` on `@RequestBody SigninRequestDTO`/`SignupRequestDTO` parameters.
**When to use:** `AuthenticationController.signin`/`signup`.
**Why it's safe [VERIFIED via WebSearch of Spring MVC argument-resolution documentation]:** `@Valid`-triggered `MethodArgumentNotValidException` is thrown by Spring's `HandlerMethodArgumentResolver` chain **during argument resolution, before the controller method body is invoked** — i.e. entirely outside `AuthenticationController.signin`'s existing `try { ... } catch (Exception e) { throw new BadCredentialsException(...); }` block [VERIFIED: src/main/java/com/vrudenko/kanban_board/security/AuthenticationController.java:47-58]. The blanket `catch (Exception e)` inside that method therefore **cannot** intercept a validation failure and collapse it into a generic 401 — it propagates straight to `GlobalExceptionHandler`'s `MethodArgumentNotValidException` handler, delivering D-08's plain 400 field errors with zero code restructuring needed in the controller beyond adding the `@Valid` annotation itself.

### Pattern 4: CorsConfigurationSource bean — auto-detected, no DSL change needed beyond the bean itself (D-10, D-11)

**What:** A `UrlBasedCorsConfigurationSource` bean with explicit origins, methods, and `allowCredentials(true)`.
**When to use:** Once, application-wide.
**Example:**
```java
// Source: official Spring Security CORS reference (docs.spring.io/spring-security/reference/servlet/integrations/cors.html)
@Bean
public CorsConfigurationSource corsConfigurationSource(
        @Value("${app.cors.allowed-origins:http://localhost:5173,http://localhost:3000}")
        List<String> allowedOrigins) {
    CorsConfiguration configuration = new CorsConfiguration();
    configuration.setAllowedOrigins(allowedOrigins);
    configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE"));
    configuration.setAllowedHeaders(List.of("*"));
    configuration.setAllowCredentials(true);

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", configuration);
    return source;
}
```
**Non-obvious mechanic [VERIFIED via WebFetch of docs.spring.io/spring-security/reference/servlet/integrations/cors.html]:** *"Spring Security will automatically configure CORS only if a `UrlBasedCorsConfigurationSource` instance is present."* `SecurityConfiguration.java:53`'s existing `http.cors(Customizer.withDefaults())` [VERIFIED: src/main/java/com/vrudenko/kanban_board/security/SecurityConfiguration.java:53] already opts into this auto-detection — **no change to that line is needed**, only adding the new bean is required. Also verified: *"CORS must be processed before Spring Security, because the pre-flight request does not contain any cookies... If the request does not contain any cookies and Spring Security is first, the request determines that the user is not authenticated... and rejects it."* Spring Security's `CorsFilter` is automatically ordered first in the chain when a `CorsConfigurationSource` bean exists — no manual filter-order wiring is required, but this is why D-12's claim ("CORS is browser-enforced, MockMvc never triggers preflight") is correct: MockMvc dispatches directly into the filter chain/DispatcherServlet in-process and never constructs a genuine cross-origin preflight `OPTIONS` request the way a browser does. A REST-Assured-based real-socket test (see D-12's "dedicated test" option) is the only way to assert real header behavior at `Access-Control-Allow-Origin`/`Access-Control-Allow-Credentials`.
**Also verified [CITED: CORS spec, corroborated by WebSearch]:** `allowCredentials(true)` structurally forbids `allowedOrigins("*")` — the CORS spec disallows the wildcard origin header value when credentials are allowed, so D-10's explicit comma-separated origin list is not just a preference, it is a hard requirement once D-11's `allowCredentials(true)` is set.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| RFC 7807 error body shape | A custom `ErrorResponse`/`ApiError` POJO | `org.springframework.http.ProblemDetail` (already on classpath) | D-01 already locks this; hand-rolling would also lose the automatic Jackson flattening behavior described in Pattern 1 |
| Unauthenticated-request interception | A custom `Filter`/`HandlerInterceptor` checking `SecurityContextHolder` manually | Spring Security's `AuthenticationEntryPoint` + `exceptionHandling()` DSL | The filter chain (`ExceptionTranslationFilter`) already does exactly this dispatch; a hand-rolled interceptor would run at the wrong layer (after `DispatcherServlet`, too late for a request that never reaches a controller) |
| CORS preflight handling | A custom `OncePerRequestFilter` adding `Access-Control-*` headers | `CorsConfigurationSource` bean, auto-detected by `http.cors(Customizer.withDefaults())` | Spring Security's own CORS integration already handles preflight `OPTIONS` short-circuiting, credential-header validation, and filter ordering ahead of authentication — a hand-rolled filter risks getting the ordering-before-auth requirement wrong (Pattern 4) |
| Optimistic-lock version comparison | A custom ETag/If-Match HTTP header scheme | The existing `@Version` + explicit-compare pattern already proven on Column/Task/Subtask | Introducing an HTTP-header-based scheme for Boards only would fragment the API's concurrency model across resources for no benefit — every other resource already uses body-field versioning |
| SQL injection defense | Manual input sanitization/escaping in service methods | JPA/Hibernate parameter binding (already in effect via `@Query`/derived queries and `EntityManager`) | D-16's injection tests exist to *prove* the existing binding holds, not to add new defense — this codebase has no raw/concatenated SQL anywhere in `src/main` to begin with |

**Key insight:** every "don't hand-roll" item in this phase already has a project-standard or framework-standard answer in use elsewhere in the codebase (Column/Task/Subtask locking) or in Spring itself (ProblemDetail, AuthenticationEntryPoint, CorsConfigurationSource) — the work here is convergence and symmetry, not invention.

## Common Pitfalls

### Pitfall 1: Returning bare `ProblemDetail` (not wrapped in `ResponseEntity`) defaults to HTTP 200
**What goes wrong:** A `@ExceptionHandler` method that returns a plain `ProblemDetail` (no `@ResponseStatus`, no `ResponseEntity` wrapper) from a plain `@ControllerAdvice` (not extending `ResponseEntityExceptionHandler`) does not automatically pick up `problemDetail.getStatus()` as the HTTP response status — it silently returns 200.
**Why it happens:** The automatic status-from-`ProblemDetail` behavior is implemented in `ResponseEntityExceptionHandler`'s own internal machinery; a bare `@ControllerAdvice` like this codebase's `GlobalExceptionHandler` (confirmed: `public class GlobalExceptionHandler` with no `extends` clause [VERIFIED: src/main/java/com/vrudenko/kanban_board/handler/GlobalExceptionHandler.java:28]) does not get that behavior for free.
**How to avoid:** D-01 already specifies `ResponseEntity<ProblemDetail>` as every handler's return type (see Pattern 1) — as long as every new handler follows `ResponseEntity.status(problem.getStatus()).body(problem)`, this pitfall never triggers. Do not "simplify" any handler to a bare `ProblemDetail` return type during implementation.
**Warning signs:** A new test asserting `status().isNotFound()` (or similar) passes with `status().isOk()` instead during a refactor — check the handler's return type first.

### Pitfall 2: `ProblemDetail` extension properties are NOT nested under `"properties"` in the JSON body
**What goes wrong:** Writing `jsonPath("$.properties.code")` in a MockMvc assertion, or `.body("properties.code", ...)` in REST Assured, silently fails to match because the actual key is `$.code` (top-level).
**Why it happens:** `ProblemDetailJacksonMixin` — auto-registered because Jackson is on the classpath — flattens `getProperties()` into top-level JSON fields (see Pattern 1's verified finding). The `"properties"`-nested shape is only what happens *without* Jackson, which never applies here.
**How to avoid:** Assert directly against the top-level key: `jsonPath("$.code").value("BOARD_NOT_FOUND")`, `jsonPath("$.errors.name").exists()`.
**Warning signs:** A brand-new test for D-02/D-03 fails with "no value at JSON path" despite the response body visibly containing the expected key when printed via `.andDo(print())`.

### Pitfall 3: The `AuthenticationEntryPoint` and the `AccessDeniedException`→403 remap are two independent code paths — do not try to unify them into one handler
**What goes wrong:** An implementation attempt that tries to route both "genuinely unauthenticated" and "authenticated but denied" through the same `GlobalExceptionHandler` branch, or conversely tries to make `AuthenticationEntryPoint` handle ownership-denial cases.
**Why it happens:** They look similar (both produce a 4xx `ProblemDetail`), but they fire from structurally different places: the entry point fires from inside `ExceptionTranslationFilter`, *before* `DispatcherServlet`/`@ControllerAdvice` ever runs, for requests that never resolve to a controller method at all; `GlobalExceptionHandler`'s `AppAccessDeniedException` branch fires *after* `DispatcherServlet` has already dispatched to a controller, for an authenticated user whose service-layer ownership check failed (see the verified filter-chain mechanic in Pattern 2 and the System Architecture Diagram above).
**How to avoid:** Implement them as two separate classes/methods exactly as D-04 and D-05 describe — a new `AuthenticationEntryPoint` bean, and a status remap inside the existing `GlobalExceptionHandler`. Both should independently produce the *same JSON shape* (same `ProblemDetail` fields), but they are two independent call sites, not one shared method.
**Warning signs:** A test hitting a protected endpoint with no session at all (expecting 401) instead gets whatever `GlobalExceptionHandler`'s `AccessDeniedException` branch now returns (403) — a sign the entry point was never wired via `http.exceptionHandling(...)` and the request is still falling through to Spring Security's default `Http403ForbiddenEntryPoint`.

### Pitfall 4: `http.cors(Customizer.withDefaults())` already exists and must NOT be re-added or changed — only the bean is new
**What goes wrong:** Adding a second `.cors(...)` call, or replacing the existing `Customizer.withDefaults()` with an explicit `.cors(cors -> cors.configurationSource(corsConfigurationSource))` — both are redundant with the existing line and risk a duplicate-bean or filter-ordering surprise.
**Why it happens:** Most CORS tutorials show a `.cors(cors -> cors.configurationSource(...))`-style explicit wiring, which reads as "the fix" — but `SecurityConfiguration.java:53` [VERIFIED: `http.csrf(AbstractHttpConfigurer::disable).cors(Customizer.withDefaults());`] already delegates to Spring Security's bean auto-detection, confirmed by the official docs quoted in Pattern 4.
**How to avoid:** Leave `SecurityConfiguration.java:53` untouched; add only the new `@Bean CorsConfigurationSource corsConfigurationSource(...)` method.
**Warning signs:** A code review flags a diff touching `SecurityConfiguration.java:53` for this decision — that line should not appear in the diff at all.

### Pitfall 5: `@Valid` alone does not enforce the D-09 "field validation before duplicate-email check" ordering without confirming the fail-fast propagation path
**What goes wrong:** Assuming `@Valid`'s pre-method-body timing (Pattern 3) is a general Spring MVC/DTO-validation fact requires no test — but the specific claim ("this falls out naturally... no explicit ordering code needed") should still be covered by at least one new/updated test asserting a malformed-and-duplicate signup (e.g. malformed email that also happens to collide) returns 400, not 409, proving the ordering empirically rather than by inference alone.
**Why it happens:** D-09 is stated as a given ("falls out naturally"), which is correct per Pattern 3's verified mechanic, but "correct in theory" and "covered by a regression test" are different guarantees — a future refactor (e.g. someone moving validation into the service layer) could silently invert the order with no test catching it.
**How to avoid:** Add one test case alongside D-16's coverage: signup with a malformed email that also matches an existing user's email, asserting 400 (field error) not 409 (duplicate).
**Warning signs:** None currently — this is a coverage gap to close, not a live bug.

### Pitfall 6: The V7 migration's `boards.version` column name will collide with `BoardEntity.column`'s Java field name confusion if not careful with generated getters
**What goes wrong:** `BoardEntity` already has a `Set<ColumnEntity> column` field (singular name on a plural-typed field — a pre-existing, deliberately-not-renamed inconsistency [VERIFIED: src/main/java/com/vrudenko/kanban_board/mapper/BoardFullMapper.java:21-25 Javadoc, and src/main/java/com/vrudenko/kanban_board/entity/BoardEntity.java:47 `private Set<ColumnEntity> column;`]). Adding `@Version private Long version;` is unrelated to this and will not collide with it, but an implementer skimming the entity should not confuse `board.getColumn()` (the columns collection) with `board.getVersion()` (the new optimistic-lock field) when writing `BoardService.updateById`'s compare logic.
**Why it happens:** Naming proximity (`column`/`version`) plus the existing inconsistency being called out explicitly in nearby Javadoc.
**How to avoid:** Copy `ColumnService.updateById`'s exact compare-then-flush shape (Pattern 5) rather than writing it from scratch — the reference implementation already gets this right.
**Warning signs:** A compile error is actually the safe outcome here (wrong getter name), so this is a low-severity note, not a runtime risk.

### Pitfall 7: D-15 only names `BoardFullResponseDTO` — the flat `BoardResponseDTO` also needs `version`, or update-then-chain breaks
**What goes wrong:** Implementing D-13/D-15 literally (only `BoardFullResponseDTO` gains `version`) leaves `BoardResponseDTO` — returned by `POST /boards`, `PUT /boards/{boardId}`, and `GET /boards` — with no `version` field at all.
**Why it happens:** CONTEXT.md's D-15 explicitly scopes the addition to `BoardFullResponseDTO` only, reasoning about the `GET /boards/{boardId}/full` → rename workflow. But `PUT /boards/{boardId}` (`BoardController.updateById`, returning `BoardResponseDTO` [VERIFIED: src/main/java/com/vrudenko/kanban_board/controller/BoardController.java:64-70]) is the endpoint a client calls to *make* a version-safe rename — and its response is the natural source of the version needed for the *next* rename. Every other resource's flat response DTO already carries `version`: `ColumnResponseDTO` [VERIFIED: src/main/java/com/vrudenko/kanban_board/dto/column_dto/ColumnResponseDTO.java:17 — `private Long version;`] and (by the same established pattern) `TaskResponseDTO`. Without it on `BoardResponseDTO`, a frontend doing sequential renames would be forced to `GET /boards/{boardId}/full` after every `PUT`, just to re-fetch the version — an asymmetric, easy-to-miss workflow gap relative to every other resource in this API.
**How to avoid:** Add `private Long version;` to `BoardResponseDTO` as well, even though CONTEXT.md's D-15 does not name it explicitly — treat this as filling an implied gap in the locked decision, consistent with the `ColumnResponseDTO`/`TaskResponseDTO` precedent, not as re-litigating D-15. Flag this explicitly to the user/planner since it technically extends a locked decision's literal scope (see Assumptions Log A1).
**Warning signs:** A new `AuthorizationGatingE2ETest` or a manual verification pass on `PUT /boards/{boardId}` finds no `version` key in the response body.

### Pitfall 8: Injection test payloads must go through real HTTP/MockMvc into real Postgres, never the service layer directly with a mocked repository
**What goes wrong:** Writing D-16's SQL-injection tests as service-layer unit tests with a mocked `BoardRepository` would prove nothing — the entire point is that JPA/Hibernate's real parameter binding (via the real `PreparedStatement` machinery against real Postgres) neutralizes the payload.
**Why it happens:** This codebase's own convention (`docs/CODE_STYLE.md` rule 4) already forbids mocks entirely, so this pitfall is unlikely to occur here specifically — noted for completeness since it is the single most common way this exact test category gets built wrong in other codebases.
**How to avoid:** Extend `AbstractAppMockMvcTest` (or `AbstractAppTest` for pure service-level cases) per the existing convention; D-17 already specifies the `security/InjectionAttemptE2ETest` location, which by this codebase's `docs/CODE_STYLE.md` rule 4 will extend one of the three sanctioned base classes, all backed by the real Testcontainers Postgres.
**Warning signs:** N/A — the codebase's existing "no mocks" ArchUnit-adjacent convention already guards against this by construction.

### Pitfall 9: The verified route count is 22, not "~19" — recount before writing the auth-gating sweep test
**What goes wrong:** D-19 estimates "~19" protected routes for `AuthorizationGatingE2ETest` to sweep. A direct grep-and-read of every `@RestController` this session counts **22** distinct `@PreAuthorize("isAuthenticated()")`-gated routes across 7 controllers: `BoardController` (6), `ColumnController` (5), `TaskController` (4), `SubtaskController` (3), `UserController` (2), `TaskMoveController` (1), `ActivityController` (1) [VERIFIED: direct Read of all 7 controller files, this session, plus `ApiPaths.java`]. `AuthenticationController`'s 2 routes (`/signin`, `/signup`) are deliberately excluded — they are the two `permitAll()` routes [VERIFIED: src/main/java/com/vrudenko/kanban_board/security/SecurityConfiguration.java:61-67].
**Why it happens:** CONTEXT.md's "~19" is an estimate from the audit, not a fresh count against the current tree — `TaskMoveController` and `ActivityController` (1 route each) may not have been included in the original tally, or a route was added since.
**How to avoid:** At plan/implementation time, re-derive the list programmatically (e.g. grep every `@GetMapping`/`@PostMapping`/`@PutMapping`/`@PatchMapping`/`@DeleteMapping` across `controller/` + `security/AuthenticationController.java`'s absence) rather than hand-transcribing CONTEXT.md's approximate count — a sweep test that silently misses `TaskMoveController`/`ActivityController` would leave exactly the two easiest-to-forget routes (a separate flat controller, and a read-only pagination endpoint) unverified.
**Warning signs:** `AuthorizationGatingE2ETest`'s route table has fewer than 22 entries.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| SQL injection via free-text fields (board/task/column/subtask names, descriptions) | Tampering | JPA/Hibernate parameter binding (already in effect everywhere — no raw/concatenated SQL exists in `src/main`); D-16/D-18 add regression proof, not new defense |
