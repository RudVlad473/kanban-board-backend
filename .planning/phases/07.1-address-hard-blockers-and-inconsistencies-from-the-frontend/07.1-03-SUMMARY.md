# Phase 07.1 Plan 03: 401/403 Split — ProblemDetailAuthenticationEntryPoint Summary

**Wired a custom `AuthenticationEntryPoint` that produces a real, RFC 7807 `ProblemDetail`-shaped 401 for every genuinely unauthenticated request, replacing Spring Security's default bodiless `Http403ForbiddenEntryPoint` and completing the 401/403 split plan 07.1-01 started.**

## Performance

- **Duration:** ~30 min
- **Tasks:** 2 (both `tdd`/`auto`)
- **Files modified:** 5 (1 created, 4 modified)

## Accomplishments

- New `ProblemDetailAuthenticationEntryPoint` (`@Component`, `@RequiredArgsConstructor`) implementing `org.springframework.security.web.AuthenticationEntryPoint`: builds a `ProblemDetail` via `ProblemDetail.forStatusAndDetail(HttpStatus.UNAUTHORIZED, "Authentication is required")`, sets `code` = `UNAUTHENTICATED` via the shared `ErrorCode` enum, sets `instance` to the request URI (to match what `HttpEntityMethodProcessor` supplies automatically on `GlobalExceptionHandler`'s arms — a finding, not something the plan called out), and writes it to the response as `application/problem+json` via the Spring-managed `ObjectMapper`
- Wired into `SecurityConfiguration` via `http.exceptionHandling(handling -> handling.authenticationEntryPoint(problemDetailAuthenticationEntryPoint))` — a new `private final AuthenticationEntryPoint problemDetailAuthenticationEntryPoint` field, following the existing `@RequiredArgsConstructor` convention. No `AccessDeniedHandler` was added; the `http.csrf(...).cors(Customizer.withDefaults())` line is byte-for-byte unchanged
- `GlobalExceptionHandlerTest` extended with a new `UnauthenticatedTest` `@Nested` group (3 tests): 401 status + `Content-Type: application/problem+json` + `code: UNAUTHENTICATED`; happy-path 200 for a signed-in request to the same route; and a key-set-equality assertion proving the 401 body (entry point) and a 403 body (`GlobalExceptionHandler`) share the exact same top-level JSON keys — two independent producers, one envelope shape
- Three pre-existing unauthenticated-403 assertions flipped to 401 and renamed per `docs/CODE_STYLE.md` rule 5 (`shouldReturnForbidden_whenNotAuthenticated` → `shouldReturnUnauthorized_whenNotAuthenticated`): `ThemePersistenceE2ETest.GetTheme` and `.UpdateTheme`, and `BoardCreationE2ETest.CreateBoard`. The stale `Http403ForbiddenEntryPoint`-describing comment in `ThemePersistenceE2ETest` was replaced with one naming the new entry point and the now-final 401/403 split. `BoardCreationE2ETest`'s real-socket (REST Assured) assertion additionally checks the response body's `code` field, proving the envelope survives a genuine HTTP round trip, not just MockMvc's in-process dispatch
- Full `./gradlew test` (whole suite, all tiers) green; `./gradlew spotlessCheck` green

## Decisions Made

- **`ProblemDetail#instance` set explicitly in the entry point** — not called out in the plan's action text. Discovered while getting the key-set-equality test GREEN: `GlobalExceptionHandler`'s `ResponseEntity<ProblemDetail>` arms get `instance` populated for free by Spring MVC's `HttpEntityMethodProcessor`, which only runs for a request that reaches a `HandlerMethod`. The entry point runs earlier, from the filter chain, so that machinery never fires — without the explicit `problem.setInstance(URI.create(request.getRequestURI()))` call, the 401 and 403 bodies would differ by exactly the `instance` key and the plan's own acceptance criterion (matching key sets) would fail. This is a Rule 1 (bug) fix under the deviation rules: the plan's stated behavior ("top-level key set matches") was not achievable without it.
- **Pre-commit hook constraint (same as 07.1-01)**: this repo's `.githooks/pre-commit` runs `./gradlew fastTest` and hard-fails any commit containing a failing test, so a literal RED-only commit cannot exist here. RED was verified via a direct, uncommitted `./gradlew test --tests '*GlobalExceptionHandlerTest'` run before writing the implementation (confirmed two real failures — bodiless 403, not 401 — for the right reason), then GREEN was written and the `test(...)`/`feat(...)` split preserved.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `ProblemDetail#instance` was missing from the entry point's envelope**
- **Found during:** Task 1, while running the key-set-equality assertion after the initial GREEN implementation
- **Issue:** The 401 body produced by `ProblemDetailAuthenticationEntryPoint` was missing the `instance` key that `GlobalExceptionHandler`'s `ResponseEntity<ProblemDetail>` arms carry — `HttpEntityMethodProcessor` populates it automatically for any `ResponseEntity<ProblemDetail>` return value reaching that processor, which a filter-chain-level entry point never does. The plan's own acceptance criterion ("top-level key set matches the key set of a 403 ownership-denial body") would fail without fixing this.
- **Fix:** Added `problem.setInstance(URI.create(request.getRequestURI()))` in `commence`, with an inline comment explaining why this manual step is needed here specifically.
- **Files modified:** `ProblemDetailAuthenticationEntryPoint.java` (part of the same feat commit, not a separate fix commit).
- **Verification:** `shouldMatchAccessDeniedBodyKeySet_whenComparing401To403` passes; full `./gradlew test` green.
- **Committed in:** `96c25ec`

**2. [Rule 3 - Blocking] Transient Windows file-lock failure in the pre-commit hook**
- **Found during:** Task 1's first `test(...)` commit attempt
- **Issue:** `./gradlew fastTest` failed with `Unable to delete directory ...build\test-results\fastTest\binary` — a stale Gradle daemon/file-handle race on Windows, not a real test failure. Two attempts also exceeded the 2-minute default Bash tool timeout before the daemon-stop retry succeeded.
- **Fix:** Ran `./gradlew --stop` and retried the identical commit command with an explicit longer timeout; the retry succeeded cleanly (`BUILD SUCCESSFUL in 3m 12s`).
- **Files modified:** None.
- **Verification:** Retry succeeded; no recurrence on the remaining two commits.
- **Committed in:** N/A (resolved by daemon stop + retry, not a code fix)
