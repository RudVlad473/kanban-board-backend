<objective>
Make Jakarta Validation actually fire on the signin and signup request bodies, surface duplicate-email
signups as an explicit 409, and harden the test fixtures that adding validation would otherwise break.

Purpose: `@Valid` is silently missing on the only two `permitAll()` routes in the API, so every field
constraint on `SigninRequestDTO`/`SignupRequestDTO` is currently dead code. Turning it on is a
one-annotation change with a repository-wide blast radius, because every fixture password in the
suite is a random lowercase word that the `@Password` constraint rejects.
Output: `@Valid` on both routes, an `existsByEmail`-guarded 409 signup path, strengthened fixture
passwords, and the `getForeignUser()` fixture plan 07.1-08 depends on.
</objective>

## Alternate approaches considered

The genuinely contested decision here is **how to stop `signup`'s blanket
`catch (Exception e) { throw new BadCredentialsException(...); }` from swallowing D-07's 409.**
This is a live defect discovered while planning, not a hypothetical: `userService.save(signupDTO)`
is called *inside* that try block, so any `AppDuplicateResourceException` it throws becomes a 401.

**Approach A (chosen): guard for the duplicate email in `UserService.save` and move the
`userService.save(...)` call outside the try block in `AuthenticationController.signup`.**

**Approach B: narrow the catch to `catch (AccessDeniedException | AuthenticationException e)`.**

**Approach C: re-throw `AppDuplicateResourceException` from inside the catch via an `instanceof`
check before collapsing everything else.**

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — move the save out of the try | + The try block then wraps exactly what it was written to wrap: the *authentication* attempt. + The duplicate check and the anti-enumeration collapse become structurally independent, so neither can regress the other. − Requires the compensating `userService.deleteById(createdUser.getId())` rollback path to still see `createdUser`, so the variable must be hoisted above the try. | **Picked.** It fixes the cause (a try block scoped too widely) rather than patching the symptom, and leaves the anti-enumeration behaviour byte-identical for the cases D-08 says must keep it. |
| B — narrow the catch | + Smallest diff. − Silently changes behaviour for every *other* exception type the blanket catch currently absorbs (e.g. a `DataAccessException` mid-signup would now surface as a 500 instead of a 401), which is an unreviewed side effect in an auth path. | Rejected — a wider behavioural change than it looks, in the most security-sensitive method in the app. |
| C — `instanceof` re-throw inside the catch | + Surgical; + no restructuring. − Encodes the exception taxonomy in two places (the catch and the handler); − the next exception that needs to escape requires editing the same fragile spot again; − reads as a workaround rather than an intent. | Rejected — it works but leaves the trap armed for the next person. |

Secondary decision — **fixture password strength**:

| Approach | Pros / Cons | Why picked |
|----------|-------------|------------|
| Central `generateValidPassword()` helper on `AbstractAppTest`, used by every fixture site | + One place to change if `@Password` ever changes; + every subclass inherits correctness. − Touches the base class every test depends on. | **Picked.** |
| A hard-coded constant password shared by all fixtures | + Simplest. − Loses the randomization the existing fixtures deliberately use; − a single literal password in a test suite invites copy-paste into non-test code. | Rejected. |
| Weakening `@Password` to accommodate the fixtures | + No test changes. − Weakens a real security control to serve test convenience. | Rejected outright. |

## Non-obvious trade-offs

- **Security (enumeration, deliberate):** D-07 knowingly trades email enumeration on signup for a
  usable error message. The user made this call explicitly, weighing it against building an
  email-verification flow, for a personal/portfolio-scope project. Recorded as `T-07.1-04-02` with
  disposition `accept` and the rationale attached — not silently absorbed.
- **Security (enumeration, preserved):** signin's generic 401 collapse is *not* relaxed. After this
  plan, signin has two distinct failure classes: malformed input (400, tells you your input was
  malformed — which the client already knows) and genuine auth failure (401, tells you nothing). A
  `prohibitions` entry guards this.
- **Blast radius:** adding `@Valid` to signin is verified to break every one of the ~12 test classes
  that call `signinCookie()`, because `dataFactory.getRandomWord(8)` produces a lowercase word with
  no uppercase, digit, or special character. This is why task 1 (fixtures) runs before task 2
  (`@Valid`) — reversing that order leaves the suite red between commits.
- **Performance:** one extra `existsByEmail` query per signup. Signup is not a hot path, and the
  alternative (catching the unique-constraint violation) does not exist here, because there is no
  unique constraint on `users.email` in the schema — see the note in task 2.
</tradeoffs>
