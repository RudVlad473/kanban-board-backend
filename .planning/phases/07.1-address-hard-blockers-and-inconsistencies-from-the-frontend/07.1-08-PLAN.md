## Alternate approaches considered

**How to express the 22-route auth-gating sweep:**

**Approach A (chosen): a parameterized route table — one data structure listing method, URL template
and the fixture ids needed, driving two parameterized tests (no-session -> 401, foreign-user -> 403).**

**Approach B: one hand-written `@Test` per route per case (44 methods).**

**Approach C: reflectively discover routes from Spring's `RequestMappingHandlerMapping` at runtime and
assert over every discovered mapping.**

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — parameterized route table | + Adding a route means adding one table row; + a missing row is visible as a short table rather than as an absent method among 44. + Failure messages name the route. − The table is still hand-maintained, so a new route can be forgotten. | **Picked.** It is the readable middle ground, and task 3 adds a count assertion that turns "forgot a row" into a build failure. |
| B — 44 hand-written tests | + Maximum clarity per case; + easiest to debug one failure. − 44 near-identical methods is exactly the scattering D-19 exists to end; − a missing route is invisible. | Rejected. |
| C — reflective discovery over `RequestMappingHandlerMapping` | + Structurally cannot miss a route — the strongest possible guarantee, and it self-updates. − Cannot know which path variables to substitute or which fixture owns what, so it degenerates into a table anyway for anything beyond a smoke check; − a reflective test that silently discovers zero mappings passes vacuously. | Rejected as the primary mechanism, but **adopted in reduced form**: task 3 uses the handler mapping only to *count* gated routes and assert the table covers them all. That captures C's completeness guarantee without its substitution problem. |

**How to prove SQL injection is inert (D-18):**

| Option | Pros / Cons | Why picked |
|--------|-------------|------------|
| Round-trip assertion — create with a payload name, read it back byte-for-byte, then assert unrelated rows and the table still exist | + Proves the payload was *stored as data*, which is the actual claim; + catches the catastrophic case (a dropped table) directly. − Slightly more setup per case. | **Picked** — D-18 requires exactly this, and a clean HTTP status alone would also be returned by a server that had just executed the payload. |
| Assert only that the response status is 2xx/4xx and not 500 | + Trivial. − A dropped table would very plausibly still produce a clean status on the request that dropped it. | Rejected — it is the weaker claim that looks like the strong one. |

## Non-obvious trade-offs

- **These tests prove an existing property; they must not create one.** There is no raw or
  concatenated SQL anywhere in `src/main`. If a test fails, the correct response is to investigate
  the binding, not to add escaping — a `prohibitions` entry states this, because "fix the failing
  security test by sanitizing input" is the tempting and wrong move.
- **Tier is load-bearing.** These must run through real MockMvc into the real Testcontainers
  PostgreSQL. A service-layer test with a mocked repository would assert nothing about parameter
  binding. `docs/CODE_STYLE.md` rule 4's no-mocks rule already forces this, but it is worth naming.
- **Runtime cost:** two new classes, each building `AbstractAppTest`'s full fixture set per test
  method, and both running in the pre-commit gate. A parameterized sweep over 22 routes times two
  cases is 44 executions with fixture setup each. Task 3 requires measuring `fastTest` before and
  after and reporting the delta — if it is severe, the mitigation is fixture reuse within the class,
  not tagging the class out of the gate (D-22 is explicit that these are exactly the tests that must
  not be silently skipped locally).
- **XSS scope is deliberately narrow.** The server-side claim is "stored and returned verbatim,
  nothing chokes". Asserting the server escapes HTML would be asserting a behaviour this API
  deliberately does not have, and would be a false sense of security for a JSON API whose consumer
  does the rendering.
</tradeoffs>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client -> another user's resources | The IDOR boundary; `OwnershipVerifierService`'s chain verification is what holds it |
| untrusted free-text input -> Hibernate -> PostgreSQL | The injection boundary; JPA parameter binding is what holds it |
| untrusted path variable -> Spring routing -> service lookup | Malformed ids cross here and must degrade to 4xx, not 5xx |
