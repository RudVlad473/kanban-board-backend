<objective>
Close the two build-tooling integrity gaps folded into this phase: pin the Gradle distribution's
SHA-256 and validate the wrapper scripts and jar in CI before Gradle ever runs, and add Gradle's own
dependency-verification metadata so an artifact republished under the same coordinates and version
cannot slip in behind an exact version pin.

Purpose: HARDEN-03 closed the CI Action integrity boundary. These are two different trust
boundaries the same phase leaves open — the build tool itself, and the artifacts it downloads. A
tampered `gradle-wrapper.jar` executes arbitrary code on every CI runner and every contributor
machine before any project code runs; a republished Maven artifact defeats version pinning entirely,
because the version did not change.

Output: a version-pinned distribution checksum, wrapper validation ahead of every Gradle invocation
in CI, and generated dependency-verification metadata proven not to break the build.
</objective>

## Alternate approaches considered (project CLAUDE.md GSD Execution Directive)

### Wrapper integrity

**A —** `gradle/actions/wrapper-validation` in CI only. **B —** `distributionSha256Sum` in
`gradle-wrapper.properties` only. **C —** both (chosen).

| Approach | Pros / Cons | Why picked / not |
|---|---|---|
| A — CI action only | **Pros:** one line per workflow; catches a tampered `gradle-wrapper.jar` or `gradlew` script against Gradle's own published checksum set. **Cons:** validates the *wrapper*, not the *distribution the wrapper downloads*. A wrapper whose jar is authentic but whose `distributionUrl` was retargeted passes this check and then executes an attacker's Gradle. Also CI-only: a contributor's local build is unprotected. | **Not sufficient alone.** |
| B — distribution checksum only | **Pros:** protects every invocation everywhere, CI and local alike, with zero CI configuration; the wrapper itself refuses to proceed on a mismatch. **Cons:** the checking code lives in `gradle-wrapper.jar` — if *that* is the tampered artifact, it can simply not check. Circular. | **Not sufficient alone.** |
| C — both | **Pros:** the two cover each other's blind spot exactly. The CI action establishes the jar is authentic; the authentic jar then enforces the distribution checksum. **Cons:** two mechanisms to keep in step on a Gradle version bump — forget the checksum and the wrapper bricks for everyone. | **Picked.** The failure mode of forgetting is loud and immediate, which is the acceptable kind. |

### Dependency artifact integrity

**A —** Gradle's native `--write-verification-metadata sha256` (chosen). **B —** a separate CI
staleness check comparing declared versions against published checksums. **C —** wrapper integrity
only; defer artifact verification.

| Approach | Pros / Cons | Why picked / not |
|---|---|---|
| A — native verification metadata | **Pros:** integrates with Gradle's own resolution pipeline, so it verifies what Gradle *actually resolved* rather than what a side-channel script thinks it should have; enforcement is automatic at resolution time, no extra CI step to keep in sync; covers plugins and transitive dependencies, not just declared ones. **Cons:** high blast radius (see below); every dependency change needs a regeneration commit. | **Picked.** |
| B — out-of-band checksum diff script | **Pros:** no build-breaking risk; fully advisory. **Cons:** hand-rolls what Gradle already does correctly; can drift from what Gradle actually resolved (that gap is the whole vulnerability); this repo's own "Don't Hand-Roll" research entry names this explicitly. | **Not picked.** |
| C — defer | **Pros:** avoids the recurring cost entirely. **Cons:** CONTEXT.md folded this todo in as in-scope; deferring it silently would be scope reduction, not a decision. | **Not picked** — but see the checkpoint, which gives an explicit, evidence-based off-ramp if the cost proves unacceptable once real. |

## Non-obvious trade-offs

- **THE BIG ONE — this interacts with HARDEN-01, which this same phase just expanded.** Once
  `gradle/verification-metadata.xml` exists, every Dependabot gradle-ecosystem PR bumps a dependency
  whose new artifact is not in the metadata, so **every such PR will fail its build** until a human
  regenerates and commits the metadata. That is arguably correct behaviour — an unverified new
  artifact *should* fail — but it converts Dependabot from "review and merge" into "review,
  regenerate, commit, merge" for every single bump. The existing `open-pull-requests-limit: 5` means
  up to five of these can be open at once. This consequence was not visible when the todo was folded
  in; the Task 3 checkpoint surfaces it explicitly with a clean revert path.
- **Blast radius (build-breaking):** an incomplete metadata file — generated from a run that did not
  resolve every configuration — fails *every* build for *every* developer and every CI job, with an
  error that reads like a security incident. This is why Task 2 requires a full `spotlessCheck test`
  resolution pass against the committed file before it is trusted, not a `help` task.
- **Performance:** SHA-256 verification of resolved artifacts adds a small, one-off cost per newly
  downloaded artifact and effectively nothing on a warm Gradle cache. Metadata *generation* is the
  expensive part and happens only when dependencies change.
- **Availability (wrapper checksum):** pinning `distributionSha256Sum` means a Gradle version bump
  that updates `distributionUrl` alone leaves the wrapper unable to run at all. Loud, immediate, and
  fixed by one line — but it must be documented next to the pin so the next person to bump Gradle is
  not debugging it cold.
- **Security (scope honesty):** SHA-256 checksums prove an artifact is byte-identical to the one
  present when the metadata was generated. They do NOT prove that artifact was ever trustworthy.
  This control defends against post-publication substitution, not against a dependency that was
  malicious from the start — that remains OWASP dependency-check's and human review's job.
</tradeoffs>

  <name>Task 3: Accept, soften, or revert dependency verification with its Dependabot cost visible</name>
  <what-built>
    Two build-tooling integrity controls are now live: a pinned Gradle distribution checksum plus

    regenerates `gradle/verification-metadata.xml` and commits it alongside the version bump. The
    existing `open-pull-requests-limit: 5` means up to five such PRs can be open at once. This is
    defensible — an unverified new artifact arguably *should* fail — but it turns every dependency
    bump into a two-commit chore, indefinitely.
  </what-built>
  <how-to-verify>
    1. Confirm the controls work, not just that they exist:
       - `./gradlew --version` reports 8.11.1 (the distribution checksum is accepted).
       - The `Validate Gradle wrapper` step appears green in the most recent `deploy.yml` and
         `security-scan.yml` runs, and appears ABOVE the first Gradle step in each job's step list
         in the Actions UI.
       - `./gradlew spotlessCheck test --refresh-dependencies` passed from a cold cache locally.
    2. See the Dependabot cost for yourself before accepting it. Open the most recent open Dependabot
       gradle PR (`gh pr list --author "app/dependabot"`), or trigger a check for updates from
       Insights -> Dependency graph -> Dependabot -> gradle -> Check for updates. When a PR exists,
       look at its `run-tests` result. Expected: red, with a Gradle dependency-verification error
       naming the new artifact.
    3. Decide, and say which:
       - **Accept as-is.** The bump-plus-regenerate chore is worth the artifact-integrity guarantee.
         Nothing further to do.
       - **Accept with a softening.** Keep verification, but reduce the friction — e.g. lower
         `open-pull-requests-limit` for the gradle ecosystem so fewer red PRs accumulate at once, or
