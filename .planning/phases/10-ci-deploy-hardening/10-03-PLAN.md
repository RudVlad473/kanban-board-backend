## Alternate approaches considered (project CLAUDE.md GSD Execution Directive)

### The NVD_API_KEY failure — how to attack it

**A —** blind fix: re-set the secret and hope. **B —** add a temporary, non-disclosing diagnostic
step, dispatch, read the result, then fix and remove the probe (chosen). **C —** remove the
preflight entirely and let `dependencyCheckAnalyze` fail on its own if the key is missing.

| Approach | Pros / Cons | Why picked / not |
|---|---|---|
| A — re-set and hope | **Pros:** one command; if the cause is a corrupted stored value, it works immediately. **Cons:** if the cause is scope, policy, or interpolation, re-setting changes nothing and you learn nothing — and you have now overwritten the evidence, so the next attempt is blinder than this one. The todo's own root-cause section is explicitly "not yet investigated". | **Not picked as the first move.** It remains the *likely remedy* once the diagnosis points at value corruption. |
| B — diagnose, then fix, then remove the probe | **Pros:** distinguishes the four live hypotheses (scope, whitespace/encoding, genuinely empty, org policy) in a single dispatched run; the probe is cheap and its output is safe by construction; the fix is then targeted rather than speculative. **Cons:** costs one extra CI round trip and one extra commit to remove the probe. | **Picked.** RESEARCH Pitfall 7 names the blind fix as the specific trap here. |
| C — delete the preflight | **Pros:** the job stops failing at step one. **Cons:** converts a loud, seconds-long, precisely-named failure into a 45-minute timeout that looks identical to "ran and found nothing" in the Actions UI — which is the exact failure mode the preflight's own comment says it exists to prevent. Removing a working alarm because the thing it is reporting is inconvenient. | **Not picked.** |

### The preflight's secret reference — textual interpolation vs `env:`

The preflight currently interpolates `${{ secrets.NVD_API_KEY }}` directly into its `run:` script
text, while the downstream analyze step passes the same secret through an `env:` block. Standardising
on `env:` is chosen for both steps.

| Approach | Pros / Cons | Why picked / not |
|---|---|---|
| Keep textual `${{ }}` in `run:` | **Pros:** no change. **Cons:** GitHub substitutes the value into the script *text* before any shell runs, so a stored value containing a quote, backslash, or newline produces malformed shell — a step failure that looks exactly like "the secret is empty". This is a genuine injection surface, and it is also a live root-cause candidate for the very bug being fixed. | **Not picked.** |
| `env:` indirection in both steps | **Pros:** the value reaches the shell as an environment variable, never as script text — no interpolation, no injection surface, and the `[ -z ]` test then genuinely tests emptiness rather than testing whether the substituted text happened to parse. **Cons:** RESEARCH cites a community report of a mis-indented `env:` block scoping a secret to the wrong step — so the indentation must be visually checked, not assumed. | **Picked.** Correct regardless of what the diagnosis turns up. |

## Non-obvious trade-offs

- **Security (real, currently live):** the textual-interpolation preflight is a script-injection
  surface today. It is low-exploitability — the injected content is a repository secret only a
  maintainer can set — but it is also, plausibly, the bug. Fixing the surface and fixing the bug may
  be the same edit; the diagnostic exists so that is established rather than assumed.
- **Information disclosure (the probe itself):** GitHub masks the exact secret string in logs but
  does NOT mask values derived from it. A full digest of a 36-character key is not practically
  reversible, but a truncated prefix plus a character-class count is strictly sufficient for the
  diagnosis and leaks strictly less. Take the smaller option.
- **Correctness (version bump, non-obvious):** bumping `actions/setup-java` across a major changes
  the bundled cache implementation. This job's `cache: 'gradle'` input and its separate
  `actions/cache@v4` step for the dependency-check H2 database are independent — the latter is keyed
  on the plugin version and is untouched. Do not conflate them; wiping the dependency-check data
  cache turns a ~1-minute warm run into a multi-hour cold NVD population.
- **Availability:** this job stays report-only at the Gradle level (`failBuildOnCVSS = 11`) and
  schedule-driven. Nothing in this plan changes that posture, and nothing in this plan should make
  the job's verdict a merge gate.
</tradeoffs>
