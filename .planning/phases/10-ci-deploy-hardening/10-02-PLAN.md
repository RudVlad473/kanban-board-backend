<objective>
Layer a live-credential verification pass on top of this repo's existing regex/entropy secret
scanning in CI, and fix the pre-commit hook's silent false-clean when it runs from a worktree
created outside the main repo tree.

Purpose: gitleaks answers "does this look like a credential?" — it cannot answer "is this
credential currently live and exploitable?", which is the question that decides whether a leak is
an incident or a nuisance. Separately, the pre-commit hook today produces a *clean* result rather
than an error when its bind-mount assumption does not hold, which is the worst possible failure
mode for a security gate: indistinguishable from a genuine pass.

Output: `secret-scan.yml` with a second, digest-pinned, diff-scoped, hard-gated TruffleHog job;
`.githooks/pre-commit` with an explicit two-branch scan-path selection covering both worktree
layouts.
</objective>

## Alternate approaches considered (project CLAUDE.md GSD Execution Directive)

### HARDEN-02 — how to invoke TruffleHog

**A —** `trufflesecurity/trufflehog` marketplace action. **B —** direct `docker run` against a
digest-pinned `ghcr.io/trufflesecurity/trufflehog` image (chosen). **C —** download the release
binary and verify its checksum in the job.

| Approach | Pros / Cons | Why picked / not |
|---|---|---|
| A — marketplace action | **Pros:** handles base/head range resolution for push and PR events itself; least YAML to write. **Cons:** its own most-copied documentation example references a mutable branch, i.e. the exact anti-pattern HARDEN-03 exists to eliminate — adopting it unpinned would contradict this phase's own thesis in the same commit; pinning it correctly means pinning a wrapper that then pulls an unpinned image underneath, so the pin buys less than it looks like. | **Not picked.** |
| B — digest-pinned `docker run` | **Pros:** structurally identical to the gitleaks invocation twelve lines above it in the same file, so the two gates cannot drift into different invocation styles; one pinned artifact, fully auditable; the image digest is the *only* trust dependency. **Cons:** the push/PR range must be resolved by hand in shell, including the degenerate cases the action would have handled. | **Picked.** The hand-written range is ~8 lines and is made explicit rather than hidden; consistency with the sibling gate is worth more here than the saved lines. |
| C — release binary + checksum | **Pros:** no Docker layer; fastest cold start. **Cons:** a third invocation style in a repo that already standardised on pinned containers for scanners; checksum bookkeeping duplicated by hand for every version bump; loses the reproducible-environment property the container gives. | **Not picked.** |

### HARDEN-05 — how to scan from an out-of-tree worktree

**A —** pipe the staged diff to `gitleaks stdin` (chosen, D-12). **B —** mount the work tree and the
shared git-dir as two separate Docker volumes and reconstruct the `commondir` link inside the
container. **C —** document the limitation and refuse the commit with an explanatory message.

| Approach | Pros / Cons | Why picked / not |
|---|---|---|
| A — `stdin` fallback | **Pros:** gitleaks' own documented pre-commit shape, not a novel workaround; no path translation, so it is immune to the MSYS/Windows path rewriting that produced the original bug; ~6 lines. **Cons:** loses path-based allowlist context, because the piped diff carries filenames only as diff headers, not as scannable paths. | **Picked (D-12).** The cost is theoretical for this repo: `.gitleaks.toml` uses only rule-scoped `regexTarget = "match"` allowlists (verified) and has no path-based entry, so nothing is actually lost today. |
| B — two mounts + commondir reconstruction | **Pros:** preserves the full `git --staged` scan mode with complete path fidelity in every case. **Cons:** reconstructing a relative `commondir` link across two mounts is exactly the fragile machinery that broke here in the first place; every future git layout change is a new edge case. | **Not picked.** D-12 already rejected it; recorded so it is not re-litigated. |
| C — document and refuse | **Pros:** zero implementation risk; honest. **Cons:** D-11 explicitly requires a real code fix this phase, and refusing every out-of-tree commit makes the hook hostile without making it more correct. | **Not picked (D-11).** |

## Non-obvious trade-offs

- **Security / network (TruffleHog, non-obvious):** verification is not a local computation. Each
  candidate finding triggers a live authentication attempt against the credential's own provider
  API. That is why the scan is range-scoped rather than full-history: a full-history scan would
  re-attempt authentication against every historical candidate on every single push. D-10 already
  settled that this outbound traffic is acceptable *from a GitHub-hosted runner* — it is not
  acceptable from a developer machine, which is why TruffleHog is CI-only and gitleaks stays the
  pre-commit scanner.
- **Availability (hard gate, accepted):** a hard gate on every push means a TruffleHog false
  positive, an image-pull failure, or a provider API outage blocks all merges to master until
  resolved. D-08 accepted this deliberately, on the reasoning that `--results=verified` only
  *narrows* what gitleaks already flags. The three-way exit branch keeps the two failure classes
  ("found a live credential" vs "the scanner could not run") legible so triage is not guesswork.
- **Correctness (worktree fallback, subtle):** the shell idiom `VAR=x cmd1 | cmd2` applies `VAR`
  only to `cmd1`. RESEARCH.md's drafted snippet places `MSYS_NO_PATHCONV=1` on the `git diff` side
  of the pipe, where it does nothing. Harmless here — the stdin path passes no path arguments to
  Docker at all, which is precisely why it is immune to the Windows path-rewriting bug — but do not
  copy that placement forward believing it is load-bearing.
- **Performance:** running TruffleHog as its own job rather than a step in the gitleaks job costs a
  second full-history checkout (seconds, for ~620 commits) and buys independent pass/fail visibility
  in the Actions UI plus parallel execution. The two run concurrently, so wall-clock does not stack.
</tradeoffs>
