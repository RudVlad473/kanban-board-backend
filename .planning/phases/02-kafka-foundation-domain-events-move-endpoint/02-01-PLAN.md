sealed `ActivityEvent` contract plus `TaskMovedEvent`, `KafkaEventPublisher`, the Kafka

    **Kafka producer configuration.** In `src/main/resources/application.properties` add a
    `# === kafka ===` section with `spring.kafka.bootstrap-servers=${KAFKA_BOOTSTRAP_SERVERS:localhost:9092}`,
    `spring.kafka.producer.key-serializer=org.apache.kafka.common.serialization.StringSerializer`
    and `spring.kafka.producer.value-serializer=org.springframework.kafka.support.serializer.JsonSerializer`.
    The JSON value serializer is required — the default String serializer cannot serialize an

    Add the bounded-failure keys to **both** `application.properties` and
    `application-test.properties`: `spring.kafka.producer.properties.max.block.ms=2000`,
    `spring.kafka.producer.properties.request.timeout.ms=2000`,
    `spring.kafka.producer.properties.delivery.timeout.ms=2000`. These are what make D-01
    literally true rather than nominally true, and the reason is not obvious: the
    `@TransactionalEventListener(AFTER_COMMIT)` method runs synchronously on the request
    thread after the commit but before the HTTP response is written, and
    `KafkaTemplate.send()` blocks inside the producer while it waits for cluster metadata —
    bounded by `max.block.ms`, whose default is 60000. With no reachable broker and the
    default, every mutation would hang the response for a full minute, which is exactly the
    blocked write path D-01 forbids. `delivery.timeout.ms` (default 120000) is what would
    otherwise leave the producer's IO thread retrying against a nonexistent broker long after
    the response returned, slowing the test suite. Add a short properties comment above the
    block recording that these bounds are what keep the write path independent of broker
    reachability, and that they warrant revisiting when a real production broker lands
    (KAFKA-V2-01, deferred to v2).

| T-02-01 | Elevation of Privilege | `TaskService.moveToColumn` — target column authorization | high | mitigate | Resolve the source task via `findById(userId, taskId)` (→ `verifyOwnershipOfTask`) and the target column via `ownershipVerifierService.verifyOwnershipOfColumn(userId, dto.getTargetColumnId())`.
