Prove the whole observability path end to end on one thin slice: one exporter (node_exporter) scraped
by one Prometheus, queried by one Grafana, reached over real public HTTPS through the existing Caddy.

Grafana-to-Prometheus datasource does not work, that is a problem worth finding after one commit
rather than after seven service blocks are already deployed. Nothing here is a prototype — these are
the production service blocks, with production-quality config, that the rest of the phase builds on.

metric visible in a Grafana panel.

**Non-obvious trade-offs:**
- *Security:* D-03 makes Grafana's own login the ONLY gate. That means two Grafana defaults are
  load-bearing rather than cosmetic — anonymous access and self sign-up must both be explicitly
  off, and the admin password must come from `.env.prod`. The image's own defaults are already
  correct today, which is exactly why they are set explicitly here: an unstated default that
  changes in a future image tag would silently remove the only gate.
- *Host visibility, and it is the trade this plan's whole deliverable rests on:* a node_exporter
  running in a container reports the container unless it is given the host's own root filesystem.
  The upstream project's own Docker recipe closes this with `network_mode: host` + `pid: host` +
  `/:/host:ro,rslave` + `--path.rootfs=/host`. This deployment cannot take `network_mode: host` —
  `scripts/verify-compose-ports.py` invariant I2 forbids it in both deployed compose files, by
  name, because host networking publishes every listening port on the host without ever touching a
  `ports:` key. So this plan takes the read-only bind mount and the `--path.*` arguments and NOT
  the two namespace grants, and pays a stated price: `node_network_*` series describe the
  exporter's own network namespace, not the host's NIC. Host CPU, memory, load and filesystem are
  all real; host network throughput is not collected by this phase. Saying that out loud is the
  point — an undisclosed gap in a metric family reads as coverage.
- *Least privilege on that mount:* `pid: host` is also omitted, and its omission is a decision, not
  an oversight. Pointing `--path.procfs` at the host's procfs through the same read-only bind gets
  the same numbers without joining the host PID namespace, and this phase collects no per-process
  metrics that would need more.
- *Certificate cost:* Caddy's automatic HTTPS is per-hostname. The third site block shares the one
  `caddy-data` named volume, so recreating the container reuses all three certificates — but the
  FIRST issuance for the new hostname is a live ACME HTTP-01 challenge that requires the DNS record
  to already resolve to this VM. Deploying the Caddyfile before the DNS record exists burns
  issuance attempts against Let's Encrypt's rate limit for nothing.
- *Memory:* every `mem_limit` this plan sets is an explicitly-labelled provisional Iteration-0
  ceiling, not a measured floor. Plan 12-05 owns the ladder. This mirrors exactly what plan 11-01
  did for the `postgres` service and 11-03 then corrected — the placeholder is deliberate and
  labelled so a reader cannot mistake it for a measurement.
- *Deliberately not enabled:* Prometheus's `--web.enable-lifecycle` flag. It would let plan 12-03
  reload a changed `prometheus.yml` without a restart, but it adds an unauthenticated POST endpoint
  to a service whose access control is "nothing else is on this network". Restarting Prometheus
  costs seconds and loses no data (the TSDB is on a named volume), so the endpoint is not worth it.
</design_alternatives>

## Decision Amendments — recorded, not silent

A locked decision whose literal text this plan does not follow exactly is amended HERE, in writing,
with a date and a rationale. A divergence that is defensible and undisclosed is still undisclosed.

### D-03 — amended 2026-09-07: "no additional Caddy-layer gate" means no additional AUTHENTICATION gate

**D-03 as written** (`12-CONTEXT.md`): Grafana sits behind Caddy's `reverse_proxy` "with no
additional Caddy-layer gate (no `basic_auth`, no IP allowlist) — relies on Grafana's own login
(admin/password or OAuth) **the same way the app's own endpoints rely on Spring Security alone
rather than a Caddy-level gate**."

**Amendment.** `basic_auth` and an IP allowlist stay forbidden, unchanged. A `rate_limit` zone
scoped by a path matcher to Grafana's login path only is PERMITTED and is required by this plan.

**Rationale, and it is D-03's own analogy carried to its conclusion.** The stated benchmark is how
the app's own endpoints are treated. Those endpoints are rate-limited at the Caddy edge today —
`Caddyfile`'s `zone auth` bounds `/api/signin*` and `/api/signup*` at 20 events per 5 minutes —
while authentication itself remains entirely Spring Security's. This repository therefore already
draws the line D-03 was reaching for, and it draws it between *throttling* and *identity gating*,
not between "Caddy does something" and "Caddy does nothing". Reading D-03 as banning throttling
makes the monitoring hostname the one public login on this box with no brute-force bound — and
under D-04/D-08 that single credential guards every metric and every container's logs across both
environments, so it is the login with the largest blast radius, not the smallest.

**Why the zone is path-scoped and not site-wide.** A rate limiter across the whole hostname would
spend Grafana's own budget: one dashboard load fires many `/api/ds/query` and `/public/**`
requests. That is the same non-obvious coupling that got design alternative C rejected. The zone
matches `/login*` only; every other path on the hostname is unthrottled.

**Falsifier.** If Grafana is later fronted by OAuth/SSO with its own throttling, or if a CDN or
load balancer is placed in front of this Caddy (which inverts the `{remote_host}` key choice the
existing zones document), revisit this. **Reversibility:** reversible — deleting the `rate_limit`
block restores D-03's literal reading with no migration and no data movement.
</decision_amendments>
