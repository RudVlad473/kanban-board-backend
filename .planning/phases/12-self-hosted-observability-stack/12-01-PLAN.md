<design_alternatives>
| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A (PICKED): one vertical tracer — node_exporter → Prometheus → Grafana → Caddy → public HTTPS — deployed and proven end to end before any second exporter, log pipeline or dashboard exists** | **+** The two genuinely unproven things in this phase (a third DuckDNS subdomain getting its own Let's Encrypt cert on the shared `caddy-data` volume, and Grafana reachable only via `reverse_proxy`) are exercised on commit one instead of commit seven. **+** node_exporter is the thinnest possible exporter: no credentials, no host socket, no cross-project network — so a failure here is unambiguously the transport path, not the exporter. **−** Requires two VM visits (this plan and each expansion plan) rather than one big deploy. | Picked. The Caddy/DNS/cert leg is the only part of this phase with no in-repo precedent for a *third* hostname, and it is also the part whose failure mode (Let's Encrypt rate-limit ban for a week) is the most expensive to discover late. |
| **B (REJECTED): add all seven services at once, deploy once, debug the whole stack together** | **+** One VM visit, one deploy, less wall-clock. **−** Seven simultaneous unknowns: if Grafana does not load, the cause could be the cert, the Caddy block, the datasource, a network, an image tag, or a `mem_limit`. **−** A Let's Encrypt failure discovered here has already burned the attempt budget for the hostname while six unrelated containers sit half-configured. | Rejected: it trades a cheap early failure for an expensive late one, and this phase's own research flags the cert/subdomain leg (Open Question 1) as the item with a genuinely unverified precondition. |
| **C (REJECTED): path-based route (`/grafana/*`) on the existing production hostname instead of a third subdomain** | **+** No new DNS record, no new certificate, no DuckDNS quota question at all. **−** Requires `GF_SERVER_ROOT_URL` plus `GF_SERVER_SERVE_FROM_SUB_PATH=true`, and sub-path proxying has a documented class of asset-loading failures where the UI half-renders if any config line is ordered wrong. **−** Puts the monitoring UI inside the site block that carries the production rate limiter, so Grafana's own asset requests would spend from the general zone's 120/minute budget — a real, non-obvious coupling. | Rejected as the default, kept as the documented fallback if Task 1 finds DuckDNS cannot host a third subdomain. |

**Non-obvious trade-offs:**
- *Security:* D-03 makes Grafana's own login the ONLY gate. That means two Grafana defaults are
  load-bearing rather than cosmetic — anonymous access and self sign-up must both be explicitly
  off, and the admin password must come from `.env.prod`. The image's own defaults are already
  correct today, which is exactly why they are set explicitly here: an unstated default that
  changes in a future image tag would silently remove the only gate.
- *Certificate cost:* Caddy's automatic HTTPS is per-hostname. The third site block shares the one
  `caddy-data` named volume, so recreating the container reuses all three certificates — but the
  FIRST issuance for the new hostname is a live ACME HTTP-01 challenge that requires the DNS record
  to already resolve to this VM. Deploying the Caddyfile before the DNS record exists burns
  issuance attempts against Let's Encrypt's rate limit for nothing.
- *Memory:* every `mem_limit` this plan sets is an explicitly-labelled provisional Iteration-0
  ceiling, not a measured floor. Plan 12-05 owns the ladder. This mirrors exactly what plan 11-01
  did for the `postgres` service and 11-03 then corrected — the placeholder is deliberate and
  labelled so a reader cannot mistake it for a measurement.
- *Deliberately not enabled:* Prometheus's `--web.enable-lifecycle` flag. It would let plan 12-03
  reload a changed `prometheus.yml` without a restart, but it adds an unauthenticated POST endpoint
  to a service whose access control is "nothing else is on this network". Restarting Prometheus
  costs seconds and loses no data (the TSDB is on a named volume), so the endpoint is not worth it.
</design_alternatives>
