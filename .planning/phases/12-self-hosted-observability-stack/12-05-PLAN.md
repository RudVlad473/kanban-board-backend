<design_alternatives>
| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A (PICKED): restart-ladder descent per service under a workload that includes wide-range dashboard loads and log queries, with the rung below the adopted value tried and observed** | **+** Three times proven in this exact repository, and its evidence format is already the runbook's shape. **+** Catches the specific failure this method was hardened against in plan 08-03: a rung that starts healthy on a point-in-time check and crash-loops only under sustained load. **+** Cheap here relative to Phase 11's ladder — none of these seven containers is in the request path, so a rung that fails costs monitoring downtime, not an application outage. **−** Slow: seven services, several rungs each. | Locked by this repository's own convention and by RESEARCH's Open Question 2, which explicitly says to reuse this method rather than estimate. |
| **B (REJECTED): read `docker stats` at idle for a few days and set each cap at peak-observed plus a fixed percentage** | **+** No restarts at all, no monitoring downtime, and it captures real elapsed-time behaviour a burst does not. **−** It never finds the failing rung, so every adopted number is a value someone stopped at rather than a boundary that was located — which is precisely the distinction the runbook's `### Step below the floor` subsection exists to record. **−** An idle observation cannot see the transient peak: Prometheus's compaction and a wide dashboard query are where its real high-water mark is, and neither happens at idle. | Rejected. It produces numbers that look measured and are not falsifiable. |
| **C (REJECTED): leave the seven services uncapped and rely on the host's memory plus the OOM killer** | **+** No measurement work, and the monitoring stack degrading is less bad than the app degrading. **−** Inverts the risk: the OOM killer picks the largest RSS, which on this box is the JVM serving production traffic. An uncapped Prometheus growing over a 30-day retention window would eventually make the monitoring stack the thing that kills production — the exact failure the `app` service's own `mem_limit` comment was written to close. **−** Contradicts the recommendation from plan 05's research that every co-resident container on this box carries a cgroup limit. | Rejected: it trades a bounded, measured cap for an unbounded one whose failure mode is production being killed by its own monitoring. |

**Non-obvious trade-offs:**
- *The caveat this phase has and the previous three did not, and it is the important one:* Prometheus's
  and Loki's working sets grow with retained data. A ladder run on day one measures a nearly-empty
  TSDB and a nearly-empty chunk store, so an adopted floor that passes today can fail in week three
  under a 30-day retention window (D-07) with no code change and no traffic change. This is not a
  reason to skip the ladder — it is a reason the adopted value must carry deliberate growth headroom
  rather than sitting one rung above the failing one, and a reason the runbook entry must state the
  falsifier explicitly: if either container is OOM-killed weeks after this measurement with no
  configuration change, this measurement's day-one basis is why, and the fix is a higher cap or a
  shorter retention window, not a re-run of the same ladder.
- *Measurement validity:* a point-in-time "it started healthy" check is not evidence. Plan 08-03
  recorded a rung that passed exactly that check and was then found crash-looping with
  `RestartCount=22` once monitored across a real recreate cycle. Every rung here must be observed
  across a recreate plus the workload plus a post-workload settle.
- *Cgroup accounting overhead:* a cap set byte-for-byte equal to a process's own measured high-water
  mark has already broken startup on this box once, for Redpanda. Every adopted value here must state
  its headroom above measured peak RSS as a number, not adopt the bare lowest-passing rung.
- *Blast radius, and why it is lower here:* none of these seven containers is in the request path.
  Restarting Prometheus loses no data (named volume) and restarting Grafana loses no dashboards (plan
  12-04 proved they are provisioned, not volume-resident). What a failing rung costs is a gap in
  monitoring history, which `12-CONTEXT.md` explicitly scopes as non-critical. This ladder therefore
  does not need the maintenance-window discipline Phase 11's did.
- *Where the floor actually is for cAdvisor:* its memory scales with the number of containers it
  watches and its housekeeping interval, not with application traffic. Its ladder will therefore look
  flat under the burst and find its floor at startup, which is a different shape from the others and
  worth recording as such rather than reporting as an anomaly.
</design_alternatives>

import re, sys
lines = open('docker-compose.prod.yml').read().splitlines()
NEW = {'node-exporter','prometheus','grafana','loki','promtail','cadvisor','postgres-exporter'}
GROWING = {'prometheus','loki'}
fails, svc, seen = [], None, set()
for i, ln in enumerate(lines):
    m = re.match(r'^  ([a-z0-9-]+):\s*$', ln)
    if m:
        svc = m.group(1)
    if re.match(r'\s*mem_limit:', ln):
        window = "\n".join(lines[max(0, i - 70):i])
        if 'MEASURED' not in window:
            fails.append(f"{svc}: mem_limit at line {i+1} has no MEASURED basis comment above it")
        if not re.search(r'20\d\d-\d\d-\d\d', window):
            fails.append(f"{svc}: mem_limit at line {i+1} has no dated comment above it")
        if svc in NEW:
            seen.add(svc)
            if '12-05' not in window:
                fails.append(f"{svc}: measured-basis comment does not cite plan 12-05")
            if svc in GROWING and not re.search(r'day[- ]one|growth headroom', window, re.I):
                fails.append(f"{svc}: comment does not state the day-one/growth-headroom caveat "
                             f"for the 30-day retention window")
missing = NEW - seen
if missing:
    fails.append(f"services with no mem_limit found at all: {sorted(missing)}")
if fails:
    print("\n".join("FAIL: " + f for f in fails)); sys.exit(1)
print("mem_limit comments OK")
