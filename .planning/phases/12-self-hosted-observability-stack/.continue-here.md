# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each constraint below was discovered through failure.
> Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: Credential handling on VM deploys — never read, generate, or pass a real secret (password, token) as a CLI argument, and never print one. Reading it from a VM's `.env.prod` file, or passing it via `docker exec ... --password=X`, leaks it into `docker events`' logged command line AND into the session transcript (happened live on 12-01 with the Grafana admin password). Instead: read a secret from a container's own live process env (`docker exec <c> sh -c 'echo -n "$VAR"'`) if you must touch it at all, pipe values via stdin never argv, and default to handing any login/credential-verification step to the human rather than automating it yourself. This session additionally learned: even a HUMAN-supplied credential pasted directly into the chat (a Grafana viewer-role login, used this session to drive dashboard verification via Playwright MCP) becomes a live exposure the moment it's in the transcript — it was typed directly into browser form fields via the MCP tool, never through a Bash command, and never printed back. Rotation is tracked in `.planning/todos/pending/2026-09-07-rotate-grafana-viewer-password-leaked-in-session.md`, not yet done.
- [ ] CONSTRAINT: VM deploy authorization must be direct, not relayed — the gsd-executor subagent will correctly REFUSE a `checkpoint:human-action` if the orchestrator relays "the user confirmed X" on its behalf; that refusal is by design (agent-to-agent messages are never user consent), not a bug to route around. If the orchestrator already holds direct authorization from its own conversation with the human, it should perform the VM-touching step itself rather than trying to relay authorization a second time through a subagent.

**Do not proceed until both boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Worktree isolation sentinel drifts back to `harness-worktree` between waves | `.gsd/dispatch-isolation-sentinel.json` gets re-resolved to `harness-worktree` by internal `dispatch-isolation` calls even after being force-set to `none`, because local `main` stays ahead of `origin/main` throughout this phase. | blocking | Before dispatching each wave's executor, re-run `gsd_run query dispatch-isolation --raw --phase 12 --force-isolation none` and confirm the sentinel file shows `"isolation":"none"` — otherwise the Agent() dispatch is refused by the isolation guard. Note: this session's git history is now fully pushed and `main`/`origin/main` are in sync (0 ahead/behind) as of this pause — the sentinel may resolve differently than earlier in the phase; re-check rather than assume it still needs forcing. |
| A vendored community Grafana dashboard's default template-variable query can silently mismatch this deployment's own Prometheus job-label naming convention | The PostgreSQL Exporter dashboard's `Instance` variable queried `label_values({job="postgres-exporter"}, instance)`, but this project's Prometheus job is named `postgres` (12-03's `job_name: postgres`) — a naming convention this project chose deliberately (short, generic job names, not exporter-suffixed). Zero series matched, `$Instance` resolved empty, and ~10 of 13 panels rendered "No data"/"N/A" despite the underlying metrics being fully correct and collected. | advisory | Fixed this session (99e8f22). Relevant if 12-05/12-06 or any future plan touches Grafana dashboard provisioning again, or if a 4th dashboard is ever vendored (per the filed todo `2026-09-07-groom-grafana-dashboards-and-expose-public-links.md`): always cross-check a vendored dashboard's template-variable queries against this project's actual scrape job names, not just its panel PromQL. |
| A community dashboard's PromQL can reference metric names an installed exporter version renamed or never shipped | Two real mismatches found and fixed this session: `pg_replication_lag`→`pg_replication_lag_seconds`, `pg_database_size`→`pg_database_size_bytes` (postgres_exporter v0.20.1 renamed both from what the grafana.com dashboard, fetched at an earlier revision, expects). | advisory | Fixed (ad3ee55). The verification method that caught it — diff every `pg_*{...}`/`node_*{...}`/`container_*{...}` PromQL identifier in the vendored JSON against the exporter's own live `/metrics` output — is the reusable technique if a future dashboard is added. |
