**Non-obvious trade-offs:**
- *Security, cAdvisor:* D-05 already accepts the `docker.sock`/`/sys`/`/proc` grant as a scoped
  exception. What must NOT drift in is the broader grant most tutorials show: `--privileged` and
  `--pid=host`. Those are needed only for PROCESS-level metrics, which D-05's stated scope
  (per-container CPU/mem/network) explicitly does not include. The risk here is a copied example, not
  a design choice, which is why the verify asserts their absence rather than trusting the action text.
- *Security, Postgres role:* reusing `kanban_prod_app`'s credentials would work and would need no new
  role. It would also blur a boundary Phase 11 drew deliberately — least-privilege roles per concern —
  and would give a monitoring sidecar an application role's write access forever. `pg_monitor` is a
  built-in role granting exactly the `pg_stat_*`/`pg_settings`/replication read surface and nothing
  else. Both databases need an explicit `GRANT CONNECT` because Phase 11's init script already revoked
  PUBLIC's default connect grant per database — so the grant is required, not defensive.
- *Isolation:* the nonprod project's isolation surface widens by exactly one network edge. Stated as a
  real, deliberate consequence: `redpanda-nonprod` becomes reachable from `prometheus`. Nothing else
  on `kanban-metrics` means nothing else can reach it, and the verify asserts membership is exactly two.
- *Availability, and the expectation is not 50/50:* neither broker's committed `command:` sets
  `--admin-addr`, and a Redpanda admin API left at its default is more likely than not to be bound
  to loopback rather than `0.0.0.0` — in which case `/public_metrics` is unreachable from
  Prometheus no matter how the networks are wired. **Plan for "the flag is needed" as the expected
  path and treat "9644 already answers from off-container" as the pleasant surprise**, not the
  other way round. This costs nothing to be wrong about in the cheap direction: Task 1 probes
  before Task 2 writes anything, so the argument lands in the SAME compose edit as the
  `kanban-metrics` wiring and Task 3 deploys once. There is no discover-then-recreate two-step in
  this plan, and Task 1's probe method is specifically chosen (below) so that the nonprod broker's
  bind address is known before Task 2 authors, not after Task 3 deploys — the one path that would
  have produced a second recreate.
- *Availability, the part that is genuinely a decision:* adding `--admin-addr` recreates the
  PRODUCTION broker, which ripples through `app`'s `depends_on: service_healthy`. That is a real
  interruption, which is why the probe is a checkpoint that reports back to a human rather than a
  step that acts on its own.
- *Credential handling, and this repository has already paid for the lesson once:* the exporter's
  password must never be interpolated into a string that also has to serve as a delimiter-bearing
  format. A DSN URI is exactly such a format — `@`, `:`, `/`, `?`, `#` and `%` are all structural
  in it — so a password containing any of them either corrupts the connection or, worse, redirects
  it to a host an attacker chose. Phase 11's plan 11-07 hardened
  `docker/postgres-init/01-create-databases-and-roles.sh` against the identical hazard (CR-01) by
  moving to `psql -v` variable substitution. The same answer applies here: hand the exporter the
  user and password as their own environment variables and let it do the encoding.

<decision_amendments>
## Decision Amendments — recorded, not silent

### D-05 — amended 2026-09-07: cAdvisor's mount set is broader than the decision's literal list, and still entirely read-only

**D-05 as written** (`12-CONTEXT.md`): include cAdvisor "with its `/var/run/docker.sock`, `/sys`,
`/proc` mounts **read-only**".

**What this plan actually mounts:** `/:/rootfs:ro`, `/var/run:/var/run:ro`, `/sys:/sys:ro`,
`/var/lib/docker/:/var/lib/docker:ro`. That is broader than D-05's list in two places (the whole
`/var/run` directory rather than the socket alone, plus `/rootfs` and `/var/lib/docker`), and
narrower in one (`/proc` is not mounted at all).

**Rationale.** D-05's literal set does not work. cAdvisor needs `/rootfs` and `/var/lib/docker` to
resolve container filesystem and image-layer state; without them it starts, answers `/metrics`, and
emits empty or self-only series — a failure that looks identical to success on a target-health
page, which is exactly why RESEARCH Pitfall 3 exists. It does not need a `/proc` bind, because it
reads the container's own procfs, which is host-wide for the counters it uses. So the choice was
never "D-05's mounts or more" — it was "D-05's mounts and a broken exporter, or the real set".

**What is preserved, and it is the part of D-05 that carries the actual security weight:** every
mount is read-only, `--privileged` is absent, and `pid: host` is absent. `/var/run` read-only is in
fact STRICTER than cAdvisor's own upstream example, which mounts it read-write. The amendment
widens the file surface and does not widen the privilege posture.

**Why this is written down rather than done quietly.** The decision-coverage gate that ran at plan
time checks only that D-05 is *referenced*, not that the concrete mounts match its text — so a
silent substitution here would have passed every automated check and been invisible to a future
reader comparing the compose file against CONTEXT.md. The cross-AI review caught precisely that.

**Where else this must be recorded.** Task 2 puts it in the compose comment; Task 3 puts it in
`docs/INFRA_RUNBOOK.md`'s `### cAdvisor mount posture` subsection, which is the operator-facing doc
trail a reader reaches from the deployment rather than from the planning directory.

**Falsifier.** If a future cAdvisor release drops the `/rootfs` or `/var/lib/docker` requirement, or
adds a `/proc` one, this amendment is stale — re-derive the set against that release's own docs and
re-record it. **Reversibility:** reversible — D-05 itself already rates cAdvisor as independently
removable; the mount set is a service-block edit with no data movement.
</decision_amendments>

the same reason.

for this:

strict precedence over the split trio in the exporter's own resolution order, so a leftover

there looking right.

not by this compose file guessing at it. State the falsifier: if a future exporter release changes
that assembly or its variable precedence, this reasoning is stale and the split must be re-verified
