**Non-obvious trade-offs:**
- *Security, and it is the real one:* Promtail needs `docker.sock` to enumerate and tail containers.
  A container with the Docker socket can create a privileged container and is therefore effectively
  host-root if compromised. Mounting it read-only does NOT remove that — the Docker API's dangerous
  operations are HTTP requests over the socket, not filesystem writes to it. Read-only is still
  correct (it removes one class of tampering for free) but the honest mitigation is that Promtail
  is a non-internet-facing container with no inbound route, and that this is the same grant D-05
  already accepts for cAdvisor. Stated here rather than left implied, because a read-only mount
  reads as a stronger control than it is.
- *Information disclosure:* from this plan onward, everything every container writes to stdout is
  centralized behind one Grafana login. That includes Postgres. If `log_statement` is ever raised to
  `all` for debugging (as Phase 11 did once for a one-off verification), bind-parameter values start
  flowing into the centralized store. Task 3 checks the live setting for exactly this reason.
- *Correctness:* Docker's `json-file` driver wraps every line in a JSON envelope. Without an explicit
  `docker: {}` pipeline stage, Loki stores the envelope as the log line. The failure is silent and
  looks like "logs are working" until someone actually reads one, which is exactly the moment it
  matters. The verify asserts the stage's presence rather than trusting the config was copied from a
  current example.
- *Disk:* Loki's 30 days share the same 222 GB headroom as Prometheus's. Neither is bounded by a
  size cap, only by time. For this workload's volume that is comfortable, and losing this data is
  explicitly not treated as data loss (`12-CONTEXT.md`, out of scope: backup of the stack's own data).
</design_alternatives>
