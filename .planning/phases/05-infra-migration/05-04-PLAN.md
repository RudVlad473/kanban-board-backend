## Execution constraint

Running commands over a real SSH session against real infrastructure, and placing real credentials into a file on that VM, are human actions. The executor prepares the exact artifacts and the exact command sequence and hands them over; the human runs them and reports the observed output. The executor may read back non-secret command output the human pastes (container status, health status, curl response codes, query-count figures) and must not ask for the contents of the environment file.

**Non-obvious trade-offs this tracer measures rather than assumes:**
- *Memory:* the broker and a JVM sharing one small VM is this phase's headline risk. The provisional caps from plan 05-02 are a guess sized to a figure that plan 05-03 has now verified. This task replaces the guess with a measurement — resident memory of both processes under a real workload — rather than declaring the caps correct because nothing crashed in the first minute.
- *Availability:* every failed Let's Encrypt issuance attempt counts against a rate limit whose ban lasts a week. That makes the certificate step the one place in this phase where iterating quickly is actively harmful, so DNS and port 80 are confirmed before Caddy is ever started.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet to Caddy | The first time this boundary is genuinely live; TLS terminates here |
| VM to Neon over the public internet | Real credentials now in use on a real connection carrying real user data |
| Environment file on the VM | The one place production credentials exist in plaintext at rest |
| App to broker and registry, internal only | Unauthenticated services whose safety depends entirely on remaining unreachable from outside |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-20 | Spoofing | TLS certificate on the public endpoint | high | mitigate | Verification requires a publicly trusted issuer accepted without a warning, and requires plain HTTP to redirect rather than serve — a self-signed certificate or a working plain-HTTP path both fail the acceptance criteria |
| T-05-21 | Information Disclosure | Production credentials in the VM environment file | high | mitigate | The file is created on the VM by the human, is never committed, and is never pasted into the conversation; the executor is explicitly forbidden from requesting its contents |
| T-05-22 | Information Disclosure | Broker or registry exposed to make testing convenient | critical | mitigate | Task 2 requires the suite to reach the registry via the VM or an SSH tunnel and explicitly forbids publishing a port for test convenience; an acceptance criterion re-confirms off-VM unreachability after the task |
| T-05-23 | Tampering | Data written to the wrong database because the app silently connected somewhere else | high | mitigate | Persistence is proven by a write through the public API surviving a container restart, not by the absence of a startup error |
| T-05-24 | Denial of Service | Broker starving the JVM, or caps loosened to make the deploy succeed | high | mitigate | Caps set from measured figures against the verified shape with stated headroom; the plan's prohibition forbids quietly loosening a cap, and the virtual-threads workaround is negative-grepped |
| T-05-25 | Denial of Service | Let's Encrypt rate-limit ban from repeated failed issuance | medium | mitigate | DNS resolution and port 80 reachability are both confirmed before Caddy is started for the first time, rather than discovered by failed issuance attempts |
| T-05-26 | Repudiation | An undocumented manual step that plan 05-05's automation then omits | medium | mitigate | Every command and every deviation is recorded in the runbook, and the acceptance criteria require deviations to be recorded rather than retro-fitted into the instructions |
