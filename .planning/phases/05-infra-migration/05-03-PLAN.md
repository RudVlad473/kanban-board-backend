## Execution constraint governing every task in this plan

The executor agent cannot create cloud accounts, click through provider consoles, or handle credential values — this is a platform-level boundary, not a preference. Every task here is a blocking human checkpoint. The executor's job is to give the human the exact sequence to perform, one action at a time, and then verify the observable outcome from outside (DNS resolution, port reachability, a recorded shape figure) without ever seeing a secret. This is D-02's guided model rather than a front-loaded list.

Values safe for the executor to receive and record in the runbook: the public IP, the hostname, the OCPU/RAM shape, the OS image name, the region, the deploy username. Values that must never reach the executor: SSH private keys, Neon passwords, full connection strings, and any API token.

**Non-obvious trade-offs surfaced by this plan:**
- *Security:* the OS-level firewall is the layer most likely to give false comfort. Docker inserts its own forwarding rules that bypass the chain a plain rule listing displays, so a container publishing a port is reachable even under a default-drop input policy. This is why INFRA-08 requires external verification, and why plan 05-06's audit is a scan from off-VM rather than a rule listing.
- *Availability:* SSH must remain reachable from arbitrary source addresses, because GitHub-hosted runners have no stable egress range worth pinning. That is a deliberate accepted exposure, not an oversight — key-only authentication carries the weight instead.

  <context>
    Published guidance says the Always Free A1 Flex allocation is 2 OCPU / 12 GB after Oracle's undocumented mid-2026 reduction, but that figure is MEDIUM confidence and not vendor-confirmed for this tenancy. Plan 05-02 has already written conservative Redpanda memory and SMP caps sized for that figure, with a comment saying they must be revisited once the real number is known. Reading the console before creating the instance costs a minute and removes the guess.

    Separately, Oracle assigns an ephemeral public IP by default and does not surface the choice as a decision in the creation flow. Three things in this phase pin themselves to that address: the DNS A record, the SSH host fingerprint pinned in plan 05-05, and the OCI ingress rules. If the instance is ever recreated — a real possibility on the free tier — an ephemeral address changes and all three break at once.
  </context>
  <options>
    <option id="reserved-ip">
      <name>Provision a Reserved (static) Public IP and attach it at instance creation</name>
      <pros>The address survives instance recreation, so DNS, fingerprint pinning and firewall rules all keep working; no dynamic-DNS updater, cron job, or extra token secret is needed anywhere in this phase.</pros>
      <cons>One extra console step; depends on this tenancy's Always Free allocation actually including a Reserved IP at no cost, which is the open question to resolve while in the console.</cons>
    </option>
    <option id="ephemeral-ip-with-updater">
      <name>Accept the default ephemeral IP and add a dynamic-DNS updater on the VM</name>
      <pros>Works even if Reserved IPs turn out to be unavailable or chargeable on this tenancy.</pros>
      <cons>Adds a recurring updater process plus a DNS provider token as a new secret on the VM; does not help the pinned SSH host fingerprint or the OCI ingress rules at all, so an instance recreation still breaks the deploy pipeline silently.</cons>
    </option>
  </options>

  <action>
    Guide the human through this sequence one step at a time, confirming each before moving on. Do not batch the whole list into a single message.

    Create the A1 Flex instance in the decided region with the decided shape and an Ubuntu LTS image, attaching the decided public-IP type. The human uploads their own existing SSH public key as the instance's initial key — this is their personal administrative access, and it is deliberately not the deploy key that plan 05-05 creates.

    Once the instance is reachable, install Docker Engine and the Compose plugin from Docker's official apt repository rather than the distribution's docker.io package, so the Compose plugin is present and versions are current. Add the human's login user to the docker group so subsequent commands need no elevation.

    Configure the OS-level firewall using the input-chain rule sequence in RESEARCH.md's Code Examples: default-drop on input, accept established and related, accept loopback, then accept exactly TCP 22, 80 and 443. Add no rule for the broker, the registry, or the application port. Persist the rules with the netfilter persistence tool so they survive a reboot, then reboot the VM and confirm both that SSH still works and that the rules are still in place — an unpersisted rule set that silently vanishes on the next reboot is the specific failure this step exists to prevent.

    Configure the OCI Security List for the instance's subnet to allow ingress on exactly TCP 22, 80 and 443 from the internet, and remove or narrow any broader default ingress rule. Then configure the Network Security Group attached to the instance with the same three-port allowance. Both layers must be set even though either alone appears sufficient, because OCI's layers are additive and an unaudited permissive layer is invisible from the other two.

    Have the human record, for each of the three layers, the resulting rule set as they see it. Write these into a new docs/INFRA_RUNBOOK.md alongside the instance metadata. Full external verification is plan 05-06's job; what this step needs is that each layer was consciously set and written down.

    Create docs/INFRA_RUNBOOK.md capturing: region, availability domain, OS image and version, shape and verified OCPU/RAM, public IP and whether it is reserved, the Docker and Compose versions installed, all three layers' rule sets, and the date. Record no private keys, no passwords, and no connection strings — this file is committed to git.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet to the Oracle VM | Three additive OCI layers govern this boundary; any one left permissive exposes everything behind it |
| Human's machine to provider consoles | Credentials are generated and entered here; the executor agent is deliberately outside this boundary |
| Committed runbook to git history | Anything written into the runbook is permanent and public to anyone with repo access |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-14 | Information Disclosure | Credentials leaking into the committed runbook or into agent context | high | mitigate | The runbook records only non-secret metadata; acceptance criteria negative-grep private-key headers and connection-string schemes in the committed file, and every task states explicitly which values the executor may receive |
| T-05-15 | Information Disclosure | An unaudited permissive layer among the three OCI network layers | critical | mitigate | All three layers are configured in the same session with their rule sets recorded; external probing confirms the effective result rather than trusting any single layer's console view |
| T-05-16 | Denial of Service | Firewall rules lost on reboot because persistence was never saved | high | mitigate | The rules are persisted and then a real reboot is performed inside this task, with reachability re-confirmed afterwards rather than assumed |
| T-05-17 | Spoofing | Instance recreation silently changing the public IP, invalidating DNS, the pinned SSH fingerprint and the ingress rules at once | high | mitigate | Reserved (static) IP provisioned by decision in task 1; if unavailable, the fallback and its residual fragility are recorded as an explicit accepted risk rather than discovered later |
| T-05-18 | Elevation of Privilege | Human's personal SSH key reused as the CI deploy credential | medium | mitigate | Task 2 uses the human's own key for administrative access only; plan 05-05 creates a separate, dedicated, minimally-privileged deploy identity |
| T-05-19 | Information Disclosure | DDL executed over the pooled endpoint instead of the direct one | medium | mitigate | Task 3 requires the human to state which endpoint is which before proceeding; plan 05-05's CI job additionally fails loudly if the configured URL carries the pooler marker |
</threat_model>
