## Approaches considered, and why the chosen one

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **Standalone `docker-compose.prod.yml`** | + The two files' service sets genuinely differ: production drops Postgres entirely and adds Caddy. + Nothing in the local dev file needs to change, matching this phase's own discretion boundary. − Some duplication between the two files' app service definitions. | **Picked.** RESEARCH.md Open Question 1 reaches the same conclusion for a structural reason: Compose overlays can add and modify services but cannot remove one, and removing the Postgres service is mandatory here. |
| Compose overlay applied on top of the local file | + No duplication. − Cannot remove the Postgres service, so production would carry a stray Postgres container competing for the free-tier VM's RAM and, worse, offering a silent wrong-database fallback target. | Rejected — the thing it cannot do is the thing that matters most. |
| A single file with profiles | + One file. − Profile-gated services still parse in both contexts and it is easy to activate the wrong profile on a manual `docker compose up`, which is exactly the command a human runs by hand in plan 05-04. | Rejected — too easy to get wrong at the one moment it is run by hand. |

**Non-obvious trade-offs carried by this plan:**
- *Memory:* Redpanda's un-tuned defaults assume it owns the whole machine. On a shared 2-OCPU/12GB VM alongside a JVM, that is a real OOM path, and the local dev preset that papers over it is precisely what must not be copied. The caps are conservative on purpose; plan 05-04 measures and adjusts.
- *Security:* every `ports:` entry in this file is a hole punched through the OS firewall by Docker itself — Docker's published-port rules bypass the filter chain a plain rule listing shows. Publishing nothing but 80/443 is therefore a load-bearing part of INFRA-08, not a stylistic choice.
- *Availability:* a Let's Encrypt rate-limit ban lasts a week and is triggered by repeated certificate requests, which is exactly what a non-persistent Caddy data directory produces during iterative debugging on a new VM.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet to the Oracle VM | Every published host port in the Compose manifest is a hole through the VM's network layers; Docker punches these itself, bypassing the filter chain a plain rule listing displays |
| Caddy to app (internal Docker network) | TLS terminates at Caddy; traffic onward to the app is plain HTTP inside the VM |
| App to Redpanda / Schema Registry (internal Docker network) | Unauthenticated broker and registry — safe only for as long as they are unreachable from outside |
| Documentation to operator behavior | A diagram that misdescribes the topology causes real misconfiguration later |
