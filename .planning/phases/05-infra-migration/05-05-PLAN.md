## Approaches considered, and why the chosen one

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **Maintained SSH/SCP actions with fingerprint pinning, copying the Compose manifest and deploying with Compose** | + Host-key pinning is a first-class input rather than something to hand-roll. + The VM needs no repository credential of its own. + Restart policy, healthchecks and log caps come from the manifest for free. − Two third-party actions to keep pinned. | **Picked.** The two rejected options each reintroduce something this phase exists to remove. |
| Keep the existing hand-rolled ssh heredoc, updated for the new host | + No new action dependency. − It is the exact shape whose defects this phase is fixing: no host-key verification at all, a bare container run with no restart policy, no healthcheck and no log caps. | Rejected — the old job is a worked example of the anti-pattern, not a template. |
| Have the VM pull the repository itself with git | + No file copying step. − Requires provisioning a repository credential on a public-facing box, adding a secret and a credential-exposure surface for no benefit at this scale. | Rejected — more secrets to protect nothing. |

**Non-obvious trade-offs carried by this plan:**
- *Security:* pinning the host key by fingerprint means a legitimately recreated VM breaks the deploy until the pin is updated. That friction is the feature — the alternative is a pipeline that would happily deploy to an impostor. The failure must be resolved by re-pinning, never by disabling verification.
- *Correctness:* placing DDL verification before deploy in the dependency graph means a schema change that fails to apply blocks the image from reaching the VM. That is the intended coupling; it also means a broken DDL script halts deploys entirely, which is the correct trade for a database whose schema has no version tracking.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner to the Oracle VM | An automated, credentialed path into production from infrastructure neither side controls |
| GitHub Actions runner to Neon direct endpoint | The DDL job holds a credential capable of altering production schema |
| Repository secret store to workflow runtime | Every secret is materialised into a runner process on every run |
| Deploy user on the VM | A standing access path whose privilege scope determines the blast radius of a leaked key |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
