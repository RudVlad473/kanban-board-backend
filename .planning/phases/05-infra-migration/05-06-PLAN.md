**Non-obvious trade-offs this plan makes explicit:**
- *Security:* the temptation at this stage is to accept the console's own rule listings as proof. They are not. Docker inserts forwarding rules that bypass the input chain a local listing shows, and OCI's three layers are additive, so each layer's view is individually incomplete. Only an external scan measures the composite result, which is exactly why INFRA-08 words itself the way it does.
- *Ordering:* revocation comes last on purpose. Removing the AWS-era secrets before the new pipeline is proven would destroy the only record of the previous configuration at the moment it might still be needed for comparison.

    Measure rather than assert. Confirm first that every running container reports the configured log driver and its size and count options as actually in effect, by inspecting the running containers rather than by re-reading the manifest — a manifest option that was never applied because the container predates it is a realistic and invisible failure.

    Then generate enough log volume from the application container to cross the configured size limit more than once. Driving the application's own request logging through repeated API calls is preferable to writing synthetic output, because it exercises the same path real logs take. After generating the volume, list the container's log directory and record the number of rotated files and their total size.

    Confirm three things from the observation: that the file count does not exceed the configured maximum; that the total bytes do not exceed size multiplied by count; and that the oldest file was deleted at rotation rather than the set growing. A count that has not yet reached the maximum proves nothing about the bound, so generate enough volume to force at least one deletion.

    Record the measured figures and the worst-case aggregate bound across all three services against the VM's actual disk capacity, so the headroom is a number rather than an assurance.
  </action>
