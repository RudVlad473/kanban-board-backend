## Approach Analysis

Required by CLAUDE.md's GSD Execution Directives.

**The decision under analysis:** RESEARCH.md Open Question 1 — what to do about `docker-compose.yml`'s `app` service hardcoding a Hibernate auto-alter env var, which Spring Boot's property precedence lets outrank D-03's `validate` setting in `application.properties`.

| Approach | Pros / Cons | Why Picked |
|----------|-------------|------------|
| **A. Set the compose `app` service's `SPRING_JPA_HIBERNATE_DDL_AUTO` to `validate`** (chosen) | **Pros:** the local stack now behaves exactly as a real deploy would, which is the only way D-03's own stated verification method ("prove migrations apply cleanly via the docker-compose Postgres") actually proves anything about `validate`; a Flyway/entity mismatch fails on this machine instead of at deploy time; keeps the variable present and explicit rather than relying on a reader knowing the properties-file default. **Cons:** a developer who adds an entity field and forgets a migration now gets a boot failure instead of a convenient auto-alter — that convenience is precisely what this phase removes, so the cost is intended. | Picked: it is the only option under which local verification exercises the behavior being shipped. The alternative leaves D-03 locally unverifiable and documents the gap instead of closing it. |
| **B. Delete the env var entirely and let `application.properties` supply `validate`** | **Pros:** one fewer place the value lives; no risk of the two drifting apart. **Cons:** silently changes behavior for anyone reading only `docker-compose.yml`; the file's own convention is to state non-obvious config explicitly with an inline comment rather than rely on an invisible default. | Rejected: less legible, same net behavior. Approach A gets the same result while keeping the value visible where a reader looking at the local stack will find it. |
| **C. Leave the auto-alter override and document the gap** | **Pros:** zero risk of breaking the local stack; developers keep the auto-alter convenience for scratch work. **Cons:** local verification would prove only "Flyway applied," never "the migrated schema matches the entities" — leaving the phase's most valuable check unexercised until a real deploy, which per D-03 does not exist yet. It also masks exactly the drift `validate` exists to surface. | Rejected: RESEARCH.md explicitly asked the planner to make a call rather than let this default silently, and this option defaults it. |

**Non-obvious trade-offs:**

- **Failure mode shift (the security-relevant one):** `validate` converts a class of silent schema drift into a hard startup failure. On a deploy target that is a fail-fast safety property; on a rolling deploy it is also an availability risk, because a mismatched migration takes the new instance down at boot rather than degrading. That is why this plan requires the clean-volume proof *before* merge rather than after — the risk is real but is paid on this machine.
- **`rehearseHistoricalSchemas` inherits both changes.** That Gradle task deliberately does not set the test profile, so it resolves `application.properties`' datasource. It now gets Flyway *and* `validate` against whatever real Postgres `DB_HOST`/`DB_NAME` point at. If that database was built by Hibernate auto-alter and has no `flyway_schema_history`, Flyway refuses to migrate a non-empty unmanaged schema. Not fixed here (out of D-01..D-04's scope, and STATE.md already tracks that task as human-run) — documented in Task 2 so the next person to run it is not ambushed.
- **State invalidation:** the clean-volume proof requires destroying `postgres-data`. Any locally-generated `activity_log` corpus is lost — this already happened during Phase 4 and was regenerated by exercising the running app, so the procedure is known.
- **Performance:** `validate` costs one metadata read per table at `EntityManagerFactory` bootstrap. Immaterial locally; worth remembering against a cold serverless Postgres in Phase 5, where it lands on the critical path of the first boot after a scale-to-zero.
