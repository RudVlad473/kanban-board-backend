## Pattern Assignments

### `build.gradle` (add `flyway-core` + `flyway-database-postgresql`)

**Analog:** `build.gradle` itself — existing `dependencies {}` block, lines 47-148.

**Convention for BOM-managed (unversioned) deps** (lines 58-63, 100, 113):
```groovy
implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
implementation 'org.springframework.boot:spring-boot-starter-validation'
implementation 'org.postgresql:postgresql'

// https://mvnrepository.com/artifact/org.springframework.boot/spring-boot-starter-security
implementation 'org.springframework.boot:spring-boot-starter-security'
...
implementation 'org.springframework.kafka:spring-kafka'
```
Pattern: single-quoted GString-style groovy dependency coordinates, no explicit version when Spring's BOM manages it (matches RESEARCH.md's own recommendation for `flyway-core`/`flyway-database-postgresql`). An mvnrepository comment link is used inconsistently — present for some (security, guava, mapstruct, collections4) but absent for others (data-jpa, postgresql, kafka) — so it is optional, not a hard convention. A short **why this is unversioned** comment is used when the deliberate omission needs explanation (see the `spring-session-jdbc` comment block, lines 65-71, and the `commons-lang3` version-bump comment block, lines 81-93) — worth doing here too since RESEARCH.md's rationale ("BOM-managed, moves with Spring Boot bumps") is exactly the kind of non-obvious constraint this project documents inline.

**Recommended insertion point:** immediately after the `implementation 'org.postgresql:postgresql'` line (58-60) — keeps the Postgres-related persistence deps grouped, matching the existing adjacency of `spring-boot-starter-data-jpa` + `postgresql` driver.

**Suggested excerpt to add:**
```groovy
implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
implementation 'org.springframework.boot:spring-boot-starter-validation'
implementation 'org.postgresql:postgresql'

// Flyway version is BOM-managed by Spring Boot 3.5.0 (pinned to 11.7.2 in
// spring-boot-dependencies) -- deliberately left unversioned so a future Spring Boot
// bump moves both artifacts together, matching this project's existing precedent of
// leaving Spring-managed deps unversioned (spring-kafka, postgresql driver above).
implementation 'org.flywaydb:flyway-core'
implementation 'org.flywaydb:flyway-database-postgresql'
```

### `src/main/resources/application.properties` (add `spring.jpa.hibernate.ddl-auto=validate`)

**Analog:** same file, `# === hibernate ===` section, lines 22-24.

**Section-header comment convention** (lines 1, 4, 7, 12, 22, 26, 44, 54, 81, 107):
```properties
# === application ===
spring.application.name=kanban-board

# === servlet ===
server.servlet.context-path=/api
```
Every logical group is preceded by a `# === lowercase-label ===` banner line, one blank line before the next section. Inline explanatory comments (no banner) are used above individual property lines when the property's behavior is non-obvious (see the `DB_PORT` comment, lines 13-17, and the `spring.session.jdbc.initialize-schema` comment block, lines 29-41) — multi-line, wrapped at ~100 chars, explaining *why*, not just *what*.

**Existing hibernate section** (lines 22-24):
```properties
# === hibernate ===
spring.jpa.hibernate.naming.physical-strategy=org.hibernate.boot.model.naming.CamelCaseToUnderscoresNamingStrategy
spring.jpa.hibernate.naming.implicit-strategy=org.springframework.boot.orm.jpa.hibernate.SpringImplicitNamingStrategy
```

**Suggested edit** (add `ddl-auto=validate` as the first line under the existing banner, with a comment explaining the Flyway/Hibernate division of labor per RESEARCH.md's Pattern 2):
```properties
# === hibernate ===
# Flyway (db/migration/V*.sql) owns making schema changes; ddl-auto=validate only checks
# this app's entity mappings agree with whatever schema Flyway has already applied --
# never both creates and validates. See src/main/resources/db/migration/ for the
# migration history this validates against.
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.hibernate.naming.physical-strategy=org.hibernate.boot.model.naming.CamelCaseToUnderscoresNamingStrategy
spring.jpa.hibernate.naming.implicit-strategy=org.springframework.boot.orm.jpa.hibernate.SpringImplicitNamingStrategy
```

**Suggested edit** (RESEARCH.md's Pitfall 1 — required, not optional; comment explains why per this project's convention of documenting non-obvious constraints inline):
```properties
# === hibernate ===
# Flyway auto-activates for ANY DataSource bean once flyway-core is on the classpath,
# including this H2 in-memory profile -- with no built-in test-profile scoping. Without
# this line, Flyway attempts V1-V4 (Postgres-flavored, including a PL/pgSQL DO $$ block
# in V4) against H2 before Hibernate's create-drop ever runs, failing every
# @SpringBootTest at context startup. ddl-auto stays create-drop (unchanged) -- this is
# an orthogonal addition, not a replacement for it.
spring.flyway.enabled=false
spring.jpa.hibernate.ddl-auto=create-drop
spring.jpa.hibernate.naming.physical-strategy=org.hibernate.boot.model.naming.CamelCaseToUnderscoresNamingStrategy
spring.jpa.hibernate.naming.implicit-strategy=org.springframework.boot.orm.jpa.hibernate.SpringImplicitNamingStrategy
```

### `src/main/resources/db/migration/V1__init.sql`

**Analog:** `docs/plans/backend-modernization/02-optimistic-locking-ddl.sql` (structure/header convention) — read in full this session at the same path pattern as `04-password-hash-not-null-ddl.sql` (read verbatim above).

**Header comment convention observed across all 3 existing DDL scripts** (e.g. `04-password-hash-not-null-ddl.sql:1-54`):
- First line: `-- <origin> -- <short description>: <classification>`
- A `WHAT THIS IS` block explaining the gap being bridged
- A `WHEN TO RUN` / applicability block (N/A for Flyway — checksummed history replaces manual timing)
- A `SAFE TO RE-RUN` / idempotency block (N/A for Flyway — strip per RESEARCH.md's Anti-Patterns; Flyway's own `flyway_schema_history` replaces this guarantee)

**What to keep vs. strip when porting to Flyway (per CONTEXT.md Reusable Assets + RESEARCH.md Anti-Patterns):**
- KEEP: the *rationale* framing (why this schema shape, what it corresponds to historically) — reframed as a short top-of-file comment, not the full manual-runbook prose.
- STRIP: `IF NOT EXISTS` guards, "run this by hand before merging" instructions, `SAFE TO RE-RUN` sections — all redundant/misleading once Flyway's checksum history is the safety mechanism.

**Suggested V1 header, matching this project's terse "why" comment convention** (mirrors RESEARCH.md's own Code Examples section, which already drafted this shape):
```sql
-- V1__init.sql
-- Reconstructs the schema as it existed before Epic 2 (optimistic locking),
-- v1.1 Phase 3 (activity_log), and quick task 260803-m3i (password_hash NOT NULL).
-- Those three deltas are intentionally NOT included here -- see V2/V3/V4.
```
Full column definitions: use RESEARCH.md's Code Examples "V1__init.sql — full baseline" section verbatim (already entity-verified, cites `UserEntity.java`, `BoardEntity.java`, `ColumnEntity.java`, `TaskEntity.java`, `SubtaskEntity.java`, `BaseEntity.java`, `ValidationConstants.java` line numbers) — do not re-derive.

### `src/main/resources/db/migration/V4__add_password_hash_not_null.sql`

**Analog:** `docs/plans/backend-modernization/04-password-hash-not-null-ddl.sql` — read in full this session (69 lines).

**Header pattern in the original** (lines 1-54): extensive WHAT-THIS-IS / WHEN-TO-RUN / PRE-FLIGHT / WHAT-THIS-IS-NOT / SAFE-TO-RE-RUN prose — this is the "one-off manual DDL bridge" runbook style. For the Flyway port, strip all of this down to the load-bearing content: the `DO $$ ... END $$` block itself (lines 56-69), reworded per RESEARCH.md's already-drafted version (only the error message text changes: "re-running this script" → "this migration"):

```sql
-- V4__add_password_hash_not_null.sql
DO $$
DECLARE
    null_hash_count bigint;
BEGIN
    SELECT count(*) INTO null_hash_count FROM users WHERE password_hash IS NULL;

    IF null_hash_count > 0 THEN
        RAISE EXCEPTION
            'Aborting: % row(s) in users have a NULL password_hash. Resolve those rows before re-running this migration.',
            null_hash_count;
    END IF;

    ALTER TABLE users ALTER COLUMN password_hash SET NOT NULL;
END $$;
```

Notable inherited detail worth preserving as a short comment: the original's "WHAT THIS IS NOT" section (lines 43-47) explicitly anticipated this exact migration — "when Epic 3 lands, this manual step must be reflected in migration history... not silently re-applied or lost." Worth a one-line acknowledgment comment in V4 closing that loop, matching this project's habit of cross-referencing prior decisions (see `application.properties`'s references to the DDL scripts, lines 37-39).

## Shared Patterns

### Section-banner comments in `.properties` files
**Source:** `src/main/resources/application.properties` (all section headers) and `application-test.properties` (mirrors the same banners)
**Apply to:** Both `application.properties` and `application-test.properties` edits — new `ddl-auto`/`spring.flyway.enabled` lines go inside the existing `# === hibernate ===` banner section, not a new banner.
```properties
# === hibernate ===
```

### "Why, not just what" inline comment convention
**Source:** pervasive across `application.properties` (DB_PORT comment lines 13-17, session initializer comment lines 29-41), `docker-compose.yml` (postgres port comment lines 8-13), `build.gradle` (commons-lang3 comment lines 81-93)
**Apply to:** every new/edited line in this phase where the *reason* isn't obvious from the line alone — `ddl-auto=validate`, `spring.flyway.enabled=false`, the unversioned Flyway Gradle deps, and (if edited) the docker-compose env var.

### Manual-DDL-script → Flyway-migration porting rule
**Source:** the 3 existing scripts in `docs/plans/backend-modernization/` (`02-optimistic-locking-ddl.sql`, `03-activity-log-ddl.sql`, `04-password-hash-not-null-ddl.sql`)
**Apply to:** V1-V4 — keep the SQL content and its domain rationale, strip `IF NOT EXISTS` guards and "run this by hand" runbook prose (Flyway's checksummed `flyway_schema_history` replaces both).

### Flyway migration file naming
**Source:** RESEARCH.md Architecture Patterns, `V<version>__<description>.sql`, double underscore separator
**Apply to:** all 4 new migration files — `V1__init.sql`, `V2__add_optimistic_locking_version_columns.sql`, `V3__add_activity_log.sql`, `V4__add_password_hash_not_null.sql`.
