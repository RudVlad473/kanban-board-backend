<objective>
Bring the self-hosted PostgreSQL instance up on the Netcup VM and cut both production and nonprod
onto it, in one operation, nonprod first.

Purpose: this is the moment the phase's structural fix actually takes effect — the outage's root
cause (a shared per-project compute-hour quota on a managed provider) stops existing because the
provider stops being in the path. It is also the only place D-01's isolation requirement can be
proven against the real deployed instance rather than a local tracer.

Output: a running `postgres` container on the VM serving two isolated databases, both public HTTPS
health endpoints answering 200 against it, and a dated runbook section carrying the verbatim
evidence.
</objective>

<design_alternatives>
| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A (PICKED): manual, operator-driven cutover over SSH — stage files by hand, bring `postgres` up alone, prove isolation, then bring nonprod and production up in that order** | **+** Every irreversible step is observed by a human at the moment it happens. **+** Matches this repository's own precedent exactly (`docs/INFRA_RUNBOOK.md`'s "Manual deploy — Plan 05-04 Task 1" and "Nonprod bring-up — Plan 08-01"), so the evidence format and the operator's muscle memory already exist. **+** Works right now: the existing `flyway-verify` CI jobs still target the quota-blocked managed provider and will fail, so no CI-driven deploy can reach the VM until plan 11-05 rewrites them. **−** Slower, and its correctness depends on the operator following the sequence. | Picked. The CI path is provably blocked at this point in the phase, so a "let CI do it" cutover is not merely riskier — it cannot run. |
| **B (REJECTED): rewrite the CI Flyway-verify jobs FIRST (plan 11-05's work), then let a normal push-to-main deploy perform the cutover** | **+** No hand-run steps; the deploy pipeline stays the single path to production. **−** The rewritten job targets `postgres` over the VM's internal Docker network — a service that does not exist yet at that point, so the new job would fail for a different reason and the deadlock just moves. **−** The very first bring-up of a one-shot init mechanism would happen unobserved, and the recovery for a half-provisioned volume (`down -v`) is destructive enough that discovering it from a CI log is the wrong place. | Rejected on the ordering deadlock: the CI job needs the container, and the container needs a first bring-up. Something has to be hand-run once. |
| **C (REJECTED): stand the new instance up alongside the old one and run both in parallel for a soak period before switching** | **+** Classic low-risk migration shape; instant rollback. **−** Requires dual-writing or accepting divergent data, and D-04 already says no data is carried over, so there is nothing to keep in sync. **−** The old side is quota-blocked and cannot serve traffic, so "parallel" would mean one live system and one dead one — the soak proves nothing. | Rejected: the parallel-run pattern buys rollback safety that D-04/D-05 have already priced out. |

**Non-obvious trade-offs this plan accepts:**
- *Data:* every board, task, subtask, user and session currently held by the managed provider is
  abandoned (D-04). Not deleted in this plan — the provider's project survives until plan 11-06 —
  but no longer read by anything.
- *Sessions:* the Spring Session JDBC tables (`spring_session`, `spring_session_attributes`) start
  empty. Any browser holding a session cookie is silently logged out at cutover, because the cookie
  names a session id the new database has never seen. Expected under D-05, but it must be written
  down as a stated consequence rather than left to be rediscovered as a bug.
- *Blast radius:* a production Postgres restart now takes nonprod down with it. Accepted under D-01.
- *CI:* the existing `flyway-verify` / `flyway-verify-nonprod` jobs will fail on every push from the
  moment the GitHub Environment secrets are repointed (they cannot reach a host-portless container
  from a GitHub runner) until plan 11-05 lands. This is a known, bounded red window, not a
  regression to debug.
</design_alternatives>

  <instructions>
Hand the operator a single copy-pasteable sequence, in this exact order. Do not reorder: the
provisioning hook is one-shot, so anything that brings the container up before the init script and
the env values are in place burns the only chance to provision without a destructive volume wipe.

This repository's own precedent (`docs/INFRA_RUNBOOK.md`, "Manual deploy — Plan 05-04 Task 1",
execution note) is that the agent may run these commands directly inside the operator's authorized
SSH session rather than the operator hand-typing them. Either is acceptable; what is not acceptable
is proceeding without the operator present, because steps 2 and 7 generate and place credentials.

**Step 1 — create the shared network.** `docker network create kanban-db` on the VM. Idempotent-safe
guard: if it already exists, that is fine and not an error. This mirrors how `kanban-edge` was
created once (recorded in the runbook's "Nonprod bring-up — Plan 08-01" step 1).

**Step 2 — generate three credentials, on the VM, never locally and never in a chat message.** Three
separate `openssl rand -hex 32` invocations: one for the engine superuser, one for the production
application role, one for the nonprod application role. Hex output specifically, because these values
are interpolated into single-quoted SQL literals by the init script and an apostrophe would break
first-boot provisioning in a way that is hard to read from a container log.

**Step 3 — populate `/opt/deploy/kanban-board-backend/.env.prod`** using `.env.prod.example` as the
key list: set `POSTGRES_SUPERUSER`, `POSTGRES_SUPERUSER_PASS`, `DB_HOST=postgres`, `DB_PORT=5432`,
`DB_NAME=kanban_prod`, `DB_USER=kanban_prod_app`, `DB_PASS`, `NONPROD_DB_NAME=kanban_nonprod`,
`NONPROD_DB_USER=kanban_nonprod_app`, `NONPROD_DB_PASS`. Delete the retired JDBC query-string
assignment line if one is present — leaving it is the single most likely way to reproduce the
incident's exact failure signature against a server that has no TLS listener. Keep `IMAGE_TAG`,
`APP_DOMAIN` and `APP_DOMAIN_NONPROD` as they are.

**Step 4 — populate `/opt/deploy/kanban-board-nonprod/.env.nonprod`**: `DB_HOST=postgres`,
`DB_PORT=5432`, `DB_NAME=kanban_nonprod`, `DB_USER=kanban_nonprod_app`, and `DB_PASS` set to the
*same value* as `.env.prod`'s `NONPROD_DB_PASS`. Delete its retired JDBC query-string assignment
line too. Everything else in that file is unchanged.

**Step 5 — stage the new manifests and the init script on the VM.** Copy the plan-11-01 versions of
`docker-compose.prod.yml` to `/opt/deploy/kanban-board-backend/`, `docker-compose.nonprod.yml` to
`/opt/deploy/kanban-board-nonprod/`, and `docker/postgres-init/01-create-databases-and-roles.sh` to
`/opt/deploy/kanban-board-backend/docker/postgres-init/` (creating the directory). Then confirm the
init script is executable on the VM and `chmod +x` it if the transfer did not preserve the mode —
a non-executable script is *sourced* rather than executed by the image's entrypoint, which still
works but changes the shell it runs in.

**Step 6 — bring up ONLY the database.** `docker compose --env-file ./.env.prod -f
docker-compose.prod.yml up -d postgres` from `/opt/deploy/kanban-board-backend`. Wait for the
container to report `(healthy)`. If it does not, read its log: an init-script failure names the
missing variable directly (the script's `:?` guards are there for exactly this). Recovery from a
partially-initialized volume is `docker compose --env-file ./.env.prod -f docker-compose.prod.yml
down -v` followed by a retry — editing the script and restarting will silently skip provisioning.

**Step 7 — prove D-01 isolation live, on the VM.** Via `docker exec` into the running container:
confirm both databases exist, confirm both login roles exist, then attempt a connection as the
nonprod role to the production database over `127.0.0.1` and confirm it is REFUSED, and the reverse
direction likewise. Then confirm each role CAN reach its own database. Capture the verbatim output —
including the refusal message — for Task 3. This is the same assertion set plan 11-01's tracer runs,
re-run against the real deployed instance, because a local tracer proves the mechanism and only this
proves the deployment.

**Step 8 — cut NONPROD over first (D-06).** From `/opt/deploy/kanban-board-nonprod`:
`docker compose --env-file ./.env.nonprod -f docker-compose.nonprod.yml --profile nonprod up -d`.
Confirm `app-nonprod` reaches `(healthy)`, then confirm `kanban_nonprod` holds 8 successful
`flyway_schema_history` rows. Nonprod is the lower-risk half by design — its reset endpoint already
TRUNCATEs everything — so it proves the setup before production goes through it.

**Step 9 — cut PRODUCTION over.** From `/opt/deploy/kanban-board-backend`:
`docker compose --env-file ./.env.prod -f docker-compose.prod.yml up -d`. Confirm `app` reaches
`(healthy)` and `kanban_prod` holds 8 successful `flyway_schema_history` rows.

**Step 10 — prove both environments live from OUTSIDE the VM**, over public HTTPS, not from a
container-internal probe: production's `/api/actuator/health` returns 200, and nonprod's returns
200. Then make one real write through the public production API (create a board via signup +
signin + POST) and confirm it survives a `docker restart` of the `app` container — the same
"a write survives a restart" proof plan 05-04 used, which is what distinguishes a working datasource
from a working health endpoint.

**Step 11 — repoint the GitHub Environment secrets.** In the `production` environment set `DB_HOST`
to `postgres`, `DB_NAME` to `kanban_prod`, `DB_USER` to `kanban_prod_app`, `DB_PASS` to the
generated production role password. In the `staging` environment set the nonprod equivalents. Warn
the operator explicitly: from this point the existing `flyway-verify` / `flyway-verify-nonprod` jobs
will fail on every push, because a GitHub-hosted runner has no route to a container that publishes
no host port. That red window closes when plan 11-05 lands, and it is expected — the alternative
(leaving the secrets pointing at a quota-blocked provider) would fail identically while also being
wrong.

**Do NOT, in this task:** delete or disable anything at the managed provider (plan 11-06, D-07),
change any `mem_limit` (plan 11-03, D-08/D-10), or edit `application.properties` (plan 11-04, D-09).
