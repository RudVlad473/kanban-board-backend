**Non-obvious trade-offs:**
- *Latency vs. failure speed:* lowering the connection-acquisition timeout makes a genuine database
  outage surface as a fast error instead of a long hang. The cost is paid on a cold VM boot, where
  `app-nonprod` cannot express a health dependency on the database (it lives in a different Compose
  project) and may restart-loop briefly until the engine accepts connections. `restart:
  unless-stopped` converges that; the chosen value must leave room for it rather than assuming
  instant availability.
- *Prepared statements:* removing the threshold override re-engages PgJDBC's server-side statement
  reuse. RESEARCH tags this LOW confidence and explicitly says to smoke-test rather than assume —
  the failure mode if something in the stack still depends on the override is an intermittent
  `PSQLException` about a prepared statement already existing or not existing, which is exactly the
  class of bug a single boot check would miss.
- *Test-suite blast radius:* these properties are not test-profile-overridden, so an idle-connection
  floor above zero opens that many connections per live Spring context against the Testcontainers
  engine. With context caching this is small, but "too many clients already" in the test suite is the
  falsifiable signal that the floor was set too high.

Revise the datasource URL template and all six HikariCP properties. Each value below is the target
state; each needs its own one-line reason in the file, and the reason must be about a same-host

**Datasource URL template.** Drop the query-string placeholder from
`spring.datasource.url` entirely, leaving a bare `jdbc:postgresql://host:port/database` shape. Both
of the things the placeholder existed to carry are gone: TLS/channel-binding parameters, because the
connection no longer crosses the public internet and the target container has no TLS listener
configured (a parameter demanding SSL against a server with no SSL listener is a hard connection
failure, not a silent downgrade — and it presents as the identical acquisition-timeout signature the
2026-08-26 incident already produced once); and the prepared-statement threshold override, whose
entire rationale was a transaction-mode connection pooler that is no longer in the path at all. Note
in the comment that re-adding an override hook later is a one-line change, so removing it now is
cheap to reverse.
  <!-- planner-discipline-allow: DB_JDBC_PARAMS -->

**`maximum-pool-size` — keep at 5, restate the reason.** The old reason named a two-OCPU shared VM
and a managed pooler's connection ceiling; neither exists. The new reason is concrete and
checkable: two application containers now share one engine configured with `max_connections=25`
(plan 11-01, D-11), so the worst case is 5 + 5 = 10 application connections plus one CI migration
one-off plus an occasional administrative session — roughly 2x headroom. Cross-reference the engine
setting by name so a future change to either side is visibly coupled to the other.

**`minimum-idle` — raise from 0 to 2.** Both reasons for the floor of zero were provider-specific
and are recorded in this file: the provider billed compute-hours per project across every branch, so
a warm connection cost real quota; and the pool's own refill of a dropped connection was itself the
activity that woke a suspended compute, defeating the scale-to-zero the setting was meant to
achieve. A same-host container has no usage meter, no autosuspend timer, and nothing to wake. A
floor of zero now buys nothing and costs a TCP connect plus a SCRAM handshake on the first request
after any idle period. Keep the line explicit and say why in the comment: an unset value is coerced
to the maximum pool size by the library's own validation, which would silently hold five permanently
warm connections per app rather than none.

**`connection-timeout` — lower from 30000 to 10000.** Thirty seconds was sized to absorb a managed
compute resuming from suspension. A same-host engine either answers a connection request in
single-digit milliseconds or is genuinely unavailable, so the old value now converts an outage into
a thirty-second request hang — the exact user-visible symptom the incident record documents. Ten
seconds is far above any healthy same-host acquisition and still leaves room for the one case where
waiting is legitimate: a cold VM boot, where `app-nonprod` cannot express a health dependency on the
database because it lives in a different Compose project, and briefly retries while the engine
starts. Make that cold-boot case the stated reason the value is not lower still.

**`idle-timeout` — raise from 300000 to 600000, `max-lifetime` — raise from 600000 to 1800000.** The
ten-minute lifetime was set deliberately shorter than the managed provider's idle-connection reaping
window so the pool would refresh connections before the provider silently closed them. There is no
reaper in front of a same-host engine, so churning every connection every ten minutes is pure
overhead. Both values become the library's own defaults, stated explicitly rather than left implicit
per this file's convention. Keep the ordering constraint and its reason in the comment: the library
disables the idle timeout entirely, with only a startup warning, when the two values sit too close
together — which is exactly why the idle timeout was made explicit in the first place.

**`keepalive-time` — raise from 0 to 120000.** This is the value that directly caused the
2026-08-26 outage, by issuing a query on every idle pooled connection every two minutes and thereby
holding a metered compute permanently awake. That mechanism does not exist for a container on the
same host: there is no meter and nothing to keep awake, and a periodic liveness probe is now purely
useful — it detects a connection the engine has dropped (a restart, an administrative termination)
before a real request discovers it. Set it explicitly to the library's own default rather than
deleting the line, and keep the existing warning in the comment: deleting this line does not disable
keepalive, and the library's own Javadoc contradicts its field initializer on that point — a finding
this file records as verified against the library sources. Guard the change with a
falsifiable statement: this reasoning depends on the datasource being same-host and unmetered, so if
this application is ever repointed at a metered or autosuspending database, this line is the first
one to revisit.

**The decision record.** Do not delete the existing dated 2026-08-26 block. Supersede it in place:
keep enough of it that a future reader can still see what the previous values were and why, and add
a new dated block above or below it stating what changed, why (a same-host engine has no cold start,
no autosuspend, no reaper, and no pooler), the accepted cost of each change, and a falsifiable
condition — the same five-part shape the existing record already models, and the shape
`docs/CODE_COMMENTS.md` prescribes for a decision record. Explicitly record that the prepared

reasoning, and name the failure mode a future reader should watch for if it turns out wrong.

Change nothing else in this file. The Hibernate, session, Kafka, CORS and pagination blocks are all
out of scope.

Prove that removing the prepared-statement threshold override is actually safe, by driving a real
repeated-query workload through a real PostgreSQL instance. This is the one change in Task 1 whose
justification is reasoning rather than evidence, and the failure mode it guards against is
intermittent rather than deterministic — a single successful boot would not detect it.

Use the live local stack, not a throwaway JUnit probe class: bring up the local Postgres and
Redpanda from `docker-compose.yml`, wait for Redpanda's healthcheck, then run the application on the
host with the documented environment (note the host-published Postgres port differs from the
container-internal one). This repository's own recorded lesson is that a probe class pays the whole
compile/format/coverage pipeline on every iteration while a live server answers any number of
questions in the sub-second range.

The workload must repeat the SAME parameterised query shapes enough times to cross PgJDBC's default
server-side statement reuse threshold, which the removed override previously held at zero. A handful
of requests is not sufficient — the point of the test is that reuse actually engages. Drive it
through the public API rather than raw SQL so the queries are the ones Hibernate really emits:
sign up, sign in, then repeat a create-read-update-delete cycle over boards, columns, tasks and
subtasks enough times that each statement shape is executed well past the threshold, and include at
least one nested full-board read (the endpoint with the widest join) in the loop.

What to look for, in this order:
1. No `PSQLException` mentioning a prepared statement that already exists or does not exist, in the
   application log, at any point. This is the specific failure the override used to suppress.
2. Every request returns its expected status.
3. `pg_prepared_statements` inside the container reports a non-empty set while the application is
   running — this is the positive confirmation that server-side reuse actually engaged, as opposed to
   the workload simply never reaching the threshold and the test proving nothing.
4. Restart the ENGINE mid-workload — not the application — and confirm the following requests still
   succeed. Dropping the backends while the client still believes its server-side statements exist
   is the second way this class of bug surfaces, and restarting the application instead would reset
   the client's own state too and prove nothing. Read the engine's prepared-statement view BEFORE
   the restart: that view is per-session and empties on reconnect.

Record the outcome in the decision record Task 1 wrote: state the workload size, that reuse was
confirmed engaged by inspecting the engine's own prepared-statement view rather than inferred, and
the observed result. If a prepared-statement exception DOES appear, do not paper over it by silently
restoring the override — stop, report it, and record the finding, because it would mean something in
this stack depends on the override for a reason nobody has identified yet.

Tear the local stack down when finished. Leave no container, volume or background process behind.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application process -> database connection | The pool configuration determines how a database outage presents to a caller and how many connections one app can consume from a shared engine. |
| Two application containers -> one shared engine | Pool sizing on either side can starve the other of connections. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
