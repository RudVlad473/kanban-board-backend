<design_alternatives>

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A (PICKED): pass every credential through `psql -v name=value` and reference it as `:'name'` (SQL literal) or `:"name"` (identifier) inside a single-quoted heredoc** | **+** The quoting is done by psql itself, against the value as received — correct for every possible input, including quotes, backslashes and semicolons, with no escaping logic of our own to get wrong. **+** `-v ON_ERROR_STOP=1` is already on this exact invocation, so the mechanism is not new to the script, only newly applied to the credentials. **+** Documented, stable psql behavior (postgresql.org `app-psql`: "a colon followed by the variable name in single quotes quotes the value as an SQL literal, while double quotes quote it as an SQL identifier"), not a hand-rolled trick. **−** Substitution silently does nothing if a variable is never set, so a typo between the `-v` name and the `:` reference produces a confusing parse error rather than a clear one. Mitigated by the existing `:?` guards and by the harness. | Named directly by CR-01's own Fix, and it is the only option where correctness does not depend on us enumerating the dangerous characters. |
| **B (REJECTED): escape single quotes in shell before interpolating — double each `'` in the value, then splice as today** | **+** Smallest possible diff; no change to the invocation, only to the values. **+** Doubling `'` is the SQL-standard escape inside a single-quoted literal, so it is correct for the apostrophe case the script's own comment worries about. **−** It is a hand-rolled escaper: it fixes the character we thought of and leaves every other one (backslash under a non-standard `standard_conforming_strings`, and identifiers, which need `"` doubling by a *different* rule) to a future reader who may not notice the asymmetry. **−** It still produces a SQL string by string concatenation, so the anti-pattern — and every future reviewer's need to re-audit it — survives the fix. | Rejected: it converts an injection hole into a narrower injection hole. The defect CR-01 names is the concatenation itself, not the apostrophe. |
| **C (REJECTED): validate the credentials instead of quoting them — reject any value that is not `^[A-Za-z0-9_]+$` and fail first boot loudly** | **+** Turns the unenforced convention into an enforced one, with a clear diagnostic, in three lines. **+** No change to how the SQL is built. **−** It hardens the convention rather than removing the dependency on it: the SQL is still assembled by concatenation, so the day someone relaxes the validator (or adds a seventh variable and forgets it), the hole is back. **−** It also breaks legitimate strong passwords for no security benefit, which is the usual reason such validators get relaxed. | Rejected as the primary fix. A narrow version of it is still *implied* by the existing `:?` guards, which stay. |

**Non-obvious trade-offs:**

- *Failure mode shifts from "wrong SQL runs" to "no substitution happens".* psql substitutes `:name`
  only when that variable is currently set; an unset variable is left as literal text and produces a
  parse error. That is a strictly better failure than today's (arbitrary SQL executing), but it is a
  different one, and the existing `: "${VAR:?...}"` guards are what keep it from ever being reached.
  They must stay.
- *The heredoc delimiter is load-bearing.* Quoting the delimiter is what stops the shell from
  expanding anything inside the SQL body. Leave it unquoted and a future edit that reintroduces a
  shell variable into the body silently reintroduces CR-01 with no visible signal. The `-` in the
  `<<-` form strips leading **tabs** only, so switching to the quoted form does not change how the
  existing space-indented body renders.
- *Security posture, honestly stated:* this script runs only against an empty data directory. The
  live `postgres-data` volume was provisioned on 2026-08-26 by the pre-fix script, and this change
  does not re-run against it, does not alter any existing role's password, and does not retroactively
  make that provisioning run safe. It protects the next provisioning — a fresh volume, a rebuilt VM,
  a disaster-recovery restore — which is exactly the path an operator takes under pressure.
- *Directory-mount hazard:* the postgres image sources **every** file it finds in
  `/docker-entrypoint-initdb.d`, and production mounts the whole `./docker/postgres-init` directory.
  A verification script placed next to the init script would therefore execute as the superuser on a
  real first boot. The harness must live outside that directory, and the directory's file count is
  worth asserting rather than trusting.
</design_alternatives>

Rewrite the single `psql` invocation so credential values are quoted by psql itself rather than
concatenated into SQL text by the shell. Nothing else in the file changes — this is a targeted defect
fix (D-01's provisioning artifact), not a rewrite of the script.

**Keep exactly as they are:** the shebang, the `set -eo pipefail` line and the comment above it
explaining why `-u` is deliberately omitted, all six `: "${VAR:?...}"` guards (they are what
guarantees every psql variable referenced below is actually set), and the whole dated `Decisions`
comment block about the load-bearing `REVOKE CONNECT` lines and the first-boot-only semantics.

**Change the invocation.** Keep `-v ON_ERROR_STOP=1`, `--username "$POSTGRES_USER"` and
`--dbname "$POSTGRES_DB"`, and add six further variable assignments on the same command, each
shell-quoted so the value reaches psql as a single argument: `-v prod_user="$PROD_DB_USER"`,
`-v prod_pass="$PROD_DB_PASS"`, `-v prod_db="$PROD_DB_NAME"`, `-v nonprod_user="$NONPROD_DB_USER"`,
`-v nonprod_pass="$NONPROD_DB_PASS"`, `-v nonprod_db="$NONPROD_DB_NAME"`. Use a line continuation so
the invocation stays readable.

**Change the heredoc delimiter to the single-quoted form** `<<-'EOSQL'`. This is the half of the fix
that is easy to drop on a later edit and is the reason to state it explicitly: with the delimiter
quoted, the shell performs no expansion at all inside the SQL body, so no future edit can
reintroduce a shell-built SQL string without also changing the delimiter. The `-` prefix strips
leading tabs only, so the body's existing space indentation renders unchanged.

**Change the eight SQL statements** to reference the psql variables instead of shell values, using
double-quoted colon form for identifiers and single-quoted colon form for the two password literals:
- `CREATE ROLE :"prod_user" WITH LOGIN PASSWORD :'prod_pass';`
- `CREATE DATABASE :"prod_db" OWNER :"prod_user";`
- `REVOKE CONNECT ON DATABASE :"prod_db" FROM PUBLIC;`
- `GRANT CONNECT ON DATABASE :"prod_db" TO :"prod_user";`
- `CREATE ROLE :"nonprod_user" WITH LOGIN PASSWORD :'nonprod_pass';`
- `CREATE DATABASE :"nonprod_db" OWNER :"nonprod_user";`
- `REVOKE CONNECT ON DATABASE :"nonprod_db" FROM PUBLIC;`
- `GRANT CONNECT ON DATABASE :"nonprod_db" TO :"nonprod_user";`

psql expands the double-quoted colon form into a correctly quoted SQL identifier and the
single-quoted colon form into a correctly quoted SQL literal, escaping anything embedded in the
value; interpolation never happens inside an ordinary quoted SQL string, which is precisely why the
colon forms are the mechanism rather than a convenience. Cited: postgresql.org `app-psql`, "SQL
Interpolation".

**Replace the script's existing hazard comment.** The current comment tells a future reader that
safety depends on every password being generated by a tool that cannot emit an apostrophe. That is
now false and actively misleading. Write a short dated `2026-08-26` entry inside the existing
`Decisions` block instead, stating: that psql performs the quoting server-side so no convention about
credential generation is load-bearing any more; that the heredoc delimiter is quoted deliberately and
must stay that way; and one falsifiable check — `scripts/verify-postgres-init-quoting.sh` boots a
throwaway container with hostile values and fails if this ever regresses. Follow this repository's
comment discipline: state the decision and how to disprove it, do not narrate the statements below
it.

**Do not** add validation of the credential values, change the variable guards, reorder the DDL,
change any database or role name, add any new file to `docker/postgres-init/`, or touch any Compose
manifest — the environment-variable contract with `docker-compose.prod.yml` is unchanged by design.
