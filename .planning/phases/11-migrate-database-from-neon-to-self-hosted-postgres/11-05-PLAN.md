<objective>
Rewrite the two pre-merge Flyway verification jobs so they reach the self-hosted database through
the VM's SSH identity and its internal Docker network, instead of connecting from a GitHub-hosted
runner to a public database endpoint that no longer exists.

Purpose: this is the change that closes the red CI window plan 11-02 knowingly opened. Preserving
the gate matters — it is the only thing that proves this repository's migrations apply cleanly
against the real reachable instance before an image is allowed to reach a VM — and D-13 explicitly
rejects both dropping it and replacing it with a throwaway ephemeral database that would prove
something weaker.

Output: two rewritten jobs, a recorded decision on the reachability mechanism, and a live green run.

<design_alternatives>
| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A (RECOMMENDED, subject to Task 1's decision): run the Flyway CLI as a one-off container ON the VM inside an SSH-action script, attached to the shared Docker network** | **+** Directly proven in this exact repository — the schema-registration job already runs a one-off container over SSH against the live Compose network, using the same digest-pinned action and the same secret set. **+** Needs no port exposure of any kind, so D-03 keeps holding with no exception. **+** Container-name DNS resolution works because the container runs inside the network's own namespace. **−** The migration `.sql` directory must be copied to the VM on every run; the runner's own checkout is not visible to a container running on the VM. **−** The Flyway container image is pulled on the VM rather than the runner, costing a little VM disk and first-run time. | Recommended by RESEARCH. The extra copy step is a real cost and is called out honestly, but it is a copy step, not a new attack surface. |
| **B (REJECTED unless Task 1 says otherwise): a literal local port-forward from the runner into the VM** | **+** Matches D-13's literal wording. **+** Keeps the Flyway container on the runner, so no per-run file copy. **−** Has no clean target: the database publishes no host port at all, so the forward's remote target must be either the container's internal bridge address — which the SSH server resolves in its own namespace, does not know Compose service names for, and which changes on every container recreate — or a loopback-only host bind, which is not internet-facing but IS a literal exception to D-03's stated rule. **−** The dynamic-address variant fails intermittently after any container recreate, which is the worst kind of CI flake. | Rejected in favour of A, but the choice is Task 1's to confirm — D-13's wording is genuinely ambiguous between "port-forwarding semantics specifically" and "reach it via SSH, however that is best implemented", and taking a D-03 exception silently would be wrong. |
| **C (REJECTED): spin up a throwaway ephemeral Postgres in CI and verify migrations against that** | **+** Simplest of all, no SSH, no VM dependency, fast, fully parallel. **−** Rejected outright by D-13. **−** It proves something materially weaker: that the migrations apply to an empty database, not that they apply to the real, already-migrated instance the deploy is about to target. Migration drift — a migration that applies to empty but conflicts with the deployed history — is precisely what this gate exists to catch, and this variant is blind to it. | Rejected by D-13 explicitly, and independently on the grounds that it would quietly downgrade the guarantee while appearing to keep it. |

**Non-obvious trade-offs:**
- *Verification runs a real migration against the real database.* That is the existing behavior, not a
  new risk — but it is worth restating, because it means the gate mutates production's schema before
  the new image deploys. The migrate-then-deploy ordering is preserved deliberately.
- *Independence:* the two jobs use different SSH identities, different deploy directories, and
  different environment declarations. That separation is load-bearing — it is what keeps production's
  and nonprod's deploy paths from gating each other — and a copy-paste rewrite is exactly how it gets
  accidentally collapsed.
- *Concurrency:* the production verification job runs while a deploy for a previous push may still
  hold the deploy concurrency lock. Staging migration files into the shared deploy directory could
  race that deploy's own file copy, so the staging path must be distinct from anything the deploy job
  writes.
</design_alternatives>

  <action>
Rewrite both verification jobs to reach the self-hosted instance via the mechanism Task 1 decided.
Keep every property of the existing jobs that is not about reachability.

**Remove the endpoint-suffix guard step from BOTH jobs.** It inspects the database hostname for a
marker that belonged to the retired provider's transaction-mode pooler. Against a Compose service
name that marker can never appear, so the step is now dead code that would read to a future
maintainer as an active protection. Delete it rather than leaving it inert. Replace the protection
it actually provided — "do not verify against something that cannot honestly verify" — with a
concrete assertion appropriate to the new target: fail the job if the Flyway container cannot resolve
and reach the database over the shared network, rather than letting a resolution failure surface as
an opaque connection error.

**Rewrite the verification step in each job** to run the already-pinned Flyway CLI image against
`jdbc:postgresql://<database service name>:5432/<database>` with no TLS parameter in the URL — the
connection is now a Docker bridge hop and the container has no TLS listener, so a parameter demanding
SSL would fail the connection outright rather than being merely redundant.

**Stage the migration files on the VM.** The container runs on the VM and cannot see the runner's
checkout, so add a copy step to each job that transfers `src/main/resources/db/migration/` to a
staging directory on the VM using the same digest-pinned copy action the deploy jobs use. The staging
path must be DISTINCT from any path the deploy jobs write, because the production verification job
can run while a previous push's deploy still holds its concurrency lock. Give each environment its
own staging path under its own deploy user's directory.

**Preserve every existing property of these jobs:**
- The `needs:` graph is unchanged: each verification job still gates only its own environment's
  deploy, and nonprod's job still references only nonprod nodes. A copy-paste rewrite is exactly how
  this separation gets accidentally collapsed — check it explicitly after editing.
- Each job keeps its own `environment:` declaration, which is what makes the identical
  `secrets.DB_*` and `secrets.NETCUP_*` references resolve to different values. Do not rename any
  secret.
- Every SSH script body starts with an explicit `set -e`. The action has no fail-fast input; without
  this, a failing command mid-script does not stop later lines from running, which has already
  produced a real bug in this file twice.
- The action references stay digest-pinned at the exact digests already used elsewhere in this file.
- Flyway's own abort-on-first-failed-migration behavior remains the mechanism — do not add
  hand-rolled abort logic, `|| true`, `set +e`, or `continue-on-error` anywhere near the invocation.

**Update the block comment above `flyway-verify`** to describe the new mechanism and why it was
