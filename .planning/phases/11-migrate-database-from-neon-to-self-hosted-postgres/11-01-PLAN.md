<objective>
Define, in the repository, the self-hosted PostgreSQL 16 topology that replaces Neon: one shared
container serving two databases with two least-privilege roles, reachable from both Compose
projects over a new external `kanban-db` network, with no host port published.

Purpose: this is the phase's tracer — it proves end-to-end, on a real container, that the
provisioning mechanism, the connect-isolation D-01 demands, the cross-project network path, and
Flyway's own V1..V8 migration set all work together BEFORE anything on the production VM is
touched. Every later plan in this phase builds out from this one proven slice.

Output: a new init script, a new `postgres` service, a new shared network, rewired app services in
both Compose manifests, updated env-file contracts, and a deploy step that carries the init script
to the VM.
</objective>

<design_alternatives>
Per this project's GSD Execution Directives, two alternates were considered before this plan's
approach was picked.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A (PICKED): one shared `postgres` service in `docker-compose.prod.yml`, joined by `app-nonprod` over a new external `kanban-db` network** | **+** Costs one container's memory on a VPS that already commits ~5.15G of 7.8G. **+** Reuses the `kanban-edge` cross-Compose-project pattern already proven in this exact repo for Caddy -> app-nonprod. **+** One data volume, one backup target, one version to upgrade. **−** `.env.prod` must carry nonprod's DB credentials for the init script (RESEARCH Pitfall 5) — a real, narrow crack in the two projects' otherwise-strict secret isolation. **−** A production Postgres restart briefly takes nonprod down with it. | Locked by D-01. The memory budget is the binding constraint, and Neon's actual failure mode (per-**project** shared compute-hour billing) has no self-hosted analog, so the isolation the second container would buy does not defend against the thing that broke. |
| **B (REJECTED): two separate `postgres` containers, one per Compose project, full parity with the `redpanda`/`redpanda-nonprod` split** | **+** Perfect secret isolation — neither `.env` file ever sees the other's credentials. **+** A nonprod restart cannot touch production. **+** No new external network needed at all. **−** A second Postgres instance's floor (shared_buffers + backend processes + WAL buffers) on a box with ~2.65G of uncommitted headroom, which plan 11-03 is about to squeeze further. **−** Two engines to patch and upgrade. | Rejected by D-01 on the memory budget, explicitly. Recorded in CONTEXT.md's Deferred Ideas as revisitable if nonprod's workload ever grows. |
| **C (REJECTED): one `postgres` container, ONE database, environments separated by PostgreSQL schema (`prod` / `nonprod` schemas)** | **+** Cheapest of all — one database, one connection pool ceiling. **−** Flyway would have to be schema-qualified per environment, changing a mechanism this phase is explicitly not touching. **−** `REVOKE CONNECT` operates at database granularity; schema-level isolation is `REVOKE USAGE`, which Hibernate's `search_path` handling makes far easier to defeat accidentally. **−** Nonprod's reset endpoint TRUNCATEs — a search_path mistake would TRUNCATE production. | Rejected: contradicts D-01's literal "two separate databases" wording, and trades a hard database-level access-control boundary for a soft one on the exact code path (the reset endpoint) that is most destructive if it aims at the wrong target. |

**Non-obvious trade-offs this approach accepts:**
- *Security:* PostgreSQL grants `CONNECT` on every database to `PUBLIC` by default
  (postgresql.org/docs/17/ddl-priv.html). `CREATE ROLE` + `CREATE DATABASE ... OWNER` therefore does
  **not** produce isolation on its own — the explicit `REVOKE CONNECT ... FROM PUBLIC` is the entire
  mechanism, and its absence fails silently (everything works, isolation just isn't there).
- *Security:* TLS on the JDBC hop is deliberately dropped, because the hop moves from the public
  internet to a Docker bridge. This is the same posture local dev already runs. Documented, not
  overlooked.
- *Operational:* `/docker-entrypoint-initdb.d/` runs **exactly once**, only when the data directory
  is empty. A half-failed first boot leaves a non-empty volume and every retry silently skips
  provisioning — the recovery is `down -v`, not "fix the script and retry".
- *Memory:* `mem_limit` here is a **provisional Iteration 0 baseline**, not a measured floor. Plan
  11-03 replaces it via the restart-ladder methodology (D-08). The comment in the file must say so,
  matching how `docker-compose.nonprod.yml`'s own `redpanda-nonprod` cap documents its basis.

**Init script (`docker/postgres-init/01-create-databases-and-roles.sh`), per D-01:**
- Shebang `#!/usr/bin/env bash`. Use `set -eo pipefail` — deliberately WITHOUT `-u`. The official
  `postgres` image's entrypoint *sources* a non-executable `.sh` file into its own shell instead of
  executing it, and a leaked `set -u` can abort the entrypoint on an unrelated optional variable
  later. Replace `-u`'s protection with explicit `: "${VAR:?message}"` guards on all six required
  variables: `PROD_DB_NAME`, `PROD_DB_USER`, `PROD_DB_PASS`, `NONPROD_DB_NAME`, `NONPROD_DB_USER`,
  `NONPROD_DB_PASS`. The `:?` form fails loudly and names the missing variable, which is a far
  better first-boot diagnostic than "unbound variable".
- Body: a single `psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname "$POSTGRES_DB"`
  heredoc. Do NOT pass `-1` / `--single-transaction`: `CREATE DATABASE` cannot run inside a
  transaction block.
- Per environment, in this order: `CREATE ROLE "<user>" WITH LOGIN PASSWORD '<pass>'`;
  `CREATE DATABASE "<name>" OWNER "<user>"`; `REVOKE CONNECT ON DATABASE "<name>" FROM PUBLIC`;
  `GRANT CONNECT ON DATABASE "<name>" TO "<user>"`. Emit both environments' four statements —
  production first, nonprod second.
- Put a segregated, dated decision-record comment block above the SQL explaining that the two
  `REVOKE` lines are load-bearing (PostgreSQL grants `CONNECT` to `PUBLIC` on every database by
  default, so `CREATE ROLE` + `CREATE DATABASE` alone leave both roles able to reach both
  databases), that the mechanism runs exactly once on an empty data directory, and that the
  recovery from a failed first boot is `docker compose down -v`, not editing and retrying. Follow
  `docs/CODE_COMMENTS.md`'s "legitimate long comment" shape — falsifiable, dated, segregated.
- No credential literal may appear anywhere in this file; every value comes from an environment
  variable. `.githooks/pre-commit` runs gitleaks on the staged diff and will refuse a literal.
- Commit the file with mode `100755`.
