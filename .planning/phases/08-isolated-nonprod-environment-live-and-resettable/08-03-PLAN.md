<objective>
Replace `redpanda-nonprod`'s provisional memory caps with a floor established by iterative live
restart cycles under a real workload, prove the two stacks coexist on the 7.8 GiB host without
production degrading, and put the second-VPS fallback decision in front of the human rather than
taking it unattended.

Purpose: STATE.md records this as the phase's one genuinely open unknown. `mem_limit` is a
per-container cap, not a host reservation, and this project has already been surprised once at
exactly this cgroup-accounting boundary. Arithmetic is not an acceptable answer here.

Output: measured `--memory` / `mem_limit` values committed with a MEASURED BASIS comment, a full
iteration log in the runbook, and a recorded, human-made decision on colocation versus the fallback
host.
</objective>

<design_alternatives>
Two alternate technical approaches were considered before this plan was written, as required by
`.claude/CLAUDE.md`'s GSD Execution Directives.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Derive the cap arithmetically** — take production's measured ~348 MiB RSS, add a margin, or halve production's 2 G cap | **Pros:** zero live iterations, no restart cycles, no production risk. **Cons:** it is precisely the method NONPROD-06 forbids by name ("not assumed from arithmetic (e.g., 'half of prod's cap')"). Redpanda's own docs recommend 2 GB per core for production hardware while this project's `--overprovisioned` production broker measures ~348 MiB — the two figures differ by a factor of six, so no arithmetic derivation from either is defensible. Worse, this project already shipped an arithmetically-equal `mem_limit` once and it broke every restart. | **Rejected.** It is the failure mode the requirement exists to prevent. |
| **B. Descend a fixed ladder with a restart cycle and a real burst per step, adopt the last known-good, and separately prove the step below it fails** | **Pros:** produces a boundary rather than a number; the recorded failure makes the floor auditable by a future reader; mirrors the methodology `docs/INFRA_RUNBOOK.md`'s own production Task 3 already used, so the two environments are documented to the same standard. Reset between iterations (available since plan 08-02) makes each measurement start from an identical state. **Cons:** several container restart cycles on a host also serving live production; each iteration costs real wall-clock time. | **Picked.** Production is never restarted — only `redpanda-nonprod` cycles — and production's health endpoint is polled throughout as the guard. |
| **C. Binary-search the floor rather than descending a fixed ladder** | **Pros:** fewer iterations to a tighter value. **Cons:** a tighter value buys nothing here (the host has headroom either way) and a binary search produces a floor whose neighbouring values were never exercised, which defeats the "one step either side" boundary evidence NONPROD-06 wants. | **Rejected.** Optimising iteration count is not the goal; producing defensible evidence is. |

**Non-obvious trade-offs this plan deliberately accepts:**

- **Memory (the actual subject).** `mem_limit` is a per-container hard cap, not a host reservation.
  Summing caps proves nothing about simultaneous peak, which is why the acceptance gate is a live
  `free -m` reading with both stacks under burst rather than a sum of the manifest's numbers.
- **Precision (the documented gotcha).** `mem_limit` must exceed Seastar's `--memory` by a real
  margin. Setting them numerically equal is not "tighter", it is broken — Seastar's own probe sees
  less usable memory than it asked for and refuses to start rather than running smaller. Production's
  recorded margin is ~150 MiB over 2048 MiB; this plan requires at least that.
- **Availability (production, during measurement).** Each iteration restarts only
  `redpanda-nonprod`. Production's containers are never stopped, and production's health endpoint is
  polled between every iteration; a non-200 aborts the measurement rather than being noted
  afterwards.
- **Cost (real money, human decision).** The fallback path is a new recurring ~EUR 4/month
  commitment. D-07 rates it one-way and requires a blocking `checkpoint:decision` before it, framed
  as two explicit doors. The agent never provisions it unattended, even under
  `workflow.auto_advance`.
- **Scope honesty.** If the fallback door is chosen, standing up a second host to production's own
  verified standard (firewall parity across both layers, Docker, deploy user, Caddy, DNS, TLS) is a
  build-out comparable in size to v1.2 Phase 5's own host setup. Task 4 says so explicitly and
  instructs the executor to surface a scope escalation rather than deliver it shallowly.
</design_alternatives>
