<objective>
Give nonprod a single-curl return-to-empty: a profile-gated, shared-secret-authenticated endpoint
that truncates both nonprod's Postgres state and its Kafka activity-log state to zero rows, and
prove — with real-broker, real-Postgres tests and a live call against the deployed nonprod stack —
that it works there and does not exist in production.

Purpose: a future Playwright suite needs a deterministic `beforeEach` baseline against a real,
non-mocked deploy. D-03 rejects seeded fixtures, so the baseline is genuine emptiness and every test
builds its own fixtures through the real API.

Output: `ResetService`, `ResetTruncateService`, `ResetController`, a profile-gated security chain,
three test classes, and a live-verified runbook entry.
</objective>

<design_alternatives>
Two alternate technical approaches were considered before this plan was written, as required by
`.claude/CLAUDE.md`'s GSD Execution Directives.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Truncate Kafka by deleting and recreating the two topics** (`KafkaAdmin` / `AdminClient.deleteTopics` + the existing `NewTopic` beans) | **Pros:** also resets the consumer group's committed offsets and any partition-level config drift, so the reset is total rather than record-level. **Cons:** `KafkaAdmin.deleteTopics()` as a runtime method only exists from spring-kafka 4.0; Spring Boot 3.5.16's BOM manages the 3.3.x line, so this needs raw `AdminClient` anyway. Worse, deleting a topic out from under a live `@KafkaListener` mid-poll is an unbounded failure mode, and topic recreation is asynchronous — the endpoint would have to poll for the topic to reappear before returning. | **Rejected.** `deleteRecords()` is the narrower primitive that satisfies D-03's literal "zero rows" without touching topic existence. |
| **B. `deleteRecords()` to each partition's current high watermark, with the listener containers paused for the duration** | **Pros:** narrow, available at this project's pinned spring-kafka version, idempotent (a second call against an already-trimmed partition is a successful no-op), and pausing the listeners removes the "an already-polled event repopulates `activity_log` after the truncate" flake. **Cons:** does not reset committed consumer offsets — harmless here, because trimming to the high watermark leaves the committed offset at or below the new log-start offset and `auto-offset-reset=earliest` resolves that to the new start. Costs one extra collaborator bean to keep the transactional truncate out of a self-invoked method. | **Picked.** |
| **C. Add `permitAll()` for the reset route to the existing `SecurityConfiguration` filter chain** | **Pros:** one line, no new class. **Cons:** the permit rule would exist in production's filter chain even though the handler does not, so production's security policy would carry a rule for an endpoint it deliberately cannot serve; and it edits a heavily-commented, security-critical file that this phase otherwise has no reason to touch. | **Rejected** in favour of a `@Profile("nonprod")`-gated, path-scoped second `SecurityFilterChain` with `@Order(1)`. In a production context that bean does not exist at all, so production's chain is byte-identical to today's. |

**Non-obvious trade-offs this plan deliberately accepts:**

- **Security (defense in depth, two independent controls).** `@Profile("nonprod")` and the shared
  secret are **not** redundant — they close different failure modes. The profile gate means the bean
  does not exist; the token means that even if a deploy script ever set the profile variable in
  production by copy-paste (RESEARCH.md Pitfall 4 — a real failure mode, not a hypothetical), the
  caller still needs the secret. Neither is treated as sufficient alone, and the security chain
  itself is profile-gated so the *permit rule* disappears with the endpoint.
- **Security (timing side channel).** A variable-time comparison of a shared secret leaks the
  matching prefix length across repeated requests. `MessageDigest.isEqual` on the UTF-8 bytes is the
  documented constant-time primitive (ASVS V6) and is enforced by a negative gate on the controller
  file.
- **Security (no oracle on header presence).** The header is bound with `required = false` so an
  absent header takes the same 403 path as a wrong value. Declaring it required would return a
  400 for absence and a 403 for a wrong value, handing a probe a free distinguisher.
- **Correctness (transaction boundary, non-obvious).** `TRUNCATE` needs a transaction, but the
  listener stop/start must happen outside it and the restart must run even if the truncate throws.
  Spring's `@Transactional` is proxy-based, so a self-invoked transactional method on the same bean
  would silently run without a transaction. That is why the transactional truncate lives in a second
  bean (`ResetTruncateService`) rather than as a private method on `ResetService`.
- **Availability (nonprod only, seconds).** Reset briefly stops the activity-log consumer. Events
  published during that window are not lost — they are trimmed by the same reset, which is the
  intended outcome. This is acceptable precisely because it only ever runs in nonprod.
- **Blast radius.** The nonprod app holds credentials for nonprod's Neon branch and nonprod's broker
  only; it has no route to production's broker (it is not on the shared `kanban-edge` network) and
  no production database credential. The endpoint's inability to affect production is structural,
  not a policy.
- **Test-suite interaction.** `ResetServiceE2ETest` truncates the shared Testcontainers PostgreSQL
  database. Test classes run sequentially within a Gradle fork and every fixture-bearing base class
  creates its own fixtures in `@BeforeEach`, so a truncate between classes is harmless; the test
  restores nothing and relies on that property deliberately.
</design_alternatives>

`resetAll()` runs four steps in order, with the fourth in a `finally` so the listeners come back even
if a truncate throws:
1. Stop every listener container from `KafkaListenerEndpointRegistry.getListenerContainers()`.
2. `truncateActivityTopics()` — open one `AdminClient` from

   `UnknownTopicOrPartitionException` (unwrapped from the `ExecutionException`) as already-empty:
   log and continue rather than failing, so a reset issued against a broker where the topic has not
   yet been created still succeeds. Any other failure propagates.
3. `resetTruncateService.truncateAll()`.
4. Restart every listener container.
