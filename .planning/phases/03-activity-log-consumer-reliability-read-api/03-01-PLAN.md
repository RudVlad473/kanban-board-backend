## Alternate Approaches Considered

Required by `.claude/CLAUDE.md` → GSD Execution Directives.

**Decision A — how the consumer dispatches across the five event types.**

| Approach | Pros / Cons | Why picked |
|---|---|---|
| **Exhaustive `switch` over the sealed `ActivityEvent`** (chosen) | + Adding a sixth event record is a compile error until handled — the compiler is the coverage gate for ACTLOG-02. + One method, one transaction boundary, one place to reason about. + Realises CODE_STYLE rule 1's stated rationale ("switch statements can be checked for exhaustiveness") on a Java 21 sealed type the codebase already owns. − Slightly longer single method than five short ones. | The sealed interface already exists from Phase 2 and is the natural discriminator. Compile-time exhaustiveness is the strongest possible guarantee against ACTLOG-02's "maps *all five* event types" requirement, and it is free. |
| `@KafkaListener` class + one `@KafkaHandler` per record type (RESEARCH.md Pattern 1) | + Framework-idiomatic, minimal per-type code. − Coverage is a *runtime* property: a missing handler surfaces as a `MethodNotFound`-class failure at delivery time, which the error handler then dead-letters — i.e. a forgotten event type silently drains into the DLT instead of failing the build. | Rejected: converts a compile-time guarantee into a production-only failure mode, on the exact requirement (ACTLOG-02) most at risk of a missed type. |
| Single handler on a `Map<String,Object>` payload, dispatching on a `type` field | + Tolerant of unknown types. − Contradicts REQUIREMENTS.md "Out of Scope" ("Generic/pluggable event schema... contradicts the epic's explicit instruction to define typed records"). | Rejected: explicitly out of scope. |

**Decision B — transaction boundary for the idempotent persist.**

| Approach | Pros / Cons | Why picked |
|---|---|---|
| **`ActivityLogRecorder.record()` with no enclosing declarative transaction; `saveAndFlush` in Spring Data's own per-call transaction; catch the integrity violation** (chosen) | + The constraint violation aborts only the repository call's own transaction, so the catch block returns into a clean state. + `saveAndFlush` forces the INSERT inside the call, so the exception surfaces deterministically at the catch site rather than at some later commit. − One extra round trip versus batching. | This is the only shape where D-05's "silent no-op" is actually true. See the perf/correctness note below for why the obvious alternative is a trap. |
| Declarative transaction on `record()`, catching the violation inside it | + Reads more naturally alongside the rest of the service layer. − **Broken**: a constraint violation marks the surrounding transaction rollback-only, so catching it and returning normally makes the *commit* throw at method exit — the duplicate then propagates out of the listener anyway and lands on the DLT, which is precisely the D-05 failure this phase must avoid. | Rejected: silently defeats the requirement it appears to satisfy. |
| Exists-check only, no unique constraint | + Simplest. − ACTLOG-03 explicitly names the DB constraint as the safety net and the exists-check as the fast path; a check-then-insert race under concurrent redelivery writes two rows. | Rejected: contradicts a locked requirement. |

**Non-obvious trade-offs recorded here rather than discovered later:**

- *Correctness / transaction semantics.* See Decision B — a caught `DataIntegrityViolationException`
  inside a declarative transaction does **not** produce a silent no-op; it relocates the failure to
  commit time. This is the single most important implementation detail in the plan.
- *Reliability.* Without `ErrorHandlingDeserializer`, a deserialization failure happens inside the
  consumer's poll loop *before* any error handler can see the record. The container cannot advance
  past the offset, so a single malformed message stalls the partition forever and never reaches the
  dead-letter topic — the opposite of RELY-01's stated goal, while looking configured.
- *Data fidelity.* When a deserialization failure is dead-lettered, `record.value()` is the raw
  `byte[]`. Re-serialising that through the application's JSON `KafkaTemplate` base64-encodes it, so
  the dead-letter record no longer carries the bytes that failed — the one artefact an operator
  needs. Hence a dedicated DLT template with a byte-preserving delegating serializer.
- *Performance / memory.* `existsByEventId` adds one indexed lookup per consumed message. That is a
  deliberate trade: it keeps the common path exception-free (throwing and catching per duplicate
  would be far more expensive) at the cost of a cheap unique-index probe. The covering index
  `(board_id, created_at DESC, id DESC)` in the DDL script exists so Plan 03's paginated read is an
  index scan rather than a sort of the whole board's history as the log grows unbounded (there is no
  retention policy — explicitly out of scope).
- *Security.* `spring.json.trusted.packages` is scoped to `com.vrudenko.kanban_board.event`, never
  `*`. A wildcard turns the consumer into a deserialization-gadget surface for anything that can
  write to the topic.

| `kanban.activity` topic → `ActivityLogConsumer` | Untrusted bytes cross here. The listener thread has no `SecurityContext` and does not re-verify that the event's `boardId`/`userId` were legitimately authorised at publish time. |

The assumption-delta detector fired `pluralization` on two prose fragments in the roadmap's Phase 3
success criteria ("never creates a **second** `ActivityLogEntity` row", "**another** confirms a
poison message reaches the DLT"). Both are descriptions of *test outcomes*, not a singular-to-plural
generalisation of a domain concept.

The question the checkpoint actually asks — *does the current primary key / identity model still
name the right noun?* — is nonetheless live here, because CONTEXT.md left `ActivityLogEntity`'s id
strategy as an open discretion item.

**Decision: `no-change`.** The row's identity noun stays the ULID `id` inherited from `BaseEntity`,
matching every other entity in this codebase, and `eventId` is modelled as a *business dedupe key*
with its own unique constraint rather than as the primary key. Rationale: `eventId` identifies the
**event**, not the **row**. Promoting it to primary key would fuse two nouns that are conceptually
distinct and would make any future many-rows-per-event shape (a fan-out, a correction row, a
re-derivation) a primary-key migration rather than an ordinary insert. Keeping them separate costs
one indexed column and preserves both options.
</assumption_delta_decision>
