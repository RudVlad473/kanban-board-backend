## Alternate Approaches Considered

Required by `.claude/CLAUDE.md` → GSD Execution Directives.

**Decision A — where the newest-first ordering is expressed.**

| Approach | Pros / Cons | Why picked |
|---|---|---|
| **Service constructs the `Sort` and passes it through the `Pageable`, ignoring any client-supplied sort** (chosen) | + Guarantees a deterministic *total* order (`createdAt DESC, id DESC`) that offset paging actually requires. + The client cannot reintroduce a non-deterministic boundary by sending its own sort parameter. + One place documents why the tiebreak exists. − One extra `PageRequest` construction in the service. | Offset pagination over a non-total order is silently wrong: with `createdAt` alone, rows sharing an instant have no defined relative position, so the database may return them in a different order per query and a row can appear on two pages or on none. The tiebreak is not polish — it is what makes READ-02 correct. |
| Encode the order in the derived method name (`...OrderByCreatedAtDesc...`) | + No service-side construction. − A `Pageable` carrying its own sort is combined with the method-name order, so a client sending `?sort=userId` changes the effective ordering and can break paging. − Expressing a two-key tiebreak in a method name produces an unreadable identifier. | Rejected: leaves the ordering contract partly in the client's hands. |
| Accept the client's sort and document the hazard | + Maximum flexibility. − Hands a correctness-critical parameter to the caller for a feed whose only sensible order is chronological. | Rejected: flexibility nobody asked for, at the cost of a correctness guarantee. |

**Decision B — how the E2E test gets activity rows to read.**

| Approach | Pros / Cons | Why picked |
|---|---|---|
| **Seed rows directly through `ActivityLogRepository`** (chosen) | + No broker, no Docker, no Testcontainers — this plan's suite runs anywhere and stays in the fast H2 context alongside every other E2E test. + Lets the test place rows at *exact* `createdAt` instants, which is the only way to construct the same-instant page-boundary case deliberately. − Does not exercise the Kafka path. | The Kafka path is already proven end-to-end by Plans 01 and 02; re-proving it here would slow this suite and prove nothing new. What this plan must prove is authorization, ordering and paging, and direct seeding is both sufficient and more precise. |
| Publish events through Kafka and wait for the consumer | + One continuous end-to-end story. − Requires a container, makes every read assertion asynchronous and flaky-prone, and makes it effectively impossible to pin two rows to the identical instant needed for the boundary test. | Rejected: worse precision and worse runtime for no additional coverage. |
| Call `ActivityLogRecorder` from the test | + No broker either. − Reaches across into the consumer-side package from a read-path test, coupling two independent slices. | Rejected: the repository is the honest seam between the two halves. |

**Non-obvious trade-offs recorded here rather than discovered later:**

- *Correctness.* See Decision A — offset paging over a non-total order is the classic
  duplicate-or-skip bug, and it only appears once a board accumulates rows sharing a timestamp.
  The `id DESC` tiebreak works precisely because ULIDs are lexicographically ordered by generation
  time, so it degrades gracefully into "newest first" rather than into an arbitrary order.
- *Correctness, accepted.* Even with a total order, offset pagination cannot give a stable snapshot
  across concurrent inserts — a row written between two page requests shifts everything after it.
  That is inherent to offset pagination and is exactly why keyset pagination is tracked as
  PAGE-V2-01; this milestone accepts it and records it as a backstop truth rather than pretending it
  away.
- *Performance.* `Page` costs a second `COUNT` query per request to populate `totalElements`. That
  is the price of D-09's metadata and is accepted. The covering index Plan 01's DDL creates on
  `(board_id, created_at DESC, id DESC)` is what keeps the row query an index scan instead of a sort
  over a board's whole history, which matters because the feed is append-only with no retention
  policy.
- *Memory / availability.* Page size is clamped by `spring.data.web.pageable.max-page-size` (set in
  Plan 01). Without a clamp a single request could materialise an entire board's history into
  memory and onto the wire.
- *Security.* Ownership is verified before any repository access, and `boardId` is re-derived from
  the verified entity rather than reused from the path variable, per CODE_STYLE rule 2 — so the id
  that was authorised is the id that gets queried.
