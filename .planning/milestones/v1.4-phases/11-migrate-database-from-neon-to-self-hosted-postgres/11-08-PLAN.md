Close 11-REVIEW.md's CR-02 / 11-VERIFICATION.md gap 1: the `postgres` service is capped at
`mem_limit: 64m` while being started with `shared_buffers=128MB` — the buffer pool the engine
believes it owns is double the cgroup ceiling that bounds it — and the measurement that adopted that

Purpose: D-11 asks for a deliberately conservative profile and D-08 asks for a live-measured floor.
The current values satisfy neither honestly — a profile whose own arithmetic exceeds its ceiling is
not conservative, and a floor measured under a workload that cannot reach the failure mode is not a
floor. The kernel already OOM-killed this postmaster once during the 11-03 ladder, at the adjacent
`32m` rung; that same mechanism is still reachable at `64m` under concurrent load.

**Why lowering `shared_buffers` alone cannot close this** — the arithmetic, stated once so it is not
re-derived later. A Postgres container's worst-case demand is roughly
`shared_buffers + (max_connections x work_mem) + (max_connections x per-backend overhead) + postmaster
and background-worker baseline`. At the configured `max_connections=25` and `work_mem=4MB`, the middle
term alone is 100MB. Any `mem_limit` at or below 100MB is therefore inconsistent with the configured
connection ceiling no matter what `shared_buffers` is set to. `64m` is not merely a bad pairing with
`128MB` of buffers; it is unreachable for this connection profile. That is why the ceiling has to move.

**Non-obvious trade-offs:**

- *Why the failure was invisible at every rung of the 11-03 ladder.* Postgres allocates
  `shared_buffers` as a shared memory segment at postmaster start, but Linux cgroup accounting
  charges a page only once something touches it. A ~55-row dataset touches a few megabytes of the
  buffer pool and no more, so peak RSS sat flat at ~29-30MiB from `512m` all the way down to `40m` —
  the number was real, and it was evidence about the dataset, not about the cap. Any measurement that
  does not grow the touched working set past `shared_buffers` cannot distinguish a safe cap from an
  unsafe one, which is exactly the methodological gap this plan has to close.
- *Sampling resolution is part of the methodology.* A 1-second `docker stats` sampler can miss a
  transient allocation entirely, and a transient allocation is precisely what killed the `32m` rung.
  Read the cgroup peak counter as well as sampling, so the recorded peak is a high-water mark rather
  than a best-effort snapshot.
- *The workload must not become the thing being measured.* Driving concurrency through the public API
  is bounded by HikariCP at 5 connections per environment, so the real path alone can never open more
  than ~10 backends. Reaching the configured ceiling needs a second pressure source, and it must run
  against a scratch database so that neither real database gains benchmark tables or rows.
- *Blast radius and honesty about it.* Every rung restarts the shared database, interrupting both
  environments, and the counter-evidence run is deliberately attempting to reproduce an OOM kill.
  Crash recovery is WAL-safe and was already observed benign three times during the 11-03 ladder, but
  this is a declared maintenance window, and a one-off `pg_dump` of both databases beforehand is
  ordinary prudence given the documented absence of any backup (D-12).
- *What justifies the adopted number.* Primary justification is the invariant: the configuration must
  not be able to request more than its own ceiling. The concurrent measurement is corroboration that
  the invariant's assumptions hold in practice, and the counter-evidence run is what makes the change
  evidence-backed rather than argued. Stating the order of those three plainly is the correction to
  11-03's framing, where the measured number carried the entire justification.

**Establish the concurrency the previous ladder lacked.** Every run below must be accompanied by a

(a) the maximum number of backends present across all databases and (b) the maximum number whose
state is not idle. These two numbers are the evidence that the workload was concurrent at all. A run
whose maximum backend count never rises above what a sequential burst produces is void — it has
reproduced the 11-03 methodology under a new name and must be re-run with more pressure.

**Capture memory two ways, not one.** Sample `docker stats` for the `postgres` container at roughly
one-second intervals throughout each run and take the maximum, as plan 11-03 did — and additionally
read the container's cgroup peak-usage counter (the kernel's own high-water mark) before and after
each run. A one-second sampler can step straight over a transient allocation, and a transient
allocation is exactly what killed the `32m` rung. Where the two disagree, the cgroup counter is the
number to trust and to record.

**The three sub-runs.** Each is a distinct pressure shape; run all three at every configuration
tested, in this order.

- *Sub-run A — real-path concurrency.* Fire the repository's established 54-request burst against
  BOTH public HTTPS APIs at the same time, with about 5 concurrent workers per environment so roughly
  10 requests are in flight at once, repeated three times back to back. This is 11-03's burst made
  parallel rather than sequential; on its own it is bounded by HikariCP at 5 connections per
  environment, which is why it cannot be the whole workload.
- *Sub-run B — buffer-pool and per-backend pressure, on a scratch database.* Create a scratch
  database on the same instance and initialise a benchmark dataset into it at a scale whose on-disk
  size is comfortably larger than the configured `shared_buffers` — roughly a million rows is
  sufficient and is the first time this instance will have had a working set that cannot fit in the
  buffer pool. Then drive it with about 18 concurrent benchmark clients for two minutes with the
  application containers idle, keeping the total under the configured connection ceiling of 25 once
  the pools' idle connections and the sampler are counted. Follow that with about 8 parallel psql
  sessions each sorting the largest table by a non-indexed column, so each backend actually allocates
  against `work_mem` rather than only reading pages. `pgbench` ships in the `postgres:16` image —
  confirm it is present; if it is not, substitute N parallel psql sessions running an equivalent
  random-access read/write loop and record which tool was used.
- *Sub-run C — combined worst case. This is the run whose peak sets the adopted value.* Sub-run A's

import re, sys, yaml
d = yaml.safe_load(open('docker-compose.prod.yml'))
pg = d['services']['postgres']
fails = []

def to_mb(v):
    m = re.fullmatch(r'(\d+)\s*([kKmMgG])?', str(v).strip())
    if not m: return None
    n, u = int(m.group(1)), (m.group(2) or 'b').lower()
    return {'k': n/1024, 'm': n, 'g': n*1024, 'b': n/1048576}[u]

cap = to_mb(pg.get('mem_limit'))
if cap is None:
    fails.append("postgres mem_limit missing or unparseable")

cmd = " ".join(str(x) for x in pg.get('command', []))
def flag(name, unit=True):
    pat = name + r'=(\d+)' + (r'\s*MB' if unit else r'')
    m = re.search(pat, cmd)
    return int(m.group(1)) if m else None

sb   = flag('shared_buffers')
wm   = flag('work_mem')
conn = flag('max_connections', unit=False)
for n, v in (('shared_buffers', sb), ('work_mem', wm), ('max_connections', conn)):
    if v is None: fails.append(f"could not parse {n} from the postgres command list")

if not fails:
    # I1: the buffer pool must be a FRACTION of the cap, never a multiple of it.
