<objective>
Decommission the managed database provider, and write down honestly what was lost by doing so.

Purpose: this project's existing decommission discipline (the earlier cloud teardown after the infra
pivot) is that a superseded provider is removed rather than left dormant and forgotten. D-07 follows
it. D-12 is the counterweight: the provider supplied point-in-time recovery for free, nothing
replaces it, and that regression is real — this phase's job is to make it a documented, acknowledged
gap rather than an undiscovered one.

Output: the provider's project deleted after a recorded human decision, its runbook section replaced,
a dated decommission record, a backup/restore-gap section carrying a written manual restore
procedure, and the pre-existing backup todo resolved against the new reality.

**Non-obvious trade-offs:**
- *Recoverability:* after this plan, there is no backup of the production database at all. Not a
  degraded backup — none. A container or volume loss means total data loss. That is the honest state
  and the runbook must say it in those words, because a reader who finds a "Backups" heading and
  skims it will otherwise assume coverage exists.
- *An untested procedure is not a procedure.* The manual restore steps written down here have not
  been executed. Say so explicitly and date the claim, rather than presenting them as verified.
- *Credential hygiene:* deleting the project is also the moment the provider's old credentials stop
  mattering. The GitHub Environment secrets were already repointed in plan 11-02, so nothing should
  still hold them — worth confirming rather than assuming, since a stale secret that still
  authenticates somewhere is exactly the kind of thing a decommission is supposed to close.
