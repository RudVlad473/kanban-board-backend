re-measure both application containers' caps now that database latency has collapsed from a
public-internet round trip to a Docker bridge hop.

arithmetic guess — that is this repository's established discipline, proven twice already for
production and nonprod Redpanda. Plan 11-01 deliberately shipped a provisional placeholder; this
plan is where it stops being provisional. The app-side caps were sized partly around a remote
database's latency assumptions and must not be carried forward unexamined either.

<design_alternatives>
| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A (PICKED): restart-ladder descent under a real 54-request burst, re-verified end-to-end at the adopted rung, with the step below it tried and observed failing** | **+** Already twice-proven in this exact repository (production Redpanda 05-04 Task 3, nonprod Redpanda 08-03 Task 2) and its evidence format is already the runbook's shape. **+** Catches the specific failure this method was hardened against: a rung that starts healthy on a point-in-time check and crash-loops only under sustained load. **−** Slow — each rung is a recreate plus a full burst plus a settle period. **−** Requires production traffic to be interruptible, which it is (D-05, and this is a personal/portfolio deployment). | Locked by D-08 and D-10, which both say "reuse this exact method". |
| **B (REJECTED): size `shared_buffers` + `max_connections` × `work_mem` arithmetically and add a fixed overhead margin** | **+** Instant, no live work, no traffic interruption. **−** This is exactly the arithmetic-guess approach D-08 exists to forbid. **−** It has already been observed wrong on this box in a way arithmetic could not have predicted: a cgroup cap set numerically equal to Redpanda's own internal memory request broke startup outright, because a byte-for-byte-equal cap budgets nothing for cgroup accounting overhead. Postgres's per-backend and shared-memory accounting has the same class of gap. | Rejected by D-08 explicitly, and by this repository's own recorded counter-example. |
| **C (REJECTED): omit `mem_limit` on `postgres` entirely and rely on the host's memory plus the OOM killer** | **+** No measurement work at all, and Postgres degrades more gracefully under memory pressure than a JVM does. **−** Removes the cgroup backstop that plan 05-04's own research recommended for every co-resident container on this box, and reintroduces exactly the unbounded-container situation the `app` service's `mem_limit: 3g` comment was written to close. **−** An unbounded Postgres competing with a 3g JVM and a 2200m broker on a 7.8GiB host means the OOM killer picks the victim, and its usual pick is the largest RSS — the JVM serving production traffic. | Rejected: trades a bounded, measured cap for an unbounded one whose failure mode is production being killed. |

**Non-obvious trade-offs:**
- *Performance vs. memory:* Postgres's floor is not steady-state RSS. Like Redpanda's, it is set by a
  transient peak — here, the largest of (a) `shared_buffers` plus per-backend private memory at the
  connection high-water mark, and (b) whatever a Flyway migration run or a nonprod TRUNCATE-all reset
  transiently allocates. A ladder that never fires those paths will adopt a floor that fails later.
  The burst workload must include a nonprod reset and an app restart (which re-runs Flyway), not just
  read/write traffic.
- *Measurement validity:* a point-in-time "it started healthy" check is not evidence. Plan 08-03
  recorded a rung that passed exactly that check and was then found crash-looping with
  `RestartCount=22` once monitored across a real recreate cycle. Every rung here must be observed
  across a full app-container recreate, a reset, the burst, and a post-burst settle.
- *Blast radius:* every rung restarts the shared database, which interrupts BOTH environments (D-01).
  The ladder must therefore be run as one deliberate maintenance window, not interleaved with other
  work.
</design_alternatives>

**Workload (the same burst this repository already uses, extended for this phase's specifics).**
Reuse plan 08-03's 54-request burst fired in rapid sequential succession through the public HTTPS
API (6 columns + 24 tasks + 24 subtasks). Extend it with two paths the previous bursts never
exercised and that are specifically capable of setting Postgres's transient peak:
  - a nonprod admin reset (the endpoint that TRUNCATEs every table), and
  - a full `app` container recreate, which re-runs Flyway's V1..V8 validation against the live
    database at boot.
Fire the burst against BOTH environments in the same rung so both HikariCP pools are open
concurrently — the connection high-water mark is what per-backend private memory scales with, and a
single-environment burst would understate it.

**Ladder for `postgres` (D-08).** Start from the provisional `512m` as Iteration 0 and descend:
`512m` -> `384m` -> `320m` -> `256m` -> `192m` -> `128m`, stopping one rung after the first
observable failure. At each rung: set the cap, force-recreate the container, wait for `(healthy)`,
run the full workload above, then wait at least 20 seconds after the burst and re-check. A rung
counts as passing ONLY if all of the following hold — a point-in-time "it started" check is
explicitly not sufficient, because that exact class of check let a crash-looping rung pass once in
plan 08-03:
  - the container reaches `(healthy)` within its `start_period`,
  - `docker inspect` reports `RestartCount=0` sustained across the whole workload,
  - both public health endpoints return 200 after the burst,
  - both databases still report 8 successful `flyway_schema_history` rows,
  - the nonprod reset endpoint completed successfully.
Record for every rung: pass/fail, the container's steady RSS and its percentage of the cap, the peak
RSS observed during the burst, `RestartCount`, and — for a failing rung — the verbatim failure
signal from `docker logs` (for Postgres this is typically an out-of-memory kill of a backend process
or the postmaster, or a `server closed the connection unexpectedly` on the client side, not a
Seastar-style allocation message).

**Adopted floor.** Take the lowest rung that passed, then apply this repository's own
cgroup-accounting-overhead lesson before adopting it: a cap set with no headroom above the engine's
own real high-water mark has already been observed to break startup on this box for a different
service. State explicitly, in the recorded result, how much headroom the adopted value leaves above
the measured peak RSS. Then independently re-verify the adopted rung from a clean slate — fresh
force-recreate, fresh reset, full burst, post-burst settle — specifically because the rung below it
just proved that class of check can be too shallow to trust.

**`app` and `app-nonprod` (D-10).** These do not need a full descent — they need a re-measurement
against the new latency profile and a recorded verdict. At the adopted `postgres` floor, capture
each app container's idle RSS and its peak RSS during the burst, as a percentage of its current cap
(`3g` for `app`, `1g` for `app-nonprod`). Then answer, with the numbers as the basis: does the
current cap still have a defensible margin now that the datasource is a Docker bridge hop rather
than a public-internet round trip? If the measured peak sits far below the cap, propose a lower cap
and descend it the same way. If it does not, keep the cap and say so — "re-measured, unchanged, here
is the evidence" is a valid and complete outcome for D-10, and is materially different from "not
looked at".

**Host coexistence.** At the adopted values, with everything running and immediately after a burst,
capture `free -m`. Record the `available` figure. Treat a drop below 1024 MiB as a stop condition
requiring a rung back up, matching the gate plan 08-03 used.

**Do NOT, in this task:** edit any Compose file, edit `application.properties`, touch the managed
provider, or change Postgres's `shared_buffers` / `work_mem` / `max_connections`. If the ladder
suggests the engine profile itself needs changing, record that as a finding for Task 2 to act on with
the evidence attached — do not change it mid-ladder, which would invalidate every prior rung.
