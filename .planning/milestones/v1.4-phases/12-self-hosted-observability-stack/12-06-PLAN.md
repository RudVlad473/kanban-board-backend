**Non-obvious trade-offs:**
- *Security, and it is what the todo is actually about:* Caddy's memory is influenced by unauthenticated
  internet traffic in a way no other container's is. The rate limiter holds per-source-address state
  keyed on `{remote_host}`, so a spray from many addresses grows that state, and each TLS handshake
  allocates. A cap here is not only an OOM backstop — it bounds what an unauthenticated party can make
  this process consume. That is why the workload must include a many-distinct-sources component and
  not just the repository's usual single-source burst.
- *Availability:* this ladder's failing rung takes the public edge down for both environments and for
  Grafana simultaneously — every request path on this box goes through this one container. Recreates
  are seconds, but they are user-visible, which is why this is a checkpoint someone schedules.
- *Certificate safety:* recreating Caddy repeatedly is safe specifically because `/data` is a named
  volume, so all three certificates are reused rather than re-requested. If a rung is so low that
  Caddy cannot start, it must not be left in a crash loop — a crash-looping Caddy that eventually
  starts fresh against an unreadable data volume is the path to a Let's Encrypt rate-limit ban.
- *Diagram drift, stated because the script's own header already measured it:* re-rendering
  `infra-physical-deployment` through the pinned renderer produces a PNG that differs in height from
  the currently committed one even with no source change — a known, recorded, pre-existing drift from
  a different mermaid version having produced the committed set. Since this plan changes the `.mmd`
  anyway, a fresh render is correct and the new PNG becomes the committed one. Do not treat that
  height change as a finding, and do not attempt to close the separate pre-existing-drift todo
  covering the other diagrams — that is not this phase's scope.
- *Honest todo closure:* the log-shipping todo has three halves and this phase closes one. Moving it
  to `completed/` would be false. Leaving it untouched would lose the information that a third of it
  is now done. It gets annotated and stays pending — which is the more useful and the less tidy
  outcome, deliberately.
</design_alternatives>

**Workload.** Caddy's peak is not driven by application traffic volume the way the app's is. Fire all
three of these in one cycle:
  1. The repository's established 54-request burst through the public HTTPS API against BOTH
     environments — exercises the two application site blocks and their TLS termination.
  2. A Grafana session over the third site block: log in and load all three dashboards at the widest

     is a materially different shape from the API burst.
  3. **The adversarial component, which is the actual point of this cap.** Drive the rate limiter's
     per-source-address state: many requests from as many DISTINCT source addresses as you can
     produce, aimed at `/api/signin`, enough to force the auth zone to start rejecting. The limiter
     keys on `{remote_host}`, so distinct sources are what grow its state — a burst from one address
     exercises the limit but not the memory. If you cannot produce many genuinely distinct source
     addresses from where you are, say so explicitly and record what you COULD produce, so the
     measurement's own coverage limit is on record rather than implied. Do not run this from the VM

  4. A post-workload settle of at least 20 seconds before the final reading.

**Ladder.** Start from a generous Iteration-0 ceiling (256m is a reasonable starting point against a
recorded ~20 MiB idle figure) and descend, stopping one rung after the first observable failure.
At each rung: set the cap, force-recreate caddy, wait for it to serve, run the full workload cycle,
settle, re-check.

A rung counts as PASSING only if ALL of these hold:
  - all three site blocks serve over HTTPS with valid certificates — a caddy that starts but cannot
    serve a site block is a failing rung;
  - `docker inspect` reports `RestartCount=0` sustained across the whole cycle;
  - both public health endpoints return 200 after the workload;
  - the rate limiter still behaves — the auth zone still rejects past its threshold and the general
    zone still admits, so a low cap has not silently degraded the control this cap is meant to bound.

Record per rung: cap, pass/fail, steady RSS and its percentage of the cap, peak RSS during the
workload (and specifically during the adversarial component), `RestartCount`, and for a failing rung
the verbatim signal from `docker logs` and from `dmesg` if the kernel OOM-killed it.

three certificates rather than re-requesting them. If any rung leaves caddy crash-looping, stop the

restarts and fails to read its data volume is the path to a week-long Let's Encrypt rate-limit ban,
which is a far worse outcome than an imprecise cap.

cgroup-accounting-overhead lesson: state the adopted value's headroom above measured peak RSS as a

because the peak is partly attacker-influenced and your adversarial component is a bounded
approximation of what the internet can send — say how much of the adopted value is that margin.
