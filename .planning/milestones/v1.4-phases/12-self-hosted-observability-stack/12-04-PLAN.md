Turn the metrics this phase now collects into something a human can actually read: three provisioned
dashboards covering the host, per-container and Postgres surfaces, committed as JSON in git.

Purpose: the phase goal is that metrics are *queryable*, and a Prometheus target reporting `up` is not
that. This is also where the "everything as code" convention this repository holds elsewhere gets

volume, is invisible in a diff, and disappears with the volume.

so a future re-fetch is reproducible.

<design_alternatives>
| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A (PICKED): pre-fetch community dashboard JSON from grafana.com once, commit it, and provision it with Grafana's file provider** | **+** Reproducible: the dashboard a future reader sees is the one in git, byte for byte. **+** Survives losing the `grafana-data` volume entirely. **+** Community dashboards already encode the correct PromQL for each exporter's specific metric names, which is the genuinely fiddly part. **−** The committed JSON is vendored third-party content nobody on this project wrote, so it is large and not meaningfully reviewable line by line. **−** Needs a one-time substitution of the downloaded dashboard's datasource input placeholder. | Picked. The vendored-content downside is real but bounded and is what every "don't hand-roll a dashboard schema" argument trades for; the alternative is hand-writing PromQL against metric names nobody has memorized. |
| **B (REJECTED): build the dashboards in Grafana's UI and leave them in the `grafana-data` volume** | **+** Fastest to a working dashboard, and tailored to exactly what this project cares about. **−** Invisible in git, so a reviewer cannot see them and a diff cannot show a change. **−** Lost with the volume, which makes the volume quietly load-bearing state rather than a cache. **−** Contradicts this repository's own convention everywhere else, where configuration is a committed file. | Rejected. This is the specific outcome `12-CONTEXT.md` left to discretion, and the discretion is being exercised toward the repository's existing convention rather than away from it. |
| **C (REJECTED): reference dashboards by `gnetId` and let Grafana fetch them at container start** | **+** No large vendored JSON in the repo at all. **−** Does not work: Grafana's file provisioning provider reads a local path only; a "provisioned by ID" dashboard still requires the JSON on disk first. **−** Building a fetch-on-boot script to close that gap would make container start depend on grafana.com being reachable, turning an external outage into a boot failure. | Rejected on both correctness and design; RESEARCH names the fetch-on-boot variant explicitly as an anti-pattern. |

**Non-obvious trade-offs:**
- *The failure mode nobody expects:* a dashboard downloaded from grafana.com carries an `__inputs`
  block declaring a datasource input (typically `DS_PROMETHEUS`), and its panels reference it as
  `${DS_PROMETHEUS}`. That placeholder is resolved by Grafana's *import* flow, which file
  provisioning does not run. Left unsubstituted, every panel renders "Datasource ${DS_PROMETHEUS}
  was not found" — the dashboard appears, looks structurally correct, and shows nothing. This is why
  Task 2's acceptance is "renders real data points", not "the dashboard is listed".
- *Provenance:* the cAdvisor and postgres_exporter dashboard IDs are `[ASSUMED]` in RESEARCH
  (assumptions A1 and A2, both rated low risk). They must be verified against grafana.com at
  execution time rather than trusted. Recording the ID and revision actually fetched is what turns a
  re-fetch from a re-search into a command.
- *Review burden, stated honestly:* these JSON files are thousands of lines of third-party content.
  They are committed because reproducibility is worth more here than line-by-line reviewability, and
  the mitigation is that provenance is recorded and the content is inert configuration read by
  Grafana, not code executed by this project.
- *No compose change:* plan 12-01 mounted the whole `docker/grafana/provisioning` directory, so this
  plan adds files underneath an existing mount. That is deliberate — it means this plan cannot break
  the manifest, and it is why this is the one plan in the phase that touches no Compose file.
</design_alternatives>

**Fetch each dashboard's JSON** with the revision-download endpoint form RESEARCH gives, and write it

**Substitute the datasource placeholder — this is the step that decides whether the dashboards work.**
A downloaded dashboard carries an `__inputs` block declaring a datasource input (commonly named
`DS_PROMETHEUS`) and its panels reference it as a `${...}` template expression. Grafana's *import*
flow resolves that; the file provisioning provider does not. Left as-is, every panel renders a
"datasource not found" error while the dashboard itself appears correctly in the sidebar. Resolve it
by replacing each such reference with this project's provisioned datasource name (`Prometheus`, or
`Loki` where a dashboard has a log panel) and removing the now-unused `__inputs` entry, so the
committed JSON is self-contained.

**Record provenance in each file.** Set each dashboard's own top-level `title` to something this
project recognizes, and add a `description` recording the grafana.com dashboard ID, the revision
fetched, and the date — inside the JSON, since a JSON file cannot carry a comment. This is what makes
a future re-fetch a command rather than a re-search, and it is the only thing standing between a
vendored file and an unattributable one.

Do not hand-edit panel PromQL beyond the datasource substitution. If a dashboard's queries do not
match this deployment's job labels, that is a finding for Task 2 to surface with evidence, not
something to patch blind here.

    if path != '/etc/grafana/provisioning/dashboards/json':
        fails.append(f"{prov}: provider path is {path!r}, not the committed JSON directory")

# The datasource names this project actually provisions.
ds = yaml.safe_load(open('docker/grafana/provisioning/datasources/datasources.yaml'))
known = {d['name'] for d in ds.get('datasources', [])}

d = 'docker/grafana/provisioning/dashboards/json'
expected = {'node-exporter-full.json', 'cadvisor.json', 'postgres-exporter.json'}
present = set(os.listdir(d)) if os.path.isdir(d) else set()
missing = expected - present
if missing:
    fails.append(f"missing dashboard files: {sorted(missing)}")

for fn in sorted(expected & present):
    full = os.path.join(d, fn)
    raw = open(full).read()
    try:
        j = json.loads(raw)
    except Exception as e:
        fails.append(f"{fn}: not valid JSON ({e})"); continue
    if not j.get('panels') and not j.get('rows'):
        fails.append(f"{fn}: has no panels")
    # The failure mode this whole check exists for: an unresolved import placeholder.
    if '__inputs' in j:
        fails.append(f"{fn}: still carries an __inputs block -- file provisioning does not resolve it")
    leftover = sorted(set(re.findall(r'\$\{(DS_[A-Z0-9_]+)\}', raw)))
    if leftover:
        fails.append(f"{fn}: unresolved datasource placeholders {leftover} -- every panel would "
                     f"render 'datasource not found'")
    # Provenance must be recorded inside the file.
    desc = (j.get('description') or '')
    if not re.search(r'\b\d{3,7}\b', desc):
        fails.append(f"{fn}: description records no grafana.com dashboard ID: {desc!r}")
    if not re.search(r'20\d\d-\d\d-\d\d', desc):
        fails.append(f"{fn}: description records no fetch date: {desc!r}")
    # Whatever datasource names survive substitution must be ones we actually provision.
    named = set(re.findall(r'"datasource"\s*:\s*"([^"$][^"]*)"', raw))
    unknown = {n for n in named if n not in known and not n.startswith('-- ')}
    if unknown:
        fails.append(f"{fn}: references datasource names this project does not provision: "
                     f"{sorted(unknown)} (provisioned: {sorted(known)})")

if fails:
    print("\n".join("FAIL: " + f for f in fails)); sys.exit(1)
