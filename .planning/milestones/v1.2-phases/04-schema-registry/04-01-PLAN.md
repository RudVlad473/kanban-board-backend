<objective>
Establish the Avro schema source of truth and the sealed-interface-to-SpecificRecord mapping layer, with nothing wired into the live Kafka path yet.

Per D-03, each of the 5 `ActivityEvent` types gets its own `.avsc` file — 5 independently-evolving schemas, not one union schema. Gradle's Avro plugin compiles those into `SpecificRecord` classes at build time, and a hand-written `ActivityEventAvroMapper` translates between them and the untouched domain records (SCHEMA-02).

**Core data-flow mechanism (3 sentences):** `.avsc` files in `src/main/avro/` are compiled by `gradle-avro-plugin` into Java `SpecificRecord` classes under `build/generated-main-avro-java/`, which land on the normal compile classpath. `ActivityEventAvroMapper.toAvro()` pattern-matches the sealed `ActivityEvent` and builds the corresponding generated record field-for-field; `toDomain()` does the reverse by generated type. Nothing in this plan touches Kafka, the publisher, or the consumer — the mapper is pure, synchronous, dependency-free translation, provable by a plain unit test with no broker.

Purpose: front-load the two highest-uncertainty items in this phase (does this specific archived-plugin + Avro 1.12.1 pairing generate `Instant`/`UUID` accessors, and does the Confluent serializer resolve cleanly against Spring Boot's managed `kafka-clients`) before any of them can force a rewrite of 10 mapper arms or a serde cutover.
Output: 5 `.avsc` schemas, Avro codegen wired into the build, a bidirectional mapper, and a round-trip unit test covering all 5 types.
</objective>

<design_alternatives>
Required by `.claude/CLAUDE.md`'s GSD Execution Directives: 2 alternate approaches, a trade-off matrix, and non-obvious trade-offs.

**The decision: how does a Java sealed interface become an Avro `SpecificRecord`?**

| Approach | Pros / Cons | Why Picked |
|---|---|---|
| **A. `.avsc`-first codegen + hand-written mapper (PICKED)** | **+** `.avsc` stays the schema source of truth, which is what D-03's "each subject evolves independently" model requires. **+** `ActivityEvent` is not touched at all, preserving the package's documented "plain, dependency-free records only" invariant. **+** The `toAvro` switch is exhaustive over the sealed interface with no `default` arm, so a 6th event type is a compile error — the same compile-time property `ActivityLogConsumer.deriveActionAndDetailIds` already provides. **−** ~10 hand-written mapper arms to keep in sync with the schemas; drift is caught only by the round-trip test, not the compiler. | The only approach that satisfies D-03 *and* SCHEMA-02 simultaneously. The drift cost is bounded (5 small records, all fields required) and is exactly what Task 3's round-trip test exists to catch. |
| **B. Avro reflection (`ReflectData` / `@Union`) over the domain records** | **+** Zero hand-written mapping code. **−** Requires either annotating `ActivityEvent`'s records (breaking the "no annotations" invariant that exists because producer *and* consumer share this package) or maintaining a parallel shadow hierarchy, which is the hand-written mapper again with extra steps. **−** Inverts the source of truth: the schema is derived from Java, so a refactor silently rewrites a registered schema. | Rejected. The inverted source of truth is disqualifying under D-03 — a Java rename would silently become a schema change on a live subject. |
| **C. MapStruct (reuse the existing Entity↔DTO mapper convention)** | **+** Matches the codebase's established mapper convention exactly, generated at compile time. **−** MapStruct maps one concrete source type to one concrete target type; it cannot generate a mapper whose source is a sealed interface dispatched by pattern matching over 5 unrelated record shapes. | Rejected as technically unavailable, not as a style preference. This is why the mapper is a plain `@Component` rather than a `@Mapper` interface — the split is deliberate and documented in the class Javadoc. |

**Secondary decision: Avro record names.** The generated classes are named `AvroTaskMovedEvent`, not `TaskMovedEvent`. The obvious alternative — identical simple names distinguished only by namespace — forces every Avro-side reference in the mapper to be fully qualified, because a single-type import of the domain `TaskMovedEvent` shadows the same-named type in the mapper's own package (JLS 6.4.1). That compiles, but leaves 10 mapper arms carrying 40-character fully-qualified type names and a reader who must check the package on every line to know which `TaskMovedEvent` is meant. The `Avro` prefix costs a slightly redundant subject name and buys an unambiguous, greppable mapper.

**Non-obvious trade-offs:**

- **Build-time / memory:** Avro codegen adds a new source-generation step to every `compileJava`. It is incremental and small (5 records), so the steady-state cost is negligible, but a clean build now regenerates 5 classes before compiling. The generated classes are added to the runtime classpath and are `SpecificRecordBase` subclasses carrying a static parsed `Schema` each — 5 small permanently-resident objects, not a per-message allocation.
- **Performance:** Avro binary encoding is materially smaller and faster than the JSON path it will replace (Plan 02), but the mapper adds one object allocation per published event (the generated record) that the JSON path did not have. On this workload — one event per mutation, published asynchronously off the request thread — that allocation is irrelevant. Do not "optimise" it away by reusing builders; Avro builders are not thread-safe and the publish path is a shared executor pool.
- **Security:** Every field in all 5 schemas is required with no default, deliberately. The reflexive alternative (`["null","T"], "default": null` everywhere) would manufacture a null-vs-absent ambiguity at the consumer boundary for fields that have never legitimately been absent — turning a schema violation that Avro would otherwise reject at the wire boundary into a silent `null` flowing into `ActivityLogEntity`, whose columns are all `nullable = false`. Strictness here moves failures earlier, which is the entire point of the phase.
- **Supply chain:** `com.github.davidmc24.gradle.plugin.avro` was archived by its owner on 2026-12-28 and 1.9.1 is its permanent final release. It is functionally complete for plain `.avsc` codegen with built-in logical types, which is all this phase needs, but it will never receive another patch. Pin the exact version; do not float it.
</design_alternatives>
