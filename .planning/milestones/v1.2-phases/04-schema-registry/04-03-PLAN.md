<objective>
Prove the two failure paths that the Avro cutover could plausibly have broken, rather than assuming they carried over.

Both were correct under JSON and both are *expected* to remain correct under Avro without any production code change — which is precisely why they need testing. SCHEMA-05's byte-fidelity guarantee depends on the dead-letter template never touching the Avro serializer, and D-01's resilience policy depends on a registry failure surfacing through the same callback a broker failure already does. Neither is visible to the compiler.

**Core data-flow mechanism (3 sentences):** When `KafkaAvroDeserializer` cannot decode a record, `ErrorHandlingDeserializer` catches it and hands `DefaultErrorHandler` the record with the raw bytes preserved, which retries three times and then passes it to `DeadLetterPublishingRecoverer`. The recoverer publishes through `deadLetterKafkaTemplate`, whose `DelegatingByTypeSerializer` dispatches on the value's runtime class and matches `byte[]` before the `Object` catch-all, so the original bytes go to `kanban.activity.dlt` unmodified. On the producer side, a registry that cannot be reached makes Confluent's serializer throw a `SerializationException` inside `KafkaProducer.doSend`, which the producer converts into a failed future — so the failure lands in `KafkaEventPublisher`'s existing `whenComplete` callback rather than propagating to whoever triggered the mutation.

Purpose: SCHEMA-05 explicitly requires re-verification rather than inheritance, and D-01's extension of the broker-down policy to registry-down has never been exercised against a real registry outage.
Output: two E2E test classes covering the poison-message and registry-outage paths under Avro.
</objective>

<design_alternatives>
Required by `.claude/CLAUDE.md`'s GSD Execution Directives.

**The decision: how is byte fidelity under Avro guaranteed?**

| Approach | Pros / Cons | Why Picked |
|---|---|---|
| **A. Change nothing in production code; add tests that prove the existing dead-letter template still holds (PICKED)** | **+** The `DelegatingByTypeSerializer` keyed on `byte[].class` is already generic over *any* deserialization failure format — it never knew or cared that the main path was JSON. **+** Zero risk of regressing a mechanism whose correctness was established the hard way (two separate production bugs found only by live Testcontainers verification, both documented at length in `KafkaConsumerConfig`'s Javadoc). **−** "We changed nothing" is an uncomfortable answer to a requirement, and is only credible with a test that would genuinely fail if it were wrong. | SCHEMA-05 asks for the guarantee to be *re-verified*, not rebuilt. The new registry-aware poison shape (valid wire format, unregistered schema id) is a genuinely new failure mode the prior test could not produce, so this is a real extension of coverage rather than a re-run. |
| **B. Add an Avro-aware branch to the dead-letter serializer** | **+** Looks thorough. **−** Actively harmful: the recoverer would attempt to re-encode a payload that just failed to decode, throwing inside the recovery path and destroying the audit trail for exactly the messages it exists to capture. **−** Adds a format-specific branch to a mechanism whose entire value is being format-agnostic. | Rejected as an anti-pattern. Named explicitly here because "the main path is Avro now, so the dead-letter path should be too" is the intuitive and wrong conclusion. |
| **C. Route dead letters through a second topic per failure format** | **+** Failure-mode segregation. **−** A second dead-letter topic to provision, monitor and drain, for a feed with no observability stack and near-zero traffic. **−** The operator question at 3am is "what were the original bytes", which one topic answers as well as two. | Rejected as disproportionate. |

**Decision 2: how is a registry outage isolated from a broker outage in the resilience test?** The mutation must be exercised with a *reachable* broker and an *unreachable* registry, otherwise a passing test proves only the already-known broker-down behaviour. The test therefore keeps the real Redpanda container and overrides only `schema.registry.url` to a port nothing is listening on. The mutation itself is driven at the service layer rather than over HTTP: the publish is dispatched by `@TransactionalEventListener(AFTER_COMMIT)` onto a separate executor, so the controller has already returned by the time the registry is ever contacted, and adding an HTTP hop would test the servlet stack rather than the resilience property. That reasoning belongs in the test's Javadoc so it does not read as a shortcut.

**Non-obvious trade-offs:**

- **Performance:** the retry policy is three attempts at a fixed one-second interval before dead-lettering, so each poison-message test costs a few seconds of real waiting that cannot be mocked away. Awaitility polling with the existing 30-second ceiling absorbs it; do not shorten the retry policy to speed up tests, since the retry count is itself a specified behaviour.
- **Memory / correctness:** the `LinkedHashMap` backing `DelegatingByTypeSerializer` is load-bearing, not stylistic. `Object.class` is assignable from `byte[]`, so with a plain `HashMap` the catch-all can win the dispatch and base64-encode the payload — a real production bug this project already shipped and caught. A test that decodes before comparing would not detect a regression of it, which is why every assertion here compares raw arrays.
- **Security:** the dead-letter topic is the audit trail for malformed and potentially hostile input. Losing byte fidelity is a repudiation failure — the one record class an operator most needs to inspect verbatim becomes the one class that arrives mangled. Avro narrows the deserialization-gadget surface on the happy path, but it widens the *variety* of poison shapes (bad magic byte, unknown schema id, incompatible writer schema), so the dead-letter path now catches strictly more, not less.
- **Test isolation:** the `kanban.activity` and `kanban.activity.dlt` topics are shared across every class in this package because the Spring context is cached. Match dead-letter records by exact payload rather than assuming the topic starts empty — the existing test already does this and the new one must too.
</design_alternatives>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Kafka topic → consumer deserializer | Arbitrary bytes, including deliberately malformed and registry-unresolvable payloads, cross here |
| Consumer failure path → dead-letter topic | The audit record of hostile or malformed input is written here and must survive unmodified |
| Application → Schema Registry | The dependency whose outage this plan proves is survivable |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-09 | Repudiation | `DeadLetterPublishingRecoverer` and `deadLetterKafkaTemplate` | high | mitigate | The dead-letter topic is the audit trail for exactly the malformed or hostile messages an operator most needs to inspect verbatim; re-encoding or base64-wrapping them destroys that record. Mitigated by the pre-existing `DelegatingByTypeSerializer` whose insertion-ordered map matches `byte[]` before the `Object` catch-all, and verified here by Task 1's direct raw-array comparisons across two distinct poison shapes. The verification is the mitigation's proof, not a substitute for it. |
| T-04-10 | Denial of Service | Single-partition `kanban.activity` topic | high | mitigate | A poison record that cannot be advanced past stalls the partition permanently and silently halts the entire activity feed. Mitigated by `ErrorHandlingDeserializer` keeping the failure out of the poll loop and by the retry-then-dead-letter handler; verified by Task 1's non-blocking case, which publishes a well-formed event behind a poison one on the same partition and asserts it still persists. |
