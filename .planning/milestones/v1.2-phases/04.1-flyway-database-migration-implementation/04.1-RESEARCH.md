## User Constraints (from CONTEXT.md)

### Locked Decisions

**Migration history**
- **D-01:** Reconstruct migration history incrementally — `V1__init.sql` (current baseline: users, boards, columns, tasks, subtasks), then separate migrations mirroring the real evolution captured in the 3 existing manual DDL scripts: optimistic-locking `version` columns (Epic 2), `activity_log` table (v1.1 Phase 3), `password_hash` NOT NULL (quick task 260803-m3i). Do not collapse into a single baseline. — **Reversibility:** costly — once merged and applied, Flyway migration files are checksummed/immutable history; splitting or renumbering after the fact requires a repair, not a simple edit.

**Spring Session tables**
- **D-02:** Flyway does NOT take ownership of `SPRING_SESSION`/`SPRING_SESSION_ATTRIBUTES`. Spring Session JDBC's own initializer (`spring.session.jdbc.initialize-schema=always`) keeps creating those tables, unchanged. Flyway only manages the app's own domain schema.

**ddl-auto cutover**
- **D-03:** Set `spring.jpa.hibernate.ddl-auto=validate` in `application.properties` (prod) as part of this phase, not deferred to Phase 5. There is currently no live prod DB for this to validate against (AWS EC2/RDS was deleted 2026-08-03; Neon isn't provisioned until Phase 5 resumes) — this phase proves migrations apply cleanly via the existing local `docker-compose.yml` Postgres service instead. — **Reversibility:** reversible — a config value; can be unset again with no schema impact.
- **Note for Phase 5:** Once this lands, Phase 5's INFRA-06 ("pre-merge DDL verification step against Neon") should be reconsidered as "run `flyway migrate`/`flyway validate` against Neon's direct connection string" rather than a new bespoke DDL check — Flyway now owns that job. Phase 5's own CONTEXT.md/planning is untouched by this note; it's a heads-up for whoever resumes Phase 5, not a decision made on Phase 5's behalf.

**Test environment**
- **D-04:** `application-test.properties` stays on Hibernate `spring.jpa.hibernate.ddl-auto=create-drop`, unchanged. Follows the Epic 3 doc's own explicit scoping: "Flyway against Testcontainers" is Epic 5's job, not this phase's. Migration correctness (V1-V4 apply cleanly, in order, against real Postgres) is proven by running the existing `docker-compose.yml` Postgres service locally, not by a new JUnit/Testcontainers suite.

## Summary

Adopting Flyway for this app is mechanically simple — Spring Boot 3.5.0's dependency-management BOM already pins `flyway-core` and `flyway-database-postgresql` to a mutually compatible version (11.7.2, confirmed by reading the actual release-tagged `build.gradle` in the Spring Boot repo), and Flyway auto-configures against the app's existing `spring.datasource.*` properties with zero extra wiring. The real complexity in this phase is entirely in getting the **migration history right** and in two **non-obvious interactions** with this specific codebase that CONTEXT.md's decisions don't spell out but that will break the build if missed:

1. **V1 must reflect the pre-Epic-2 schema, not the current one.** D-01 requires the 3 manual DDL scripts to become *separate* incremental migrations mirroring real history. That means `V1__init.sql` must NOT include the `version` columns (added by script 02) or the `password_hash NOT NULL` constraint (added by script 04) — those belong in later migrations. A naive "generate V1 from current entities" approach silently collapses the history D-01 explicitly asked to preserve.
2. **Flyway will try to run against the H2 test datasource too**, because Spring Boot auto-configures `FlywayAutoConfiguration` for any `DataSource` bean it finds on the classpath, with no profile scoping. `application-test.properties` keeping `ddl-auto=create-drop` (D-04) does not stop Flyway from *also* trying to apply the Postgres-flavored migrations (including `V4`'s `DO $$ ... $$` PL/pgSQL block, which H2 cannot execute even in `MODE=PostgreSQL`) against the H2 in-memory database before Hibernate ever runs. Every `@SpringBootTest` in the suite — and CI's `./gradlew test` — will fail at context startup unless `spring.flyway.enabled=false` is added to `application-test.properties`. This is a **required change to a file D-04 says "stays unchanged"** — D-04's wording is about `ddl-auto` specifically, not about every property in the file; this addition is orthogonal to that decision, not a violation of it, but it must not be missed.
3. **`docker-compose.yml`'s `app` service already hardcodes `SPRING_JPA_HIBERNATE_DDL_AUTO: update`** as an environment variable. Spring Boot environment variables outrank `application.properties` values, so even after D-03 sets `ddl-auto=validate` in `application.properties`, running the full `docker compose up` stack will still let Hibernate silently auto-alter the schema, masking exactly the kind of Flyway/entity mismatch `validate` exists to catch. This is a genuine, unaddressed gap between D-03's stated verification method ("prove migrations apply cleanly via docker-compose Postgres") and what `docker-compose.yml` currently does — flagged in Open Questions, not resolved here, since it's a scope call CONTEXT.md didn't make.

**Primary recommendation:** Add `flyway-core` and `flyway-database-postgresql` as version-less Gradle dependencies (BOM-managed), write `V1__init.sql`…`V4__add_password_hash_not_null.sql` reconstructing the pre-Epic-2 → current schema evolution in order, disable Flyway for the `test` profile, and treat the `docker-compose.yml` `ddl-auto: update` override as an open question for the planner to resolve explicitly rather than silently work around.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Schema migration execution (Flyway `migrate`) | API/Backend | Database/Storage | Runs inside the Spring Boot app process at startup, but its effect is entirely on the DB tier's persisted schema |
| Schema shape validation (Hibernate `ddl-auto=validate`) | API/Backend | — | Pure in-process check at `EntityManagerFactory` bootstrap; no DB-side component |
| Migration file version history (`db/migration/*.sql`) | API/Backend | — | Ships as a classpath resource inside the app artifact, not a standalone deployable |
| Spring Session table lifecycle | API/Backend | Database/Storage | Owned by `spring-session-jdbc`'s own initializer (D-02), deliberately outside Flyway's scope |
| Local "migrations apply cleanly" verification | Database/Storage | API/Backend | Target is the docker-compose Postgres container; the app process is the mechanism, the DB state is what's being proven |

|---------|---------|---------|--------------|
| `org.flywaydb:flyway-core` | 11.7.2 (BOM-managed by Spring Boot 3.5.0) | Migration engine, schema history tracking | The de facto standard SQL-first migration tool for Spring Boot; Epic 3 doc names it explicitly |
| `org.flywaydb:flyway-database-postgresql` | 11.7.2 (BOM-managed by Spring Boot 3.5.0) | PostgreSQL-specific dialect support | Required separately since Flyway 10 split per-database support out of `flyway-core` — PostgreSQL migrations fail without it |

**Version verification:** `[CITED: github.com/spring-projects/spring-boot/blob/v3.5.0/spring-boot-project/spring-boot-dependencies/build.gradle]` — read the actual release-tagged dependencies file directly. It defines `library("Flyway", "11.7.2")` and that Flyway library group's module list includes both `flyway-core` and `flyway-database-postgresql` among ~19 other per-database modules (Oracle, MySQL, SQL Server, etc.). Since both artifacts share one BOM-pinned version, declaring them with **no explicit version string** in `build.gradle` (matching this project's existing convention of omitting versions for Spring-managed deps, e.g. `spring-boot-starter-security`) is correct and future-proof against drift — a Spring Boot version bump moves both together.

Do not pin an explicit Flyway version in `build.gradle` unless a specific reason arises (e.g. needing a Flyway patch ahead of the next Boot bump) — this project already has a documented precedent (`spring-kafka`, `postgresql` driver) of leaving Spring-BOM-managed deps unversioned and only pinning where Spring's version would be wrong (see the `commons-lang3:3.18.0` override, `build.gradle:81-93`).

### Supporting

None needed. No Flyway Gradle plugin (`org.flywaydb.flyway`) is required — Spring Boot's auto-configuration runs `migrate()` automatically at application startup for both `bootRun`/`bootJar` and `./gradlew test`/`fastTest` invocations (once enabled for the relevant profile). The plugin exists to expose standalone CLI tasks (`flywayInfo`, `flywayValidate`, `flywayRepair`) independent of a running Spring context; D-04's verification method (run the app against docker-compose Postgres, observe startup succeeds/fails) doesn't need it. If a future phase wants a CI-invocable `flyway validate` step against Neon without booting the full app (Phase 5's INFRA-06 reshaping, per D-03's note), that is the moment to add the plugin — not this phase.

### Pattern 1: Historically-accurate baseline reconstruction

**What:** `V1__init.sql` encodes the schema shape as it existed *before* any of the 3 DDL bridge scripts were ever needed — not the current entity-derived shape.
**When to use:** Any time D-01-style "reconstruct real history" migration adoption is chosen over a single flattened baseline.
**Example (derived from entity source read this session — see Code Examples for full verbatim column list):**
```sql
-- V1__init.sql (excerpt) — password_hash has NO NOT NULL yet; that's V4's job
CREATE TABLE users (
    id            varchar(255) NOT NULL PRIMARY KEY,
    email         varchar(255) NOT NULL,
    display_name  varchar(255),
    password_hash varchar(255),
    CONSTRAINT uk_users_email UNIQUE (email)
);
```

### Pattern 2: Flyway + Hibernate `validate` division of labor

**What:** Flyway owns *making* schema changes; Hibernate's `ddl-auto=validate` owns *checking* the running app's entity mappings agree with whatever schema is currently in place. Neither one ever both creates and validates.
**When to use:** Standard pattern once Flyway is adopted in any Spring Boot + JPA app — this is what Epic 3's own doc calls "the correct pattern (Hibernate validates, Flyway migrates)."
**Example:**
```properties
# application.properties (prod) — D-03
spring.jpa.hibernate.ddl-auto=validate
```
```properties
# application-test.properties — Flyway must not run at all against H2;
# ddl-auto stays create-drop per D-04, unchanged, but this new line is required
# for the test suite to even boot once flyway-core is on the classpath (Pitfall 1)
spring.flyway.enabled=false
```

### Anti-Patterns to Avoid

- **Copying the DDL scripts' `IF NOT EXISTS`/idempotency guards into the Flyway migrations verbatim:** Flyway's own checksummed `flyway_schema_history` table already guarantees each `V`-migration runs exactly once, ever. Carrying forward `ADD COLUMN IF NOT EXISTS` etc. is harmless but redundant, and can mask a genuine "this migration ran against a schema I didn't expect" condition that Flyway would otherwise surface as an error. Strip the "safe to re-run by hand" framing (already called out in CONTEXT.md's Reusable Assets note) — Flyway's guarantee replaces it.
- **Generating V1 from current entity state:** produces a migration history that lies about when `version`/`activity_log`/`password_hash NOT NULL` were introduced, defeating D-01's explicit purpose ("migration history tells the real story of the project's evolution" — Epic 3 doc, line 24).
- **Editing an already-applied migration file after it has run anywhere (including a shared local Postgres volume):** Flyway checksums each migration's content into `flyway_schema_history`; editing a `V`-file that has already run trips `Validate failed: Migration checksum mismatch`, requiring `flyway repair` — costly, matches CONTEXT.md's own reversibility note on D-01.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Tracking which DDL has been applied to a database | A custom "applied_migrations" table + manual runner script | Flyway's built-in `flyway_schema_history` table | This is the exact problem this phase exists to stop hand-rolling — the 3 manual DDL scripts *are* the hand-rolled version being replaced |
| Detecting a migration file was edited after being applied | A manual hash-comparison script | Flyway's built-in checksum validation (`flyway validate`, runs automatically at every startup by default) | Already built in; a custom version would just reimplement `flyway_schema_history`'s checksum column |
| Guarding against Hibernate auto-altering prod schema | Manual code review discipline / a wiki page telling humans not to touch `ddl-auto` | `spring.jpa.hibernate.ddl-auto=validate` (D-03) | Turns a social convention into a fail-fast in-process check |

**Key insight:** This entire phase is itself a "stop hand-rolling" phase — the 3 manual `psql`-run DDL scripts under `docs/plans/backend-modernization/` are the thing being replaced. The main risk is *re-introducing* hand-rolled patterns inside the new Flyway migrations (idempotency guards, informal versioning) out of habit carried over from the old scripts.

## Common Pitfalls

### Pitfall 1: Flyway auto-runs against the H2 test datasource and breaks every test

**What goes wrong:** The moment `flyway-core`/`flyway-database-postgresql` land on the classpath, Spring Boot's `FlywayAutoConfiguration` activates for *any* Spring context with a `DataSource` bean — including every `@SpringBootTest` in this suite, which uses `jdbc:h2:mem:testdb` (`application-test.properties:14`, no `MODE=PostgreSQL`). Flyway will attempt to run `V1`–`V4` against H2 before Hibernate's `ddl-auto=create-drop` ever gets a chance to build the schema from entities. `V4__add_password_hash_not_null.sql`'s `DO $$ ... END $$;` block is PL/pgSQL — H2 does not execute PL/pgSQL under any compatibility mode `[ASSUMED — standard, extremely well-established H2/PostgreSQL limitation, not independently verified against H2's source this session; recommend a quick smoke test in Wave 0]`. Even setting that aside, several other Postgres-specific constructs in the migrations may not parse under plain H2.
**Why it happens:** Flyway's Spring Boot auto-configuration has no built-in "only run for this profile" scoping — it runs for every `DataSource` Spring wires up unless explicitly told not to (`[CITED: community consensus — self-learning-java-tutorial.blogspot.com, javathinking.com, both describing the standard `spring.flyway.enabled=false` test-profile pattern]`).
**How to avoid:** Add `spring.flyway.enabled=false` to `application-test.properties`. This is an *addition*, not a change to the `ddl-auto=create-drop` line D-04 locks — the two properties are independent, and D-04's "stays unchanged" language refers specifically to the `ddl-auto` setting.
**Warning signs:** `./gradlew test` (or `fastTest`) fails immediately at Spring context startup with a Flyway `FlywayException` referencing a syntax error inside a `DO $$` block, or a "relation already exists"/checksum-adjacent error, well before any actual test assertion runs. CI's `deploy.yml` test job (`.github/workflows/deploy.yml:40`, `./gradlew test`) would go red project-wide, not just on Flyway-specific tests.

### Pitfall 2: `docker-compose.yml`'s `SPRING_JPA_HIBERNATE_DDL_AUTO: update` silently outranks D-03's `validate`

**What goes wrong:** `docker-compose.yml:76` sets `SPRING_JPA_HIBERNATE_DDL_AUTO: update` as an environment variable on the `app` service — verbatim, this is the exact line already present in the file read this session. Spring Boot's environment-variable property source outranks `application.properties` in the default resolution order (`[CITED: docs.spring.io externalized-configuration precedence, corroborated by community reports that env vars are observed to win in practice — javatechonline.com]`), and this exact mechanism is already how this app gets `DB_HOST`/`DB_NAME`/etc. into `application.properties`'s `${VAR}` placeholders. So after D-03 lands, running the full `docker compose up` stack will still let Hibernate silently `update` (auto-alter) the schema against any drift from the Flyway-migrated state — defeating the entire point of `validate` for exactly the scenario D-03 names as its verification method.
**Why it happens:** `docker-compose.yml`'s `update` override predates this phase (it exists to let a fresh `docker compose up` bootstrap schema without any manual DDL step, back when Flyway didn't exist yet) and nothing in D-01–D-04 mentions touching `docker-compose.yml`.
**How to avoid:** Not resolved by this research — this is a genuine scope question for the planner (see Open Questions). Two viable directions: (a) remove/change the `SPRING_JPA_HIBERNATE_DDL_AUTO: update` override in `docker-compose.yml`'s `app` service so `validate` actually takes effect locally too, or (b) explicitly document that the compose-based local verification exercises "does Flyway apply cleanly" but not "does `validate` catch a mismatch," and rely on the migrations being hand-verified against the entities instead (this research phase's V1–V4 SQL was derived directly from entity source for exactly this reason).
**Warning signs:** A Flyway/entity mismatch that should fail loudly on `validate` instead succeeds silently under `docker compose up`, with Hibernate quietly altering the table to match — only surfacing later against a `validate`-only target (a real deploy) that has no `update` escape hatch.

### Pitfall 3: Non-empty local Postgres volume triggers Flyway's non-empty-schema refusal

**What goes wrong:** Flyway's default `baselineOnMigrate=false` means it refuses to migrate a database that already has tables but no `flyway_schema_history` — which describes the *current* `postgres-data` docker volume exactly, since it has been populated by `ddl-auto=update` runs across many prior dev sessions with no Flyway involved at all.
**Why it happens:** This is Flyway's intended safety behavior (don't silently assume an unknown existing schema matches migration V1) but is easy to trip locally without realizing the volume isn't actually empty.
**How to avoid:** `docker compose down -v` before the verification run (see Runtime State Inventory). `baselineOnMigrate=true` is not needed as a permanent setting for this phase — there is no real prod DB to baseline against (D-03), and the local dev target should be proven from a genuinely clean state, not baselined over drifted state.
**Warning signs:** Flyway startup error: `Found non-empty schema(s) "public" but no schema history table`.

### Pitfall 4: Migration file naming/immutability discipline

**What goes wrong:** Editing a migration file after it has been applied anywhere (including a shared local Postgres volume a teammate already ran) trips a checksum-mismatch validation failure.
**Why it happens:** Flyway checksums migration content at apply time and re-validates on every subsequent startup — deliberate, not a bug (`[CITED: red-gate.com/hub/product-learning/flyway/flyways-repair-command-explained-simply]`).
**How to avoid:** Treat every `V`-file as immutable the moment it's committed; add a new `V{n+1}` migration for any correction instead of editing history. Matches CONTEXT.md's D-01 reversibility note ("costly — requires a repair, not a simple edit").
**Warning signs:** `Validate failed: Migration checksum mismatch for migration version X`.

```sql
-- V1__init.sql
-- Reconstructs the schema as it existed before Epic 2 (optimistic locking),
-- v1.1 Phase 3 (activity_log), and quick task 260803-m3i (password_hash NOT NULL).
-- Those three deltas are intentionally NOT included here -- see V2/V3/V4.

CREATE TABLE users (
    id            varchar(255) NOT NULL PRIMARY KEY,
    email         varchar(255) NOT NULL,
    display_name  varchar(255),
    password_hash varchar(255),
    CONSTRAINT uk_users_email UNIQUE (email)
);

CREATE TABLE boards (
    id      varchar(255) NOT NULL PRIMARY KEY,
    name    varchar(255) NOT NULL,
    user_id varchar(255),
    CONSTRAINT fk_boards_user FOREIGN KEY (user_id) REFERENCES users (id)
);

CREATE TABLE columns (
    id       varchar(255) NOT NULL PRIMARY KEY,
    name     varchar(255) NOT NULL,
    board_id varchar(255),
    CONSTRAINT fk_columns_board FOREIGN KEY (board_id) REFERENCES boards (id)
);

CREATE TABLE tasks (
    id          varchar(255) NOT NULL PRIMARY KEY,
    column_id   varchar(255),
    title       varchar(32) NOT NULL,
    description varchar(512),
    CONSTRAINT fk_tasks_column FOREIGN KEY (column_id) REFERENCES columns (id)
);

CREATE TABLE subtasks (
    id            varchar(255) NOT NULL PRIMARY KEY,
    task_id       varchar(255),
    title         varchar(255) NOT NULL,
    is_completed  boolean NOT NULL DEFAULT false,
    CONSTRAINT fk_subtasks_task FOREIGN KEY (task_id) REFERENCES tasks (id)
```

### V4__add_password_hash_not_null.sql

```sql
-- V4__add_password_hash_not_null.sql
DO $$
DECLARE
    null_hash_count bigint;
BEGIN
    SELECT count(*) INTO null_hash_count FROM users WHERE password_hash IS NULL;

    IF null_hash_count > 0 THEN
        RAISE EXCEPTION
            'Aborting: % row(s) in users have a NULL password_hash. Resolve those rows before re-running this migration.',
            null_hash_count;
    END IF;

    ALTER TABLE users ALTER COLUMN password_hash SET NOT NULL;
END $$;
```
Source: `docs/plans/backend-modernization/04-password-hash-not-null-ddl.sql:56-69` (read this session, quoted near-verbatim — only the error message's "re-running this script" was reworded to "this migration" for accuracy). PostgreSQL's transactional DDL means if the `RAISE EXCEPTION` fires, the whole migration rolls back cleanly and Flyway marks it failed — no partial-apply state to clean up (`[CITED: general PostgreSQL transactional-DDL behavior, corroborated by sergiolema.dev/2023/12/04/my-problems-with-flyway describing exactly this PostgreSQL-vs-non-transactional-DDL-database distinction]`). No `-- flyway:executeInTransaction=false` pragma is needed for this migration.

## Open Questions

1. **Should `docker-compose.yml`'s `app.environment.SPRING_JPA_HIBERNATE_DDL_AUTO: update` be changed as part of this phase?**
   - What we know: it currently overrides D-03's `validate` setting for any `docker compose up` run (Pitfall 2), which is the exact local verification path D-03 names.
   - What's unclear: whether "prove migrations apply cleanly" (D-03) requires `validate` to actually run locally, or whether "the app boots and serves traffic against the freshly-migrated schema" is a sufficient bar on its own (in which case `update` staying is a deliberate, orthogonal local-dev convenience, not a bug).
   - Recommendation: planner should make an explicit call here rather than let it default silently either way — either drop the `update` override (making local verification match prod's `validate` behavior exactly) or explicitly note in the plan that local `docker compose up` is not exercising `validate`, and that the V1–V4 SQL's fidelity to the entity source (this research's Code Examples section) is what stands in for it locally.

2. **Does the `rehearseHistoricalSchemas` Gradle task's real Postgres target (holding genuine historical `activity_log` data, per STATE.md's pending todo) already have Flyway-unmanaged tables?**
   - What we know: that task deliberately runs against `application.properties`'s default (non-test) datasource, not H2 (`build.gradle:210-215`), so once Flyway is on the classpath it will attempt to migrate whatever real Postgres instance `DB_HOST`/`DB_NAME`/etc. point to at the time.
   - What's unclear: whether that target database already has tables from a prior Hibernate `update`/`create` run with no `flyway_schema_history` (same non-empty-schema refusal as Pitfall 3), since it's a separate real Postgres instance from the docker-compose one.
   - Recommendation: out of this phase's stated scope (SCHEMA-06's rehearsal is Phase 4 territory, already flagged as blocked on a human running it per STATE.md), but worth a one-line note in the plan so whoever next runs `rehearseHistoricalSchemas` isn't surprised by a Flyway non-empty-schema error.
