## Approach Analysis

Required by CLAUDE.md's GSD Execution Directives (2 alternates + trade-off matrix + non-obvious trade-offs) before any PLAN.md is approved.

**The decision under analysis:** how to prove "Flyway is wired and applies migrations" for the tracer slice.

| Approach | Pros / Cons | Why Picked |
|----------|-------------|------------|
| **A. Full `docker compose up --build` against a wiped `postgres-data` volume, assert on `flyway_schema_history`** (chosen) | **Pros:** exercises the exact runtime path production will use — Spring Boot's `FlywayAutoConfiguration` inside the app process, against real PostgreSQL 16, through the app's own `DB_*` env-var datasource wiring; `flyway_schema_history` is a table Hibernate can never write to, so the assertion stays valid regardless of what `ddl-auto` does afterwards; it is the exact verification method D-03/D-04 name. **Cons:** slow (multi-stage Docker build, several minutes); needs Docker + a populated `.env`; requires the destructive `down -v` step. | Picked: it is the only option that proves the real integration, and D-03 explicitly designates the docker-compose Postgres as this phase's verification target now that no prod DB exists. Speed is not the binding constraint for a once-per-plan gate. |
| **B. Add the Flyway Gradle plugin and run `./gradlew flywayMigrate` / `flywayInfo` against compose Postgres** | **Pros:** fast, no image rebuild, gives CLI-invocable `validate`/`repair` verbs. **Cons:** proves the *plugin's* migration run, not Spring Boot's auto-configured one — a false positive is possible (e.g. the auto-config could be disabled/misbound and the plugin would still go green); adds a plugin + a second datasource config surface that RESEARCH.md explicitly recommends deferring to Phase 5's INFRA-06 reshaping. | Rejected: verifies the wrong actor. Deliberately deferred per RESEARCH.md "Supporting: none needed". |
| **C. Add a Testcontainers-backed JUnit test that boots the app against a throwaway Postgres and asserts the migration applied** | **Pros:** fully automated, repeatable in CI, no manual Docker choreography. **Cons:** directly violates D-04, which scopes "Flyway against Testcontainers" to Epic 5 and states migration correctness is proven by the local compose Postgres, not a new JUnit suite. | Rejected: out of scope by locked decision D-04. |

**Non-obvious trade-offs:**

- **Startup latency / cold-boot cost:** Flyway adds a schema-history read plus, on a fresh database, N DDL statements to every application boot. Steady state is one `SELECT` against `flyway_schema_history` — negligible. The real cost lands in Phase 5's Neon target, where a cold serverless Postgres pays connection latency before that read; not this phase's problem, but it is why `validate`-time failures should be caught locally rather than at deploy.
- **State invalidation risk (the important one):** the moment `V1__init.sql` is applied anywhere — including the local `postgres-data` volume — Flyway records its checksum. Editing the file afterwards trips `Validate failed: Migration checksum mismatch` and needs `flyway repair`, not an edit. This is why Task 1 is a blocking decision checkpoint: it is the last cheap moment to change the numbering/split.
- **Security (privilege surface):** the runtime `DB_USER` now needs `CREATE`/`ALTER` privileges for Flyway to apply DDL at startup, which is strictly more than the DML a steady-state app needs. Accepted for this phase (no role management is in D-01..D-04's scope); flagged in `<threat_model>` as a Phase 5/Neon decision.
- **Memory:** `flyway-core` + `flyway-database-postgresql` add a small classpath/heap footprint at startup only; migration SQL is streamed per-file, so a large V-file does not scale heap usage in any way that matters at this schema size.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo → database schema | Committed `.sql` files under `src/main/resources/db/migration/` become executed DDL at every app startup. Content that passes code review is executed with the runtime `DB_USER`'s privileges. |
| build classpath → app process | Two new third-party artifacts (`flyway-core`, `flyway-database-postgresql`) resolve into the runtime image and execute at startup before any application code. |
| app process → Postgres | Flyway now issues DDL, not just DML, over the existing `DB_HOST`/`DB_USER` connection. |
