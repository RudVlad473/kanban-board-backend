## Approach Analysis

Required by CLAUDE.md's GSD Execution Directives.

**The decision under analysis:** how faithful the ported migrations should be to the three manual DDL scripts they replace — specifically whether to keep their idempotency guards and their pre-flight data check.

| Approach | Pros / Cons | Why Picked |
|----------|-------------|------------|
| **A. Port the SQL content, strip the idempotency guards, keep the V4 pre-flight data guard** (chosen) | **Pros:** Flyway's `flyway_schema_history` already guarantees exactly-once application, so the existence guards are redundant — and worse, they convert "this migration ran against a schema I did not expect" from a loud failure into a silent no-op. The V4 data guard is a different animal: it protects against *data* state (pre-existing `NULL` hashes), which Flyway knows nothing about, so it stays. **Cons:** the migrations are no longer hand-re-runnable by a human with `psql`, which is a deliberate loss of a capability that this phase exists to remove. | Picked: it matches RESEARCH.md's Anti-Patterns section and CONTEXT.md's Reusable Assets note, and it keeps exactly the one guard that Flyway cannot replace. |
| **B. Port the scripts verbatim, guards and all** | **Pros:** zero translation risk; the files stay runnable by hand as an escape hatch. **Cons:** re-introduces the hand-rolled safety mechanism the phase is replacing; a guarded migration silently succeeds against a schema that has drifted, which is precisely the failure mode `validate` and Flyway checksums exist to catch. | Rejected: keeps the hand-rolled pattern this phase removes. |
| **C. Fold V2/V3/V4 into V1 as one flattened baseline** | **Pros:** one file, simplest possible history, trivially matches the current schema of every existing database. **Cons:** contradicts locked decision D-01 outright. | Rejected by D-01, and already re-confirmed at Plan 01's blocking decision checkpoint. |

**Non-obvious trade-offs:**

- **Time complexity of V4's guard:** `SELECT count(*) FROM users WHERE password_hash IS NULL` is a sequential scan. On this schema's row counts it is free; on a large production `users` table it is an `O(n)` scan holding the migration's transaction open before the `ALTER TABLE` takes its `ACCESS EXCLUSIVE` lock. Acceptable here, and worth remembering when Phase 5 points this at Neon.
- **Lock behaviour:** `ALTER TABLE ... SET NOT NULL` takes an `ACCESS EXCLUSIVE` lock and, on PostgreSQL 12+, validates the constraint without a full table rewrite when no rows violate it. `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT 0` (V2) is also metadata-only on PostgreSQL 11+ — no rewrite. Neither is a long-lock hazard at this scale, but both are DDL against tables an application may be reading, which is why they run at startup before traffic is accepted rather than against a live instance.
- **State invalidation:** all three files become checksummed and immutable the instant they are applied. A correction after this plan lands is a new `V5`, never an edit. This is the same one-way property Plan 01's checkpoint gated; that approval covers V2-V4 as well as V1.
- **Security:** V4's `RAISE EXCEPTION` guard is the only real security-relevant control added here. Without it, a `SET NOT NULL` against rows with `NULL` hashes would either fail with an opaque constraint error or — if a default were carelessly supplied instead — create authenticatable-looking accounts with no real credential. PostgreSQL's transactional DDL means the raised exception rolls the whole migration back cleanly and Flyway records it as failed, leaving nothing half-applied.
