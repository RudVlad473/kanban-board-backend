**Gathered:** 2026-08-05

<domain>
## Phase Boundary

Adopt Flyway as the schema-migration tool for the app's own domain schema (users, boards, columns, tasks, subtasks), replacing the current pattern of hand-run, one-off manual DDL scripts against production Postgres (`docs/plans/backend-modernization/02-optimistic-locking-ddl.sql`, `03-activity-log-ddl.sql`, `04-password-hash-not-null-ddl.sql`). This is the Flyway half of Epic 3 (`docs/plans/backend-modernization/03-flyway-openapi.md`) split out on its own — the OpenAPI polish half of that epic is explicitly NOT in scope here. Inserted ahead of Phase 5 (Infra Migration, currently paused) so it can be delivered and claimed independently.

Covers: adding Flyway dependencies, writing incremental migration files that reconstruct the schema's real history, deciding Spring Session JDBC table ownership, and flipping prod to `ddl-auto=validate`. Does not cover: OpenAPI annotations (deferred back to the Epic 3 doc's own scope, untouched by this phase), Testcontainers-based migration testing (Epic 5, per the Epic 3 doc's own explicit deferral), or anything from Phase 5 (Oracle/Neon/Redpanda/Caddy/CI — still paused, untouched by this phase).

<decisions>
## Implementation Decisions

### Migration history
- **D-01:** Reconstruct migration history incrementally — `V1__init.sql` (current baseline: users, boards, columns, tasks, subtasks), then separate migrations mirroring the real evolution captured in the 3 existing manual DDL scripts: optimistic-locking `version` columns (Epic 2), `activity_log` table (v1.1 Phase 3), `password_hash` NOT NULL (quick task 260803-m3i). Do not collapse into a single baseline. — **Reversibility:** costly — once merged and applied, Flyway migration files are checksummed/immutable history; splitting or renumbering after the fact requires a repair, not a simple edit.

### Spring Session tables
- **D-02:** Flyway does NOT take ownership of `SPRING_SESSION`/`SPRING_SESSION_ATTRIBUTES`. Spring Session JDBC's own initializer (`spring.session.jdbc.initialize-schema=always`) keeps creating those tables, unchanged. Flyway only manages the app's own domain schema.

### ddl-auto cutover
- **D-03:** Set `spring.jpa.hibernate.ddl-auto=validate` in `application.properties` (prod) as part of this phase, not deferred to Phase 5. There is currently no live prod DB for this to validate against (AWS EC2/RDS was deleted 2026-08-03; Neon isn't provisioned until Phase 5 resumes) — this phase proves migrations apply cleanly via the existing local `docker-compose.yml` Postgres service instead. — **Reversibility:** reversible — a config value; can be unset again with no schema impact.
- **Note for Phase 5:** Once this lands, Phase 5's INFRA-06 ("pre-merge DDL verification step against Neon") should be reconsidered as "run `flyway migrate`/`flyway validate` against Neon's direct connection string" rather than a new bespoke DDL check — Flyway now owns that job. Phase 5's own CONTEXT.md/planning is untouched by this note; it's a heads-up for whoever resumes Phase 5, not a decision made on Phase 5's behalf.

### Test environment
- **D-04:** `application-test.properties` stays on Hibernate `spring.jpa.hibernate.ddl-auto=create-drop`, unchanged. Follows the Epic 3 doc's own explicit scoping: "Flyway against Testcontainers" is Epic 5's job, not this phase's. Migration correctness (V1-V4 apply cleanly, in order, against real Postgres) is proven by running the existing `docker-compose.yml` Postgres service locally, not by a new JUnit/Testcontainers suite.

### Claude's Discretion
- Exact column/table definitions inside each migration file (types, constraints, indexes) — derived from the current entity classes and the 3 existing DDL scripts; researcher/planner's call to get these byte-accurate.
- Whether the incremental migrations are numbered V1-V4 or use additional intermediate numbers if the planner finds a schema change not covered by the 3 known DDL scripts — planner verifies against the actual entity history/current schema, not just the 3 scripts, and adjusts numbering as needed.
- `flyway-database-postgresql` version pinning and Gradle plugin vs. dependency-only setup — planner/researcher's call, informed by the Spring Boot 3.5.0 BOM.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- The 3 existing manual DDL scripts are near-complete migration content already — they just need to move into `src/main/resources/db/migration/` with Flyway's `V{n}__description.sql` naming and have their one-off "run this by hand" framing stripped (their `IF NOT EXISTS`/idempotency notes are useful context, not literal Flyway requirements — Flyway's own checksum/history table is what prevents re-application).
- `docker-compose.yml`'s existing local Postgres service is the manual verification target — no new infra needed for this phase.

### Established Patterns
- Env-var-driven config via `${VAR:default}` placeholders in `application.properties` — Flyway's own datasource config should reuse the same `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER`/`DB_PASS` variables already defined, not introduce parallel ones.
- Naming strategy: `CamelCaseToUnderscoresNamingStrategy` — migration DDL must use snake_case table/column names matching what Hibernate already expects (e.g., `password_hash`, `activity_log`), confirmed by the existing DDL scripts.

### Integration Points
- `build.gradle` — add `org.flywaydb:flyway-core` and `org.flywaydb:flyway-database-postgresql`.
- `src/main/resources/application.properties` — add `ddl-auto=validate`; Flyway auto-configures against the same datasource by default, no new connection config expected unless Spring Boot's Flyway auto-config needs an explicit nudge.
- `src/main/resources/db/migration/` — new directory, does not exist yet (confirmed: no `*migration*` paths found in the repo outside `.planning/`).

</code_context>
