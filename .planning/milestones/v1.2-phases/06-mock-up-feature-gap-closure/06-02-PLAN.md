<design_rationale>
## Alternate approaches considered (required by CLAUDE.md GSD Execution Directives)

The genuine open decision here is the HTTP shape of a duplicate-name conflict — CONTEXT.md's
Claude's Discretion section leaves it explicitly to the planner.

**Approach A (chosen): a new `AppDuplicateResourceException` mapped to 409, plus a
`DataIntegrityViolationException` arm also mapped to 409.**

**Approach B: reject the duplicate as a 400 field-validation error via a query-backed
`ConstraintValidator` on `SaveBoardRequestDTO.name`.**

**Approach C: service-layer check only, no database constraint and no second handler arm.**

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| A — new exception, 409, plus an integrity-violation arm | **+** 409 matches the semantic line `GlobalExceptionHandler` already draws: 400 is for `IllegalArgumentException`-style request-shape problems, 409 is for state conflicts, and a name already taken is a state conflict, not a malformed request. **+** The second arm converts the race backstop from a 500 into the same 409 the non-racing path returns, so the client sees one behaviour regardless of timing. **+** One-arm-per-exception-type matches the file's existing structure exactly. **−** Adds a class and two handler arms. | **PICKED.** Also matches RESEARCH.md's own recommendation, arrived at from the same 400-vs-409 distinction. |
| B — query-backed bean validator, 400 | **+** Puts the message in the field-error map clients already parse for validation. **−** This codebase has zero DB-querying validators; everything in `dto/annotation/` is pure-syntax (`@BoardName`, `@TaskTitle`). A repository-injecting `ConstraintValidator` would be the first of its kind and needs its own DI wiring. **−** A validator has no access to the authenticated user id, so it cannot scope the check per user without threading the security context into validation — a much worse coupling. | **REJECTED.** The per-user scoping requirement alone rules it out: an unscoped validator is precisely prohibition 1. |
| C — service check only | **+** Smallest diff. **−** Leaves a real check-then-act race: two concurrent POSTs both see "not taken" and both insert. **−** Plan 01's V5 already adds `uk_boards_user_id_name`, so the race would surface as an unmapped 500. | **REJECTED.** The constraint is already in the schema; leaving it unmapped is strictly worse than not having it. |

## Non-obvious trade-offs

- **Time complexity:** `existsByUserIdAndName` is an index-backed existence probe against
  `uk_boards_user_id_name` — O(log n), one extra prepared statement per create and per rename. Board
  counts per user are in the tens, so this is not measurable.
- **Race / state invalidation:** the service check and the insert are not atomic. The window is
  microseconds and only reachable by one user racing themselves across their two permitted concurrent
  sessions. It is closed at the database, not in Java: `uk_boards_user_id_name` makes the second
  insert fail, and the new handler arm renders that failure as the same 409 the checked path returns.
  Deliberately no pessimistic lock and no serializable isolation — both would be new concepts in a
  codebase that has neither, to protect a name field.
- **Security:** the scoping of the existence query is a genuine information-disclosure control, not
  a correctness detail. A global `existsByName` would let any user enumerate other users' board
  names by probing for 409s. The signature is `existsByUserIdAndName` for exactly this reason.
- **Breaking change:** none. `GET/PUT/DELETE /boards` and `POST /boards/{boardId}/columns` are
  untouched; the only behaviour change to an existing route is that a rename to an already-used name
  now returns 409 where it previously succeeded.
</design_rationale>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-06-05 | Information Disclosure | `BoardRepository` uniqueness query | high | mitigate | The query signature is `existsByUserIdAndName`, scoped by the *verified* user entity's id. A global `existsByName` would let any authenticated user enumerate other users' board names by probing for 409 responses. Enforced by an acceptance criterion that greps for the unscoped variant and requires zero hits. |
| T-06-06 | Elevation of Privilege | `BoardService.updateById` rename guard (IDOR) | high | mitigate | The guard is inserted AFTER `findById(userId, boardId)`, which routes through `OwnershipVerifierService.verifyOwnershipOfBoard`. | T-06-07 | Tampering | Concurrent same-name creates | medium | mitigate | `uk_boards_user_id_name` (plan 01, V5) makes the second insert fail; the new `DataIntegrityViolationException` arm renders that as 409 rather than 500. Proven by the concurrency test in task 3. |
| T-06-08 | Spoofing | New POST route auth | medium | mitigate | The route inherits `BoardController`'s class-level `@PreAuthorize("isAuthenticated()")` and takes its user id from `@CurrentUserId` (the session), never from a request field — so a caller cannot create a board owned by someone else. Proven by the unauthenticated-POST case in task 1. |
| T-06-09 | Information Disclosure | 409 message body content | low | accept | The message names the resource type and the conflict, not the conflicting board's id or owner. Since the check is user-scoped, a 409 can only ever confirm something the caller already owns. |
| T-06-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable — zero new external packages; nothing added to `build.gradle`. No install task exists to gate. |
