<objective>
Lay the entire database and entity foundation this phase depends on, in one Flyway migration, and
prove it works end-to-end by shipping the smallest complete feature that rides on it: subtask
optimistic locking (GAP-06).

Purpose: `spring.jpa.hibernate.ddl-auto=validate` is the default in BOTH
`src/main/resources/application.properties` and `src/main/resources/application-test.properties`.
Every entity field later plans add (`TaskEntity.position`, `ColumnEntity.position`,
`SubtaskEntity.version`, `UserEntity.theme`) is therefore a hard compile-and-boot requirement to
also write the matching migration. Landing all four columns plus all new `ApiPaths` constants here,
in wave 1, is what lets plans 02-06 run in parallel without fighting over the same entity,
migration and constants files.

Output: `V5__add_position_subtask_version_theme_board_name_uniqueness.sql`, four modified entities,
one new enum, five new `ApiPaths` constants, a version-guarded `SubtaskService.updateById`, and a
`SubtaskLockingE2ETest` proving the 409.
</objective>

## Alternate approaches considered (required by CLAUDE.md GSD Execution Directives)

**Approach A (chosen): one V5 migration + all four entity fields land together in wave 1, with
GAP-06 as the proving slice.**

**Approach B: each feature plan writes its own migration (V5 position, V6 subtask version, V7
theme).**

**Approach C: relax `ddl-auto` to `update` in the test profile so entity fields can land without
migrations, and backfill migrations at the end of the phase.**

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| A — one V5, all fields, wave 1 | **+** Only one `FlywaySchemaProvenanceTest` edit instead of three. **+** Removes the migration file, all four entity files and `ApiPaths.java` from every later plan's `files_modified`, which is exactly what unlocks the 3-plan-wide wave 3. **+** Matches V2's precedent, which also added two columns to two tables in one migration. **−** Ships three columns (`tasks.position`, `columns.position`, `users.theme`) that nothing reads until waves 3. | **PICKED.** The unread-column cost is cosmetic and confined to one phase; the parallelism and single-test-edit benefits are structural. |
| B — one migration per feature | **+** Each plan is self-contained. **−** Three plans serialize on `FlywaySchemaProvenanceTest` and on version-number allocation (two parallel plans both claiming `V6` is a real merge collision). **−** Forces plans 04 and 06 into separate waves purely over migration numbering, not over real dependency. | **REJECTED.** Flyway version numbers are a global, non-mergeable namespace; parallel plans cannot safely allocate them. |
| C — relax `ddl-auto` in tests | **+** Fastest to write. **−** Deletes the exact guarantee `FlywaySchemaProvenanceTest` exists to enforce, and `docs/CODE_STYLE.md` rule 8 forbids a second, driftable schema-configuration path. **−** Production still runs `validate`, so the break simply moves from CI to deploy. | **REJECTED.** This is the failure mode the whole Flyway phase (04.1/04.2) was built to prevent. |

## Non-obvious trade-offs

- **Time complexity:** unchanged. Four `ALTER TABLE ... ADD COLUMN ... DEFAULT` statements on
  PostgreSQL 11+ are metadata-only operations (no table rewrite), so V5 is O(1) in row count for
  the column additions. The `boards` UNIQUE constraint is the one O(n log n) step (index build).
- **State invalidation:** `subtasks.version` is added with `DEFAULT 0`, so every pre-existing
  subtask row starts at version 0. A client holding a subtask response fetched before this phase
  has no `version` field at all, so its next update is rejected with 409 rather than silently
  applied. That is the intended, correct behaviour of introducing optimistic locking, but it is a
  behaviour change for any in-flight client and is called out here rather than discovered later.
- **Security:** adding `@NotNull Long version` to `UpdateSubtaskRequestDTO` closes a real
  lost-update window on a field (`isCompleted`) that a checkbox UI toggles rapidly — the highest
  realistic concurrency point in the whole mock-up.
- **Memory:** negligible; four scalar columns.
</design_rationale>
