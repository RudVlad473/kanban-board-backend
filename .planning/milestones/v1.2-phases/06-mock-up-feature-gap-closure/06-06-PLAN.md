<design_rationale>
## Alternate approaches considered (required by CLAUDE.md GSD Execution Directives)

D-10 through D-12 fixed the *what* (persist server-side, as a two-member enum, defaulting to LIGHT).
CONTEXT.md left the *where* genuinely open: it records that "no `UserController` exists today" and
that this is "a real 'where does it go' question for planning, not pre-decided here."

**Approach A (chosen): a new `UserController` at a users path, with the theme read and write hanging
off a session-derived `me` segment.**

**Approach B: fold the theme onto `AuthenticationController`, which is the only place user-scoped
operations live today.**

**Approach C: no dedicated route — return the theme on every existing response and accept it as an
optional field on some existing update, avoiding a new controller entirely.**

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| A — new `UserController`, session-derived path | **+** Structurally identical to `BoardController` (class-level path constant, `@Validated`, `@PreAuthorize("isAuthenticated()")`, `@CurrentUserId` on every method), so it introduces no new controller shape. **+** A `me` segment resolved from the session means the route *cannot* express "another user's theme", so the IDOR is closed by construction rather than by a check. **+** Gives every future user-scoped preference an obvious home. **−** One more controller class. | **PICKED.** The by-construction IDOR closure is the deciding factor; see prohibition 1. |
| B — fold onto `AuthenticationController` | **+** No new class. **−** That controller deliberately carries no class-level `@PreAuthorize` and no `@CurrentUserId` anywhere — its two routes are the only unauthenticated entry points in the application, documented in its own comment. Adding an authenticated route there would either weaken that boundary or make the class inconsistent with itself. | **REJECTED.** Decisive evidence against, and it is a security boundary, not a style preference. |
| C — no dedicated route | **+** Smallest surface. **−** There is no existing user-update endpoint to attach a theme write to; one would have to be invented anyway. **−** Makes the theme readable only as a side effect of unrelated calls, which is worse for a client that wants to set it and confirm it. | **REJECTED.** Invents more than it avoids. |

**Route shape** (also planner's call): a `me` segment rather than a user-id path variable. Every
authenticated route in this codebase already takes its user id from `@CurrentUserId` (the session)
and never from a path variable; a user-id path variable here would be the first exception and would
need an ownership check that has nothing above it to chain from — `UserService` is the identity root.

**Verb**: PUT rather than PATCH. The resource is a single scalar; a PUT replaces it wholly, and
there is no partial-update semantic to express. This also means the request DTO does **not** need
`@JsonInclude(NON_NULL)` or a version field: per `docs/CODE_STYLE.md` rule 6, `@JsonInclude` is
precisely what marks a class as a partial-update DTO, and this is not one.

## Non-obvious trade-offs

- **Optimistic locking, deliberately absent.** `UserEntity` carries no `@Version` field and this plan
  does not add one. A theme write is last-write-wins. That is correct for a single-user preference
  toggled from that user's own two permitted sessions: rejecting a theme change with a 409 because
  the user flipped it on their phone first would be worse than simply applying it. This is a
  deliberate deviation from the version-guarded pattern the rest of this phase follows, and it is
  the reason `UpdateThemeRequestDTO` has no `version` field despite `docs/CODE_STYLE.md` rule 6 —
  rule 6 governs `Update*RequestDTO`s on `@Version`-guarded entities, and `UserEntity` is not one.
  Record this in the DTO's Javadoc so a future reader does not read the missing field as an
  oversight.
- **Time complexity / memory:** one indexed load and one update per write; negligible.
- **Null handling:** D-12 made the column non-nullable with a LIGHT default precisely to avoid a
  null branch in every consumer of `UserResponseDTO.theme`. Do not reintroduce nullability by making
  the DTO field optional or by allowing an unset value to clear it.
- **Security:** the only real risk surface is identity. Handled by construction (no user id in the
  route) rather than by a check.
- **Breaking change:** `UserResponseDTO` gains a field. It is returned by signup and by the
  test-only `findAll`; any test asserting on its exact field set needs updating. No client contract
  is narrowed — a field is added, none removed.
</design_rationale>
