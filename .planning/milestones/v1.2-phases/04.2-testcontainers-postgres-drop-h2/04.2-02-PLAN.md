<design_alternatives>
## Approaches considered (project directive: 2 alternates + trade-off matrix)

The open decision in this plan is **how per-test isolation survives the loss of `create-drop`** for
the one table the existing cleanup cannot reach.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Extend the existing `@AfterEach` hook with `activityLogRepository.deleteAll()` (picked)** | **Pros:** one line, additive, uses a method `JpaRepository` already supplies; keeps exactly one isolation model in the codebase; costs one extra `DELETE` per test method. **Cons:** an author adding a future FK-less table must remember to extend the hook again — the hook is not self-maintaining. | Picked. It is the minimum change that closes D-02a, and the new `ActivityLogCleanupIsolationTest` turns "remember to extend the hook" from a convention into a failing test for at least the `activity_log` case. Research confirmed no repository method needs writing. |
| **B. Test-managed `@Transactional` rollback** | **Pros:** genuinely faster; isolation becomes automatic for every table, present and future. **Cons:** three verified breakages — `@TransactionalEventListener(AFTER_COMMIT)` never fires, so `ActivityEventPublicationTest`/`TaskMoveE2ETest` assert on empty lists; a shared persistence context puts fixtures in the L1 cache so `countQueries()` stops seeing `findById()`, destroying the metric `docs/CODE_STYLE.md` rule 4 explicitly sanctions; and REST Assured E2E tests get no isolation at all because the HTTP request runs on a different thread. | Rejected — and locked as rejected by D-02, which records that this was initially selected and then reversed after the three conflicts were verified against real code. Recorded here so it is not re-proposed downstream as an obvious optimization. |
| **C. Raw `TRUNCATE activity_log` (or a `@Sql` script) in the hook** | **Pros:** fastest possible reset; independent of JPA. **Cons:** a second, JDBC-level cleanup mechanism sitting beside the service-level one, invisible to anyone reading `UserService.deleteAll()`; and `TRUNCATE` takes an ACCESS EXCLUSIVE lock, which is a latent hazard if parallel test execution is ever enabled. | Rejected. `JpaRepository.deleteAll()` already exists; hand-rolling SQL for it is exactly the "don't hand-roll" case research flagged. |

### Non-obvious trade-offs

- **Performance:** `activityLogRepository.deleteAll()` issues a `SELECT` then a `DELETE` per row (JPA
  `deleteAll()` semantics), not a single bulk statement. For a table that is empty in nearly every
  `AbstractAppTest` context — no broker, therefore no consumer, therefore no writes — this is one
  cheap `SELECT` per test method. It is *not* free for `ActivityReadE2ETest`, which seeds rows
  directly; that class seeds single-digit row counts, so the cost stays negligible.
- **State-invalidation:** the shared container means `AbstractKafkaContainerTest`'s 9 subclasses and
  `AbstractAppTest`'s ~19 now write into the same `activity_log` table. The Kafka hierarchy has no
  `@AfterEach` cleanup and never has; its tests already scope every assertion by `eventId` precisely
  because the topic and consumer group are shared. Adding a `deleteAll()` on the other hierarchy is
  therefore safe *only because JUnit runs these classes sequentially in one JVM* (no
  `junit-platform.properties` declares parallelism anywhere in this repo) — a delete from one class's
  `@AfterEach` can never land mid-test in another. Enabling parallel test execution later would
  invalidate this and is already listed as a deferred idea for that reason.
- **Memory:** one long-lived Postgres container plus its JDBC pool replaces an in-process H2 engine.
  Net JVM heap goes *down* (H2's pages lived in the test JVM's heap); host RAM goes up by the
  container's footprint, which is small next to the Redpanda container already required.
- **Security:** `ddl-auto=validate` is set explicitly rather than omitted. Omitting it looks harmless
  but is worse than the status quo: Spring Boot's `create-drop` default applies only to databases it
  auto-detects as embedded, and a real Postgres URL is never embedded, so Hibernate's effective
  default becomes `none` — entity/schema drift would go completely unchecked instead of failing
  loudly. This is the ASVS V14 configuration-drift control this phase actually delivers.
</design_alternatives>
