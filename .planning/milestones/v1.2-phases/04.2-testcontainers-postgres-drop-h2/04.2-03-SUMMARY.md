## Accomplishments

- **Reuse question answered from measurement, not intuition.** Three `./gradlew fastTest --rerun-tasks` runs (same session, same machine, no `clean` between runs) measured **232s, 224s, 242s** (155 tests each, all green). The PostgreSQL container's own Testcontainers start-duration log line, captured via a `-i`-flag probe run of `FlywaySchemaProvenanceTest`, measured **PT2.287909S (~2.29s)** on Docker Server 29.4.1 — roughly 1% of wall-clock, smaller than the 18-second run-to-run variance already visible across the three timings. Combined with D-01's one-static-container-per-JVM-run design (which caps any reuse benefit to a *second, separate* `./gradlew` invocation, never a single run) and `docs/CODE_STYLE.md` rule 8 ruling out the standard `~/.testcontainers.properties` opt-in, the decision is: **reuse is NOT enabled.** Full writeup, including a real correctness argument independent of the numbers (a reused container would carry `spring_session` rows across runs, which this phase's `@AfterEach`-only isolation model does not clean) and the condition for revisiting: `docs/LOCAL_DEV.md`.
- **`docs/CODE_STYLE.md` rule 4 corrected** to name the real substrate (Testcontainers PostgreSQL 16, Flyway-built schema) and `AbstractPostgresContainerTest` as the shared container ancestor a test author needs to know about — the no-mocks prohibition, the fixture-placement sentence, and the `countQueries()` guidance are untouched.

Two adjacent claims that this phase's own H2 removal had made false — "faster loop *without containers*" and "*without paying container startup*" for `fastTest` — were also corrected (`fastTest` still starts the shared Postgres container; it only skips the Kafka-backed `*E2ETest` classes).

Two honest comparisons, not one, because the raw pre-cutover baseline and the final run don't have
matching test counts (199 vs. 210 — this phase added 11 test methods across the tracer and the
`activity_log` isolation guard):

- **Like-for-like (same test count, 208 vs. 210 is a 2-method difference, both post-this-phase's-own-additions):** this run's 295s vs. the post-tracer H2 baseline's 310s is **-15s / -4.8% faster**. 04.2-02's own run (291s) was **-19s / -6.1% faster** against the same baseline. Both runs land in the same direction and the same rough magnitude — the improvement reproduces, it isn't a one-off.
- **Raw pre-cutover comparison (different test counts, included for completeness):** 295s vs. 288s is **+7s / +2.4%**, but with 11 more tests running (+5.5% more test methods), a small nominal increase alongside a real per-test speedup is expected, not contradictory.

**The likely mechanism, stated as a hypothesis per 04.2-02's own SUMMARY, confirmed by reproduction but not independently proven further here:** H2's `create-drop` rebuilt the schema from scratch on every one of the ~30 per-test-class Spring context creations across the run; Flyway now migrates the schema exactly once against a container shared for the entire JVM lifetime. No per-context timing instrumentation was added in this plan to isolate the mechanism further — that would be its own piece of scope, and the wall-clock evidence across two independent runs (04.2-02 and this plan) already supports the conclusion at the level this phase needed it proven.

It stays; the `@Testcontainers`/`@Container` annotations it supplies are deliberately unused per D-01. No action taken, noted per the plan's instruction.
