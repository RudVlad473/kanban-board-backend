<objective>
Retarget the pre-commit `fastTest` gate from a class-name substring match to JUnit 5 `@Tag`
selection, rename the in-process classes that carry a misleading `E2ETest` suffix, and fix the stale
comment that names a deleted test class.

Purpose: Phase 7 downgraded a block of classes from the real-socket tier to in-process MockMvc but
kept their names, because `fastTest` excludes by the literal `E2ETest` suffix — so renaming them
would silently change what runs before every commit. This plan breaks that coupling permanently,
which is also what lets plan 07.1-08's new security tests land in the gate under their natural names.
Output: tag-based `fastTest` selection, 9 tagged classes, 11 renamed classes, and an accurate comment
in `UserAuthenticationProvider`.
</objective>

## Alternate approaches considered

The source todo (`2026-08-09-decide-e2etest-suffix-vs-fasttest-filter-coupling.md`) framed three
options; D-21 selects the third. Recording all three, since the decision is the point of the plan:

**Approach A: keep the `E2ETest` suffix on the 11 downgraded classes and change nothing.**

**Approach B: rename the 11 classes and change `fastTest`'s filter to a new name pattern that
matches whatever the real container-backed classes end up called.**

**Approach C (chosen, = D-21): rename the 11 classes AND retarget `fastTest` to JUnit 5 `@Tag`
exclusion, matching the style the `test` task's `rehearsal` exclusion already uses.**

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — status quo | + Zero risk. − 11 class names actively lie about their tier, which is what confused Phase 7 in the first place; − the pre-commit gate's membership is still an emergent property of naming. | Rejected — leaves the trap armed. |
| B — rename + new name pattern | + Simple, one-line build change. − Substitutes one naming coupling for another; − the next tier change hits the identical problem; − a class can be silently mis-gated by a typo in its name with nothing failing. | Rejected — same defect, new spelling. |
| C — rename + `@Tag` | + Gate membership becomes an explicit, per-class declaration independent of naming. + Matches the local precedent already in `build.gradle` (`excludeTags 'rehearsal'`). + A new class's default (no tag) is "runs in the gate", which is the safe default and exactly what D-22 wants for the new security tests. − Both halves must be correct: a tag typo silently excludes nothing, and neither Gradle nor JUnit fails on an unknown tag name. | **Picked** (D-21). Task 3 exists specifically to close the silent-typo failure mode with a counted verification rather than a visual one. |

## Non-obvious trade-offs

- **The silent-failure mode is the real risk here.** JUnit does not error on an `excludeTags` value
  that matches no test, and Gradle does not error on a `@Tag` value that appears in no build filter.
  A typo in either half produces a green build that quietly runs the wrong set. This is why task 3
  verifies by *counting executed tests* in each task's output rather than by reading the diff.
- **Renaming across a live phase:** these 11 files were edited by plans 07.1-01 through 07.1-06.
  Renaming them last minimizes churn, which is why this plan sits at wave 5 rather than wave 1.
- **Test-count invariant:** the rename must not change which tests exist. `./gradlew test`'s total
  count before and after must be identical — a drop means a class stopped being discovered, which a
  green build would otherwise hide.
- **Performance:** `fastTest`'s runtime should be roughly unchanged. If it changes materially, the
  tag set is wrong — recorded as an explicit check in task 3.
</tradeoffs>
