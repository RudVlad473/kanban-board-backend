# Phase 07.1 Plan 01: RFC 7807 ProblemDetail Convergence & 401/403 Split Summary

**Converged all 13 GlobalExceptionHandler branches onto Spring's RFC 7807 `ProblemDetail` envelope with a stable `ErrorCode` extension property, and split the previously-overloaded 401 by remapping ownership denials to 403 while leaving bad-credentials 401 untouched.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 3 (1 checkpoint:decision auto-resolved, 1 tracer, 1 auto)
- **Files modified:** 9 (2 created, 7 modified)

## Accomplishments

- New `ErrorCode` enum (`com.vrudenko.kanban_board.constant`) declaring all twelve taxonomy members plus `CODE_PROPERTY`/`ERRORS_PROPERTY` extension-key constants, documented as a published API contract
- Every one of `GlobalExceptionHandler`'s 13 `@ExceptionHandler` methods now returns `ResponseEntity<ProblemDetail>` — zero branches dropped, all four pre-existing explanatory comment blocks (GAP-05, D-09, `uk_boards_user_id_name`/dead-code, db/auth markers) preserved verbatim
- `handleMethodArgumentNotValidException` (D-02) now nests its field-error map under a top-level `errors` `ProblemDetail` property instead of returning the raw map as the body
- `handleAccessDeniedException`/`handleAppAccessDeniedException` remapped `HttpStatus.UNAUTHORIZED` → `FORBIDDEN` (D-05); `handleBadCredentialsException` is untouched and still returns 401
- Six existing cross-user E2E assertions across `BoardFullReadE2ETest`, `ColumnDeletionE2ETest`, `ColumnOrderingE2ETest`, `SubtaskLockingE2ETest`, `ActivityReadE2ETest`, and `TaskMoveE2ETest` updated from expecting 401 to expecting 403, with test names/comments saying "unauthorized" renamed to "forbidden" where applicable
- New `GlobalExceptionHandlerTest` with six `@Nested` groups covering every behavior in the plan's verification section: 404+code, 403 cross-user+code+no-leak, 400 validation+nested `errors`, 409 optimistic lock+code, 409 duplicate+code, and the absence of a top-level `properties` wrapper key (proving Jackson's `ProblemDetailJacksonMixin` flattening locally)
- Full `./gradlew test` (whole suite, all tiers) green; `./gradlew spotlessCheck` green

## Decisions Made

- **Task 1 checkpoint auto-resolved to option-a** (approve taxonomy as proposed): the project's `workflow.auto_advance` config is `true` and the checkpoint carried `gate="blocking"` (not `"blocking-human"`), so per the auto-mode checkpoint protocol the first/recommended option was auto-selected without pausing for human input. The two 404 branches (`EntityNotFoundException` and `AppEntityNotFoundException`) deliberately share `ENTITY_NOT_FOUND` rather than getting resource-specific codes — a frontend that needs to distinguish "board not found" from "task not found" reads `detail`, not `code`.
- **`GET /boards/{unknownBoardId}` from the plan's Task 2 behavior spec was executed as `GET /boards/{unknownBoardId}/full`** — the codebase has no flat single-board `GET /{boardId}` endpoint (only `DELETE`/`PUT` on that path and `GET .../full`); `/full`'s `BoardService.findFullById` calls the same `findById` → `verifyOwnershipOfBoard` chain that throws `AppEntityNotFoundException("Board")` for an unknown id, so the 404 path being tested is identical.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] This repo's pre-commit hook makes a literal RED-only commit impossible**
- **Found during:** Task 2, first commit attempt
- **Issue:** The plan's TDD flow calls for a `test(...)` commit while the new test is still failing (RED), followed by a `feat(...)` commit once it passes (GREEN). This repo's `.githooks/pre-commit` runs `./gradlew test --exclude-tests '*E2ETest'` (the `fastTest` task) on every commit and hard-fails the commit if any test fails — so a commit containing a genuinely-failing test cannot be created here, full stop. `--no-verify` was not an option (explicitly forbidden for parallel executors).
- **Fix:** For both Task 2 and Task 3, RED was verified with a direct, uncommitted `./gradlew test --tests '*GlobalExceptionHandlerTest'` run against the pre-conversion handler state (confirmed real assertion failures for the right reasons — e.g. `expected application/problem+json but was text/plain`), then the GREEN implementation was written/restored and the `test(...)`/`feat(...)` two-commit split was preserved so the TDD gate sequence (`test(...)` commit exists, then a `feat(...)` commit after it) is still satisfied in git history — it's just that the `test(...)` commit's tree state is GREEN by the time git records it, not RED. Task 3's temporary handler rollback used `git checkout HEAD -- <single file>` (an explicitly sanctioned operation, not a blanket reset) to restore the task-2-only committed state, ran the RED verification, then rewrote the file back to the full GREEN state before committing.
- **Files modified:** No extra files — this affected commit sequencing only.
- **Verification:** RED confirmed via direct test run (see commit messages for the exact failure text); GREEN confirmed via the same direct run before each commit, and the pre-commit hook's own fastTest re-run passed on both actual commits.
- **Committed in:** `0b85493` (test, GREEN at commit time), `a14e002` (feat), `63536a0` (feat)

**2. [Rule 3 - Blocking] Transient Windows file-lock failure in the pre-commit hook**
- **Found during:** Task 2, first RED-commit attempt
- **Issue:** `./gradlew fastTest` failed with `Unable to delete directory ...build\test-results\fastTest\binary` — a stale Gradle daemon/file-handle race on Windows, not a real test failure.
- **Fix:** Retried the identical commit command; the retry succeeded cleanly (`BUILD SUCCESSFUL in 3m 23s`). No code or config change was needed.
- **Files modified:** None.
- **Verification:** Retry succeeded; no recurrence in the remaining two commits.
- **Committed in:** N/A (resolved by retry, not a code fix)
