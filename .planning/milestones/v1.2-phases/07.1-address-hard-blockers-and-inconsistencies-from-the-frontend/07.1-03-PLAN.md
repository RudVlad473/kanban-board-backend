<objective>
Wire a custom `AuthenticationEntryPoint` so a genuinely unauthenticated request returns 401 with the
same RFC 7807 envelope every other error path now uses, completing the 401/403 split started in
plan 07.1-01.

Purpose: Today an unauthenticated request silently gets Spring Security's default
`Http403ForbiddenEntryPoint` — a bare 403 with no body. After plan 07.1-01 moved ownership denials
to 403, that default would make 403 mean two different things. This plan is what makes the split real.
Output: `ProblemDetailAuthenticationEntryPoint`, its explicit DSL wiring, and three existing
assertions flipped from 403 to 401.
</objective>

<tradeoffs>
## Alternate approaches considered

**Approach A (chosen): a `@Component` implementing `AuthenticationEntryPoint`, serializing a
`ProblemDetail` with the injected `ObjectMapper`, wired via `http.exceptionHandling(...)`.**

**Approach B: `HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)` — Spring's built-in status-only
entry point.**

**Approach C: an `AuthenticationEntryPoint` that re-throws into `HandlerExceptionResolver` so
`GlobalExceptionHandler` produces the body, keeping body construction in exactly one place.**

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — custom entry point serializing `ProblemDetail` | + Produces the exact same envelope as `GlobalExceptionHandler`, which is the whole point of D-04. + Small, self-contained, directly testable. − The envelope shape now has two construction sites that must not drift; mitigated by both sourcing `code` from the shared `ErrorCode` enum and by a test asserting both paths' key sets. | **Picked.** D-04 requires a body, and this is the only approach that delivers one without indirection. |
| B — `HttpStatusEntryPoint` | + Zero custom code; + impossible to get the status wrong. − Emits an empty body, so an unauthenticated response would be the one error path with no `code` and no `detail` — precisely the inconsistency this phase exists to remove. | Rejected — fails D-04's stated requirement. |
| C — delegate to `HandlerExceptionResolver` | + Single body-construction site, no drift risk. − Reaches back into the MVC layer from inside the filter chain for a request that never resolved to a handler; − the resolver needs a `HandlerMethod` it does not have; − a well-known source of subtle NPE/ordering bugs; − much harder to reason about than 15 lines of direct serialization. | Rejected — clever, fragile, and RESEARCH's Pitfall 3 warns specifically against fusing these two structurally different paths. |

## Non-obvious trade-offs

- **Security (the whole point):** before this change, an unauthenticated caller and an
  authenticated-but-forbidden caller are indistinguishable to a client. After it, they are distinct,
  which lets a frontend correctly choose "redirect to login" vs "show a permission error". This is a
  deliberate, small increase in information given to an unauthenticated caller — it reveals only that
  the route exists and requires auth, which the route table already reveals. Recorded as
  `T-07.1-03-02`, disposition `accept`.
- **Envelope drift:** two construction sites for one contract is a real maintenance hazard. Mitigated
  structurally (shared `ErrorCode` enum, no duplicated string literals) and by test
  (`GlobalExceptionHandlerTest` asserts the 401 body carries the same top-level keys as a 403 body).
- **Performance:** one `ObjectMapper.writeValue` per rejected unauthenticated request. Negligible,
  and it replaces a response that was already being written.
</tradeoffs>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous client -> Spring Security filter chain | An unauthenticated caller crosses here and is rejected before any application code runs |
| filter chain -> response writer | The entry point writes directly to the servlet response, bypassing the MVC message converters |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07.1-03-01 | Elevation of Privilege | `http.exceptionHandling(...)` wiring | high | mitigate | The entry point changes only the *response* to a rejection; the rejection decision remains `auth.anyRequest().authenticated()`, untouched. A regression that accidentally admitted an unauthenticated request would surface as the happy-path 401 test returning 200, and plan 07.1-08's 22-route auth-gating sweep re-proves every protected route rejects a no-session request. |
| T-07.1-03-02 | Information Disclosure | 401 response body | low | accept | The body states only that authentication is required. It reveals no user, resource, or route existence beyond what the 401 status itself already reveals, and distinguishing 401 from 403 is the explicit, user-approved goal (D-05). |
| T-07.1-03-03 | Denial of Service | `ObjectMapper.writeValue` on every rejected request | low | accept | Serializing a five-field object per rejected request is cheaper than the request parsing that already happened. No unbounded allocation, no per-request map growth. |
| T-07.1-03-04 | Spoofing | envelope drift between the entry point and `GlobalExceptionHandler` | medium | mitigate | Both producers source `code` from the shared `ErrorCode` enum (compile-checked, no string literals), and task 1's key-set-equality assertion fails the build if the two shapes diverge. |
| T-07.1-03-SC | Tampering | npm/pip/cargo installs | n/a | accept | No package-manager install — `AuthenticationEntryPoint` ships in `spring-boot-starter-security`, already a direct dependency. |
</threat_model>
