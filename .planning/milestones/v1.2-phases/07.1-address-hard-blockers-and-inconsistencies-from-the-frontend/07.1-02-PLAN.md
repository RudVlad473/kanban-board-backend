<tradeoffs>
## Alternate approaches considered

**Approach A (chosen): a standalone `@Configuration CorsConfig` class exposing a
`UrlBasedCorsConfigurationSource` bean, auto-detected by the existing
`http.cors(Customizer.withDefaults())`.**

**Approach B: add the `@Bean` method directly to `SecurityConfiguration`.**

**Approach C: `WebMvcConfigurer#addCorsMappings` (the Spring MVC layer, not Spring Security).**

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — standalone `config/CorsConfig` | + Zero edits to `SecurityConfiguration`, which plan 07.1-03 is editing concurrently — no file contention, no accidental churn on the `.cors(...)` line Pitfall 4 warns about. + Single-responsibility file, easy to review. − One more small config class. | **Picked.** The file-ownership property is worth more than the file count here, and it makes Pitfall 4 structurally impossible to hit. |
| B — bean on `SecurityConfiguration` | + Keeps all security config in one file, matching the existing `sessionAuthenticationStrategy` bean's placement. − Puts this plan and plan 07.1-03 in the same file in the same wave; − raises the chance a reviewer or an agent "tidies" the adjacent `.cors(Customizer.withDefaults())` line. | Rejected on contention and Pitfall-4 risk. |
| C — `WebMvcConfigurer#addCorsMappings` | + Familiar from non-Security Spring apps. − Registers CORS at the MVC layer, which runs *after* the Security filter chain; a credentialed preflight carries no cookie, so Security rejects it before MVC ever sees it. Documented explicitly in the Spring Security CORS reference. | Rejected — wrong layer, actively broken for this app's cookie-session auth. |

## Non-obvious trade-offs

- **Security:** `allowCredentials(true)` plus an origin allow-list is the only combination that works
  for cookie-session auth. The CORS spec forbids `*` once credentials are allowed, so there is no
  "just allow everything for now" shortcut — good, because that shortcut is exactly the CSRF-adjacent
  hole this control exists to close. `setAllowedOriginPatterns` would technically permit a
  wildcard-with-credentials and is explicitly prohibited above.
- **CSRF interaction:** `http.csrf(...disable)` is already in force. CORS is not a CSRF defence, and
  this plan does not claim to be one — it only stops the browser blocking *legitimate* calls from
  the two configured dev origins. Recorded as `T-07.1-02-02` below.
- **Testability:** MockMvc dispatches in-process and never constructs a real cross-origin preflight,
  so a MockMvc test cannot prove browser behaviour (D-12). The test therefore asserts the *resolved
  bean configuration*, which is the strongest claim available at this tier without moving to the
  real-socket tier.
- **Performance:** nil. One extra filter already present in the chain, now with a non-null
  configuration source.
</tradeoffs>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser origin -> API | An arbitrary web origin can attempt a credentialed request; the CORS policy is what the browser consults to decide whether to let the response through |
| deployment config -> running app | `app.cors.allowed-origins` is externally supplied; a permissive value in a production environment widens the boundary |
