<objective>
Close the Board optimistic-locking asymmetry: add `@Version` to `BoardEntity` with a V7 Flyway
migration, require a `version` on board updates, expose it on every board response DTO, and prove a
stale rename conflicts.

Purpose: Board is the only resource in the hierarchy without concurrency control, and the gap is
undocumented — Column, Task and Subtask all have it. A frontend rendering a board list has no way to
make a safe rename today.
Output: V7 migration, `@Version` on the entity, `version` on three board DTOs, a version-guarded
`BoardService.updateById`, and a new `BoardLockingTest`.
</objective>

<tradeoffs>
## Alternate approaches considered

**Approach A (chosen): mirror the existing Column/Task/Subtask convention exactly — `@Version` field,
explicit `dto.getVersion()` compare before mutation, `OptimisticLockingFailureException`, then
`entityManager.flush()`, with a required `version` on `UpdateBoardRequestDTO`.**

**Approach B: `@Version` on the entity only, relying on Hibernate's implicit version check at flush
time, with no explicit compare and no DTO field.**

**Approach C: HTTP-level concurrency via `ETag` / `If-Match` headers on the board resource.**

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — explicit compare, matching the three existing resources | + Byte-for-byte symmetry with `ColumnService`, `TaskService`, `SubtaskService` — one concurrency model across the whole API. + The conflict is detected before any mutation, so the error is deterministic rather than dependent on flush timing. + `@NotNull Long version` on the request DTO matches `docs/CODE_STYLE.md` rule 5's `Update*RequestDTO` shape. − A client must now send `version`, which is a breaking change for any existing caller. | **Picked.** D-13 locks it, and the symmetry argument is the entire point of the phase item. |
| B — implicit Hibernate version check only | + No DTO change, so no breaking change for callers. − The client has no way to *express* which version it read, so a stale rename would silently win instead of conflicting — it would only catch two writes racing inside one flush window, which is not the concurrency this is meant to guard. − Diverges from the three existing resources. | Rejected — it looks like locking without providing it. |
| C — `ETag` / `If-Match` | + Standards-based, no request-body change. + Cache-friendly. − Boards would be the only resource in the API using a header-based scheme while Columns, Tasks and Subtasks use a body field; − a frontend would need two mental models; − RESEARCH's "Don't Hand-Roll" table calls this out explicitly. | Rejected — it trades one inconsistency for a worse one. |

Secondary decision — **does the flat `BoardResponseDTO` also get `version`?** (RESEARCH Assumption A1,
Pitfall 7). D-15 names only `BoardFullResponseDTO`.

| Option | Pros / Cons | Why picked |
|--------|-------------|------------|
| Add `version` to `BoardResponseDTO` too | + `ColumnResponseDTO` already carries `version`, so this is the established precedent, not an invention. + Without it, a client doing sequential renames must call `GET /boards/{id}/full` after every `PUT` purely to re-read a number the `PUT` already knew. − Technically extends a locked decision's literal wording. | **Picked**, and flagged in the task-1 checkpoint so the operator confirms rather than discovers it. The cost of being wrong is one unused field; the cost of omitting it is an asymmetric client workflow. |
| Follow D-15 literally, `BoardFullResponseDTO` only | + Zero interpretation of the locked decision. − Leaves `POST /boards`, `PUT /boards/{id}` and `GET /boards` returning a board with no version, which is the exact class of asymmetry this phase exists to remove. | Rejected, with the reasoning surfaced at the checkpoint. |

## Non-obvious trade-offs

- **Reversibility: one-way.** Once boards ship with a required `version` on update, removing it breaks
  any client built against it, and the column cannot be dropped without a migration. This is why task
  1 is a blocking decision checkpoint.
- **Migration performance:** `ALTER TABLE boards ADD COLUMN version bigint NOT NULL DEFAULT 0` uses a
  constant, non-volatile default, which on PostgreSQL 10+ (this project targets 16) is a catalog-only
  change with no full table rewrite. The same property V2 already relied on for `tasks` and `columns`.
- **Startup coupling:** `ddl-auto=validate` outside the test profile means the entity field and the
  column must land together. Splitting them across commits produces an application that will not
  start. Task 2 delivers both in one task for exactly this reason.
- **Breaking change for existing tests:** three test sites build `UpdateBoardRequestDTO` without a
  version and will fail `@NotNull` once it is required. They are enumerated concretely in task 3.
</tradeoffs>
