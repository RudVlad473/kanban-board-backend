<objective>
Converge every `GlobalExceptionHandler` branch onto Spring's built-in RFC 7807 `ProblemDetail`
envelope with a stable per-exception `code` extension property, and split the currently-overloaded
401 by remapping ownership denials to 403.

Purpose: This is the single shape every other plan in the phase asserts against. Building it first
means the injection, auth-gating, validation and locking tests written later are authored once
against the final envelope instead of being rewritten.
Output: `ErrorCode` enum, a fully converted `GlobalExceptionHandler`, a new
`GlobalExceptionHandlerTest`, and six existing cross-user assertions flipped from 401 to 403.
</objective>

<tradeoffs>
## Alternate approaches considered

**Approach A (chosen): Spring's built-in `org.springframework.http.ProblemDetail`, one
`ResponseEntity<ProblemDetail>` per handler, `code` sourced from a new `ErrorCode` enum.**

**Approach B: a hand-rolled `ApiError` record/POJO with explicit fields.**

**Approach C: extend `ResponseEntityExceptionHandler` and lean on its built-in
`ProblemDetail` machinery instead of a bare `@ControllerAdvice`.**

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — built-in `ProblemDetail` + `ErrorCode` enum | + Zero new dependencies; already on the classpath via spring-web. + Jackson auto-registers `ProblemDetailJacksonMixin`, so `setProperty` keys render top-level for free. + `ErrorCode` as an enum satisfies `docs/CODE_STYLE.md` rule 1 (enums over magic Strings). − Requires wrapping every return in `ResponseEntity.status(...)`, an easy-to-forget step (Pitfall 1). | **Picked.** D-01 locks the type; the enum closes the only genuine ergonomic gap (stringly-typed codes). |
| B — hand-rolled `ApiError` POJO | + Total control over field names and nesting. − Reinvents a standardised media type; − loses `application/problem+json` content-type negotiation; − a frontend can no longer use an off-the-shelf RFC 7807 client. | Rejected — contradicts D-01 and RESEARCH's "Don't Hand-Roll" table. |
| C — `extends ResponseEntityExceptionHandler` | + Status is derived from `ProblemDetail` automatically, so Pitfall 1 cannot happen. − Overrides ~15 framework handler methods this app does not want to inherit; − silently changes the response shape of framework-raised exceptions the app never handled explicitly; − a much larger, harder-to-review diff for a phase whose whole point is a reviewable convergence. | Rejected — the safety it buys is cheaper to buy with a test that asserts the status on every branch. |

## Non-obvious trade-offs

- **Security (information disclosure):** the `Exception.class` catch-all currently puts
  `ex.getMessage()` straight into the response body, and this plan preserves that behaviour to keep
  the diff a pure shape change. A raw JDBC/Hibernate message can leak schema details. This is
  recorded as threat `T-07.1-01-04` below with disposition `accept` for this plan and is explicitly
  re-tested by plan 07.1-08's injection suite, which asserts no 500s reach the client for malformed
  input in the first place.
- **Performance:** negligible. One extra short-lived `ProblemDetail` object plus a `HashMap` of
  extension properties per error response; error responses are not on any hot path.
- **Contract (reversibility: costly):** every error body's shape changes at once. There is no
  versioned error envelope and no deprecation window — that is exactly why task 1 is a blocking
  decision checkpoint rather than an assumption.
</tradeoffs>
