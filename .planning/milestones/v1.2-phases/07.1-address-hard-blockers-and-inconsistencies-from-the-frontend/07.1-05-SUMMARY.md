# Phase 07.1 Plan 05: Board Optimistic Locking Summary

**Closed the last Board/Column/Task/Subtask concurrency-model asymmetry: Flyway V7 adds `boards.version`, `BoardEntity` carries `@Version`, `BoardService.updateById` explicitly rejects a stale write with 409, and `version` now flows through every board DTO (request and both response shapes) with a new `BoardLockingTest` proving all of it over real HTTP.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 4 (1 checkpoint auto-resolved, 3 code tasks)
- **Files modified:** 11 (2 created, 9 modified)

## Accomplishments

- `V7__add_board_optimistic_locking_version_column.sql`: single additive `ALTER TABLE boards ADD COLUMN version bigint NOT NULL DEFAULT 0` — a catalog-only change on PostgreSQL 10+, no existing migration touched.
- `BoardEntity` gains `@Version private Long version`, placed after `user`, explicitly excluded from Lombok's `@EqualsAndHashCode` (mirroring the existing `column`-field exclusion) since this entity — unlike `ColumnEntity`/`TaskEntity` — still derives equals/hashCode from its fields.
- `BoardService.updateById` gains the explicit `dto.getVersion()` compare-before-mutate guard (throwing `OptimisticLockingFailureException` before the pre-existing duplicate-name check), then `entityManager.flush()` so the response DTO carries the incremented version — byte-for-byte the same shape `ColumnService.updateById` already uses.
- `UpdateBoardRequestDTO` gains `@NotNull private Long version`; `BoardResponseDTO` and `BoardFullResponseDTO` both gain `version` (task 1's approved decision extends D-15's literal `BoardFullResponseDTO`-only wording to the flat DTO too, matching `ColumnResponseDTO`'s existing precedent). MapStruct's `unmappedTargetPolicy = IGNORE` auto-mapped the same-named field on every mapper with zero interface changes — confirmed by running the tests, not assumed.
- New `BoardLockingTest` (`e2e/board/`, no `E2ETest` suffix per plan 07.1-07's naming direction, no `@Tag` per D-22): proves the stale-rename 409 with `code=OPTIMISTIC_LOCK_CONFLICT`, the first-rename-succeeds-with-incremented-version case, the missing-version 400 with `code=VALIDATION_FAILED` and an `errors.version` key, and version exposure on `GET /boards/{id}/full` (top-level board version, not only nested) and `GET /boards` (every board in the list).
- `BoardControllerTest.UpdateById`'s three pre-existing tests were quietly broken (posting a version-less `SaveBoardRequestDTO` body to a route that now requires `UpdateBoardRequestDTO.version`) — fixed and a new controller-tier missing-version 400 test added.
- Full `./gradlew test` (159 test classes, whole suite, all tiers): **0 failures**. `./gradlew fastTest`: green, `BoardLockingTest` confirmed present in `build/test-results/fastTest/` (not excluded). `./gradlew spotlessCheck`: green.

## Decisions Made

- **Task 1 checkpoint auto-resolved to option-a** (`workflow.auto_advance: true`, gate is `"blocking"` not `"blocking-human"`): full symmetry — required `version` on update, and `version` added to the flat `BoardResponseDTO` in addition to `BoardFullResponseDTO`. This is the plan's own front-loaded recommended option (Approach A in the trade-off matrix) and closes the exact asymmetry class this phase exists to remove; option-b (literal D-15 scope only) would have left `POST`/`PUT`/`GET /boards` returning a versionless board.
- **`UpdateBoardRequestDTO.version` folded into task 2's commit**, not task 3's, because task 2's own `BoardService.updateById` change cannot compile without it — a real compile-order dependency the plan's task 2/task 3 file-list boundary did not account for (task 2's file list omits every DTO, but its action text requires `boardDTO.getVersion()` to exist). Documented rather than silently worked around: task 2's commit necessarily leaves `BoardServiceTest` red until task 3's `BoardResponseDTO.version` field lands, since the existing test callers read `.getVersion()` off the response DTO to build the follow-up update. Both commits were verified together as a combined change before being split along their file boundaries.
- **`BoardEntity.version` excluded from equals/hashCode.** The plan's task 2 action text said to mirror `ColumnEntity`'s field shape exactly, but `ColumnEntity` carries no `@EqualsAndHashCode` annotation at all (it moved to identity-based equals/hashCode specifically because a mutable field/collection driving equals is unsafe in a Hibernate-populated `Set`). `BoardEntity` still has `@EqualsAndHashCode(callSuper = false)`, so an unexcluded `version` field would have reproduced that exact hazard for the first time on this entity. Verified by grep that no current caller stores a `BoardEntity` in a hash-based collection (so this is preventive, not a live bug), and excluded it the same way the entity's own `column` field already is, with an inline comment explaining why.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `UpdateBoardRequestDTO.version` needed to exist before `BoardService` could compile**
- **Found during:** Task 2, immediately after writing `BoardService.updateById`'s version-compare guard
- **Issue:** The plan assigns `UpdateBoardRequestDTO`'s `version` field to task 3's scope, but task 2's own action text requires `boardDTO.getVersion()` in `BoardService.updateById` — a hard compile dependency the plan's task boundaries did not resolve.
- **Fix:** Added the minimal `@NotNull private Long version` field to `UpdateBoardRequestDTO` as part of task 2's commit (not the two response DTOs, which stayed in task 3).
- **Files modified:** `UpdateBoardRequestDTO.java` (part of task 2's commit, not a separate fix commit).
- **Verification:** `./gradlew compileJava` succeeds; full suite green once task 3's response-DTO fields also landed.
- **Committed in:** `37dc8c3` (Task 2 commit)

**2. [Rule 1 - Bug] `BoardControllerTest.UpdateById`'s three tests posted the wrong DTO type**
- **Found during:** Task 3's full-suite verification run
- **Issue:** All three tests built a `SaveBoardRequestDTO` (name-only) and POSTed its JSON to `PUT /boards/{boardId}`, which the controller deserializes as `UpdateBoardRequestDTO`. Once `@NotNull Long version` was added, the missing field failed validation before the handler body ever ran, turning `shouldUpdateBoard_whenBoardExists` (expects 200) and `shouldReturnNotFound_whenBoardDoesNotExist` (expects 404) into 400s. `BoardControllerTest.java` is not in task 3's `<files>` list, but the plan's own acceptance criterion ("`./gradlew test` passes with zero failures across the whole suite") requires it.
- **Fix:** Switched both tests to build a real `UpdateBoardRequestDTO` with a correct `version`; reworked the full-JSON-equality assertion in `shouldUpdateBoard_whenBoardExists` into explicit field assertions (id/name/version-changed) since guessing the exact post-increment version for a JSON string comparison was more fragile than asserting on the parsed response.
- **Files modified:** `BoardControllerTest.java`.
- **Verification:** `BoardControllerTest` (all 4 nested classes) passes; full suite green.
- **Committed in:** `bda8955` (Task 4 commit — grouped with `BoardControllerTest`'s task-4-mandated missing-version-400 addition since both touch the same file and the same nested class)
