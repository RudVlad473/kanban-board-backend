<objective>
Make every resource-creating POST return 201 Created, closing the last inconsistency named in the
phase title: today board, task and signup creation return 201 while column and subtask creation
return 200.

Purpose: A frontend that branches on `response.status === 201` to distinguish "created" from
"updated" gets the wrong answer for two of the five creation endpoints. The majority pattern is
already correct and already in this codebase — this makes the two stragglers match it.
Output: 201 + `Location` on `POST /boards/{boardId}/columns` and
`POST .../tasks/{taskId}/subtasks`, with every affected assertion updated.
</objective>

## Alternate approaches considered

**Approach A (chosen): change both endpoints to `ResponseEntity.created(URI.create(request.getRequestURI()))`,
matching the two endpoints that already do it, and update the affected assertions.**

**Approach B: leave the two endpoints at 200 and instead downgrade the three 201 endpoints to 200,
making "consistently 200" the convention.**

**Approach C: leave the inconsistency alone and document it.**

| Approach | Pros / Cons | Why picked / rejected |
|----------|-------------|-----------------------|
| A — converge on 201 | + 201 is the semantically correct status for a POST that creates a resource (RFC 9110). + It is already the majority pattern here (3 of 5 endpoints) and the pattern the phase title names. + The `Location` header comes with it, which is genuinely useful to a client. − Breaking for any caller asserting exactly 200; the six affected assertion sites are enumerated in task 2. | **Picked.** The phase title states the target explicitly ("consistently 201"), and it is both the correct and the cheaper direction. |
| B — converge on 200 | + Fewer files change; + no breaking change for the two current 200 callers. − Semantically wrong; − contradicts the phase title verbatim; − would mean *changing* three currently-correct endpoints to be incorrect. | Rejected. |
| C — document, do not fix | + Zero risk. − The phase's own scope statement lists this as one of the audit's hard blockers; deferring it silently would be exactly the scope reduction this planning process forbids. | Rejected. |

## Non-obvious trade-offs

- **Breaking change, deliberately taken now:** any existing caller asserting `200` on these two routes
  breaks. There is no external consumer yet — the frontend does not exist — which is precisely why
  this is the cheapest moment in the project's life to make it. Waiting makes it strictly more
  expensive.
- **`Location` header semantics:** the two endpoints that already return 201 use
  `URI.create(request.getRequestURI())`, i.e. the *collection* URI the POST was made to, not the URI
  of the newly created resource. That is arguably imprecise, but it is the established local
  convention and matching it keeps all five creation endpoints identical. Deviating here — emitting a
  precise per-resource URI on two endpoints and a collection URI on the other three — would replace
  one inconsistency with a subtler one. Recorded as a note rather than fixed.
- **Performance / security:** none. Status code and one response header.
</tradeoffs>

## STRIDE Threat Register

|-----------|----------|-----------|----------|-------------|-----------------|
| T-07.1-06-01 | Tampering | `Location` header built from `request.getRequestURI()` | low | accept | `getRequestURI()` returns the servlet-decoded path Spring already matched to a handler, not a raw client-supplied string, and it is reflected only in a response header the client itself just sent. This is the identical construction the two pre-existing 201 endpoints already use, so this plan adds no new exposure — it extends an existing accepted pattern. Header-injection via CR/LF is prevented by the servlet container's header encoding. |
| T-07.1-06-02 | Repudiation | a client mis-detecting create vs update because two endpoints returned 200 | low | mitigate | This plan is the mitigation: after it, 201 unambiguously means a resource was created on all five creation routes, so a client can branch on status alone. |
