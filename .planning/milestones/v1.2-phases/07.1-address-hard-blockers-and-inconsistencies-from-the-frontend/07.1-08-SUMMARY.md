## Decisions Made

- Cookie-replay auth (`signinCookie()` once, `.cookie(cookie)` on every subsequent call) in `InjectionAttemptTest` instead of `.with(user())` — see key-decisions above for the concurrent-session-ceiling finding that forced this.
- SQL/XSS round-trip proofs run against Column/Task/Subtask fields, not Board name, because `@BoardName`'s own `@Pattern` (letters/digits/spaces only) rejects every classic meta-character payload before JPA ever sees it — Board name instead gets a dedicated "cleanly rejected, 400, never 500" case for both payload categories.
- `OversizedBoundary` asserts each field's actually-observed error code rather than assuming one uniform code across all seven controllers — see the `CONSTRAINT_VIOLATION`/`VALIDATION_FAILED` finding above.
- Route-table body values in `AuthorizationGatingTest` are static constants, never fixture-derived — every service method in this codebase resolves ownership before touching any other field, so an arbitrary-but-`@Valid`-passing body still exercises the intended 401/403 path.
- Task 2 and Task 3 committed together (one file, interdependent `routeTable()` shared by both the sweep and the completeness guard) rather than split, since the plan's own per-task file list names the same file for both.

### Auto-fixed Issues

### Test-approach deviations (not production fixes)

**1. Switched InjectionAttemptTest's authentication mechanism mid-implementation**
- **Found during:** Task 1, first full test run
- **Issue:** `.with(user(userId))`, the shortcut used throughout this codebase's `controller/*ControllerTest` classes, establishes a brand-new HTTP session on every authenticated MockMvc call. Several `InjectionAttemptTest` cases make 3+ such calls per test method for the same user (create, list, create-again, list-again); the 3rd call was silently rejected with 401 `UNAUTHENTICATED`. Root-caused by reproducing with a throwaway scratch test (4 identical calls: 200, 200, 401, 401) and confirming `SecurityConfiguration`'s `MAX_CONCURRENT_SESSIONS = 2` + `SessionManagementFilter` as the mechanism — invisible in production because the real signin path pre-establishes its session before the security context is ever saved, so `SessionManagementFilter` never treats it as "new."
- **Fix:** Rewrote every helper/test in `InjectionAttemptTest` to call `signinCookie()` once and replay the returned cookie on every subsequent request in that test method. Verified via the same scratch reproduction (4/4 now return 200).
- **Files modified:** `src/test/java/com/vrudenko/kanban_board/security/InjectionAttemptTest.java` (test-only, this plan's own file — not a production change)
- **Verification:** Full `InjectionAttemptTest` run, 32/32 pass.
- **Committed in:** `3845d1f`

**2. Adjusted OversizedBoundary assertions to match each controller's actual validation-exception routing**
- **Found during:** Task 1, first full test run
- **Issue:** Task title/description and Subtask title MAX+1 cases initially asserted `VALIDATION_FAILED` + a per-field `errors` map (matching the Board/Column-name cases), and failed with `CONSTRAINT_VIOLATION` and no `errors` map instead.
- **Fix:** Investigated and confirmed the root cause is `@Validated`'s presence/absence at the controller class level (Board/User/Activity have it; Column/Task/Subtask/TaskMove don't), which changes whether Spring throws `MethodArgumentNotValidException` or `HandlerMethodValidationException` for the identical kind of `@Valid @RequestBody` failure. Adjusted the four affected test cases to assert `CONSTRAINT_VIOLATION` (their actual, observed behavior) instead of forcing a fix into `GlobalExceptionHandler` or the four controllers, which would have violated this plan's test-only scope.
- **Files modified:** `src/test/java/com/vrudenko/kanban_board/security/InjectionAttemptTest.java`
- **Verification:** Full `InjectionAttemptTest` run, 32/32 pass.
- **Committed in:** `3845d1f`
- **Follow-up:** Filed `.planning/todos/pending/2026-08-10-reconcile-validation-failed-vs-constraint-violation-envelope.md` (major) — this is a real, pre-existing gap in this phase's own error-envelope convergence claim, not something introduced here.

## Malformed Path Variable — Observed Statuses (per acceptance criteria)

Measured directly (not assumed) via the committed `MalformedPathVariable` parameterized tests, confirmed against all four resource types (Board/Column/Task/Subtask — identical pattern across all four):

| Payload shape | Observed status | Why |
|---|---|---|
| `../../../etc/passwd` (path-traversal-shaped) | **400** | The literal `../` sequence in a URI-template-substituted path segment is rejected by Spring's request-path normalization/validation before the request reaches the service layer |
| `1' OR '1'='1` (SQL meta-characters) | **404** | Reaches the service layer; `ownershipVerifierService`'s `findById` finds no matching row for the literal string, throwing `AppEntityNotFoundException` |
| `not-a-real-ulid-value` (non-ULID) | **404** | Same as above — a syntactically plain string that simply doesn't match any row |

Both observed codes are within D-16's required `400 or 404, never 5xx` envelope; the 400/404 split itself was Claude's discretion per CONTEXT.md and is recorded here for a future follow-up to tighten deliberately if desired.
