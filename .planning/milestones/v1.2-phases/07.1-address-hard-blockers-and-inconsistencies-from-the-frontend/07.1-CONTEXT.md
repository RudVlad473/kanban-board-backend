<decisions>
## Implementation Decisions

### Error Response Envelope
- **D-01:** Converge every `GlobalExceptionHandler` branch onto Spring's built-in RFC 7807 `ProblemDetail` type (`ResponseEntity<ProblemDetail>`), replacing today's mix of bare-string bodies and the one `Map<String,String>` branch. — **Reversibility:** costly — every handler's return type changes, and any frontend code already written against the old bare-string shape would break.
- **D-02:** Field-level validation errors (from `MethodArgumentNotValidException`) nest under an `errors` extension property inside the `ProblemDetail`, rather than being their own top-level shape.
- **D-03:** Each `ProblemDetail` carries a stable `code` extension property (e.g. `BOARD_NOT_FOUND`, `OPTIMISTIC_LOCK_CONFLICT`), one per exception type, so the frontend can branch on more than just HTTP status.
- **D-04:** Wire a custom `AuthenticationEntryPoint` so a genuinely unauthenticated request (rejected by the Spring Security filter chain before reaching any controller or `GlobalExceptionHandler`) returns the same `ProblemDetail` shape as every other error path — today it likely falls through to Spring Security's own default response instead.

### 401 vs 403 Split
- **D-05:** `AppAccessDeniedException` and `AccessDeniedException` (both ownership-related, currently mapped to 401 at `GlobalExceptionHandler.java:60-68`) move to **403 Forbidden**. `BadCredentialsException` stays 401 (bad signin credentials). The new `AuthenticationEntryPoint` (D-04) is the sole source of true 401s for unauthenticated access — `@PreAuthorize("isAuthenticated()")` failures at the filter-chain level ARE that case, already covered by D-04; no separate `AccessDeniedHandler` needed.

### Signup / Signin Validation & Exposure
- **D-06:** Add `@Valid` to both `SigninRequestDTO` and `SignupRequestDTO` parameters in `AuthenticationController` so field-level Jakarta Validation constraints (`@AppEmail`/`@Password`/`@DisplayName`) actually fire — currently silently skipped.
- **D-07:** Signup reveals duplicate-email conflicts explicitly: 409 via the existing `AppDuplicateResourceException` pattern (already used for board-name uniqueness), with a clear "email already taken" message. Deliberately accepts the enumeration tradeoff — judged acceptable for this project's personal/portfolio scope versus building an email-verification flow.
- **D-08:** Signin's malformed-input validation failures (e.g. malformed email format) return normal 400 field errors, same as every other `@Valid`-annotated endpoint. Only genuine bad-credentials failures (valid-shaped input, wrong password/unknown email) stay collapsed into the existing generic-401 anti-enumeration behavior.
- **D-09:** On signup, Jakarta field validation runs before the duplicate-email check — this falls out naturally from `@Valid`'s automatic pre-method execution; no explicit ordering code needed.

### CORS Configuration
- **D-10:** New `CorsConfigurationSource` bean; allowed origins externalized via a new `app.cors.allowed-origins` property in `application.properties` (comma-separated), defaulting to `http://localhost:5173,http://localhost:3000` when unset.
- **D-11:** Allow `GET/POST/PUT/PATCH/DELETE` (every method this API's controllers expose, including `PATCH` for reorder/move), all headers, `allowCredentials(true)` (required for cookie-based session auth — forces an explicit origin allow-list, no wildcard).
- **D-12:** No special handling needed in the test profile — CORS is browser-enforced and MockMvc never triggers preflight/origin checks. A dedicated test may assert the bean's configuration or an `OPTIONS` response's headers directly if coverage of the config itself is wanted.

### Optimistic Locking — Board/User
- **D-13:** Add `@Version` to `BoardEntity`, matching Column/Task/Subtask. Requires a new Flyway migration **V7** (current highest is `V6__change_activity_log_event_id_to_varchar.sql`) adding `boards.version`, and `UpdateBoardRequestDTO` gains a required `version` field following the existing `Update*RequestDTO` pattern. — **Reversibility:** one-way — once boards ship with a required `version` field, removing it later breaks any frontend already built against it.
- **D-14:** `UserEntity` does **NOT** get `@Version`. Per the audit, `UpdateThemeRequestDTO`'s last-write-wins is a deliberate, already-documented design choice for a low-stakes UI setting, not a gap — this phase closes only the genuinely inconsistent, undocumented Board asymmetry the audit flagged.
- **D-15:** `BoardFullResponseDTO` gains the board's `version` field (today it only exposes column/task/subtask versions) — needed so a frontend that loads a board via `GET /boards/{boardId}/full` has the version it needs to make a version-safe board rename afterward.

### Security/Injection Test Coverage
- **D-16:** New tests cover: SQL injection payloads against every free-text field (proving JPA/Hibernate parameter binding holds); XSS/stored-script payloads (stored and read back verbatim — proves nothing server-side chokes; sanitizing for display is explicitly a frontend concern, not tested here); oversized/boundary payloads against length-validated fields; malformed/non-ULID path variables (path-traversal-style strings, SQL-meta characters) in ID path segments, confirming clean 400/404 responses rather than 500s.
- **D-17:** These live in a new dedicated class, e.g. `security/InjectionAttemptE2ETest`, following the existing `security/` package convention (alongside `AuthenticationE2ETest`) rather than being folded into each `*ControllerTest`.
- **D-18:** SQL injection tests assert the payload round-trips as **inert stored data** (e.g. create a board named with a SQLi payload, read it back byte-for-byte, confirm other test data/the table itself survives) — not just a clean HTTP response.

### Auth-Gating Test Coverage
- **D-19:** New tests live in one consolidated class, e.g. `security/AuthorizationGatingE2ETest`, sweeping every protected route (~19) for both unauthenticated (401) and cross-user (403) rejection — centralizes the "is every endpoint actually gated" guarantee in one place instead of scattering it across 4+ `*ControllerTest` files.
- **D-20:** Cross-user fixtures extend the existing `AbstractAppTest`/`AbstractAppMockMvcTest` pattern with a new `getForeignUser()` helper (name chosen over the earlier "createOtherUser" for being unambiguous at call sites — "a user foreign to this resource"), alongside the existing `getOwningUser()`/`getNoBoardsUser()` fixtures.

### E2ETest Suffix / fastTest Filter (folded todo)
- **D-21:** Rename the 12 mistiered `*E2ETest` classes (from Phase 7's tier downgrade) to drop the misleading suffix, and retarget `build.gradle`'s `fastTest` exclusion filter from a class-name substring match to a JUnit 5 `@Tag` (e.g. `@Tag("realSocket")` / `@Tag("kafka")`) on the classes that genuinely need a real socket or Kafka. Decouples the pre-commit gate from naming permanently.
- **D-22:** This phase's new security/injection and auth-gating test classes default to running in the pre-commit `fastTest` gate (in-process MockMvc tier, no `@Tag`) — these are exactly the tests that shouldn't be silently skipped locally. Only tag/exclude a class if it turns out to genuinely need Kafka or a real socket.
- **D-23:** Fix the stale `UserAuthenticationProvider.java:38` comment (still names the deleted `SessionPersistenceE2ETest`) as a drive-by while touching this area for the rename/`@Tag` work.

### `/claude-security` Scan (locked requirement — user-mandated, not discussed)
- **D-24:** Run the newly-installed `/claude-security` plugin (`claude-security@claude-plugins-official`, installed 2026-08-09) as the **LAST** step of this phase, strictly after this phase's own test coverage (D-16 through D-20) is written and passing — not before, and not in place of it. ## Existing Code Insights

### Reusable Assets
- `AbstractAppTest` fixture base (`getOwningUser()`, `getNoBoardsUser()`) — extend with `getForeignUser()` per D-20
- `AppDuplicateResourceException` — already used for board-name uniqueness (`06-02-PLAN.md`); reuse directly for D-07's signup duplicate-email conflict

### Established Patterns
- `Update*RequestDTO` always carries a mandatory `@NotNull Long version` once locking applies (Column/Task/Subtask precedent) — `UpdateBoardRequestDTO` should follow suit per D-13
- Services explicitly compare `dto.getVersion()` against the loaded entity before mutating, throwing `OptimisticLockingFailureException` on mismatch, then `entityManager.flush()` — see `ColumnService.java:136-139`/`:175-178`, `TaskService.java:119-122`/`:177-180`, `SubtaskService.java:73-76`
- MockMvc + `.with(user(userId))` for authenticated requests; in-process `signinCookie()` (via `AbstractAppMockMvcTest`) for classes that need to exercise the real `POST /signin` call site
- Flyway migrations are the only schema-change path (`ddl-auto=validate` outside test profile) — D-13's Board version column needs `V7__*.sql`

### Integration Points
- `SecurityConfiguration.java` — `.cors(Customizer.withDefaults())` at line 53 (needs the new `CorsConfigurationSource` bean per D-10/D-11); needs the new `AuthenticationEntryPoint` wiring per D-04
- `GlobalExceptionHandler.java` — all branches (lines 31-135 per the audit) need conversion to `ProblemDetail` per D-01 through D-03, plus the 401→403 remap per D-05
- `AuthenticationController.java` — `@Valid` additions per D-06 (currently missing at `:44-45`, `:66-67`)
- `BoardEntity`/`BoardService`/`UpdateBoardRequestDTO`/`BoardFullResponseDTO` — version field addition per D-13/D-15
