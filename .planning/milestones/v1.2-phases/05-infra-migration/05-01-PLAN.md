## Planner finding that changed this plan's scope

RESEARCH.md and PATTERNS.md both describe INFRA-06 as "run the three existing idempotent bridge scripts against Neon." Reading those three scripts directly shows that is not sufficient against a fresh, empty Neon database:

| Script | First statement | Behavior against an empty database |
|---|---|---|
| `02-optimistic-locking-ddl.sql` | `ALTER TABLE tasks ADD COLUMN IF NOT EXISTS version ...` | **Fails** — relation "tasks" does not exist |
| `03-activity-log-ddl.sql` | `CREATE TABLE IF NOT EXISTS activity_log (...)` | Succeeds (self-sufficient) |
| `04-password-hash-not-null-ddl.sql` | `ALTER TABLE users ALTER COLUMN password_hash SET NOT NULL` | **Fails** — relation "users" does not exist |

Production `application.properties` sets no `ddl-auto` at all (only `application-test.properties` sets `create-drop`, and only the local-dev compose file sets `update` via env var). On AWS the base tables had been created at some earlier point; Neon starts genuinely empty. Without a baseline script the app cannot start against Neon and INFRA-06's CI job cannot pass. Task 3 closes this.

**Approaches considered for the baseline, and why the chosen one:**

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **Generate from Hibernate's own schema export, review, check in as a baseline script** | + Machine-generated against the real entity set, correct across all seven entity classes. + Keeps production ddl-auto unset, preserving the documented convention. + Leaves a reviewable artifact in git, which is what makes INFRA-06's CI gate meaningful. − Generated DDL needs post-processing to add idempotency guards. | **Picked.** The post-processing cost is bounded and one-time; the alternatives each break something structural. |
| One-shot Hibernate ddl-auto=update on the first production boot, then remove it | + Zero new artifacts, mirrors the local-dev mechanism. − Leaves no schema description in git, so INFRA-06's job would verify a schema nothing in the repo describes, making the gate theatre. − Puts ddl-auto in production, the exact thing every bridge script header argues against. | Rejected — defeats INFRA-06's purpose. |
| Hand-author the baseline DDL from the entity classes | + Full control over guards and ordering. − Error-prone across seven entities, ULID id types, and the naming strategy; a single mismatched column type is a production-only failure. | Rejected — no reason to hand-write what Hibernate can emit correctly. |

**Reversibility:** `costly`, not one-way — the Neon database is empty until 05-04, so a wrong baseline can be dropped and regenerated at near-zero cost. No decision checkpoint required.

**Non-obvious trade-offs carried by this plan:**
- *Security:* adding Actuator widens the HTTP surface. A `health`-only exposure list and disabled detail rendering are the entire mitigation; getting this wrong publishes a heapdump — full JVM memory, including the session store and bcrypt hashes — to the internet.
- *Performance:* disabling PgJDBC's server-side prepared-statement reuse means every statement is re-planned server-side. At this project's traffic that is negligible; it is not negligible advice to carry into a high-QPS context, so the rationale is written down next to the property.
- *Availability:* HikariCP's default connection-timeout (30s) already exceeds Neon's cold start, but its default max-lifetime (30 min) is longer than Neon's idle-connection reaping, which surfaces as random broken connections rather than as a clean pool refresh.

| Boundary | Description |
|----------|-------------|
| Internet to Caddy to app HTTP surface | The new Actuator path is reachable by anyone once Caddy proxies it; unlike every other permitAll path it is not a login or docs page |
