<objective>
Turn Plan 01's configured reliability machinery into proven reliability: prove that a redelivered
event produces exactly one row (including under genuine concurrency, where the database constraint
rather than the exists-check is the arbiter), and that a genuinely malformed message isolates itself
on `kanban.activity.dlt` — carrying its original bytes, without blocking the events behind it.

Purpose: RELY-01 and ACTLOG-03 are the two requirements most likely to be *configured correctly and
still broken*. A duplicate that quietly exhausts three retries into the dead-letter topic looks
identical to working idempotency from the outside; a deserialization failure that stalls the poll
loop looks identical to a quiet topic. Only an adversarial test against a real broker tells them
apart.

Output: two Testcontainers-based test classes — one for idempotency under redelivery and
concurrency, one for the dead-letter path's routing, payload fidelity, non-blocking behaviour and
tombstone handling.
</objective>

## Alternate Approaches Considered

Required by `.claude/CLAUDE.md` → GSD Execution Directives.

**Decision A — how the concurrent-redelivery race is exercised.**

| Approach | Pros / Cons | Why picked |
|---|---|---|
| **Two threads invoking `ActivityLogRecorder.record()` directly with the same `eventId`** (chosen) | + Actually reaches the check-then-insert race window, which is the only thing that proves the DB constraint is load-bearing. + Deterministic and fast — no broker timing involved. − Bypasses the Kafka transport for this one assertion. | The transport is already proven by Plan 01 and by this plan's own redelivery test. RESEARCH.md Pitfall 3 states the requirement plainly: publishing twice to a one-partition topic consumed by one thread is *sequential*, so it can never reach the race — a test that only did that would assert the fast path and leave the constraint unproven. |
| Publish the same `eventId` twice and hope the consumer parallelises | + Pure end-to-end. − One partition and one consumer thread (D-08) make concurrent delivery impossible by construction; the test would pass while proving only the exists-check. | Rejected: structurally cannot exercise what it claims to. |
| Raise topic partitions and consumer concurrency for the test | + Real concurrency through the transport. − Contradicts D-08 (exactly one partition), and a test-only topology divergence means the tested pipeline is not the shipped pipeline. | Rejected: changes the thing under test to make the test possible. |

**Decision B — how the poison message is produced.**

| Approach | Pros / Cons | Why picked |
|---|---|---|
| **Raw `KafkaProducer<String, byte[]>` publishing unparseable bytes** (chosen) | + A genuine, deterministic deserialization failure, exactly what D-06 requires. + Uses only `kafka-clients`, already on the classpath through `spring-kafka` — no new dependency. + Lets the test capture the exact bytes it sent, so payload fidelity becomes assertable. − One more client to construct in the test. | D-06 is explicit and this is the only way to satisfy it honestly. |
| A test-only failure-injection hook on the consumer | + Trivial to trigger. − Explicitly forbidden by D-06; proves the hook works, not that real bad data is isolated; and leaves test-only branching in production code. | Rejected: forbidden, and self-defeating. |
| Send a well-formed object of an untrusted type through the application's `KafkaTemplate` | + No new client. − The failure is a trusted-packages rejection, which is RESEARCH.md Pitfall 2's exact false positive: a test that passes for a reason that would also mean *every* message is failing. | Rejected: indistinguishable from total pipeline failure. |

**Non-obvious trade-offs recorded here rather than discovered later:**

- *Reliability / correctness.* Asserting "exactly one row" after a redelivery is necessary but not
  sufficient. If the duplicate were signalled by an exception, the retry policy would still
  eventually give up and the row count would still be one — while the dead-letter topic quietly
  filled with routine traffic. That is why the redelivery test must *also* assert the dead-letter
  topic stayed empty for that `eventId`; without that second assertion the test cannot distinguish
  D-05 working from D-05 broken.
- *Timing / flakiness.* Every assertion here is on an asynchronous outcome. Proving a *positive*
  (a row appeared, a record reached the dead-letter topic) uses polling with a generous ceiling.
  Proving a *negative* (no second row, no dead-letter record) cannot poll — it requires a settle
  signal. The settle signal used is a subsequent, distinct sentinel event: once the sentinel's row
  has appeared, the consumer has demonstrably drained past the record under test on the same
  single-partition topic, so the negative can be asserted without an arbitrary wait.
- *Performance.* Both classes reuse Plan 01's container harness, so the JUnit/Spring context cache
  starts one broker for the whole `activitylog` package rather than one per class — provided none of
  the three classes diverge in their `@TestPropertySource` values. Keep them identical.
- *Security.* The dead-letter topic now durably holds payloads that failed to parse, including
  whatever an untrusted producer put on the topic. Its contents are never served over HTTP by this
  phase, and no admin/replay surface is built (explicitly out of scope in REQUIREMENTS.md).
