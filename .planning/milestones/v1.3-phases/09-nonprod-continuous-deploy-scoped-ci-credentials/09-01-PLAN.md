<objective>
Introduce the credential boundary CI-02 requires and prove it by driving one real nonprod deploy
through it: two GitHub Environments holding every deploy secret, a second Linux deploy identity on
the VM confined to nonprod's directory, a second Docker Hub repository, and the first two nonprod
jobs (`flyway-verify-nonprod`, `deploy-to-nonprod`) wired end to end.

Purpose: CONTEXT.md's own sequencing says CI-02 must land ahead of CI-01, because adding a nonprod
job to a workflow whose secrets are all repository-scoped would hand that job production's SSH key,
production's database and production's registry credential by default. This plan builds the fence
first, then walks one real deploy through the gate in it.

Output: a green workflow run in which a single push to master deploys BOTH environments, nonprod
running its own image from its own repository under its own SSH identity, with production's
behaviour unchanged.
</objective>

| **B. The structural fail-loud property is worth it. |
| **C. Distinct secret names per environment (`NETCUP_SSH_KEY_NONPROD`, `DB_HOST_NONPROD`, ...) as bare repository secrets, no GitHub Environments at all** | **Pros:** no new GitHub concept; trivially auditable by name; no production retrofit. **Cons:** CI-02 names GitHub Environments specifically; naming is a convention a copy-paste defeats in one character; and every job would still be able to read every secret, so the "unreachable" half of success criterion 3 is simply false. | **Rejected.** This is the status quo with longer names. |

**Non-obvious trade-offs this plan deliberately accepts:**

- **Security (residual, root-equivalence):** `deploy-nonprod` must be in the `docker` group to run
  `docker compose`, and Docker group membership is root-equivalent on the host — a holder of the
  nonprod key can mount `/opt/deploy/kanban-board-backend` into a container and read `.env.prod`
  regardless of the `chmod 750` this plan applies. D-02 explicitly rejects forced-command /
  restricted-shell hardening as disproportionate. This is not a new exposure (production's own
  `deploy` user has had exactly this property since v1.2 Phase 5) and this phase strictly narrows
  the blast radius relative to the alternative of running nonprod deploys as `deploy`, but it does
  mean the Unix-permission confinement stops *accidental* and *filesystem-only* access, not a
  determined attacker who already holds the key. Surfaced for explicit acceptance at Task 1's
  decision checkpoint and recorded in the runbook — see `<threat_model>` T-09-03.
- **Security (residual, Docker Hub credential):** Docker Hub per-repository token scoping is a
  Pro/Team-plan feature (RESEARCH.md Assumption A1, account tier unverified). Option A is taken:
  one account-wide token, stored as an environment secret in *both* environments so no unscoped
  repository secret remains, with the residual — a compromised staging-scoped step could call
  production's Docker Hub endpoints — written down rather than papered over. Task 1's checkpoint
  offers Option B (a second Docker Hub account) if the operator wants full isolation.
- **Performance (CI wall-clock, near zero):** the second tag costs one extra `docker push` of an
  already-built image; `docker/build-push-action` pushes both tags from one build, and the layers
  are shared, so the marginal cost is a manifest write, not a second build. Rejecting the
  alternative (a `build-and-push-docker-image-nonprod` job) avoids doubling the ~minutes-long build.
- **Availability (production, first environment-scoped run):** adding `environment: production` to
  live production jobs is the one genuinely risky edit here. It is mitigated by ordering — both
  environments are fully populated *before* the workflow edit is pushed, and the repository secrets
  stay in place through this whole plan, so a mis-set environment secret degrades to the
  repository-level value rather than to nothing.
- **Correctness (image tag, already burned once):** `IMAGE_TAG` must come from
  `needs.build-and-push-docker-image.outputs.image_tag`. This project publishes no floating `latest`
  tag; Phase 8's first schema-registration attempt failed on exactly that assumption
  (docs/INFRA_RUNBOOK.md, "Deviations from the plan text").
</design_alternatives>
