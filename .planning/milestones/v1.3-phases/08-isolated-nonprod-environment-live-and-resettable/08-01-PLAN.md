<objective>

over real Let's Encrypt HTTPS at `kanban-board-rud-vlad-473-nonprod.duckdns.org`, backed by its own
empty Neon branch and its own Redpanda broker/schema registry, with every Compose identity axis
distinct from production and CORS configured for the expected nonprod frontend origin.

Purpose: production has been live since v1.2 Phase 5 but there is nowhere to point a real,
non-mocked E2E suite. This plan creates that target and proves — by measurement, not assertion —
that it cannot touch production.

Output: `docker-compose.nonprod.yml`, a second Caddy site block, `.env.nonprod.example`, a live

</objective>

<assumption_delta_decision>
**Noun now primary:** *environment* (parameterized: `prod` | `nonprod`).

**Decision: `promote`** — the codebase/config model moves from an implicitly-singular "the
deployment" to an explicitly environment-parameterized one, rather than bolting nonprod on as a
special case beside a still-singular production.

**Rationale:** the user already confirmed (2026-08-17, REQUIREMENTS.md Out of Scope, CONTEXT.md
D-07) that colocation is the default with a *second dedicated VPS held as an exercised fallback*.
A model where nonprod is a special case of a singular production cannot express "the same app,
two environments, one of which may move to a different host" — so environment identity is promoted
into the artifacts themselves: a per-environment Compose project name, per-environment container /
network / volume names, a per-environment env file, and a per-environment Caddy site block. This
is advisory and records the outcome; it does not gate the phase.
</assumption_delta_decision>

<design_alternatives>
Two alternate technical approaches were considered before this plan was written, as required by
`.claude/CLAUDE.md`'s GSD Execution Directives.

| Approach | Pros / Cons | Why picked / rejected |
|---|---|---|
| **A. Extend `docker-compose.prod.yml` in place** with `profiles: ["nonprod"]`-gated `app-nonprod`/`redpanda-nonprod` services (RESEARCH.md's stated primary recommendation) | **Pros:** one file as the single source of truth for "what runs on this host"; no second `name:` pin to keep in sync; matches the researcher's recommendation verbatim. **Cons:** Compose supports exactly one project name per file, so nonprod *cannot* get a distinct Compose project name — which NONPROD-01 names explicitly as a required identity axis. Worse, `docker compose -f docker-compose.prod.yml --env-file .env.nonprod --profile nonprod up -d` (the invocation PATTERNS.md line 84 proposes) targets **all** enabled services in the project, so Compose would re-resolve production's own `app` service against nonprod's `DB_*` values and **recreate the live production container pointed at the nonprod database**. Avoiding that depends entirely on always naming services explicitly on the command line. | **Rejected.** It fails a literal requirement (distinct Compose project name) and makes a catastrophic failure mode reachable by omitting a CLI argument. RESEARCH.md's own "Alternatives Considered" table already lists the separate-file variant as workable. |
| **B. Separate `docker-compose.nonprod.yml`, separate project name, shared external `kanban-edge` network** | **Pros:** satisfies every NONPROD-01 identity axis literally, including Compose project name and directory; makes the "nonprod deploy mutates production" failure mode *structurally impossible* rather than procedurally avoided (Compose only ever reconciles services inside its own project); the production file's edit shrinks to three additive lines. **Cons:** two files to keep in sync when a shared concern changes (image tag mechanism, logging anchor); the shared `kanban-edge` network must be created out-of-band once. | **Picked.** The structural guarantee is worth the duplication, and the duplication is small — the nonprod file shares no service definition with production. |
| **C. Second Caddy container on alternate ports fronted by a port-forwarding layer** | **Pros:** complete separation of the TLS layer too. **Cons:** only one process can bind host 80/443, so this needs a third proxy or a non-standard port; a non-standard port breaks the Let's Encrypt HTTP-01 challenge and makes the nonprod URL awkward for a Playwright base URL. | **Rejected.** Caddy natively serves multiple site blocks with per-hostname SNI certificates; a second container buys nothing and costs the automatic-HTTPS path. |

**Non-obvious trade-offs this plan deliberately accepts:**

- **Memory (host-level):** `mem_limit` is a per-container *cap*, not a host *reservation*. Adding
  ~1.2 GB of nonprod caps on top of production's ~5.15 GB of caps does not guarantee the 7.8 GiB
  host can satisfy both at simultaneous peak. This plan sets deliberately generous provisional caps
  and defers the real floor to plan 08-03's live measurement — the same discipline production's own
  Task 3 used. Setting a cap now that "looks safe on paper" is exactly the arithmetic this phase
  exists to replace.
- **Availability (production, seconds):** joining `caddy` to a second network requires recreating
  the `caddy` container. Its `caddy-data`/`caddy-config` named volumes persist, so the existing
  Let's Encrypt certificate is reused and no new certificate is requested (a repeated request would
  risk a week-long rate-limit ban — the exact hazard `docker-compose.prod.yml`'s caddy comment
  names). Expected production TLS interruption: single-digit seconds. This is the only production
  service this plan touches at all.
- **Security (blast radius):** the shared `kanban-edge` network is the one deliberate connection
  between the two stacks. Only `caddy` (prod side) and `app-nonprod` (nonprod side) join it —
  production's `app` and `redpanda` do not, so nonprod cannot reach production's broker or app even
  at the network layer. Nonprod's Kafka listener and schema registry publish no host port and are
  absent from `kanban-edge`, so they are reachable only from `app-nonprod`.
- **Security (secret separation):** `.env.nonprod` never lives beside `.env.prod`. The nonprod stack
  gets its own VM directory so an `--env-file` typo cannot resolve to the wrong file by relative
  path, and `SPRING_PROFILES_ACTIVE` never appears in the production env file
  (RESEARCH.md Pitfall 4). <!-- planner-discipline-allow: SPRING_PROFILES_ACTIVE -->
- **Correctness (schema-only branch, non-obvious):** Neon's `init_source: schema-only` copies the
  parent's DDL *including an empty `flyway_schema_history` table*. Flyway would then find an empty
  history against an already-populated schema and fail on `V1__init.sql` with `relation "users"
  already exists`. Task 1 therefore drops and recreates the `public` schema on the nonprod branch
  before the app first boots, so Flyway genuinely applies V1–V7 from scratch. This is not optional
  polish; without it the first `app-nonprod` boot fails.
</design_alternatives>
