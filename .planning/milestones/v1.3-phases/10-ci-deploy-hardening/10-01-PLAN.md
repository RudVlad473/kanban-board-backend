<objective>
Close the GitHub Actions supply-chain gap in `deploy.yml`: pin the two third-party `appleboy/*`
actions that hold real production and staging SSH keys to immutable commit digests, document the
deliberate non-pinning of first-party actions, wire Dependabot's `github-actions` ecosystem so
those pins stay maintained, and add the missing Gradle cache to `run-tests`.

Purpose: `deploy.yml` currently trusts two third-party actions by mutable tag while handing them
`NETCUP_SSH_KEY`. A retargeted tag (the March 2025 `tj-actions/changed-files` attack class) would
hand a compromised publisher direct shell on the production VM. This plan closes that specific
trust boundary and makes the closure maintainable rather than a one-off snapshot.

Output: `deploy.yml` with six digest-pinned `appleboy/*` references, a risk-acceptance comment for
the untouched first-party actions, `cache: 'gradle'` on `run-tests`, and a DELETE status check in
`cleanup-unused-image`; `.github/dependabot.yml` with a `github-actions` ecosystem entry.
</objective>

## Alternate approaches considered (project CLAUDE.md GSD Execution Directive)

**Approach A — digest-pin every `uses:` reference in both workflows** (the phase description's
literal success-criterion text).
**Approach B — digest-pin only the two `appleboy/*` third-party actions, tag-trust the rest, and
document the non-pin explicitly** (D-05, chosen).
**Approach C — adopt a repo-wide pinning tool (`pin-github-action`, StepSecurity `secure-repo`) to
mechanically pin and maintain every reference.**

| Approach | Pros / Cons | Why picked / not |
|---|---|---|
| A — pin everything | **Pros:** maximal supply-chain coverage; satisfies the roadmap text verbatim; no risk-tiering judgement to defend. **Cons:** every future version bump on eight first-party actions becomes a two-step lookup-then-edit forever; that recurring cost buys defence against a threat class (GitHub/Docker org compromise) that is materially less likely than a single-maintainer action compromise; higher chance the pins rot into a stale, unmaintained set — which is worse than an honest tag. | **Not picked.** D-05 locked the narrower scope, and CONTEXT.md's Locked Decisions outrank the roadmap's pre-discussion text (RESEARCH Pitfall 1). |
| B — third-party only + documented risk acceptance | **Pros:** covers the two actions that actually receive `NETCUP_SSH_KEY`/`NETCUP_SSH_KEY_NONPROD`, i.e. the only ones whose compromise yields shell on a VM; maintenance cost bounded to two references; the non-pin becomes an auditable, reasoned decision instead of an invisible gap. **Cons:** first-party actions remain tag-trusted — a real, accepted residual risk. | **Picked (D-05).** Risk-tiered by blast radius rather than by uniform policy, and the residual is written down in the file rather than left implicit. |
| C — pinning tool | **Pros:** mechanical, no transcription errors, keeps pins fresh automatically. **Cons:** adds a whole new third-party tool to the supply chain in order to secure the supply chain — the tool itself becomes an unpinned trust dependency; contradicts this repo's established habit of small, legible, hand-audited config; overkill for two references. | **Not picked.** The `gh api` lookup already gives the reproducibility a tool would, without the new dependency. |

## Non-obvious trade-offs

- **Security (residual, accepted):** first-party actions stay tag-mutable. If GitHub's own
  `actions/checkout` tag were retargeted, this pinning does not help. Accepted per D-05 and made
  explicit in-file so a future reader does not mistake it for an oversight.
- **Security (new, small):** a digest pin defeats Dependabot only if Dependabot cannot parse it.
  D-07 exists precisely because `dependabot-core` has open issues where the SHA and its version
  comment desync. An unparseable pin is *worse* than a tag: it freezes the action at a fixed
  commit with no update signal at all. Task 4 verifies this rather than assuming it.
- **Performance (positive, unmeasured):** `cache: 'gradle'` trades runner disk and cache-storage
  quota (GitHub caps a repo at 10 GB, LRU-evicted) for dependency-resolution wall time on
  `run-tests`. The saving is real but this repo has never measured it; do not assert a number.
- **Performance (negative, first run):** the first `run-tests` after the cache line lands is
  *slower* than today — it does the full resolution and then pays a cache-write. Do not read a
  slower first run as a regression.
- **Correctness (cache-key soundness):** `setup-java`'s Gradle cache keys on `**/*.gradle*` and
  `**/gradle-wrapper.properties`. This repo resolves plugins and a Confluent Maven repository from
  `build.gradle` only, so the default key inputs do cover the dependency graph — but that is an
  assertion to confirm against the actual step log, not to assume.
</tradeoffs>
