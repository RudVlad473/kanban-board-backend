## Non-obvious trade-offs

- **Where the attribute actually comes from (non-obvious):** Spring Session JDBC is on the
  classpath, so the cookie is written by Spring Session's `DefaultCookieSerializer`, not directly by
  Tomcat's `SessionCookieConfig`. Spring Boot's session auto-configuration maps
  `server.servlet.session.cookie.*` onto that serializer. This matters concretely: had the property
  been left unset, `DefaultCookieSerializer` derives `Secure` from whether the *current request* was
  secure — a per-request value. Setting it explicitly to `true` makes the attribute unconditional,
  which is the point. It is also why the assertion must be made against a real `Set-Cookie` header
  rather than against any container config object.
- **Local development (worth knowing, not a blocker):** browsers treat `http://localhost` and
  `http://127.0.0.1` as trustworthy origins and will store and send `Secure` cookies to them, so
  `docker compose up` on plain HTTP continues to work for a browser client. A plain-HTTP deployment
  at any *other* hostname would break — none exists (production and nonprod are both TLS-served per
  Phases 5 and 8), but it is the constraint this change introduces and it belongs in
  `docs/AUTH_FLOWS.md`, which currently documents `max-age` and `SameSite` consequences for
  frontend/QA readers and would otherwise be silently incomplete the moment this ships.
- **Test-suite behaviour (proven, not assumed):** the E2E tier runs over plain HTTP. The server will
  still *emit* `Secure` — a server does not withhold the attribute because the connection is not
  TLS — and REST Assured's manual `given().cookie(name, value)` replay does not evaluate it. So the
  suite stays green AND the assertion is meaningful. Both halves matter; a scheme where the suite
  stayed green because the attribute was never emitted would be worthless.
- **Security scope honesty:** `Secure` prevents transmission over cleartext. It does not prevent an
  active network attacker from stripping TLS at connection time (that is HSTS's job) and it does not
  protect a cookie already captured. It closes one specific, real leak path.
</tradeoffs>
