2. SUMMARY
================================================================

On 2026-09-05 we saw four occasions on which inbound TCP connections to
port 443 failed to establish at all. There was no SYN-ACK, no RST and no
ICMP reply. The connection attempts were met with silence.

Each attempt gave up after about 134.8 seconds. That is not a timeout we
configured. It is how long the Linux kernel on the affected client takes
to abandon a connection when every SYN it sends goes unanswered.

We verified this rather than assuming it. From the same client, we
opened a connection to 192.0.2.1 port 443, an address reserved by
RFC 5737 and guaranteed to be unrouted, so every SYN is certain to be
discarded. That control attempt gave up after 134.71 seconds. The real
failure gave up after 134.812 seconds. The two agree to within
0.1 seconds.

We therefore have direct evidence that the failure signature is total
loss of every SYN packet for the whole duration, and not a slow server,
a refused connection or an application error.

Between these occasions the host answers normally, in 40 to 160 ms.

further from our side, so please treat each range as "the failure
occurred somewhere within this window".

================================================================
8. WHAT WE HAVE RULED OUT
================================================================

Each of these was excluded by its own measurement.

  - A new deployment. The only container change on 2026-09-05 was at
    16:38 UTC, which is after all four windows.

  - Memory exhaustion. The most recent kernel OOM events are from
    2026-08-26.

  - DNS. On 2026-09-05 we queried three independent public resolvers
    (Google 8.8.8.8, Cloudflare 1.1.1.1 and Quad9 9.9.9.9). All three
    returned A = 159.195.114.230 and no AAAA record, so no IPv6 path is
    involved. No dynamic-DNS updater runs on the host; we confirmed
    there is no cron job and no systemd timer for one. The A record is
    static. A DNS failure would also produce a resolution error rather
    than a connection timeout.

  - The application. There is no HTTP status code at all, because the
    TCP connection never completes.

  - Our own rate limiting. The affected hostname has no rate limit
    configured, and a rate limit returns HTTP 429 rather than causing a
    connection timeout.

  - The client software and the client network. The same unchanged code
    passed one CI run and failed three others, and failures came from
    two unrelated networks.
